01What We Have

v2.1.0 is a genuinely strong release. The following areas are already at or near production-grade trustworthiness. These should be preserved and used as the quality benchmark for everything else.

Core insight. The hard parts are solved. Event model, identity, dispatch, projections, storage backends, docs generation, and middleware are all credible, tested, and composable. The remaining work is mostly connective tissue and production hardening.

02Where We Are Not Yet Perfect

GapSeverityWhat It Means for Consumers
No generic read-model store High Every projection writes its own SQL. No typed read-model store abstraction between projection/ and query/.
SQL storage lacks Journal Medium Cross-aggregate replay from SQL requires table-scan workarounds instead of native ReadAll/ReadFrom.
Pebble gaps Medium No BackwardsSource or StreamLoader; limits parity with SQL/memory.
Turso coverage 29% Medium Remote sync (Push/Pull/Checkpoint) is effectively untested. Consumers cannot trust it in production.
No reusable crash-recovery relay Medium The outbox was removed (YAGNI). Crash recovery uses SeekableJournal + CheckpointStore, but every consumer hand-rolls the tail → publish → checkpoint loop. A Relay component would close this gap without reintroducing an outbox table.
No schema registry middleware Medium Consumers can upcast on load, but cannot enforce schema compatibility at publish time.
Test utilities are thin Medium No fluent AggregateTester, ProjectionTester, or BusTester. Every consumer hand-rolls setup.
BuildFlow pre-commit hook broken Low Requires --no-verify. Annoying, not blocking, but erodes contributor trust.
Catalog lint issues (7) Low Pre-existing; not correctness issues, but they stain an otherwise zero-lint codebase.

03Vision of the Perfect State

A perfect go-cqrs-lite would mean any team can build a production CQRS system by composing modules without writing infrastructure glue. The library would handle the boring, risky parts: persistence, schema evolution, observability, caching, and resilience.

Type-safe everything

No any in public APIs. Branded IDs, generic stores, generic projections, generic queries. The compiler prevents mixing IDs and payloads.

Observable by default

Every store, bus, dispatcher, projection, and query handler emits OTel traces and metrics. Zero config means zero telemetry.

Resilient by default

Crash recovery via SeekableJournal + CheckpointStore guarantees at-least-once delivery without an outbox table. Retries, circuit breakers, and DLQ are opt-out, not opt-in.

Schema-aware

Publish-time validation against a registry. Versioned read models. Upcasters migrate both event and projection schemas.

Testable without mocks

High-level test utilities let consumers write Given-When-Then specs against real in-memory infrastructure.

Modular acyclic graph

No module depends on more than it needs. Consumers import only what they use. No replace-directive tangles.

04Roadmap to Perfect

01

Add a typed readmodel/ store module

This is the highest-impact missing piece. It sits between projection/ (writes read models) and query/ (reads them). A generic Store[K,V] — the common denominator across KV, SQL, and document backends — with cursor pagination, optimistic concurrency, cache decorator, and OTel.

02

Complete SQL Journal and Pebble parity

SQL storage should implement event.Journal and event.SeekableJournal natively. Pebble should implement BackwardsSource and StreamLoader. All three backends should pass a shared contract test suite.

03

Add a reusable Relay component

The outbox was removed because SeekableJournal + CheckpointStore already solves crash recovery. But consumers still hand-write the "tail journal, publish, save checkpoint" loop. A library-provided Relay would close this gap without reintroducing an outbox table or crossing the library/framework boundary.

04

Production-harden Turso

Add integration tests for Push/Pull/Checkpoint against a local libSQL replica or testcontainer. Document sync semantics, conflict resolution, and offline-first guarantees. Target 80%+ coverage.

05

Add schema registry middleware

A publish-side middleware that validates event payloads against the catalog JSON schema. Prevents incompatible events from ever reaching the bus. Complements the existing load-time upcaster.

06

Build testing/ fluent utilities

AggregateTester, ProjectionTester, BusTester, and StoreContractSuite so consumers write BDD-style tests without boilerplate. This is the missing DX layer.

07

Polish developer experience

Fix BuildFlow pre-commit, eliminate catalog lint issues, add a dedicated "getting started" example that uses command dispatch → decider → event store → projection → query end-to-end. Make onboarding 15 minutes, not 2 hours.

05New Module Proposals

readmodel/ — Typed Read-Model Store

The core insight: KV backends are great at Get/Put, terrible at List. SQL backends are great at List, okay at Get/Put. The interface doesn't pretend these are equivalent. Each backend is a separate package with its own constructor. A detector suggests what's available in your environment — it never forces a choice.

// readmodel/store.go — the interface everything implements
type Source[K comparable, V any] interface {
    Get(ctx context.Context, key K) (Record[K, V], error)
    List(ctx context.Context, opts ListOptions[K]) (Page[Record[K, V]], error)
}

type Sink[K comparable, V any] interface {
    Put(ctx context.Context, rec Record[K, V]) error
}

type Store[K comparable, V any] interface {
    Source[K, V]
    Sink[K, V]
    io.Closer
}

type Record[K comparable, V any] struct {
    Key       K
    Value     V
    Version   uint64
    UpdatedAt time.Time
    Status    event.TombstoneStatus
}

// Capabilities exposes what a backend is actually good at
type Capabilities struct {
    GetCost      Cost // Fast / Moderate / Slow
    PutCost      Cost
    ListCost     Cost // KV: Slow (full scan). SQL: Fast (indexed).
    Consistency  string // "strong", "eventual", "single-writer"
    Durability   bool   // survives process restart?
    Network      bool   // requires network?
}

type Stater interface {
    Capabilities() Capabilities
}

// Per-backend packages — explicit constructors, no god factory
// readmodel/sqlite.NewStore[K,V](db)      // embedded SQL
// readmodel/postgres.NewStore[K,V](db)    // production SQL
// readmodel/pebble.NewStore[K,V](db)      // embedded LSM-tree
// readmodel/etcd.NewStore[K,V](client)    // in-cluster K8s
// readmodel/dynamodb.NewStore[K,V](client) // AWS serverless
// readmodel/memory.NewStore[K,V]()        // tests only

Smart Defaults — Detect What's Already There

The factory doesn't guess — it detects what's already running in the environment and uses it. No extra infrastructure to provision.

// OpenAuto: detects what's already available, zero config
store, err := readmodel.OpenAuto[UserID, UserSummary]()
// KUBERNETES_SERVICE_HOST set  → etcd (in-cluster, already running)
// AWS_LAMBDA_FUNCTION_NAME set → dynamodb (serverless-native)
// K_SERVICE set (GCP)          → firestore (serverless-native)
// GITHUB_ACTIONS=true          → memory (tests, ephemeral)
// DATABASE_URL set             → postgres (explicit, user-managed)
// None of the above            → sqlite:./readmodel.db (dev, zero ops)

// Explicit with structured suggestions
store, err := readmodel.Open[UserID, UserSummary](readmodel.Config{
    URL: "pebble:./data",
    Suggest: true,
})
// Output: {Backend: "pebble", IsNative: false, SetupNeeded: false,
//          Reason: "Pebble List requires full key-range scan.
//                   Consider postgres if you paginate frequently."}

Mix and Match: Decorators

// Write-through: hot cache + SQL fallback
hot := readmodel.NewMemoryStore[UserID, UserSummary]()
cold := readmodel.NewPostgresStore[UserID, UserSummary](db)
store := readmodel.NewWriteThrough(hot, cold)

// Tiered: L1 memory → L2 pebble → L3 postgres
store := readmodel.NewTiered(
    readmodel.NewMemoryStore[UserID, UserSummary](),
    readmodel.NewPebbleStore[UserID, UserSummary](pebbleDB),
    readmodel.NewPostgresStore[UserID, UserSummary](sqlDB),
)

// Cached source: otter LRU over any inner store
source := readmodel.NewCachedSource[UserID, UserSummary](
    inner,
    readmodel.WithCacheSize(10_000),
)
  • Concrete constructors match project convention: NewMemoryStore, NewSQLiteStore, NewPostgresStore, NewPebbleStore, NewScyllaStore.
  • Honest capabilities: Every backend exposes Capabilities() — no pretending Pebble List is cheap.
  • Smart defaults: OpenAuto detects environment. Open warns on workload mismatch.
  • Composable: Write-through, tiered, and cached decorators wrap any concrete store.
  • Dependencies: event, id, codec, otel only. No coupling to projection or query.
  • Quality gate: ≥90% coverage, BDD suite, benchmarks per backend.

relay/ — Crash-Recovery Event Relay

// relay/relay.go
type Relay struct {
    journal     event.SeekableJournal
    checkpoint  event.CheckpointStore
    publisher   event.Publisher
}

func (r *Relay) CatchUp(ctx context.Context, projectionName string) error
func (r *Relay) Run(ctx context.Context) error // tail + publish + checkpoint loop
  • Replaces the outbox pattern without a secondary table. Uses the event store's own journal.
  • Reads from SeekableJournal.ReadFrom(checkpoint), publishes to bus, saves checkpoint atomically.
  • Composable: consumers opt into it, not forced by the framework. Pure library building block.

06Module Graph Target

Layer 0: id/, dispatcher/, codec/ Layer 1: event/ (id, codec), command/ (id, dispatcher), query/ (dispatcher) Layer 2: schema/ (event), snapshot/ (event) Layer 3: decider/ (event, snapshot) Layer 4: memory/, signing/, otel/, readmodel/ Layer 5: middleware/, storage/, projection/ (+readmodel), listing/ (+readmodel), watermill/, pebble/, turso/, relay/ Layer 6: integration/, catalog/, examples/, cmd/cqrs-gen, cmd/api-stability, testing/, registry/

The key addition is readmodel/ at Layer 4 alongside memory/, signing/, and otel/. It becomes the standard read-model persistence contract, allowing projection/, listing/, and consumers to write typed read models without touching SQL.

07Decision Principles for New Work

PrincipleApplication
Library, not framework Never impose a transport, message broker, or SQL driver. Provide interfaces and reference implementations.
Zero any in public APIs The only exception is database driver interop. Everything else is generic or strongly typed.
Composition over inheritance Store decorators (cached, versioned, retrying) wrap inner stores. No base structs.
Observability built-in Every new module uses otel/ for traces and metrics from day one.
Tombstone over delete Read models use event.TombstoneStatus; deletes are soft and reversible.
Test like we mean it ≥90% coverage, BDD suite, benchmarks, contract tests shared across implementations.
Acyclic module graph No lower-layer module may depend on a higher layer. Replace directives only for CI isolation.

08Summary — What to Do Next

If I had one quarter to move this project from "excellent" to "perfect," the order would be:

  1. Build readmodel/ — this is the biggest missing capability and unlocks everything else.
  2. Add relay/ — reusable crash-recovery component using SeekableJournal + CheckpointStore, without an outbox table.
  3. Complete storage parity — SQL Journal, Pebble BackwardsSource/StreamLoader, shared contract tests.
  4. Harden Turso — integration tests for sync semantics; target 80% coverage.
  5. Add registry middleware — publish-time schema validation to complement upcasters.
  6. Ship testing/ — fluent BDD utilities. This is the DX multiplier.
  7. Polish — fix BuildFlow, zero catalog lint, better onboarding example.

Bottom line. go-cqrs-lite is already one of the most thoughtfully architected Go CQRS libraries available. The remaining work is not about fixing fundamental mistakes — it is about closing the last gaps so consumers can assemble a complete, production-grade CQRS stack using only library modules, with zero hand-rolled infrastructure glue.
