Event Redaction, Reviewed

A privacy-filtering pattern — stripping sensitive payload fields before broadcasting events to viewers based on role — evaluated against the design principles of go-cqrs-lite. The pattern is legitimate; the reference implementation leaks concerns in the wrong places.

±

Steal the principle. Reject the implementation.

Role-based filtering at a read egress is architecturally consonant with the library's existing boundary transformers (signing/, encryption/, tombstone soft-delete). But hardcoding sensitivity into the domain enum and mutating payload shape at one transport breaks the type system and centralizes policy in the worst possible place.

01What the Design Gets Right

The core intuitions are sound. These two decisions alone place the design above naive approaches that redact at write time or treat privacy as an afterthought.

Source of truth stays intact

Redaction is a view concern, applied at egress. The stored event is never mutated. This is the correct boundary — the same principle the library already applies to signing (sign-then-store, verify-on-read) and encryption (encrypt-then-store, decrypt-on-read).

Two granularities of redaction

Distinguishing a full payload wipe (redacted()) from targeted field-level stripping (redact_window_title()) is the right instinct. Not every sensitive event needs wholesale erasure; some only need specific fields masked.

Why this matters: redaction-at-egress composes naturally with the library's existing read-side middleware stack. A consumer could layer decrypt → verify → redact → trace on every read path, and the stored event would remain canonical and auditable.

02Six Problems With the Implementation

Each problem below is a place where a policy concern was glued to a layer that should not own it. Left unaddressed, they compound: the next transport added re-derives the rules, the type contract erodes, and the admin cliff becomes a liability.

1

Sensitivity baked into the domain enum

is_sensitive() hardcoding 15 event types inside EventType leaks a policy concern into the domain layer. "Is this sensitive?" is a deployment- or tenant-specific decision, not an intrinsic property of an event type. What counts as sensitive in a healthcare context differs from a logistics system — the enum cannot encode that.

In go-cqrs-lite terms, this belongs in configurable middleware or a projection filter, not in the event type definition.

2

Redaction mutates the payload shape

redacted() replaces the payload with {"redacted":true}. This breaks the typed contract: any consumer unmarshaling into UserCreated now gets a silent structural mismatch. The type system can no longer guarantee that a UserCreated event actually contains the fields the type promises.

This is precisely the "make impossible states unrepresentable" violation the library fights against. A redaction layer should produce a properly-typed view (zeroed or redacted-marker fields) or a distinct redacted envelope type — never a shape-shifting payload.

3

Redaction gated at a single transport

Applying the filter only at the WebSocket broadcast boundary leaves the journal, replay, projections, and any direct read API unprotected. Privacy filtering applied at one egress point is a leak waiting to happen — the next transport added (SSE, gRPC, HTTP) re-derives the policy and gets it wrong.

It must be a policy applied to all read egress, consistently, not patched into each handler as it appears.

4

Branching logic in the transport layer

The if / else if chain in ws.rs couples role resolution, permission flags, and event classification directly to the WebSocket handler. It is fragile — note that WindowFocused is checked before is_sensitive(), making the ordering load-bearing in a non-obvious way. And it is untestable in isolation: you cannot exercise the redaction policy without standing up a transport.

This should be a composable policy chain, testable against any event.Event in isolation.

5

Full-wipe default discards analytic value

Defaulting regular users to whole-payload erasure on sensitive events throws away information that could have been retained with field-level masking. A keystroke event redacted to {"key_count": 42, "keys": "[redacted]"} preserves analytics; {"redacted": true} preserves nothing.

Field-level redaction is almost always preferable to whole-payload erasure. The default should bias toward retaining structure.

6

Admin bypass is a binary trap

"Admins see everything" means one compromised admin credential equals a full surveillance feed. Real systems want attribute-based, field-level access — an auditor may see that a clipboard event occurred without seeing what was copied. A binary admin/not-admin cliff offers no middle ground.

03Anti-Pattern vs. Idiomatic

Each design decision has a wrong home and a right home. The move is always the same: push policy out of the domain and into a composable, configurable layer.

As Designed

EventType::is_sensitive() hardcodes 15 types inside the domain enum. Policy cannot change without a code change and a redeploy.

Idiomatic

A RedactionPolicy maps event type → field rules, configured per deployment or tenant. The domain knows nothing about sensitivity.

As Designed

redacted() swaps the payload for {"redacted":true}, breaking the typed unmarshal contract for every consumer.

Idiomatic

Redaction produces a typed view — same struct shape, fields zeroed or replaced with sentinel values. Or a distinct RedactedEvent envelope type that the type system can distinguish from a live event.

As Designed

Redaction lives inside ws.rs. The journal, replay, projections, and any future transport are unprotected and must re-derive the rules.

Idiomatic

Redaction is a read-side middleware applied on every egress path — a sibling to middleware.EventTracing and encryption.DecryptMiddleware.

As Designed

Admins bypass all redaction. One compromised credential exposes the entire stream.

Idiomatic

Attribute-based access: roles map to which fields they may see, not a binary see-all flag. An auditor sees metadata; a security officer sees payloads.

04The Target Shape in go-cqrs-lite

If this capability were added to the library, the idiomatic shape would fit cleanly into the existing module graph — a sibling to the other boundary transformers, layered 4–5.

Proposed module: redaction/ — a read-side middleware that takes a RedactionPolicy and a viewer context, producing typed redacted views. Composes with signing/ and encryption/: encrypt-then-sign the original, redact per-viewer on the way out.

Placement in the existing stack

The pipeline on every read egress would compose as follows:

// Read egress pipeline (composed per transport, applied uniformly)
// 1. decrypt  — restore the canonical payload
// 2. verify   — confirm integrity / signature
// 3. redact   — apply viewer-aware field rules
// 4. trace    — record the access for audit

bus.Use(
    encryption.DecryptMiddleware(enc),
    signing.VerifyMiddleware(signer),
    redaction.Middleware(policy),   // viewer from ctx
    middleware.EventTracing(tracer),
)

How viewer identity reaches the policy

The library already has a precedent: correlation IDs and processing mode (ModeLive / ModeReplay) travel as context.Context values. Viewer identity should follow the same pattern — a context-scoped viewer, never resolved inside a transport handler. 

// Attach viewer to context, same pattern as ProcessingMode
ctx := redaction.WithViewer(ctx, viewer)

// Middleware reads it back
viewer := redaction.ViewerFrom(ctx)

05Proposed Interface Sketch

A first-draft shape for the redaction/ package, consistent with the library's interface-first, composition-over-inheritance conventions. The key contract: a View is a distinct type from a live Event, so the type system can tell them apart. 

// Package redaction provides viewer-aware payload filtering
// applied at read egress. The stored event is never modified.

type Viewer struct {
    Roles     []Role      // e.g. "admin", "auditor", "user"
    Perms     []Permission // fine-grained, attribute-based
}

type Rule func(payload map[string]any, v Viewer) map[string]any

type Policy struct {
    // eventType → field rules; configured per deployment/tenant
    Rules map[string][]Rule
}

// Apply returns a typed View, never mutating the original event.
func (p Policy) Apply(evt event.Event, v Viewer) (View, error)

// View is a redacted projection of an event. Distinct type so
// consumers cannot accidentally treat it as a canonical event.
type View struct {
    Event  event.Event      // metadata preserved
    Payload []byte       // redacted, still valid JSON for its type
}

// Middleware wires the policy into the read pipeline.
func Middleware(p Policy) event.Middleware

Design note: whether View should wrap the original event or be a fully standalone type is worth a dedicated decision. The constraint is that a redacted view must never be passable where a canonical event is expected — the type system must enforce the distinction.

06An Ethical Flag Worth Naming

The event taxonomy in the reference — keystrokes, screenshots, audio capture, clipboard, SMS, sudo/SSH authentication — is unambiguous employee and user surveillance territory. That context explains why the design defaults to aggressive full-wipe redaction and a hard admin cliff: the product is built around monitoring people.

The pattern is general and legitimate — GDPR / PII filtering, role-based read views, field-level masking are all standard, defensible privacy techniques. Transfer the pattern to the library freely. The sensitive-type catalog is not. It is domain-specific to a surveillance product and does not belong in a general-purpose CQRS library.

The library's contribution should be the mechanism — a composable, configurable redaction layer that any consumer can populate with their own rules. The library should ship with no opinion about what counts as sensitive.

07Recap

Aspect As Designed For go-cqrs-lite
Source of truth Unmodified — correct Keep
Redaction granularity Full wipe + field-level — correct instinct Keep
Sensitivity classification Hardcoded in domain enum Reject — external policy
Payload shape Mutated to {"redacted":true} Reject — typed views
Egress coverage WebSocket only Reject — all read paths
Policy location Inline in transport handler Reject — middleware
Access model Binary admin bypass Reject — attribute-based
Sensitive-type catalog Surveillance-specific Reject — consumer-defined

Bottom line: the redaction pattern belongs in a CQRS library — every event-sourced system with multiple viewers eventually needs it. But it belongs as a composable, policy-driven, type-preserving middleware that applies uniformly across all read egress, not as hardcoded domain knowledge with shape-mutating output patched into a single transport.
