The Bundle Layer

A proposal to separate infrastructure wiring from domain logic in go-cqrs-lite — honestly: it moves the deployer's decision into its own file, not eliminates it. Every claim below has been pressure-tested against the actual codebase interfaces.

01The Pain Today

The canonical example is example/todo/cmd/api/main.go. Its run() function is ~200 lines, of which roughly 80 are pure infrastructure glue: opening databases, constructing stores, wiring buses, building projection runners. The remaining ~120 lines (HTTP server, routes, signal handling, graceful shutdown) remain regardless of any abstraction — this proposal does not claim to eliminate them. 

// --- ~80 lines of infrastructure decisions embedded in app code ---
readModelStore, err := storage.NewPebbleStore(dataDir, logger)
eventStore := cqrsPebble.NewStore(readModelStore.DB(), logger)
eventBus := memory.NewMemoryBus()
checkpointStore := memory.NewMemoryCheckpointStore()
runner, err := projection.NewRunner(eventStore, eventBus, checkpointStore)
// ... plus snapshot stores, command stores, query stores, middleware chains

To swap Pebble for SQLite, a deployer must edit this file, change imports, and recompile. The domain logic (handlers, projections, aggregate) is buried underneath.

Honest scoping

This proposal targets the ~80 lines of store/bus wiring. It does not touch HTTP routing, signal handling, or the projection runner's goroutine lifecycle. A realistic reduction is ~80→~15 lines of infrastructure glue, not “200→10.”

02Design Principles

These rules constrain every design decision below. Each was learned the hard way — the previous draft of this proposal violated most of them.

# Principle Why
1 ISP at the field level Use EventSink / EventSource, never Store. A command handler should not see Load.
2 Options, not Provider No Provider interface. Go has no partial interface implementation. Use func(*Bundle) error options.
3 Read models typed by the app The deployer provides an untyped readmodel.Backend. The app wraps it with Store[T]. No generic propagation to the Bundle.
4 Publisher ≠ Subscriber The codebase already splits them (event/bus.go:13-30). NATS may use different connections. The Bundle respects the split.
5 Co-location ≠ atomicity No claim of cross-store transactions without an outbox. Both event.Save and command.Save create private transactions today.
6 Presets are sugar stack.New(opts...) is the canonical API. Presets are thin wrappers. The granular API is not an “escape hatch.”
7 Every gap is visible The capability matrix shows exactly which backends provide what. No silent omissions.

03The Bundle

A Bundle is a struct of wired capability interfaces. It is named for what it IS — a bundle of peers, not a LIFO stack or a layered call-passing chain. Every field is a segregated interface, per the codebase's ISP discipline. 

type Bundle struct {
    // Write side — command handlers use these
    EventSink     event.EventSink       // Save, AppendBatch
    CommandSink   command.CommandSink   // Save (audit trail)
    SnapshotSink  snapshot.SnapshotSink  // Save, Delete

    // Read side — loaders, queries, projections use these
    EventSource     event.EventSource        // Load, LoadFromVersion, time-travel
    Journal        event.Journal            // ReadAll (projection replay)
    SnapshotSource snapshot.SnapshotSource  // Load, LoadAtVersion

    // Messaging — split per codebase convention (bus.go:13-30)
    Publisher  event.Publisher   // command handlers publish events
    Subscriber event.Subscriber  // projection runner subscribes

    // Infrastructure
    Checkpoints event.CheckpointStore
    ReadModels  readmodel.Backend     // untyped; app wraps with Store[T]

    // Lifecycle — internal, not for app code
    closers []io.Closer
}

Why these fields and not event.Store

The codebase defines event.Store as EventSink + EventSource (store.go:78-81). But it also defines Journal (ReadAll), SeekableJournal (ReadFrom), and BackwardsSource (LoadBackwards). Using event.Store as the Bundle field would silently drop Journal — which the projection runner needs for replay.

Optional capabilities

SeekableJournal (cursor-based ReadFrom) and BackwardsSource (reverse load) are not Bundle fields — not every backend supports them. Consumers who need cursor-based catch-up type-assert the Journal field: if sj, ok := bundle.Journal.(event.SeekableJournal); ok { ... }. This is honest: the minimum contract is ReadAll; the optimization is optional.

05The Composition API

The canonical API is stack.New(opts ...Option). No Provider interface — Go has no partial interface implementation, and faking it with reflection violates the zero-overhead principle. Each option is a plain function that sets one or more fields. 

type Option func(*Bundle) error

// One capability per option. Each line tells the exact truth about one thing.
bundle, err := stack.New(
    stack.WithEventSink(logDB),
    stack.WithEventSource(logDB),
    stack.WithJournal(logDB),
    stack.WithCommandSink(logDB),
    stack.WithSnapshotSink(viewsDB),
    stack.WithSnapshotSource(viewsDB),
    stack.WithReadModels(viewsDB),
    stack.WithPublisher(bus),
    stack.WithSubscriber(bus),
    stack.WithCheckpoints(memCheckpoints),
)
Why not Provider?

The previous draft proposed a Provider interface where “each backend implements only the methods that make sense.” Go does not support partial interface implementation — either the backend satisfies the full interface or it doesn't. Detecting optional methods requires reflection or type assertions, which the performance contract forbids. Option functions solve this natively: each backend package exports the options it can support. No detection needed.

06Convenience Bundles

For the common case where multiple capabilities share one connection, preset packages ship option groups — functions returning a single stack.Option that sets multiple related fields. They are not types; they are shorthand. 

// Two databases, grouped by shared characteristic.
// AppendLog: events + commands — both are append-only records.
// Views: read models + snapshots — both are derived, rebuildable state.
bundle, err := stack.New(
    sqlite.AppendLog("data/log.db", logger),
    sqlite.Views("data/views.db", logger),
    memory.Bus(),
    memory.Checkpoints(),
)

sqlite.AppendLog internally calls stack.WithEventSink, stack.WithEventSource, stack.WithJournal, and stack.WithCommandSink — all pointing at one *sql.DB. The DB is registered for cleanup exactly once.

Where snapshots actually belong

Snapshots are internal decider optimizations (point-in-time aggregate state for replay short-circuiting), not query-facing views. They are read on the same path as events (decider.Repository.Load). Co-locating them with read models works but is debatable — co-locating them with events (sqlite.AppendLog + snapshots) is equally valid and keeps the aggregate reconstruction path on one DB. The Views bundle is a convenience, not a mandate. Use stack.WithSnapshotSink(logDB) if you prefer snapshots with the event log.

07Presets

A preset is a convenience function that returns a fully-wired *Bundle for a single-backend topology. Each preset's doc comment must state its capability gaps honestly.

Preset Capabilities included Gaps
memory.New() All 7 None (ephemeral)
sqlite.New(dir) Events, Commands, Queries, Snapshots, Checkpoints Bus, ReadModels (bus is memory; read-model backend is new)
pebble.New(dir) Events, Snapshots, Checkpoints Commands, Queries, Bus, ReadModels
postgres.New(dsn) Events, Commands, Queries, Snapshots, Checkpoints Bus, ReadModels

Every preset accepts stack.Option variadics for additions: sqlite.New(dir, memory.Bus()) adds an in-memory bus to a SQLite preset.

08Split Topologies

The granular stack.New API is the canonical path, not an escape hatch. It handles any topology the deployer needs. The common patterns:

Single DB (everything in one file)

bundle, _ := sqlite.New("data/app.db", logger, memory.Bus())

Journal + Views (the 2-DB split)

bundle, _ := stack.New(
    sqlite.AppendLog("data/log.db", logger),    // events + commands
    sqlite.Views("data/views.db", logger),       // read models + snapshots
    memory.Bus(),
)

Heterogeneous (different backends per capability)

bundle, _ := stack.New(
    stack.WithEventSink(pgEventStore),
    stack.WithEventSource(pgEventStore),
    stack.WithJournal(pgEventStore),
    stack.WithReadModels(pebbleBackend),
    stack.WithPublisher(natsPublisher),
    stack.WithSubscriber(natsSubscriber),
)
No atomicity claim

Co-locating events and commands in one database does NOT give you a cross-table transaction. Both event.Save (event_store.go:84) and command.Save (command_store_save.go:33) create and commit their own private *sql.Tx. There is no shared-transaction API. True command+event atomicity requires an outbox pattern, which is a future enhancement (see §15). Co-location shares workload characteristics and connection overhead — nothing more.

10The Read Model Problem

The hardest design challenge. A generic readmodel.Store[T] in the Bundle would make Bundle[T] generic — but the deployer constructs the Bundle and does not know the domain type T. Go cannot infer T from a preset function.

The solution: split the concern

The Bundle exposes an untyped readmodel.Backend — the deployer's concern (which storage engine). The app developer wraps it with a typed readmodel.Store[T] — the domain concern (which Go type). The generic stays in the app's package, never propagates to the Bundle. 

// Deployer side: provides the storage engine (in Bundle)
type Backend interface {
    Get(ctx context.Context, key []byte) ([]byte, error)
    Put(ctx context.Context, key, val []byte) error
    Delete(ctx context.Context, key []byte) error
    Scan(ctx context.Context, prefix []byte) (Iterator, error)
}

// App side: wraps Backend with domain types
type Store[T any] struct { backend Backend }
func (s *Store[T]) Get(ctx context.Context, id TodoID) (*T, error) { ... }
Why Put/Delete are honest here

The DOMAIN_LANGUAGE.md prohibition on CRUD applies to the write side (event store — append-only, never update/delete). The read side (projections, read models) is explicitly mutable — that's the entire point of CQRS. Read models reflect current state: they are upserted when events arrive and deleted when aggregates are tombstoned. Put/Delete on a read model backend is not CRUD smuggling; it is the read side doing its job.

Filtered queries

A KV Backend cannot express SQL WHERE/ORDER BY. For projections that need filtered lists (like the todo example's List(filter)), the app developer has two paths:

  • KV backends: Scan with prefix + filter in Go. O(n) but adequate for small read models. This is what the todo example does today.
  • SQL backends: implement a SQLBackend that satisfies readmodel.Backend but also exposes SQL-specific query methods via a separate interface. The app type-asserts when it needs filtered queries: if sb, ok := backend.(*SQLBackend); ok { sb.Query(ctx, "WHERE status = ?", ...) }.

This is honest: one interface cannot serve both KV and SQL query patterns without leaking one into the other. The split keeps each backend honest.

11Lifecycle & Resource Safety

Close() ownership

The Bundle tracks every io.Closer it receives. On Close(), it closes each once, deduplicated by pointer identity. When the same *sql.DB backs both EventSink and EventSource (via AppendLog), it is registered once and closed once. 

func (b *Bundle) Close() error {
    var errs []error
    seen := make(map[uintptr]bool)
    for _, c := range b.closers {
        ptr := uintptr(unsafe.Pointer(c)) // dedup by identity
        if seen[ptr] { continue }
        seen[ptr] = true
        if err := c.Close(); err != nil { errs = append(errs, err) }
    }
    return errors.Join(errs...)
}

Partial failure during construction

If stack.New fails on the third option (e.g., a DB fails to open), all already-registered closers are closed before the error returns. No leaked handles. 

func New(opts ...Option) (*Bundle, error) {
    b := &Bundle{}
    for i, opt := range opts {
        if err := opt(b); err != nil {
            // Rollback: close everything opened so far
            for j := range opts[:i] { opts[j](b) } // re-run to find closers
            b.Close()
            return nil, fmt.Errorf("stack.New: option %d: %w", i, err)
        }
    }
    return b, nil
}
Ownership caveat

When a deployer passes a borrowed *sql.DB (via stack.WithEventSink(myDB)), the Bundle does NOT close it — only closers created by preset/bundle options are registered. The caller owns what they passed in.

12Performance Contract

Zero-cost composition — scoped honestly

bundle.EventSink is an interface field. A call through it pays one interface dispatch — the same cost as any event.EventSink variable in the codebase today. The Bundle adds no proxy, no wrapper, no re-dispatch. The guarantee: calling bundle.EventSink.Save(...) has the same allocation profile as calling store.Save(...) through any event.EventSink variable. It does NOT claim to match a call through the concrete *SQLEventStore — that would require exposing the concrete type, which breaks deployer portability.

Scope: the zero-cost guarantee holds when no accelerators are enabled. An LRU cache (WithReadModelCache) IS a wrapper that adds a lookup per read. This is by design and documented at the call site.

Tuning profiles — named by I/O pattern

The previous draft's ForAppends/ForReads were backwards: the “log” DB is read constantly (Load, replay), and the “views” DB is write-heavy during catch-up. Tuning profiles must name the I/O pattern, not the assumed CQRS role:

Profile SQLite pragmas For
ForSequentialIO synchronous=NORMAL, larger wal_autocheckpoint Append logs, journals — sequential writes + sequential scans
ForRandomIO Larger cache_size, mmap_size, more readers Read models, snapshots — random point lookups + burst upserts

What the Bundle will NOT do

  • No mandatory middleware injected into every call
  • No runtime type-switching on store operations
  • No “smart router” that picks backends at runtime
  • No auto-tuning at runtime — pragmas are startup decisions
  • No hiding perf problems behind caching — fix the defaults first

13Honest Tradeoffs

What we gain

Deployer portability: swap backends without touching domain logic. Infrastructure wiring consolidated from ~80 scattered lines to one stack.New call. ISP-honest: command handlers see only EventSink, projections see only EventSource + Journal. Every capability gap is visible in the matrix, not hidden.

What it costs

Two new modules (stack + readmodel). Backend work: Pebble needs command/query/read-model stores before its preset is complete. The readmodel.Backend interface can't express SQL filtered queries without a type assertion. The separation is a convention enforced by code review and optionally .go-arch-lint.yml, not by the Go compiler.

The “library not framework” line

A composition root with lifecycle ownership and driver-specific presets IS a framework feature. The honest framing: the Bundle layer is an optional composition layer. Consumers who want zero framework influence keep importing individual modules and wiring by hand — the current behaviour, fully supported. The Bundle is the happy path, not the only path. The line between “library with optional helpers” and “framework” is whether the helpers are required. They are not.

14What This Does NOT Solve

Honest scope. These are real production concerns that the Bundle layer does not address. They are listed here so nobody mistakes this proposal for a silver bullet.

Concern Status Why it's out of scope
Outbox pattern Not implemented decider.Repository.Execute does Save-then-Publish as independent operations. If the process crashes between them, events are persisted but not published. The Bundle does not fix this. It requires an outbox table + relay — a separate module.
Schema migrations Deployer's responsibility SQL stores need CREATE TABLE. The Bundle does not auto-migrate (that's an opinion). Presets call InitSchema if the deployer opts in via sqlite.New(dir, sqlite.WithAutoMigrate()).
Multi-tenant isolation Not in the Bundle Key namespacing (tenantID:itemID) is an app-layer concern. The readmodel.Backend is untyped bytes; the app controls key format.
Connection pool budgeting Deployer's responsibility In a 3-DB split with 25 conns each, that's 75 connections per process. The Bundle does not enforce a global budget. Tune each preset's pool size.
Projection runner lifecycle App developer's responsibility The Bundle provides the ingredients (EventSource, Subscriber, Checkpoints). The app constructs, starts, and stops the runner. The Bundle does not own the goroutine.
Import boundary enforcement Convention + optional linter Go has no language-level import restrictions. The separation between “deployer code” and “app code” is enforced by code review and optionally .go-arch-lint.yml, not by the compiler.

15Migration Path

The Bundle layer is additive. No existing interface changes. Backends gain new stack.Option-returning functions, but existing constructors (storage.NewSQLiteBackend, pebble.Open) are untouched.

  1. Existing consumers keep hand-wired main.go. Works identically. Raw wiring remains the documented power-user path.
  2. New consumers start with a preset. The happy path is the default in docs and examples.
  3. Migrating consumers replace their glue with stack.New at their own pace. No big-bang rewrite.
  4. Custom enrichers (e.g., decider.Repository's enricher chain) are unaffected — they're configured on the Repository, not the Bundle.

16Execution Plan

1

readmodel module

Define readmodel.Backend (untyped) + readmodel.Store[T] (typed wrapper) + memory adapter. Highest impact: projections need a write target.

2

stack core

Bundle struct with segregated interface fields. stack.New(opts ...Option) with partial-failure rollback. Pointer-deduplicated Close().

3

memory preset + bus option

memory.New() returns a full *Bundle. memory.Bus() returns an option setting both Publisher and Subscriber. Validates the Bundle shape with zero deps.

4

sqlite preset + AppendLog/Views options

sqlite.New(dir) + sqlite.AppendLog(dir) + sqlite.Views(dir). Includes tuning profiles (ForSequentialIO, ForRandomIO).

5

fill Pebble gaps

Add command store, query store, and read-model backend to Pebble. Then pebble.New(dir) becomes a complete preset.

6

postgres preset

Same shape as SQLite, different driver/dialect.

7

rewrite example/todo

Port to sqlite.New. Measure: if the infrastructure glue doesn't shrink dramatically, the design is wrong. Also add a split-topology example.

8

benchmarks + docs

stack/bench/ suite parameterised by *Bundle. docs/PRESETS.md. Update SKILL.md and STORAGE_GUIDE.md.

Where to start

Phase 1 (readmodel) and Phase 2 (stack core). Everything downstream is blocked until the read-model Backend exists and the Bundle type is defined.
