Could go-cqrs-lite benefit from sqlc?

A deep, evidence-driven analysis of whether sqlc's type-safe SQL code generation would improve the storage/ module of a multi-module Go CQRS library — and exactly where it would (and wouldn't) fit. Includes a phased, reversible adoption plan.

00Bottom line

Yes, partially and incrementally. The storage/ module carries 290 lines of hand-written scan code (verified) plus ~39 DML operations whose scan destinations are only implicitly coupled to the SQL string — a bug class that sqlc eliminates at compile time. But sqlc is fundamentally static, so the dynamic parts (variable-arity batch inserts, runtime-assembled WHERE fragments) must stay hand-written. Realistic coverage is ~60% of queries.

The honest verdict: sqlc would type-safe ~15 of ~25 query shapes, at the cost of dialect duplication and a new code-gen step. The LOC reduction is modest (~100–150 lines, not 300 — the branded-ID / time / error reconstruction stays as adapter code); the real win is compile-time column-order safety + schema unification. The biggest immediate win — extracting schema to .sql files — is valuable even if you never adopt sqlc, because it kills today's dual source of truth (Go strings + golden fixtures).

01The storage layer today

Before judging sqlc, here is the evidence base: every SQL query, scan pattern, and dialect abstraction currently in storage/ and storage/sql/.

Where SQL lives

Embedded Go string literals in storage/sql/dialect.go:53-221 (all DDL), storage/sql/helpers.go (shared DML), and per-store files. Not greppable as SQL — schema and queries are interleaved with Go.

Dual source of truth

Schema DDL exists twice: as Go string returns from Dialect.EventSchema() methods and as 8 checked-in golden .sql fixtures in storage/testdata/golden/. Both must be kept in sync by hand.

The hand-written scan coupling

This is the single most fragile pattern. The destination order in every rows.Scan(...) call is only correct because it matches a SQL SELECT column list built elsewhere. Reorder a column in one place and you get silent data corruption — no compile error.

Today (event_store_scan.go:20-44)
After sqlc

What sqlc does NOT eliminate: the ~65 lines of domain reconstruction after the Scan — parsing time, reconstructing branded IDs (id.ParseEventID), and wrapping errors in the 5-family taxonomy. sqlc replaces the brittle column-order Scan + the row struct + placeholder injection; the typed domain adapter stays hand-written. This is why the LOC win is modest (~100–150 lines) and the safety win is the real prize.

Compensating linters already enabled

Tellingly, .golangci.yml already enables the linters that exist precisely because hand-written SQL is fragile:

.golangci.yml ├── sqlclosecheck (rows.Close() correctness) ├── rowserrcheck (rows.Err() correctness) └── unqueryvet (sql.Rows misuse)

The dialect abstraction

SQL text is largely dialect-agnostic. Branching happens only in three narrow places, abstracted behind the Dialect interface (dialect.go:15):

Axis Postgres SQLite Where
Placeholders $1, $2, ... ?, ?, ... Sprayed through ~25 queries via Dialect.Placeholder(n)
Time round-trip time.Time native RFC3339Nano string ScanTimeDest / ParseSQLiteTimestamp (6 layouts)
DDL types BYTEA, JSONB, TIMESTAMPTZ BLOB, TEXT, datetime('now') dialect.go:53-221
Structural divergence SQLite 999-param chunking in SharedBatchInsertEvents helpers.go:107

02What sqlc is (and is not)

sqlc is a compiler: it reads .sql schema + annotated query files and emits type-safe Go. You write SQL; it writes the boilerplate. The generated code imports only database/sql — zero runtime dependencies.

sqlc IS
sqlc is NOT
-- name: GetEvent :one
SELECT * FROM events
WHERE id = $1;

// Generates:
// func (q *Queries) GetEvent(
//   ctx, id string) (Event, error)
// NOT an ORM
// NOT a query builder
// NOT dynamic SQL

// Cannot do:
// - variable-arity INSERT
// - runtime WHERE assembly
// - schema reflection
Key capability: A single sqlc.yaml can declare multiple engines side-by-side — e.g. one PostgreSQL block and one SQLite block, each emitting to its own package. This maps cleanly onto the existing PostgresDialect / SQLiteDialect split.

03Concrete benefits

Each benefit below is tied to specific code locations in storage/, not abstract claims. Verified against the current source (3,455 production lines, 290 scan lines, ~39 DML operations across the module).

1
Compile-time scan correctness — the biggest win Every rows.Scan(&id, &type, ...) today has dest order implicitly coupled to a SQL string built elsewhere. sqlc generates the scan from the SQL → the entire bug class vanishes. Affects event_store_scan.go:20-44, command_store_scan.go:17-103, query_store_scan.go:17-78, snapshot.go:147-178.
2
Removes the brittle Scan + placeholder injection The ~25-line column-order rows.Scan per store, the row struct, and the fmt.Sprintf+Placeholder(n) calls sprayed across ~25 queries all become generated. Net ~100–150 lines removed (the branded-ID / time / error reconstruction stays as adapter code) — a modest LOC win, but the column reordering bug class is gone for good.
3
Single source of truth for schema Today DDL lives in Go strings and is mirrored as golden .sql fixtures. With sqlc the .sql is the input; Go is generated; golden tests become redundant.
4
Removes placeholder injection fmt.Sprintf(..., s.Dialect.Placeholder(n)) disappears from ~25 queries; sqlc emits fixed $1/? per engine.
5
Kills the time-round-trip hack ScanTimeDest / FormatTime / ParseTime / ParseSQLiteTimestamp exist solely because SQLite stores time as text. Per-engine generated code scans natively (PG) / parses text (SQLite) internally.
6
Forces a real migration story Today there are zero migration files — InitSchema does drop+recreate. sqlc schema files pair naturally with golang-migrate / atlas, closing a genuine production-readiness gap.
7
Clean on the dependency budget Generated code imports only database/sql — zero new runtime deps, consistent with the per-module budgets enforced by nix run .#check-layers. sqlc itself is a dev-only binary.
8
Boosts the catalog story Real .sql DDL can feed ERD / dbdocs tooling alongside the existing AsyncAPI / OpenAPI exporters in catalog/.

04Pro / Contra

The honest tradeoff, side by side. The Pro column is what sqlc delivers; the Contra column is what you give up or take on.

Pro — what you gain

  • Compile-time type safety SQL and Go stay in sync by construction; column reorder can no longer cause silent scan corruption.
  • Scan + injection elimination ~100–150 lines of brittle Scan + row structs + fmt.Sprintf+Placeholder plumbing deleted (domain reconstruction stays).
  • Unified schema source One .sql file is the input; golden fixtures become assertions-on-generated-output or are deleted.
  • No placeholder injection Fixed per-engine SQL replaces ~25 fmt.Sprintf+Placeholder call sites.
  • No SQLite time-string hack Per-engine generated code handles time natively per backend.
  • Native migration opening Schema files become a natural home for golang-migrate / atlas.
  • Zero new runtime deps Generated code uses only database/sql; honors the dependency budget.
  • Greppable SQL Queries live in .sql files, searchable as SQL — not buried in Go string concatenation.

Contra — what you give up / take on

  • Dialect duplication sqlc emits one package per engine → pg/ + sqlite/. You lose the single-file Dialect indirection.
  • Dynamic queries don't fit SharedBatchInsertEvents (variable multi-VALUES + 999-param chunking), buildListQuery, and LoadParams.Where fragments are runtime-built — sqlc is fundamentally static.
  • The generic QueryRows[T] engine breaks Load / LoadFromVersion / LoadToVersion / LoadToTimestamp / LoadBackwards are assembled dynamically. They become 5 explicit sqlc queries per store, or stay hand-written.
  • Scope limited to storage/ pebble/, kv/, turso/, memory/ are not SQL and gain nothing.
  • New contributor workflow step Editing a query now means: edit .sql → sqlc generate → commit generated code. sqlc must enter the nix devShell.
The crux of the tradeoff: sqlc converts static SQL into type-safe generated code but cannot express dynamic SQL. The existing codebase deliberately leans on a generic QueryRows[T] engine and LoadParams.Where fragments to share one code path across five load variants. sqlc would force that to become five explicit queries — more code, but each type-checked and individually simpler.

If you devalue those (e.g. you trust the linters and never touch the schema), the case weakens fast — which is exactly why Phase 1 (schema extraction) is the highest-value, lowest-regret step: it captures the schema-unification gain independently of the sqlc decision.

06Alternatives considered

sqlc is one of several ways to address hand-written SQL pain. Naming and dismissing the alternatives makes the recommendation honest rather than default.

sqlc pick

Compile SQL → type-safe Go. Static only, but maps to ~60% of our queries. Zero runtime deps. This report's recommendation (Phases 0–2).

jet dismiss

Type-safe query builder with per-table codegen. Fully dynamic — but heavier output, more opinionated, and overkill for ~25 fixed queries. We don't need a query DSL.

scaneo / sq dismiss

Lightweight scan-only generators (emit struct + Scan from a table, no query codegen). Solves only half the problem — leaves placeholder injection and schema duplication untouched. sqlc is a strict superset.

squirrel / goqu dismiss

Runtime query builders. Dynamic, but not type-safe — the exact bug class we're solving — and they add a runtime dependency, violating the budget.

Plain refactor baseline

Phase 1 alone: extract schema to .sql, keep hand-written queries. The honest "do nothing fancy" option — and the correct fallback if the Phase 0 spike disappoints.

Status quo do nothing

Keep Go-string SQL + linters. Defensible today, but the dual schema source and the scan-order fragility remain. Acceptable only if the codebase stops evolving.

Convert 1:1 (~15 queries)

Snapshot, checkpoint, version-check, single-row inserts, the 3× ReadAll/ReadFrom/ fromStart patterns. These are fully static and hand-scanned today — they convert cleanly and deliver ~80% of the type-safety gain on ~20% of the risk surface.

Keep hand-written (~5)

SharedBatchInsertEvents, buildListQuery, and the LoadParams.Where-driven loads. sqlc is fundamentally static; these are runtime-built by design.

Deliberate decision (~5)

The five Load variants could be expanded into explicit per-variant sqlc queries (more boilerplate, but type-checked). This is a judgment call — Phase 3.

08Phased, reversible action plan

Each phase is independently shippable and revertible. Effort is T-shirt sized against the current storage/ structure; rollback cost is what it takes to undo if the phase disappoints. The early phases are low-risk and high-signal; the later phases are where the real tradeoffs live.

0

Spike — one query, isolated, deleted afterward effort: S rollback: delete dir

Add sqlc to flake.nix devShell only. Create storage/spike/sqlc/ with a minimal SQLite sqlc.yaml, schema.sql (extracted from SQLiteDialect.EventSchema()), and one query: -- name: LoadSnapshot :one. Run sqlc generate; compare generated Go against snapshot.go:142-178. Decision gate: was the generated code better? Delete the spike. If yes → Phase 1.

1

Extract schema to .sql files — pure refactor, no behavior change effort: S–M rollback: revert embed

Move DDL out of dialect.go:53-221 into storage/sql/schema/{postgres,sqlite}/*.sql. Have dialect.go //go:embed these files so InitSchema still works and golden tests still pass. This unifies the two sources immediately — a win before any sqlc adoption.

2

First real queries — snapshot + checkpoint effort: M rollback: restore hand-scan

Add sqlc.yaml with two engines (pg, sqlite), output to internal storage/sql/pg + storage/sql/sqlite. Convert snapshot upsert/load/loadAtVersion + checkpoint load/save + version-check. Delete the corresponding hand-written scan code. Run nix run .#test + golden tests; confirm green.

3

Inserts + journal reads effort: M–L rollback: per-query revert

Convert single-row inserts (event/command/query) and the 3× ReadAll/ReadFrom/fromStart. Decide explicitly: keep LoadParams.Where dynamic loads hand-written, or expand them into explicit per-variant queries (the real tradeoff).

4

Decide on migrations effort: L rollback: hard

Evaluate pairing the .sql schema with golang-migrate / atlas to replace InitSchema drop-recreate. This is a separate, consumer-facing decision — document in an ADR.

09Risks & open questions

What could go wrong, and what the Phase 0 spike must answer before committing. An honest brainstorm names its unknowns.

Risk

SQLite engine maturity vs PostgreSQL

sqlc engine parity

PostgreSQL is sqlc's first-class engine; SQLite support is solid but historically a step behind on edge cases. Our modernc.org/sqlite driver + TEXT time column is an unusual combination. Phase 0 must verify the generated SQLite code round-trips our schema, especially time columns.

Risk

ON CONFLICT / RETURNING divergence

snapshot upsert, inserts

Our snapshot upsert uses ON CONFLICT DO UPDATE. sqlc handles this, but PG (RETURNING) and SQLite codegen differ. Phase 0 must confirm both engines generate working upsert code for our exact statement.

Open question

Public API isolation

module boundary

This is a library — generated code must live in an internal package and not leak into the public surface. Confirm sqlc can emit to storage/sql/internal/... without consumers seeing it.

Open question

CI verification mode

sqlc.yaml database.managed

sqlc can verify queries against a live DB (database.managed) or parse the schema file. Which mode fits our Nix CI without a DB service? Default (parse-only) likely suffices, but needs confirmation.

The escape hatch: every risk above is answered by Phase 0 — a throwaway spike that touches no production code. If the spike reveals a blocker (SQLite time handling, ON CONFLICT, internal package emission), we fall back to the Plain refactor baseline (Phase 1 alone) and lose nothing.

10Recommendation

Do not rewrite storage/ wholesale. Start with the ~15 queries that are fully static and hand-scanned today — they convert 1:1 and deliver ~80% of the type-safety gain on ~20% of the risk surface.

My pick: Phase 0 + Phase 1 are low-risk, high-signal, and fully reversible. Phase 1 (extracting schema to .sql) is valuable even if you never adopt sqlc, because it kills the dual-source-of-truth problem (Go strings + golden files). Run Phase 0 first as an isolated spike to judge the real generated code rather than claims about it.
Phase 0: spike → Phase 1: extract schema → Phase 2: snapshot + checkpoint → Phase 3: the real tradeoff → Phase 4: migrations (ADR)
