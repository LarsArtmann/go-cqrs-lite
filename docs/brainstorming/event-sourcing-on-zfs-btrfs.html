Event Sourcing on ZFS / btrfs

Design brainstorm — how much of CQRS can the filesystem be, not just hold?

Core Insight

ZFS and btrfs already implement most event-sourcing primitives at the storage layer. The question isn't "how to store events on ZFS" — it's "how much of CQRS can the filesystem BE?"

ES Concept ZFS / btrfs Primitive
Append-only event log Copy-on-Write + ZIL (Intent Log)
Event immutability CoW guarantees old data is never overwritten
Projections / Materialized Views Snapshots of projection datasets
Time-travel queries zfs send -i @snap1 @snap2 / mount snapshot read-only
Event replication zfs send -R / btrfs send (incremental)
Data integrity Per-block checksumming (edonr / blake3 / sha256)
Event compaction Clone + flatten = snapshot without history
Global ordering TXG (Transaction Group) — ~5 s windows
Checkpointing ZFS bookmarks / btrfs subvolume snapshots

The Five Novel Angles

1. Snapshot = Instant Consistent Projection Checkpoint

# Atomic, consistent snapshot of ALL projections simultaneously
zfs snapshot -r tank/projections@2024-W26

# Or individual projection — O(1) operation
zfs snapshot tank/projections/user-by-email@v42

# Time-travel query: mount any past state READ-ONLY
mkdir /mnt/projection-past
mount -t zfs tank/projections/user-by-email@v42 /mnt/projection-past
cat /mnt/projection-past/a/alice@   # State as of v42
Why this matters Traditional event sourcing replays events to rebuild projections. ZFS snapshots give you O(1) access to any historical projection state — no replay. You get 1 000 time-travel queries for the cost of 1 projection run.

2. Send / Receive = Native Event Replication

# Full initial replication
zfs send tank/store@baseline | zfs receive backup/store

# Incremental — ONLY the new events (differential)
zfs send -i tank/store@baseline tank/store@v42 | zfs receive backup/store

# To a DIFFERENT machine for disaster recovery
zfs send -R tank/store@v42 | ssh backup-server zfs receive tank/store
Why this matters No Kafka, no Debezium, no custom CDC pipeline. The filesystem is your replication engine. Incremental sends are exactly zfs send -i @old @new — the diff between two snapshots. This is event streaming at the block level.

3. Clones = Branch the Event Store for Testing / Replay

# Clone the entire event store at a point in time
zfs clone tank/store@v42 tank/store-test

# Replay projections against a COW fork — zero space for shared blocks
# The test branch diverges; original is untouched.
# When done:
zfs destroy tank/store-test   # Instant cleanup
Why this matters Want to test a new projection handler against historical data? Clone the store, replay, validate — then destroy. Zero risk, near-zero cost. This is git branch semantics for your entire event store.

4. ZFS Properties as Event Store Metadata

# Checkpoint tracking (no external database needed)
zfs set user:projection:offset=00000001:00456789 tank/projections/user-by-email
zfs set user:projection:txg=1847293 tank/projections/user-by-email

# Schema version tracking
zfs set user:aggregate:schema-version=3 tank/store/aggregates/user

# Compression already built-in
zfs set compression=zstd-3 tank/store   # Events are JSON → 70–85 % compression

# Per-projection retention policy
zfs set user:snapshot:retain=90d tank/projections/dashboard-stats
zfs set user:snapshot:retain=365d tank/projections/user-by-email

5. btrfs reflink = Per-File Snapshots Without Full Snapshots

# Before updating a projection entry, reflink it (instant, COW)
cp --reflink=always projections/user-by-email/a/alice@ \
                     projections/user-by-email/a/alice@.prev

# Now update the projection atomically
mv alice@.tmp alice@

# Per-file time travel — no full snapshot needed
# Unique to btrfs — ZFS snapshots are all-or-nothing per dataset
Why this matters btrfs reflink gives you per-file COW snapshots. You can do per-key projection history without snapshotting the entire dataset. ZFS can't do this (snapshots are dataset-level).

The Hard Problems (Honest Assessment)

1. Global Event Ordering Across Aggregates

ZFS TXGs batch writes every ~5 seconds. Events within one TXG have no guaranteed order. You need either:

  • A global log (store/log/) with monotonic sequence numbers in the application layer
  • Or accept per-aggregate ordering only (most CQRS systems are fine with this)
  • Hybrid: global log for ordering, per-aggregate files for fast load

2. Concurrent Writers

ZFS has no record-level locking. For a single aggregate file:

  • Single-writer lock in application layer (flock or distributed lock)
  • Or use the global log + single consumer per aggregate partition

3. Projection Fan-Out / Notification

Filesystems don't have SELECT … FOR UPDATE or pub/sub. Options:

  • inotify / FSEvents on the log directory — kernel notifies on new segments
  • Poll the .cursor file (simple, low-tech, works)
  • TXG sync callback (ZFS-specific, requires kernel module)

4. Querying Projections

The filesystem is the index. Lookups are O(depth) directory traversal.

  • Works well: Key-value lookups (cat path/to/key), prefix scans (ls path/to/prefix*)
  • Doesn't work well: Range queries over values, full-text search, aggregations — compute at projection time, store result

5. Billion-Scale Files

ZFS handles millions of files well, but practical limits exist:

  • Directory listing gets slow at >100 K entries → use sharding: a/al/ prefix tree
  • DMU object numbers are 64-bit — no theoretical limit
  • Consider segmented files (one file per N events) instead of one file per aggregate

Killer Use Cases

  1. Audit-critical systems — Every state change is a ZFS snapshot. Regulatory compliance is zfs list -t snapshot -o name,creation. You literally cannot delete history.
  2. Edge / embedded systems — No Kafka, no Postgres. Just the filesystem. btrfs on a Raspberry Pi running your event-sourced IoT gateway.
  3. Disaster recovery — zfs send -R tank/store@latest | ssh dr-site zfs receive tank/store. Entire event store + projections replicated incrementally. Sub-second RPO.
  4. Multi-tenant isolation — One dataset per tenant. tank/tenant-a/store, tank/tenant-b/store. Per-tenant snapshots, quotas (quota=10G), compression, encryption keys.
  5. Event replay debugging — Clone the store at the failing point. Replay with logging. Destroy. Zero risk to production.
  6. Data locality compliance — encryption=aes-256-gcm per dataset, different keys per region. Snapshot + send for compliance exports.

The Pipe Dream: ZFS Channel Programs as Projection Handlers

ZFS Channel Programs (ZCP) let you run Lua scripts inside ZFS as atomic transactions. Theoretically: 

-- This runs INSIDE ZFS, as a single transaction
-- Read events, compute projection state, write to projection dataset
-- ALL ATOMIC — no partial state possible

events = zfs.list.children("tank/store/log")
for _, segment in ipairs(events) do
    local data = zfs.read(segment)
    for event in data:gmatch("[^\n]+") do
        if event:match('"type":"usercreated"') then
            local email = extract_email(event)
            local uid   = extract_id(event)
            zfs.write("tank/projections/user-by-email/" .. path_from_email(email), uid)
        end
    end
end
zfs.set_property("tank/projections/user-by-email", "user:offset", current_offset)

Kernel-level projection processing — no userspace round-trip. Pure speculation, but technically possible.

Should You Actually Build This?

✓ Yes, if …

  • Maximum infrastructure simplicity (filesystem = database + message bus + backup)
  • Audit / compliance is critical (snapshots = immutable audit trail)
  • Edge / embedded deployment (no external services)
  • Multi-tenant isolation with per-tenant encryption

✗ No, if …

  • Complex ad-hoc queries over projections (use Postgres)
  • Sub-millisecond fan-out to 1 000s of consumers (use Kafka)
  • Team doesn't know ZFS / btrfs operationally
  • Cloud-portability required (no ZFS on AWS RDS)
The most interesting angle This isn't about replacing databases. It's about recognizing that modern CoW filesystems already solve 80 % of event sourcing infrastructure. The remaining 20 % (ordering, notification, complex queries) is what you'd actually build.
