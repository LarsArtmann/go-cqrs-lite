A brutally honest review of go-cqrs-lite's architecture and data model, evolved through deep conversation. Every claim backed by verbatim source. The guiding principle: consumers never decide on infrastructure; deployers do. Grounded in research of Eventuous, Marten, LiveStore, Sekiban.

00Executive Summary

go-cqrs-lite has excellent foundations — ISP-split stores, branded IDs, error taxonomy, pure-function Decider. But the architecture has organic sprawl: 5 modules that should dissolve, a "projection" module that is actually a message bus, a read-model module that should merge into KV, storage backends scattered at root level, and Metadata types trapped in the wrong home.

The path to "best in the world" is not a rewrite — it is five dissolutions, one consolidation, and a delivery-layer commitment:

The verdict: The domain model is right. The packaging needs consolidation. Dissolve projection/, readmodel/, memory-bus, PostgresBus, and the reactive EventBus. Commit to Watermill as the single delivery layer. Merge readmodel into kv/. Move all storage backends under storage/ as subpath modules. Extract shared Metadata into its own type family. The library gets smaller while getting more capable.

01The North Star — Deployer Decides, Consumer Doesn't

"My goal is for consumers of this lib to NOT decide on the implementation of infrastructure — DB, message buses, etc. They should have a simple API that allows the person deploying the app to decide where they want to keep their data and what they want to store. We should have recommendations though — some metadata or projections (materialized views) may be better placed in a SQL/KV/columnar/Graph DB — but we should also be able to run fully with just a SQLite + Memory setup, maybe even multiple SQLite DBs, e.g. 1 for Command + Event Sourcing, 1 for Query (logs), and 1 for materialized views."
— Lars Artmann, project owner

This is the architectural north star. Every module decision must serve it. Here's what it means concretely:

Consumer API (app developer writes) Deployer API (ops engineer configures)
stack.Repository[State, Cmd](bundle, decider) Picks preset: sqlite.New(), pebble.New(), postgres.New()
stack.View[TodoView, TodoID](bundle) Chooses: same DB as events? Separate DB? KV backend?
repo.Execute(ctx, aggID, cmd) Never sees the store, bus, or codec. Gets a *Bundle with capabilities wired.
query.DispatchTyped[R](ctx, dispatcher, q) Chooses: persist all queries? Metadata-only? Off? sqlite.WithQueryDB("audit.db")
Defines materialization: On[UserCreated](...) Chooses where views live: SQL table? Pebble KV? In-memory?
The minimum viable deployment: SQLite + Memory. One process, zero external services. Three SQLite files if the deployer wants separation: events.db (event store + commands + snapshots), queries.db (query audit log), views.db (materialized read models). The consumer code is identical regardless of which configuration the deployer chose.

02Module Inventory — 39 Modules, Too Many at Root

The library already uses subpath modules — proven pattern:

stack/pebble/go.mod → module github.com/larsartmann/go-cqrs-lite/stack/pebble/v2 stack/sqlite/go.mod → module github.com/larsartmann/go-cqrs-lite/stack/sqlite/v2 stack/postgres/go.mod → module github.com/larsartmann/go-cqrs-lite/stack/postgres/v2

This means pebble/ can move to storage/pebble/ with zero risk — the import path just becomes storage/pebble/v2, independently versioned, independently importable. The pattern is already battle-tested in this repo.

The problem: storage backends are scattered across root level instead of grouped:

05Problem Catalog — Brutal Honesty with Evidence

Seven themes. Every claim backed by verbatim source with file:line.

Theme A — The Leaky Event Abstraction

Critical

A1 · "Generic" helpers type-assert to the concrete impl

event/codec.go:44-50 · event/codec.go:62-64 · event/codec.go:69-75 · event/tombstone.go:93-100 
// event/codec.go:44 — verbatim
func payloadForDecode(evt Event) []byte {
    if ie, ok := evt.(*ImmutableEvent); ok {
        return ie.payload  // bypasses clone — reaches into PRIVATE field
    }
    return evt.Payload()
}

Four helpers do this. The interface is a lie; *ImmutableEvent is the real contract. Fix: Make Event a concrete struct. One production impl. Type-assertions become direct field access.

High

A2 · eventOptions pointer leaks construction config into event lifetime

event/event.go:86 · event/event.go:89-93

Every event carries opts *eventOptions (codec + clock + deadline) for its entire lifetime — config only needed at construction. Fix: Keep config in constructor scope; materialize Event with data fields only.

Theme B — Metadata Lives in the Wrong Home

Critical

B1 · command.Metadata and query.Metadata are aliases of event.Metadata

command/metadata.go:11 · query/query.go:36
// command/metadata.go:11 — verbatim
type Metadata = event.Metadata  // ALIAS — command inherits event's shape

// query/query.go:36 — verbatim
type Metadata = event.Metadata  // ALIAS — query inherits event's shape

The problem: event.Metadata has CausationID (meaningless for queries), tombstone soft-metadata in Custom (event-specific), and no command-specific fields (RetryCount, IdempotencyKey). The aliasing forces every message type into the event's shape.

Fix — three options, ranked by simplicity:

A) Kill aliases, embed shared base (simplest): Extract a Tracing struct (CorrelationID, CausationID, UserID, RequestID) into event/. Each module defines its own Metadata that embeds Tracing + adds type-specific fields. No new module.

B) Extract to domain/ module: A new module holds Tracing, AggregateRef, Type, Version. event/, command/, query/ import it. Clean but adds a module everyone depends on.

C) Keep aliases but split event.Metadata: Shared shape stays aliased; event-specific concerns (tombstone, security) move to a separate EventMetadata on the Event struct.
Critical

B2 · The "real" event schema lives in Custom strings

event/metadata.go:10-19 · event/tombstone.go:48 · event/causality.go

12 first-class domain concepts (tombstone, rebirth, command-causation, client-timing, signing, encryption) all live as strings in Custom map[MetadataKey]string. The 7 typed fields are the minority; the string map is the real model. Fix: Promote to typed fields — TombstoneMark, Causation, SecurityEnvelope. Keep Extensions for consumer-defined concerns only.

Theme E — "Projection" is a Message Bus, Not a Projection

Critical · The Biggest Naming Lie

E1 · projection.Runner subscribes to events — it IS a message bus

projection/runner.go:36 · projection/runner.go:54
// projection/runner.go:36 — verbatim
subscriber  event.Subscriber  // ← requires a BUS interface!

// projection/runner.go:54 — verbatim
func NewRunner(
    journal event.Journal,
    subscriber event.Subscriber,  // ← the BUS
    checkpoint event.CheckpointStore,
    ...
) (*Runner, error)

The user's reaction: "event → do something... that's not a projection, that sounds like a message bus! WTF?"

They're 100% right. A projection is a materialized view — the data structure that results from applying events. projection.Runner is delivery infrastructure: it subscribes to events, dispatches to handlers, manages checkpoints, retries, DLQ. That's what a message bus does. The "projection" is the read model — which is the kv.TypedStore the handler writes to.

The whole module dissolves into:

projection.Runner → becomes → Watermill Router + retry middleware + poison queue
projection.Builder + On[T] → becomes → stack.Materialize[V,K] + router.AddHandler
projection.DistributedRunner → becomes → Watermill Router + leader election plugin
What dies: The entire projection/ module. Replay logic → Watermill catch-up plugin. Checkpoint → Watermill middleware. DLQ → Watermill poison queue (already built, better than our fire-and-forget callback). Handler registration → standard Watermill handler. ~1500 LOC of parallel delivery machinery → gone.

Delivery = Watermill (One Layer, Not Five)

The watermill/ adapter becomes bidirectional — cqrs events go into Watermill, Watermill messages come back as cqrs events: 

// watermill/ — bidirectional adapters

// cqrs → Watermill: event.Publisher backed by Watermill
func NewPublisher(pub message.Publisher, topic string, c codec.Codec) event.Publisher

// The decider only needs event.Publisher (1 method). That stays.
// Everything else — Bus, Subscriber, Middleware, reactive — goes to Watermill.
// Consumers register handlers directly on the Watermill Router.

What dies: event.Bus, event.Subscriber, event.Middleware, event.PublishMiddleware, event.EventBus (reactive), memory.MemoryBus, memory.MemoryCommandBus, storage.PostgresBus, projection.Runner, projection.DistributedRunner, projection.Builder, middleware/retry, middleware/circuit_breaker. ~2000 LOC of parallel delivery machinery replaced by Watermill's battle-tested Router.

Materialization = kv.TypedStore + Watermill Handler

The user's pain: projection.On[UserCreated](builder, "user.created", codec, func(ctx, evt) error { return viewStore.Set(...) }) — "this sucks ass."

The fix: a fluent materialization API that lives in stack/ and wires event → decode → apply → kv.TypedStore automatically. It models the full lifecycle — including tombstones. There is no OnDelete that hard-removes a row: the event store has no Delete (ADR-0006), and the materialize layer follows the same invariant. Deletions are soft, via tombstone markers. 

// stack/materialize.go — the projection people actually want

mat, _ := stack.Materialize[UserView, UserID](bundle).
    OnCreate("user.created", func(ctx, evt UserCreated) (UserID, *UserView, error) {
        return evt.AggregateID, &UserView{Name: evt.Name}, nil
    }).
    OnUpdate("user.renamed", func(ctx, evt UserRenamed, existing *UserView) (*UserView, error) {
        existing.Name = evt.NewName
        return existing, nil
    }).
    OnTombstone("user.deleted", func(ctx, evt UserDeleted, existing *UserView) (*UserView, error) {
        existing.Status = event.TombstoneSet      // mark deleted, DON'T remove the row
        return existing, nil
    }).
    OnRebirth("user.restored", func(ctx, evt UserRestored, existing *UserView) (*UserView, error) {
        existing.Status = event.TombstoneRebirth   // un-delete
        return existing, nil
    })

// mat.Register(router) — wires as Watermill handler
// mat.View(ctx, id) — typed read from kv.TypedStore
// mat.List(ctx, kv.IncludeTombstoned) — show all, with Status field
// mat.List(ctx, kv.ExcludeTombstoned) — hide deleted (the default)
// mat.List(ctx, kv.OnlyTombstoned)   — show only deleted
No OnDelete. Ever. The event store has no Delete (ADR-0006) — hard-removing a materialized row would violate the same invariant the store enforces. Deletions are always soft via OnTombstone; the row stays, its Status flips to TombstoneSet. OnRebirth reverses it. This is the materialize layer mirroring the tombstone model the write side already enforces.
No manual codec. No manual key construction. No manual store wiring. Type-safe. Tombstone-aware. The "projection" is the data in kv.TypedStore. The "runner" is the Watermill Router. Everything just clicks.

10Anti-Patterns to Avoid

Don't build a second bus

Watermill is the delivery layer. Any new in-process pub/sub duplicates it. If you need delivery, use Watermill's Router.

Don't call delivery "projection"

A projection is materialized data. The machinery that updates it is delivery. Naming matters.

Don't alias Metadata across message types

Commands need RetryCount. Queries don't need CausationID. Each type owns its Metadata.

Don't scatter storage backends at root

All backends under storage/. Subpath modules give grouping + independent versioning.

Don't force a backend on the consumer

Consumer code is identical regardless of SQLite/Pebble/Postgres. The Bundle hides the choice.

Don't conflate Decide and Apply

Different functions, different signatures. Mixing them creates indirection.

Don't make DLQ fire-and-forget

Watermill's poison queue is durable. Use it. Callbacks that log = silent data loss.

Don't hard-delete materialized rows

The store has no Delete (ADR-0006). The materialize layer follows the same invariant: OnTombstone marks, it never destroys. Hard-removing a read-model row would lose data the event log still holds. Use OnTombstone / OnRebirth, query with ExcludeTombstoned.

12Conclusion

go-cqrs-lite has the right domain model and the right foundations. The path to "best in the world" is consolidation, not addition: dissolve 5 modules that duplicate what Watermill already does, merge the read-model facade into KV, group all storage backends under one tree, and kill the Metadata aliasing that forces event-shaped metadata onto commands and queries.

The north star — consumers never decide on infrastructure, deployers do — is achievable with multi-DB presets and the Bundle capability bag. The consumer writes repo.Execute() and stack.Materialize[V,K](). The deployer picks SQLite, Pebble, or Postgres — even split across multiple databases. Same code, different deployment.
