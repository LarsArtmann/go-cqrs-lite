Architecture Deep-Dive · Data Model Review

The Best CQRS/ES SDK in Go
— a First-Principles Review

A brutally honest, deep review of go-cqrs-lite's data model — celebrating what is world-class, exposing where the type algebra has rotted, and redesigning the model from first principles to make invalid states unrepresentable and the developer experience exceptional. Grounded in research of Eventuous, Marten, LiveStore, Sekiban, and the aggregateless-event-sourcing frontier.

30 modules reviewed ~70 type definitions State-of-the-art: Eventuous · Marten · LiveStore Goal: Best SDK in any language

00Executive Summary

go-cqrs-lite is already one of the most thoughtfully architected CQRS libraries in any language. Its ISP-split store interfaces, branded ULID identifiers, five-family error taxonomy, pure-function Decider, and tombstone-soft-delete model are genuinely excellent. The hard architectural problems — immutability, optimistic concurrency, replay-safe projections, schema evolution — are solved.

But the type algebra has accumulated organic rot in three places that block the path to "best in the world":

  1. The Event interface is a leaky abstraction — every internal hot path type-asserts to *ImmutableEvent, and the real domain model lives in a string-keyed Metadata.Custom escape hatch (tombstone, causality, command-causation, signing, encryption all live there).
  2. The materialization story is incomplete — no projection lifecycle choice (Marten's Inline/Live/Async), a fire-and-forget DLQ, no shipped projection→readmodel integration, and compute-on-read vs project-on-write are separate unconnected worlds.
  3. Massive duplication and asymmetry between command/query modules, typed/untyped parallel hierarchies, inconsistent context handling, and a packaging problem that locks generic algorithms behind the full CQRS stack.

01The Three-Pillar Foundation — What "Best" Means

Before cataloging problems, we must define what "best in the world" actually means. Deep research into the leading CQRS/ES libraries (Eventuous .NET, Marten, LiveStore, Axon, Sekiban DCB, hallgren/eventsourcing, thefabric-io/eventsourcing) reveals three pillars that the best libraries share — and that no current Go library has fully achieved.

Pillar 1 — Three Pure Functions, Nothing Else

Eventuous taught us this. The entire domain layer reduces to three pure, side-effect-free functions. Everything else is infrastructure: 

// The complete domain algebra of event sourcing
Decide(Command, State) → ([]Event, error)   // command → events (the decision)
Apply (State, Event)  → State              // event → new state (the fold)
Project(Event)        → error              // event → read-model mutation

No current Go library separates Decide from Apply as distinct pure functions — they conflate them in aggregate methods. go-cqrs-lite is closest: it has Decider.Fold (which is really Apply) and a per-call DecideFunc. But the naming lies, and Decide is not a field on the struct. This is opportunity #1.

Pillar 2 — Projection Lifecycle is a First-Class Choice

Marten's killer feature. Every read model declares when it gets built:

Inline

Updated in the same transaction as the event append. Strong consistency. Cost: slower writes.

Live

Rebuilt on read from the event log. Always fresh. Cost: slower reads, no persistence.

Async

Updated by a background tail. Eventual consistency. Fast reads, fast writes, at-least-once.

go-cqrs-lite ships only Async (the projection.Runner) and an ad-hoc Live (listing.InMemoryAggregateReader rebuilds on query). No Inline. No way for the consumer to choose per-view. This is opportunity #2 — and it's the biggest one.

Pillar 3 — The Dual-Store Architecture

LiveStore's innovation. Production event sourcing is two databases, not one:

Event Log → immutable, append-only, the source of truth → Materializer → derives → Materialized State DB (queryable, rebuildable, disposable)

The materialized state DB can be fully recreated from the event log at any time. This is the architectural pattern that makes event sourcing operationally viable: schema migrations trigger automatic rebuilds, projections can be added retroactively, and the read model's storage format is decoupled from the write model's.

go-cqrs-lite has all the pieces (event store, projection runner, readmodel store) but never wires them into this dual-store contract. The consumer hand-glues the projection→readmodel seam. This is opportunity #3.

What no Go library has achieved yet: (1) Type-safe event application without runtime any casts.
(2) Projection lifecycle as a declarable choice.
(3) Decide/Apply as separate pure functions.
(4) A clean dual-store architecture where the read DB is disposable. Achieving all four makes go-cqrs-lite the reference Go implementation.

02What's Already World-Class (Preserve These)

Before any critique, this library gets a remarkable amount right. These patterns are the quality benchmark. Every redesign must preserve them.

+
ISP-split store interfaces EventSink | EventSource | Journal | SeekableJournal | BackwardsSource — consumers depend only on what they use. A projection never sees write methods. A writer never sees read methods. ADR-0006 was the right call.
+
Branded ULID identifiers id.Of[T] = cbid.ID[T, ulid.ULID] — phantom-typed, compile-time-safe, time-ordered, binary-sortable. EventID can never be confused with AggregateID at the type level. The marker exports (ADR-0024) enable downstream tooling.
+
The five-family error taxonomy Rejection | Conflict | Transient | Infrastructure | Corruption — classified via go-error-family, re-exported through event. Retry middleware can IsRetryable(err) structurally. This is genuinely ahead of most Go libraries.
+
Pure-function Decider Decider[State]{Initial, Fold} + per-call DecideFunc — functional core, imperative shell. No base class, no reflection, no embedded infrastructure. ADR-0001 was visionary; it matches the Eventuous / functional-ES frontier.
+
Tombstone soft-delete via metadata Hard delete is impossible at the type level (no Delete on Store). Soft-delete via DetectTombstone / MarkTombstone preserves history. The concept is right — the implementation location (string metadata) is the problem we'll address.
+
Replay-safe processing-mode context WithProcessingMode(ctx, ModeReplay) lets handlers distinguish live from replay (don't send emails during replay). This matches Axon's isLive() — implemented at the context level, which is cleaner.
+
Codec abstraction with BufferEncoder codec.Codec interface + BufferEncoder extension for zero-alloc encoding. JSON, CBOR (canonical), CBOR-compact, Raw. Clean separation of payload encoding from event structure.
+
Defensive cloning on all public accessors Payload() clones, Metadata() deep-copies, EventTypes() clones. The immutability contract is enforced at the boundary, even though it's contractual at the interface level. Internal PayloadReadOnly bypasses for hot paths.
+
Stack presets as composition root stack/memory, stack/sqlite, stack/pebble, stack/postgres — one call wires the full stack. The deployer picks the preset; the app developer never imports a backend. This is the right DX direction.

Theme A — The Leaky Event Abstraction

The event.Event interface is documented as the public, immutable contract — but the concrete *ImmutableEvent is the only production implementation, and the library's own helpers silently require it.

Critical · P0

A1 · "Generic" helpers type-assert to the concrete impl

event/codec.go:44 · event/codec.go:62 · event/codec.go:69 · event/tombstone.go:93

Four exported/unexported helpers — payloadForDecode, PayloadReadOnly, encodingForCopy, tombstone.copyWithMetadata — all do evt.(*event.ImmutableEvent) and reach into private fields to bypass the defensive clone. A custom Event implementation (e.g., a test fake, or a future record-replay proxy) silently pays the clone cost or breaks entirely. The interface is a lie; the concrete struct is the real contract.

Fix: Either (a) make Event a concrete struct (accept that there's one impl) — the simplest, most honest choice — or (b) add an unexported method to the Event interface that exposes a read-only payload pointer, making the zero-copy contract explicit and implementable by any conforming type. Option (a) is strongly recommended: there is exactly one production Event impl, and the "interface for testability" benefit is already provided by eventtest.FakeStore operating on []Event values.
High · P1

A2 · eventOptions pointer leaks config into event lifetime

event/event.go:89 · event/event.go:75

ImmutableEvent carries an opts *eventOptions pointer holding a codec.Codec and Clock — configuration that is only needed at construction time but persists for the event's entire lifetime. Events reconstructed from storage carry a codec reference they will never use. This bloats every event in memory and couples the immutable data record to construction-time machinery.

Fix: Construction-time config belongs in the constructor's local scope, not on the struct. Apply options to a local builder, then materialize an ImmutableEvent with only the data fields. The codec is needed for New() (typed payload) and never again.
High · P1

A3 · Encoding() normalizes "" to JSON, hiding unset state

event/event.go:119 · event/codec.go:69 · event/codec.go:113

ImmutableEvent.Encoding() returns codec.EncodingJSON when the field is the zero value "". This means "encoding was never set" is indistinguishable from "genuinely JSON". encodingForCopy works around this by reaching into the private field. And validateEncodingMatch treats "" and codec.EncodingJSON as equivalent — so a freshly-zero-valued event decodes as JSON even if the bytes aren't JSON.

Fix: Make encoding a required field at construction (default to JSON explicitly, never zero-value). Or use a sentinel EncodingUnknown = "" and reject it at decode boundaries. The current "lie by default" is a corruption vector.
Critical · P0

A4 · Immutability is contractual, not compiler-enforced

event/event.go:60 (interface doc) · decider/enricher.go:25

The Event interface documents that Payload() must return a copy — but any third-party implementor can violate this. Worse, decider.applyEnricher type-asserts to *ImmutableEvent and mutates events in place between decide and Save, applying event.Options. The "Immutable" name is a documentation claim, not a type-system guarantee.

Fix: Make ImmutableEvent a true value type with no exported setters and no in-place enrichment. Enrichment should produce a new event (the existing Clone+options pattern), not mutate. The decider should enrich by maping the decide result through the enricher, producing a new slice.

Theme B — The Soft Metadata Escape Hatch

event.Metadata has 7 typed fields (CorrelationID, CausationID, UserID, RequestID, Source, IPAddress, UserAgent) and an escape-hatch Custom map[MetadataKey]string. The escape hatch has become the real domain model — tombstone state, rebirth, command causation, client timing, signing algorithm/key-id, and encryption metadata all live there as strings.

Critical · P0

B1 · Tombstone state is a magic string in a string map

event/tombstone.go:48-51 · event/tombstone.go:57 · event/tombstone.go:93

MarkTombstone writes Custom["tombstone"] = "true". DetectTombstone reads Custom["tombstone"] == "true" — only the literal string "true" is honored; any other value is silently treated as "not tombstoned". The soft-delete state of an aggregate — a critical domain concept — is encoded as a stringly-typed boolean in a map that's documented as the escape hatch for "custom" concerns. This is the textbook example of a domain concept that should be a first-class type.

Fix: Promote tombstone to a typed field. Either a dedicated Tombstone *TombstoneMarker on Metadata, or — better — make it part of an explicit AggregateStatus derived type rather than metadata at all. The detection algorithm (last-event-wins) is fine; the storage location is wrong.
High · P1

B2 · Command causation splits its typing across two fields

event/causality.go:11 · event/options.go:99 · event/causality.go:55

causalityCtx.commandType is a bare string while causalityCtx.commandID is a branded id.CommandID. They're stored as two separate Custom entries ("command.type", "command.id"). The asymmetry — branded ID, unbranded type — is a structural lie: command.Type exists as a named type, but causality throws it away.

Fix: Promote to a typed Causation *Causation{CommandType command.Type, CommandID id.CommandID} on Metadata. The existing WithCommandCausality API stays; it just writes to a typed field instead of two string-map entries.
High · P1

B3 · omitempty inconsistency leaks zero-value ULIDs into JSON

event/metadata.go:10-22

CorrelationID, CausationID, UserID, RequestID are always serialized (no omitempty), so zero-value ULIDs ("00000000000000000000000000") leak into JSON output. The three string fields (Source, IPAddress, UserAgent) and Custom correctly use omitempty. The result: events with no correlation produce JSON with four 26-character zero strings.

Fix: Either give the branded ID types an IsZero()-aware MarshalJSON that omits when zero (preferred — fixes it everywhere), or add omitempty to the four fields. The former is one change in id/; the latter is four tags.
Critical · P0

B4 · The "real" event schema is a string-keyed map

event/metadata.go:10 + event/tombstone.go + event/causality.go + signing/event.go + encryption/envelope.go

When you catalog every concept that actually travels with an event through the system, you find: tombstone status, rebirth marker, command-causation type+id, client id, client occurred-at, signing algorithm, signing key-id, signature value (single + multi), encryption algorithm, encryption key-id, IV/nonce. Twelve first-class concepts, all encoded as strings in Custom or in signing/encryption-specific envelopes. The 7 typed Metadata fields are the minority; the string map is the real model.

Fix: The redesign introduces a Metadata with typed fields for the established concepts (correlation, causation, tombstone, signing, encryption) and a strictly-scoped Extensions map[string]string for genuinely consumer-defined concerns. The escape hatch shrinks to its proper role: extensibility, not core domain.

Theme C — Command/Query Duplication & Asymmetry

The command/ and query/ modules are structurally near-identical but copy-pasted, with subtle asymmetries that invite bugs. This is ~600 LOC of duplicated Type, Metadata, Middleware, Dispatcher, reactive bus, and error boilerplate.

High · P1

C1 · Identical Type, Metadata, Middleware types duplicated

command/command.go:10 vs query/query.go:11 · command/metadata.go:11 vs query/query.go:36 · command/handler.go:9 vs query/query.go:99

type Type string is defined twice with identical methods (String, IsZero, ParseType). Metadata = event.Metadata is aliased twice. Middleware func(Handler) Handler is defined separately in each (they can't be shared because Handler differs). The reactive bus (CommandBus, QueryBus), filters, HandlerToObserver, and the entire error-re-export block are near-verbatim copies.

Fix: Two viable paths. (a) Code generation — extend cqrs-gen to emit the symmetric types from a single template, keeping module isolation. (b) A shared message/ module at Layer 1 that both command and query import — but this creates a dependency. Path (a) preserves the multi-module isolation principle; path (b) is simpler. Recommended: code-gen the boilerplate, keep modules independent.
High · P1

C2 · Handler signatures are asymmetric

command/handler.go:6 vs query/dispatcher.go:27

command.Handler = func(ctx, Command) error — fire-and-forget, no result. query.Handler = func(ctx, Query) (any, error) — type-erased result, requires DispatchTyped[T] to recover the type. The asymmetry is real (commands have no return, queries do), but it means there's no shared Handler abstraction — and the any on the query side is the one place this library uses untyped any in a public API.

Fix: The asymmetry is intrinsic (commands vs queries really do differ). The any is the price of Go's lack of variance — accept it, but document the "typed bookend" pattern (ADR-0008 already does this well). The fix here is consistency: command.Handler uses type Handler func(...) (named type) while query.Handler = func(...) (alias). Pick one.
Critical · P0

C3 · Query has no Bus interface; command does

command/bus.go:29 (Publisher+Subscriber+Bus) · query/ has only reactive QueryBus

The command side ships both a callback-based Bus interface (Publisher, Subscriber, PublishMiddleware) and a reactive CommandBus = ro.Subject[Command]. The query side ships only the reactive QueryBus. This asymmetry means there's no way to do query pub/sub with middleware in the callback style — you must use the reactive API. For a library that prides itself on symmetric treatment, this is a jarring gap.

Fix: Either add a callback-based query.Bus for symmetry, or document that queries are reactive-only by design (queries are typically request/response, not pub/sub — so reactive-only may be defensible). Recommended: remove the asymmetry by documenting the design decision in an ADR, and add the callback Bus if consumers ask for it.

Theme D — The Decider Identity Crisis

The Decider[State] is the library's crown jewel — but its naming lies, it's missing the Decide function as a field, and its snapshot integration is asymmetric.

Critical · P0

D1 · Decider has no Decide field

decider/decider.go:24-27 · decider/decider.go:94

The struct is named Decider[State] but contains only Initial and Fold. The decision logic is passed per-call as a DecideFunc to Repository.Execute. This means the Decider doesn't actually decide anything — it's a Fold-spec. Every caller closes over their command inside the DecideFunc, so the command type is invisible to the type system. There's no compile-time link between Decider[UserState] and the command type CreateUser it handles.

Fix — the Eventuous-inspired redesign: 
type Decider[State any, Cmd any] struct {
    Initial State
    Decide  func(Cmd, State) ([]Event, error)
    Apply   func(State, Event) (State, error)  // renamed from Fold
}
Now Decider[UserState, CreateUser] binds the command type at compile time. Apply replaces Fold (standard ES terminology). The old single-param Decider[State] with per-call DecideFunc remains available as a thin adapter for backward compatibility.
High · P1

D2 · LoadAtVersion/LoadAtTime bypass snapshots

decider/load.go:100-163 vs decider/decider.go:231-260

Repository.Load uses snapshots when configured (loads from snapshot, folds only events since). But LoadAtVersion and LoadAtTime — the time-travel APIs — always replay from version 0, ignoring snapshots entirely. A snapshot at version 10 + LoadAtVersion(15) replays all 15 events when it could load the v10 snapshot and replay 5.

Fix: Time-travel loads should use LoadAtVersion(min(snap.Version, targetVersion)) from the snapshot, then replay forward to the target. The snapshot store's LoadAtVersion already exists for exactly this. The asymmetry is an oversight, not a design choice.
High · P1

D3 · Snapshot save errors are silently swallowed

decider/decider.go:169-227

saveSnapshotAfterEvents writes the snapshot after Publish, and any error is logged via slog.WarnContext and discarded. There is no way for the caller to observe snapshot failure — not via the return value, not via a metric, not via an OTel span event (the span is recorded, but the error doesn't propagate). A silently-failing snapshot means the optimization silently stops working.

Fix: At minimum, emit an OTel span event + a counter metric on snapshot failure. Better: return snapshot errors as a structured SnapshotResult alongside the primary error, so callers who care can observe without breaking the "snapshot is best-effort" contract.

Theme E — Materialization Gaps (The Biggest Opportunity)

This is where the library is furthest from "best in the world" — and where the biggest wins live. The pieces exist (projection runner, readmodel store, listing reader, cache decorator) but they're not unified into the coherent materialization story that Marten and LiveStore demonstrate.

Critical · P0

E1 · No projection lifecycle choice (Marten's killer feature)

projection/runner.go:34 (Async only) · listing/in_memory.go:16 (ad-hoc Live) · no Inline anywhere

Marten's three projection lifecycles — Inline (same transaction as event append, strong consistency), Live (rebuild on read, always fresh), and Async (background tail, eventual consistency) — are the most practical innovation in any modern ES library. They let the consumer declare per-view how they want consistency vs performance.

go-cqrs-lite ships only Async (projection.Runner) and an ad-hoc Live (listing.InMemoryAggregateReader rebuilds the full cache on query). There is no Inline projection. The consumer cannot say "this view must be strongly consistent" or "this view is fine eventually-consistent" or "this view is cheap enough to recompute on every read" — at the type level.

Fix — the Materialization Vision (§05): Introduce a ProjectionMode enum and make it a first-class field on every projection. The runner infrastructure for Async already exists; Live is a wrapper that delegates reads to a re-builder; Inline requires a transactional event-store hook (the TransactionalSink that was removed in ADR-0006 — but now with a narrower, projection-only scope).
Critical · P0

E2 · DLQ is a fire-and-forget callback, not a durable queue

projection/options.go:22 · projection/runner_live.go:112

DeadLetterHandler is func(ctx, projectionName, evt, err) — invoked inline after retries exhaust. If the callback itself only logs (the common case), the event is silently lost from the projection's perspective. There is no persistent dead-letter store, no replay-from-DLQ API, no way to recover. For a library aiming at production-grade trustworthiness, this is the weakest link in the reliability model.

Fix: Introduce a DeadLetterStore interface (Sink + Source + Journal, mirroring the event store ISP). The default impl is in-memory; SQL/Pebble backends ship. WithDeadLetterStore wires it. runner.ReplayDeadLetters(ctx, projectionName) re-drives failed events after a handler fix. This turns "lost events" into "recoverable events".
High · P1

E3 · replayIDs is unbounded + racy

projection/runner.go:41 · projection/options.go:78

The replay/live dedup seam uses replayIDs map[id.EventID]struct{} — a plain map written during replay (single-threaded, OK) and read concurrently by the live dedup filter. Default capacity is 0 (unbounded), so the map grows forever for 24/7 runners. WithDedupCapacity bounds it, but the default is a memory leak. And the map-pointer swap on RunReplay relies on the state CAS for happens-before — fragile, no formal guarantee published via the atomic.

Fix: Default to a bounded dedup (e.g., 10k entries with FIFO eviction — the bounded code already exists in event.DistinctByEventIDBounded). Use a sync.Map or an explicit mutex for the replay/live seam. Document that the dedup is best-effort and idempotency is the handler's responsibility.
High · P1

E4 · No shipped projection→readmodel integration

projection/ (no import of readmodel) · readmodel/ (no import of projection) · listing/ (no import of readmodel)

The library has a clean separation: projection (event → handler), readmodel (typed KV store), listing (aggregate reader). But the consumer must hand-wire the projection handler closure to call readmodel.Store.Set. There is no shipped TypedProjection[V] that materializes events into a readmodel.Store[V,K] automatically. The clean separation is architectural — but never demonstrated. A new consumer has to invent the integration.

Fix: Ship a projection.TypedProjection[V, K] in a new stack/materialize module (or in readmodel itself) that wires the projection handler to the readmodel store. Provide 3-4 recipes in the docs. The dual-store architecture (Pillar 3) should be a one-liner, not a research project.

Theme F — Storage & Composition Leaks

High · P1

F1 · IsDuplicateKeyError matches driver error strings

storage/sql/duplicate.go:8

The function string-matches "UNIQUE constraint failed" (SQLite) and "duplicate key value violates unique constraint" (Postgres). Any driver version change that tweaks the error message breaks this silently — optimistic concurrency detection fails, and conflicts get misclassified. This is the textbook "don't parse errors by string" anti-pattern.

Fix: Use typed error inspection: pgconn.PgError with code 23505 for Postgres, SQLite extended error code SQLITE_CONSTRAINT_UNIQUE via the driver's typed error. Fall back to string matching only as a last resort, and log when the fallback fires so drift is detectable.
High · P1

F2 · Context is ignored by kv.Store and readmodel.Store

kv/kv.go:6-83 (no ctx) · readmodel/store.go:20-23 (ctx accepted but ignored) · storage/kv_sql.go:28 (uses context.Background())

kv.Store methods take no context.Context — so cancellation and deadlines cannot propagate. readmodel.Store accepts _ context.Context (underscore-named, ignored) and documents that the backend doesn't honor cancellation. SQLKVStore uses context.Background() internally. For a library that correctly threads context everywhere else, this is a real consistency gap — and a production hazard (a slow KV operation can't be cancelled).

Fix: Breaking change to kv.Store: add ctx context.Context as the first param on every method. readmodel.Store already has the param; wire it through. SQLKVStore uses the passed ctx. This is a v3-worthy change — schedule it.
High · P1

F3 · stack errors use plain errors.New, not the classified family

stack/errors.go:6-40

The stack module's errors (ErrMissingEventStore, ErrMissingPublisher, etc.) use errors.New — plain sentinels with no family classification. Every other module uses event.NewInfrastructure / event.NewRejection so errors.As and IsRetryable work. The stack errors are invisible to the retry middleware.

Fix: Re-define as event.NewInfrastructure("stack.missing_event_store", "...") for all configuration errors. One-file change, full classification parity.

Theme G — Packaging (The Adoption Blocker)

The "Why I Can't Use You" feedback was clear: the patterns are world-class, but the dependency graph blocks adoption. A consumer who wants only retry+backoff+circuit-breaker must import the entire CQRS stack + the OpenTelemetry SDK.

Critical · P0

G1 · Generic algorithms locked behind CQRS types

middleware/circuit_breaker.go · middleware/generic.go (retry/backoff are typed to Handler)

Retry, exponential backoff with jitter, and circuit breaker are pure algorithms operating on func() error. They have no business knowing about events, commands, queries, or OpenTelemetry. Today they're packaged as Middleware func(Handler) Handler — locked to the CQRS handler type. The algorithms are 90% of the value; the packaging is the blocker.

Fix — the resilience extraction: 
// New module: resilience/ — stdlib only, zero CQRS deps
package resilience

type RetryConfig struct {
    MaxAttempts  int
    InitialDelay time.Duration
    MaxDelay     time.Duration
    Multiplier   float64
    Jitter       bool
    IsRetryable  func(error) bool
}

func Do(ctx context.Context, cfg RetryConfig, fn func() error) error

type CircuitBreaker struct { /* three-state machine */ }
func (b *CircuitBreaker) Do(fn func() error) error
The existing middleware.CommandRetry / EventRetry become thin wrappers: func(ctx, h) error { return resilience.Do(ctx, cfg, func() error { return h(ctx) }) }. Zero breaking changes. Every Go project making network calls can now adopt the resilience layer without importing CQRS.
High · P1

G2 · go.mod hygiene inflates perceived coupling

event/go.mod lists test-only siblings as direct deps

The maintainer's response to the feedback correctly noted that event/v2's production imports are only id, codec, go-error-family, samber/ro — but the go.mod lists test-only siblings (command, query, memory, schema, snapshot) as direct requires. A consumer running go mod tidy sees the inflated graph and concludes "this is a hub". The architecture is right; the manifest lies.

Fix: Move test-only sibling imports into an event/eventtest sub-module with its own go.mod, or use build constraints. The production event/go.mod should reflect the production import graph. Combined with a dependency-budget CI check (mechanical enforcement), this kills the "hub" perception permanently.

04The Redesigned Data Model

From first principles — using Go's full type power (branded types, generics, composition via embedding, interface-based unions, constructor functions). Every design decision below has a rationale; rejected alternatives are in §06.

Core Value Types — Refinements

The branded IDs are excellent — keep them. The Version and SchemaVersion types have one fix each: switch from int to uint64/uint32 to make negative values unrepresentable. 

// event/types.go — redesigned

// Version is the 1-based positional index of an event in its aggregate stream.
// Zero means "no events". uint64 makes negative versions unrepresentable.
type Version uint64

func (v Version) IsZero() bool      { return v == 0 }
func (v Version) IsPositive() bool  { return v > 0 }
func (v Version) Increment() Version { return v + 1 }
func (v Version) Int() int          { return int(v) }  // only at boundaries

// SchemaVersion is the 1-based payload schema version. uint32 — schemas don't overflow.
type SchemaVersion uint32

// AggregateID is unified with the rest of the ID family.
// Today: cbid.ID[AggregateMarker, string] — the lone string-backed ID.
// Redesign: cbid.ID[AggregateMarker, ulid.ULID] + a separate DerivedID type for
// human-readable/deterministic IDs. The fork disappears.
type AggregateID = id.Of[AggregateMarker]
type DerivedAggregateID = cbid.ID[AggregateMarker, string]  // for "lock_user1_user2"

The Event Algebra — Honest and Immutable

The redesign makes Event a concrete struct (not an interface) — there is exactly one production implementation, and the "interface for testability" benefit is provided by the store interfaces operating on []Event. The leaky type-assertions disappear. The Metadata promotes soft concepts to typed fields. 

// event/event.go — redesigned

// Event is an immutable domain event. All fields are set at construction;
// there are no setters. Payload is cloned on construction and on every Payload() call.
type Event struct {
    id            id.EventID
    eventType     Type
    aggregateRef  AggregateRef    // typed pair, not split fields
    version       Version
    schemaVersion SchemaVersion
    encoding      codec.Encoding  // never zero — required at construction
    payload       []byte
    metadata      Metadata
    occurredAt    time.Time
    deadline      time.Time       // zero = no deadline
    // NO eventOptions pointer — config stays in the constructor's scope
}

// AggregateRef bundles the (type, id) pair. StreamKey is derived, escaped.
type AggregateRef struct {
    Type AggregateType
    ID   id.AggregateID
}

// Metadata carries tracing/context + first-class domain concepts.
// The string Custom map shrinks to Extensions — genuinely consumer-defined only.
type Metadata struct {
    CorrelationID id.CorrelationID  `json:"correlationId,omitempty"`
    CausationID   id.CausationID    `json:"causationId,omitempty"`
    UserID        id.UserID         `json:"userId,omitempty"`
    RequestID     id.RequestID      `json:"requestId,omitempty"`
    Source        Source            `json:"source,omitempty"`
    IPAddress     IPAddress         `json:"ipAddress,omitempty"`
    UserAgent     UserAgent         `json:"userAgent,omitempty"`

    // First-class domain concepts (were string Custom entries):
    Causation  *Causation     `json:"causation,omitempty"`   // command that caused this
    Tombstone  TombstoneMark  `json:"tombstone,omitempty"`   // soft-delete marker
    ClientTime *ClientTime    `json:"clientTime,omitempty"`  // offline-first occurredAt

    // Security envelope (signing + encryption unified):
    Security   *SecurityEnvelope `json:"security,omitempty"`

    // True escape hatch — for consumer-defined concerns only.
    Extensions map[string]string `json:"extensions,omitempty"`
}

// TombstoneMark is a closed three-state enum. Zero value = Active (default).
type TombstoneMark uint8
const (
    TombstoneNone TombstoneMark = iota  // not a tombstone event
    TombstoneSet                       // soft-delete
    TombstoneRebirth                   // un-delete
)

type Causation struct {
    CommandType command.Type  // typed, not bare string
    CommandID   id.CommandID
}
What this fixes: Twelve first-class concepts move from Custom strings to typed fields. The tombstone state of an aggregate is now a typed TombstoneMark on Metadata — discoverable, validated, and impossible to typo. Command causation carries a typed command.Type. Security (signing algorithm, key-id, signature, encryption algorithm, IV) collapses into one SecurityEnvelope. The Extensions map is honestly named and honestly scoped.

Decider Evolution — Decide/Apply Separation

The Eventuous-inspired two-type-parameter Decider. Decide becomes a field; Fold is renamed Apply (standard ES terminology). The command type is bound at compile time. 

// decider/decider.go — redesigned (Eventuous-inspired)

// Decider captures the three pure functions of an event-sourced aggregate.
// Decide maps a command + current state to new events. Apply folds an event
// into state. Both must be pure — no I/O, no side effects, no mutation of inputs.
type Decider[State any, Cmd any] struct {
    Initial State
    Decide  func(Cmd, State) ([]event.Event, error)
    Apply   func(State, event.Event) (State, error)
}

// Execute loads state, applies Decide, saves events, publishes, snapshots.
func (r *Repository[State, Cmd]) Execute(
    ctx context.Context,
    ref event.AggregateRef,
    cmd Cmd,
) error

// Backward-compat: the old single-param Decider[State] + per-call DecideFunc
// remains available as a thin adapter.
type LegacyDecider[State any] = Decider[State, any]

The Materialization Vision — Projection Lifecycle

The killer feature from Marten, adapted to Go. Every projection declares when it gets built. The dual-store architecture (event log + disposable materialized state DB) becomes a one-liner via stack presets. 

// projection/projection.go — redesigned with lifecycle

// Mode declares when a projection's read model is updated.
type Mode uint8
const (
    // ModeLive: recompute on every read. No persistence. Always fresh, slower reads.
    ModeLive Mode = iota
    // ModeInline: update in the same transaction as event append. Strong consistency.
    ModeInline
    // ModeAsync: background tail via Runner. Eventual consistency, fast reads+writes.
    ModeAsync
)

// Projection is the contract every materialized view implements.
type Projection interface {
    Name() string
    Mode() Mode                          // ← NEW: lifecycle choice
    EventTypes() []event.Type
    Handle(ctx context.Context, evt event.Event) error
}

// TypedProjection — type-safe materialization into a readmodel.Store.
// The handler receives the decoded event payload + the view store; it returns
// the updated view(s). No manual codec juggling, no untyped any.
type TypedProjection[V any, K fmt.Stringer] struct {
    ProjectionName   string
    ProjectionMode   Mode
    EventTypeFilter  []event.Type
    Codec            codec.Codec
    Apply            func(ctx context.Context, evt event.Event, store *readmodel.Store[V, K]) error
}

// DeadLetterStore — durable DLQ (replaces fire-and-forget callback).
type DeadLetterSink interface {
    Save(ctx context.Context, projectionName string, evt event.Event, err error) error
}
type DeadLetterSource interface {
    Load(ctx context.Context, projectionName string) ([]DeadLetter, error)
}
type DeadLetterStore interface {
    DeadLetterSink
    DeadLetterSource
    io.Closer
}

07Anti-Patterns to Avoid

Don't add a Delete to Store

History is immutable. ADR-0006 was right. Soft-delete via tombstone is the only path. Adding Delete back "for convenience" breaks the core invariant.

Don't make Event generic Event[T]

Storage stores bytes. A generic Event forces every store to be generic, every slice to be homogeneous, and breaks the journal (cross-aggregate, multi-type events). Keep Event as a concrete envelope; decode to T at the boundary.

Don't reimplement the outbox

It was removed for good reason (YAGNI, complexity). Crash recovery via SeekableJournal + CheckpointStore + the new durable DLQ is the path forward. The Relay component (if added) uses the event store's own journal, not a secondary table.

Don't force a transport/broker/driver

"Library, not framework" is the founding principle. Every transport adapter (Watermill, pg LISTEN/NOTIFY, NATS, Kafka) is an optional module. Never bake one into the core.

Don't conflate Decide and Apply

They are different functions with different signatures and different test profiles. Decide produces events; Apply consumes them. Mixing them (Axon-style @CommandHandler + @EventSourcingHandler on one class) creates indirection.

Don't use string error matching for driver errors

IsDuplicateKeyError matching "UNIQUE constraint failed" breaks on driver updates. Use typed error codes (pgconn.PgError 23505, SQLite extended codes). String matching is the last resort, logged when it fires.

Don't make DLQ fire-and-forget

A callback that logs is a silent data loss vector. The DLQ must be a durable store with a replay API. "Best-effort" is acceptable for snapshot writes; it is not acceptable for projection failures.

Don't ignore context.Context anywhere

Every I/O operation must accept and honor context. kv.Store ignoring ctx is a production hazard. The "forward-compatible API, currently misleading" comment in readmodel is technical debt — schedule the fix.

09Conclusion

go-cqrs-lite is already one of the most thoughtfully architected CQRS libraries available in any language. Its ISP-split interfaces, branded identifiers, error taxonomy, pure-function Decider, and tombstone model are genuinely excellent — the hard architectural problems are solved. The path from "excellent" to unequivocally best is not a rewrite; it is three targeted extractions (resilience, go.mod hygiene, soft-metadata promotion), three state-of-the-art additions (projection lifecycle, durable DLQ, Decide/Apply separation), and a consistency pass.

The opportunity is concrete and named: no Go library today offers projection lifecycle choice, type-safe event application, clean Decide/Apply separation, or a dual-store architecture. Achieving all four — and the library is 70% of the way there — makes go-cqrs-lite the reference implementation that other Go CQRS libraries are measured against.

The one-sentence summary: The architecture is right. The type algebra needs one honest pass to move soft-metadata concepts to first-class types, the materialization story needs the projection-lifecycle concept Marten proved is essential, and the packaging needs the resilience extraction that unblocks every non-CQRS Go project. Then it's the best.
