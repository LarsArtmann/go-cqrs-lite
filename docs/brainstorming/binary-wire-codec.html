Serialization Blueprint

Three architectures for zero-overhead event serialization in go-cqrs-lite — FlatBuffers, CBOR, and custom binary — analyzed against a library that consumers extend with their own types.

✅
Phase 1 Complete — CBORCodec shipped

CBORCodec is implemented in codec/cbor.go using fxamacker/cbor/v2 with Canonical encoding (RFC 7049: sorted map keys, shortest floats) and a configured DecMode with DupMapKeyEnforcedAPF. 17% faster encode, 38% faster decode than JSON. Deterministic encoding verified.

Tests: 15 unit tests, 4 fuzz tests, 4 benchmarks, 1 golden test, 1 example function, 1 end-to-end event integration test.

Committed: a576dadc · ADR-0015 · example/cbor-codec/

The Problem

Every event payload today traverses three serialization passes for a single round-trip through the Pebble store. The SQL store avoids the worst of it, but still pays reflection tax on every json.Marshal / json.Unmarshal.

struct → json.Marshal → []byte in ImmutableEvent → json.Marshal (envelope) → base64(payload) → disk
Base64 Tax

Go's encoding/json automatically base64-encodes []byte fields. A 256-byte payload becomes 344 bytes on wire — a 33% size inflation with zero informational gain. This affects every event stored via the Pebble backend.

Current State

The codec/ module is a leaf — zero external dependencies, clean interface: 

type Codec interface {
    Encoding() Encoding
    Encode(v any) ([]byte, error)
    Decode(data []byte, v any) error
}

Three implementations exist: JSONCodec (wraps encoding/json), CBORCodec (wraps fxamacker/cbor/v2 with canonical encoding), and RawCodec (passthrough for []byte). The payload lifecycle already has zero-copy internal reads via PayloadReadOnly() and payloadForDecode() — but the Pebble wire format remains pure JSON (Phase 2 will address this). The payload codec is now consumer-selectable via event.WithCodec(codec.CBORCodec{}).

Where serialization happens today

Why Pebble doesn't use the codec

Pebble imports codec/v2 but only for reading the Encoding field on deserialization. The envelope serialization bypasses the codec entirely — it builds its own serializableEvent struct and calls json.Marshal directly. Why? Because codec.Codec is a struct↔bytes abstraction for payloads. It doesn't know what an event envelope is. There's no EncodeEvent(Event) method. This gap is exactly what any of the three candidate architectures would fill. Phase 2 (not yet started) would address this by switching Pebble's envelope serialization from json.Marshal to CBORCodec.

Three Candidates

After researching the landscape — CBOR, FlatBuffers, msgpack, protobuf, Chronicle Wire, ConnectRPC, Buf — three architectures remain viable. msgpack was eliminated: it lacks deterministic encoding (signing hazard), has no RFC standard, and CBOR dominates it on every axis that matters.

How they relate to each other

The three options are not variants of the same thing. They operate at different abstraction levels and can be composed:

Envelope (type, ID, version, timestamp) Payload (UserCreated, OrderPlaced) Zero-copy access
FlatBuffers FlatBuffers schema (code gen) FlatBuffers schema (code gen) Envelope + payload
All-in CBOR CBOR map (struct tags) CBOR map (struct tags) Neither
Custom + CBOR Fixed-offset binary header CBOR (struct tags) Envelope only

Option A: FlatBuffers

Google's FlatBuffers is a zero-copy serialization library. You define a schema per type, generate Go code, and access fields directly from the byte buffer without parsing or allocating. Used in Android, games, and latency-critical systems.

How it would work

Define a FlatBuffers schema for the event envelope and one schema per event payload type. Generate Go code via flatc --go. Events are created and read directly from flat buffer bytes. 

// Example schema: event_envelope.fbs
table EventEnvelope {
    id:            string;
    event_type:    string;
    aggregate_id:  string;
    aggregate_type:string;
    version:       uint32;
    schema_version:uint32;
    payload:       [ubyte];
    encoding:      string;
    occurred_at:   int64;
    metadata:      Metadata;
}
table Metadata {
    correlation_id: string;
    causation_id:   string;
    custom:         [KVPair];
}
table KVPair { key: string; value: string; }
root_type EventEnvelope;

Strengths

  • True zero-copy decode — no deserialization. Access fields at byte offsets.
  • Zero allocs on read — the buffer is the object. No intermediate structs.
  • ~10x faster decode than JSON for typical event shapes.
  • Schema evolution built in — add fields without breaking old readers.
  • Cross-language — generated code in Go, Rust, Java, C++, Python.

Weaknesses

  • Code generation required — consumers must run flatc --go for every event type. This is a significant adoption friction for a library.
  • Schema per event type — go-cqrs-lite consumers define plain Go structs today. FlatBuffers would require .fbs files for each one. Violates the "no opinionated transport" principle.
  • Opaque on disk — stored events are binary blobs. No SELECT inspection, no debug without tooling.
  • Builder pattern overhead — creating events is verbose. FlatBuffer builders require offset management that's more complex than event.New().
  • Not self-describing — a FlatBuffer blob without its schema is uninterpretable. Schema lock-in is permanent.
The library vs. application distinction

FlatBuffers is excellent for applications that own their event types and control their build pipeline. go-cqrs-lite is a library that consumers extend with their own types. Requiring consumers to define .fbs schemas and run code generation would fundamentally change the adoption model.

Verdict

Viable as a future opt-in mode for consumers who need extreme throughput and are willing to adopt FlatBuffers schemas. Not suitable as the default or only option.

Option B: All-in CBOR

CBOR (RFC 8949, IETF Internet Standard) is a binary data format that replaces JSON. It has native byte string support, deterministic encoding, and a production-grade Go library (fxamacker/cbor) with an API identical to encoding/json.

Why CBOR over msgpack

Property CBOR (RFC 8949) Msgpack
Standard IETF Internet Standard Community format, no RFC
Binary data Major type 2 (byte strings) — explicit binary/text separation Ambiguous "raw" type
Deterministic encoding Yes (RFC 8949 §4.2) — same struct = same bytes No — map ordering undefined
Signing-safe Yes — deterministic encoding means HMAC/Ed25519 is stable No — non-deterministic map ordering can break signatures
Self-describing Yes — any CBOR decoder can read it Mostly, but ambiguous types
Go library fxamacker/cbor — no unsafe, 100x faster rejection vmihailenco/msgpack/v5

How it would work

Replace JSONCodec with CBORCodec for both envelope and payload. The envelope struct gets CBOR struct tags. The payload uses the same Codec interface — consumers just pass CBORCodec{} instead of JSONCodec{}. 

// CBORCodec implements Codec using fxamacker/cbor.
// Shipped in codec/cbor.go — commit a576dadc.
type CBORCodec struct{}

var cborEncMode = func() cbor.EncMode {
    enc, err := cbor.CanonicalEncOptions().EncMode()
    if err != nil {
        panic("cbor: failed to create EncMode: " + err.Error())
    }
    return enc
}()

var cborDecMode = func() cbor.DecMode {
    dec, err := cbor.DecOptions{DupMapKeyEnforcedAPF: true}.DecMode()
    if err != nil {
        panic("cbor: failed to create DecMode: " + err.Error())
    }
    return dec
}()

func (CBORCodec) Encoding() Encoding { return EncodingCBOR }
func (CBORCodec) Encode(v any) ([]byte, error) { return cborEncMode.Marshal(v) }
func (CBORCodec) Decode(data []byte, v any) error { return cborDecMode.Unmarshal(data, v) }

For Pebble, the serializableEvent struct gets CBOR tags instead of JSON tags. The payload field is a byte string (major type 2) — no base64. On disk, the event is a CBOR map that any CBOR decoder can inspect.

Strengths

  • Minimal change — drop-in replacement for JSONCodec. Same Codec interface, same struct tags pattern, same consumer API.
  • Base64 eliminated — CBOR byte strings store raw binary. No encoding tax.
  • IETF standard — not a proprietary format. Tooling exists across languages.
  • Deterministic encoding — signing works correctly. Same struct always produces same bytes.
  • Self-describing — stored events can be inspected with any CBOR decoder. cbor.diagnose() converts to human-readable text.
  • One dependency — fxamacker/cbor. Zero transitive deps.
  • No code generation — consumers keep using plain Go structs with struct tags.

Weaknesses

  • Reflection-based — cbor.Marshal/Unmarshal still use reflection. Not zero-copy. Slower than hand-rolled binary.
  • No zero-copy envelope parse — must decode the entire CBOR structure to access fields. Can't read just the event type without parsing the whole map.
  • ~2-3x improvement — meaningful but not transformative. The ceiling is limited by reflection overhead.
  • Not human-readable on disk — CBOR is binary. Better than base64-in-JSON, but you still need a decoder to inspect stored events. JSON you can read with cat.
The pragmatic choice — now implemented

All-in CBOR was the highest ROI option. Minimal code change, one well-maintained dependency, eliminates base64, adds deterministic encoding for signing, and gives ~2-3x performance improvement. It didn't achieve the theoretical maximum — but it got 80% of the benefit for 20% of the effort. Phase 1 shipped at a576dadc. Actual benchmarks: 17% faster encode (2 vs 6 allocs), 38% faster decode (9 vs 12 allocs). CBOR output is smaller than JSON for the same data.

Option C: Custom Binary + CBOR

A domain-aware binary envelope for the fixed event metadata, paired with CBOR for the variable payload. The envelope is a hand-rolled fixed-offset binary header — zero-copy, zero-reflection. The payload is CBOR-encoded — standards-compliant, deterministic, signing-safe.

Event Wire Layout (Custom Binary Envelope)
 ┌──────────────────────────────────────────────────────┐
 │  Header  (32 bytes, fixed)                           │
 │                                                       │
 │  [2]  magic          0xC5 0x51                    │
 │  [1]  version        format = 1                   │
 │  [1]  flags          bitfield                      │
 │  [4]  payload_len    uint32 LE                     │
 │  [2]  type_len       uint16 LE                     │
 │  [2]  agg_type_len   uint16 LE                     │
 │  [8]  occurred_at    int64 (unix nano)             │
 │  [4]  version        uint32                        │
 │  [4]  schema_version uint32                        │
 │  [4]  reserved       zeros                        │
 ├──────────────────────────────────────────────────────┤
 │  Fixed Fields  (variable length, zero-copy parse) │
 │                                                       │
 │  [type_len]     event_type     UTF-8 bytes          │
 │  [agg_type_len] aggregate_type UTF-8 bytes          │
 │  [16]           aggregate_id   raw ULID, no string  │
 │  [16]           event_id       raw ULID, no string  │
 ├──────────────────────────────────────────────────────┤
 │  Payload  (CBOR-encoded domain struct)           │
 │                                                       │
 │  [payload_len]  CBOR bytes    raw, no base64        │
 ├──────────────────────────────────────────────────────┤
 │  Metadata  (optional, keyed by flags)             │
 │                                                       │
 │  [2]            metadata_len   uint16 LE              │
 │  [metadata_len] kv pairs       length-prefixed       │
 └──────────────────────────────────────────────────────┘

Strengths

  • Zero-copy envelope parse — read event type, version, timestamp at fixed offsets. No parsing. ~5-10 ns.
  • Zero reflection on envelope — hand-rolled encode/decode for 10 fixed fields. No struct tags, no reflection.
  • CBOR payload — standards-based, deterministic, signing-safe. Consumers keep using plain Go structs.
  • No base64 — payload bytes go raw into the wire layout.
  • ULIDs as raw 16 bytes — saves 10 bytes per ID (26-char string → 16 raw bytes).
  • Envelope codec is dependency-free — pure encoding/binary + unsafe. Only the payload codec (fxamacker/cbor) adds a dependency.

Weaknesses

  • Custom format — the envelope is not self-describing. Needs its own spec, versioning, and diagnostic tooling.
  • Implementation complexity — hand-rolling an encoder/decoder with unsafe is more work than cbor.Marshal.
  • Two formats to understand — the envelope is custom binary, the payload is CBOR. Debugging requires understanding both.
  • Marginal gain over all-CBOR — the envelope decode is ~3-5x faster than CBOR, but the payload decode (CBOR) is the same. Total round-trip improvement may be ~30-50% over all-CBOR, not 3x.
  • Only matters for Pebble — SQL stores already use columns. The custom envelope only benefits embedded KV stores.
The engineering trade-off

Custom binary + CBOR is the theoretically optimal solution. But the gain over all-in CBOR is marginal for most use cases. The zero-copy envelope parse saves ~30-50 ns per event on replay. Over 100K events, that's ~3-5 ms. Worth it for latency-critical replay paths, but not a game-changer for most consumers.

Integration Points

Pebble store

Today pebble/serialization.go uses json.Marshal(serializableEvent{}). With CBOR, replace json with cbor — same struct, same tags, no base64. With custom binary, replace the entire function with BinaryCodec.Encode(evt). FlatBuffers would replace it with flat buffer construction. Status: Phase 1 (CBORCodec payload codec) is done. Phase 2 (Pebble envelope migration) is next.

SQL store

Already stores payload as raw []byte in a BLOB column. The codec only changes how the payload is encoded before insertion — CBOR instead of JSON. No column layout changes.

Event creation

event.New() already accepts a codec.Codec parameter via event.WithCodec(). Pass CBORCodec{} and events are created with CBOR encoding. The encoding field on ImmutableEvent records "cbor". DecodePayload validation works unchanged. Status: Done. Tested via TestDecodePayload_CBORCodec in event/codec_test.go.

Signing

CBOR's deterministic encoding is a direct win for signing. Today, JSON map ordering is undefined — the same struct can produce different bytes on different runs, potentially breaking HMAC/Ed25519 verification. CBOR deterministic mode guarantees same struct = same bytes. Status: Verified via TestCBORCodec_SigningDeterminism (triple-encode produces identical bytes).

Catalog / AsyncAPI / OpenAPI exporters

Catalog reads event metadata, not wire format. The Encoding field records the codec used. Exporters describe the logical schema (JSON Schema), not the physical encoding. No changes needed.

What We Dismissed

Msgpack

Lacks deterministic encoding — map ordering is undefined, which means HMAC/Ed25519 signatures can break across runs. No RFC standard. Ambiguous "raw" type conflates binary and text. CBOR dominates msgpack on every axis that matters for event sourcing. Eliminated.

Protobuf / Buf

Requires .proto schemas per event type, code generation, and the google.golang.org/protobuf dependency (~2MB). go-cqrs-lite is a library consumers extend with their own types — requiring protobuf schemas would fundamentally change the adoption model. Buf's schema governance (breaking-change detection, BSR) is excellent for organizations but wrong for a library. The governance happens in the consumer's repo, not ours.

ConnectRPC

An RPC framework, not a serialization format. Its streaming envelope ([1 byte flags][4 bytes length][payload]) validates our design principle — thin binary frame around opaque bytes — but ConnectRPC wraps RPC messages, not domain events. The envelope has 3 fields. Our events need 10+. Built for service-to-service HTTP communication, not in-process event serialization.

Gob encoding

Go-specific, not cross-language. Type registration complexity. No random field access. No deterministic encoding.

Compression (zstd/snappy)

Orthogonal concern. Compression is a transport-layer optimization, not a codec concern. Can be layered on top via middleware at any point. Not part of this proposal.

"Just optimize JSONCodec"

Can't fix base64 tax. Can't fix reflection overhead. Can't achieve deterministic encoding. Can't do zero-copy decode. The ceiling is too low.

Appendix: Industry Patterns

Six systems that have solved event storage at scale. Each made different serialization choices. Here's what we can learn.

1. EventStoreDB — Custom binary, opaque to the outside world

EventStoreDB stores events in append-only chunk files (256 MiB each). The physical format is a custom binary record layout with a fixed header per record: event type, stream ID, sequence number, timestamp, metadata, and payload as raw bytes. The payload is opaque — EventStoreDB never inspects it. Metadata (correlation IDs, custom headers) is stored as a separate field, not inside the payload.

Indexes are maintained in PTables (persistent sorted tables) with bloom filters for stream existence. Scavenging (compaction) rewrites chunks to remove tombstoned events.

What we learn

  • Envelope and payload are separate — the store never parses the payload. This is our Layer 1/Layer 2 split.
  • Fixed-header binary records — validates the custom binary approach for Option C.
  • Append-only is king — no in-place updates, no delete. Events are immutable. go-cqrs-lite already follows this (tombstone over delete).
  • Index is separate from data — EventStoreDB doesn't parse records to find events. It uses offset-based indexes. Our Pebble keys already serve this role.

2. Apache Kafka — Zero-copy, batch-level compression, varint encoding

Kafka's record batch format is a masterclass in systems engineering. Records are grouped into batches with a shared header: base offset, CRC-32C checksum, compression type, producer ID, and timestamp deltas. Individual records use varint encoding for lengths and deltas, keeping overhead minimal. Headers are key-value byte pairs (similar to our metadata KV pairs).

The throughput secret isn't the format — it's zero-copy transfer via Linux sendfile(). Data flows directly from disk page cache to network socket without entering userspace. 4.1x throughput, 3.9x less CPU.

What we learn

  • Batch-level compression — compress at the batch boundary, not per-record. Single-event compression has <5% savings. Batched compression gets 65-70%. go-cqrs-lite should compress batches, not individual events.
  • Varint encoding for small values — Kafka uses varints for lengths and deltas. Our version field (often 1-10) wastes 3 bytes as uint32. Varints would be 1 byte.
  • Timestamp deltas, not absolute — Kafka stores base timestamp per batch, then deltas per record. For events within an aggregate, timestamps are close together. Delta encoding saves bytes.
  • Zero-copy is a transport concern — it's about sendfile(), not serialization format. We can't apply this to in-process reads, but it's relevant for any network transport layer consumers build.

3. Axon Framework — Serializer-per-concern, upcasting as first-class citizen

Axon uses different serializers for different concerns: one for events (long-term storage), one for commands/queries (distributed messages), one for internal state (tokens, sagas, snapshots). The event serializer defaults to XStream (XML) or Jackson (JSON). Axon 5 uses SQL columns for event metadata and BLOB for payload.

Axon's most notable contribution: structured upcasting. Events have a version field (called "revision"). Upcasters transform old event structures to new ones during replay. One-to-one, one-to-many, and context-aware upcasting are all supported.

What we learn

  • Serializer-per-concern is the right pattern — events need long-term stability. Commands need speed. Snapshots need compactness. go-cqrs-lite's codec.Codec already allows this (consumers pass different codecs). We should document this pattern.
  • Upcasting is orthogonal to serialization — our schema/ module already handles this. The codec doesn't need to know about schema evolution.
  • Metadata as first-class SQL columns — Axon 5 indexes aggregate type, sequence number, timestamp as columns. This is what our SQL store already does. Validates the design.
  • XML is still alive in 2026 — Axon defaults to XStream. If the Java ecosystem can ship XML-based event sourcing at scale, CBOR is not a risky choice.

4. Lagom — JSON with compression threshold, Akka underneath

Lagom wraps Akka Persistence with higher-level abstractions. Events are stored as JSON via Jackson in Cassandra BLOB columns. Events larger than 32 KB are automatically compressed. The Cassandra schema separates event (BLOB), ser_id (serializer identifier), ser_manifest, and tags into distinct columns.

What we learn

  • Compression threshold — compress events above a configurable size, leave small events uncompressed. This avoids the CPU cost of compression on tiny payloads. Our codec could add a CompressedCodec wrapper that delegates compression to a threshold.
  • Serializer identifier in the record — Lagom stores ser_id and ser_manifest alongside each event. This allows multiple serializers to coexist in the same journal. Our Encoding field already does this, but only stores the format name. A numeric serializer ID would be more compact.
  • JSON at scale works — Lagom powers production systems with JSON serialization. The argument that JSON is "too slow" for event sourcing is overstated. CBOR is already a significant improvement over JSON; we don't need custom binary to be production-viable.

5. Akka Persistence — Pluggable serialization, Jackson CBOR support

Akka Persistence provides a pluggable serialization infrastructure with binding-based resolution: you register which serializer handles which type. Out of the box: Jackson JSON, Jackson CBOR, and Protobuf. Event adapters separate domain model from storage model. Schema evolution via SerializerWithStringManifest and upcasting.

Notably, Akka recommends CBOR as a first-class option via CborSerializable. Same Jackson API, binary wire format, native byte support. This is essentially our Option B.

What we learn

  • CBOR is production-proven in the Akka ecosystem — not experimental. Major deployments use Akka CBOR serialization for event-sourced systems.
  • Event adapters separate domain from storage — write adapters convert domain events to storage format, read adapters convert back. This is what our Codec interface already does, but the explicit separation of write/read adapters is a cleaner pattern to consider.
  • String manifests for schema evolution — instead of class names (fragile, refactoring-hostile), Akka uses string manifests to identify event types. Our event.Type is already a string, not a Go type name. Good.
  • Multiple serialization bindings coexist — the journal can contain events serialized with different serializers. Our Encoding field per event already supports this.

6. Datomic — Datom as the universal primitive, Fressian encoding

Datomic takes a fundamentally different approach. Facts are stored as datoms — 5-tuples of (Entity, Attribute, Value, Transaction, Operation). The storage format uses Fressian, a compact binary encoding optimized for Clojure data structures. Attribute IDs are compressed to 32-bit ints. Transaction ID and operation boolean are fused into a single tOp field.

Four covering indexes (EAVT, AVET, AEVT, VAET) are maintained as immutable segments in S3. Time travel is free — every database value is a point-in-time snapshot. No separate audit system needed.

What we learn

  • Bit fusion for small fields — Datomic packs transaction ID + operation into a single long (shift + LSB). Our flags bitfield does the same for has_metadata, has_schema_version, encoding. This pattern is universal in efficient binary formats.
  • Index structure is separate from data — Datomic's indexes are materialized views of the datom log, stored as immutable segments. The log is append-only. Indexes are rebuilt periodically. This validates our approach: the event store is the log, projections are the indexes.
  • Fressian is a precedent for custom binary in the JVM — even the Java/Clojure ecosystem, with its culture of standard formats, builds custom binary encodings when performance matters. We're not crazy for considering it.
  • Universal primitive vs. domain-specific format — Datomic stores everything as datoms. go-cqrs-lite stores everything as events. Datomic's universalism gives it flexibility (any query pattern via index selection). Our specificity gives us performance (fixed envelope, domain-aware layout). The trade-off is clear: universality costs parsing, specificity costs flexibility.
Synthesis

The industry converges on a consistent set of patterns:

  • Envelope and payload are separate (EventStoreDB, Axon, Lagom, Kafka)
  • The store never parses the payload (EventStoreDB, Kafka, Axon)
  • Metadata is a separate concern from payload (EventStoreDB, Axon, Lagom, Kafka headers)
  • Serializer identifier travels with the record (Lagom ser_id, Akka manifest, our Encoding)
  • CBOR is production-proven (Akka recommends it as first-class)
  • Compression is a batch-level concern (Kafka, Lagom threshold)
  • Custom binary formats exist when performance matters (EventStoreDB, Datomic/Fressian, Chronicle Wire)
  • Materialized views in SQLite for instant reads (LiveStore)

None of these systems use msgpack. Several use CBOR. Most use JSON for the payload and custom binary or structured columns for the envelope. LiveStore demonstrates that SQLite-based materialization can eliminate the need for fast envelope parsing entirely — the read path is SQL, not event replay. Our Option B (all-in CBOR) follows the Akka pattern. Our Option C (custom binary + CBOR) follows the EventStoreDB pattern. Both are well-precedented in production.

7. LiveStore — Reactive SQLite, git-inspired sync, materialization-first

LiveStore is a TypeScript state management framework built on event sourcing, reactive SQLite, and git-inspired sync. It replaces Redux/MobX with an embedded SQLite database that is automatically kept in sync via materializers. Events are the source of truth; SQLite tables are derived views.

Architecture

  • Three nodes per client — Client Session (in-memory pending events), Client Leader (durable eventlog + materialized SQLite), Sync Backend (authoritative append-only log).
  • Event format: { name, args, seqNum, parentSeqNum, clientId, sessionId }. Args are schema-validated via Effect Schema. Events are versioned (v1.TodoCreated).
  • Sequence numbers are composite: { global, client, rebaseGeneration }. Global is assigned by sync backend. Client tracks local events. Rebase generation increments on conflict resolution. Events render as strings: e5, e5.1, e5r1.
  • Materializers map events to SQLite operations. Each event handler returns SQL insert/update/delete. The materialized SQLite database is the query layer — no event replay on read.
  • Git-inspired sync: pull before push, rebase local events on top of upstream changes, push confirmed events. Conflict resolution is last-write-wins by default, customizable.
  • Encoded events use JSON for args (Date → ISO string, binary → base64). Stored in SQLite as structured columns.

What we learn

  • Materialization eliminates the need for fast envelope parsing — LiveStore's read path is SQL on materialized tables, not event replay. The eventlog is the write-only source of truth. This means envelope decode speed (our Option C's main advantage over Option B) matters less when reads go through materialized projections. Our projection/ module already follows this pattern.
  • SQLite as the read model is a validated architecture — LiveStore achieves 120 FPS with reactive SQLite queries. Our turso/ module (embedded LibSQL) is the same idea. The event store writes; the SQL read model reads. The codec only matters on the write/replay path.
  • Versioned event names as schema evolution — v1.TodoCreated, v2.TodoCreated. New versions are new event types. Old versions never deleted. This is simpler than upcasting and avoids the migration complexity. Our schema/ module handles upcasting, but versioned names are a lighter alternative for many consumers.
  • Unknown event handling is configurable — older clients receiving newer events can warn, ignore, fail, or callback. This is a production-grade concern we don't address yet. When the codec changes, old events must still be readable.
  • Parent sequence numbers for causal ordering — every event points to its parent, enabling DAG-based conflict detection and deterministic rebase. Our events have version numbers (per-aggregate sequence) but no cross-aggregate causal links. For multi-aggregate workflows, this is worth considering.
  • Rebasing, not rejecting — when two clients commit concurrently, LiveStore rebases the loser's events on top of the winner's, rather than rejecting. This is a fundamentally different conflict model than "last write wins" or "reject and retry." go-cqrs-lite currently has no rebasing story for distributed scenarios.
LiveStore's implications for our codec choice

LiveStore proves that JSON encoding is fast enough when reads are served from materialized SQLite. The eventlog is written once, replayed rarely (only on leader restart), and never queried directly for UI reads. This means:

  • Option B (all-in CBOR) is more than sufficient if most reads go through projections. The codec only matters for event append and occasional replay.
  • Option C (custom binary) is only worth it for heavy replay workloads — initial load, full rebuild, or batch processing over millions of events.
  • The real investment should be in materialization quality, not envelope decode speed. A fast projection pipeline with SQLite/LibSQL gives more user-facing performance than a custom binary envelope.

Appendix: Why Base64?

It's not a choice — it's the JSON tax

Go's encoding/json automatically base64-encodes any []byte field during json.Marshal. There is no opt-out. This is mandated by RFC 8259 §8.1: JSON text is Unicode. Binary data must be encoded.

In pebble/serialization.go, the serializableEvent struct has a Payload []byte field. When json.Marshal encounters it, every byte of the payload becomes ~1.33 bytes of base64 on disk. A 1 KB event payload inflates to ~1.37 KB before the JSON envelope overhead is even counted.

The math

Base64 encodes 3 bytes into 4 characters. Overhead = 4/3 − 1 = 33.3%. This is a constant, not a worst case. Every []byte field pays it.

Could we use a better binary-to-text encoding?

In theory, yes. In practice, none solve the real problem. The problem isn't base64 — it's putting binary data inside a text format.
