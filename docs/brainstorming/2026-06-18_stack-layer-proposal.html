The Stack Layer

A proposal to decouple application code from infrastructure decisions in go-cqrs-lite — so the person deploying the app chooses where data lives, while the person writing the app never imports a backend.

01The Problem

go-cqrs-lite is a library, not a framework. Its design principle is explicit: consumers import what they need, compose their own stack, and no opinionated transport, broker, or SQL driver is forced on them.

That principle is correct — and it has an unintended consequence. Because the library provides excellent primitives (stores, buses, dispatchers, projections) but no composition root, every consumer must write the same ~150 lines of glue: open the database, build the backend facade, pull each store out, create the bus, construct the projection runner, register projections, wire the dispatchers, and manage the close lifecycle.

That glue is the infrastructure decision. And today it lives inside the consumer's application code — exactly where the deployer cannot reach it without editing Go source.

The tension

“Library, not framework” says: don't force a backend. But “consumers should not decide on infrastructure” says: don't make them wire it either. These are compatible only if the wiring lives in an optional layer that the deployer controls.

02The Pain Today

The canonical example is example/todo/cmd/api/main.go. It is a real, working application — and its run() function is a wall of infrastructure wiring. Here is the actual shape of it, abbreviated: 

// --- The deployer's decision, hardcoded into app code ---
dataDir := getEnv("DATA_DIR", "./data")
readModelStore, err := storage.NewPebbleStore(dataDir, logger)
if err != nil { return err }
defer readModelStore.Close()

eventStore := cqrsPebble.NewStore(readModelStore.DB(), logger)
eventBus := memory.NewMemoryBus()
checkpointStore := memory.NewMemoryCheckpointStore()

runner, err := projection.NewRunner(eventStore, eventBus, checkpointStore)
runner.Register(todoProjection)
go runner.Run(ctx)

// --- 4 more Register calls, query wiring, HTTP server ---

Every line above the comment marker is a deployment decision: which database, which bus, which checkpoint store, where read models live. To change any of it, a deployer must edit this file, change imports, and recompile. The application developer's domain logic (the handlers, the projection) is buried underneath the infrastructure noise.

What the app developer cares about

Commands, queries, the aggregate's Decide and Fold functions, and the projection that turns events into read models. None of these should know whether the backing store is SQLite, Pebble, or Postgres.

What the deployer cares about

Where data lives, how it's backed up, whether it's embedded or remote, whether the bus is in-memory or NATS. None of these should require rewriting command handlers.

03The Core Idea

Add a single optional composition layer — the stack module — that sits above the existing backend facades. It does three things:

  1. Bundles capabilities. A Stack is a struct holding every store, bus, and dispatcher the app needs, wired together and lifecycle-managed.
  2. Offers presets. One function call produces a fully-wired Stack for a given backend (sqlite.Open, pebble.Open, memory.New).
  3. Stays out of the way. Consumers who want full control keep importing individual modules and wiring manually — exactly as today. Nothing breaks.
The separation principle

Application code's import graph never touches a backend package. The deployer's import graph touches exactly one preset. This is enforceable, testable, and is the single property that makes the goal real.

The result: the same run() function becomes this —

// Deployer's entire decision: one line.
stk, err := sqlite.Open("./data/app.db", sqlite.WithBus(), logger)
if err != nil { return err }
defer stk.Close()

// App developer wires ONLY domain logic.
runner, _ := projection.NewRunner(stk.Events, stk.Bus, stk.Checkpoints)
runner.Register(NewTodoProjection(stk.ReadModels))
go runner.Run(ctx)

app := NewApp(stk) // commands + queries against stk.Events / stk.ReadModels
return app.Serve(":8080")

Swapping SQLite for Postgres is a one-line change in the deployer's code. The application developer changes nothing.

04Three Actors, Three Responsibilities

The frame that makes this design legible: recognise that three distinct people touch a go-cqrs-lite application, and give each one a clean boundary.

Layer 0

Library Author

Defines capability interfaces (event.Store, snapshot.SnapshotStore, readmodel.Store) and ships backend implementations. Decides what is possible.

Deployer

Operator / DevOps

Picks where data lives via one preset call. Chooses topology: single SQLite, embedded Pebble, managed Postgres, or a split multi-DB layout. Never writes domain logic.

Layer 1+

App Developer

Writes what the app does: aggregates, commands, queries, projections. Imports event, command, query, decider, projection. Never imports a backend.

Today, the deployer and app developer are collapsed into one person staring at main.go. The Stack layer gives the deployer their own file — typically main.go or wire.go — and frees the rest of the codebase from infrastructure imports.

05Architecture

Three layers, stacked. Each layer only knows the one below it.

Layer 3 — Deployer's entry point (one import)
PRESETS   stack/sqlite.Open() · stack/pebble.Open() · stack/memory.New()
             stack/postgres.Open() · stack.Compose(...)
▲ builds
Layer 2 — Composition root (new module)
STACK   type Stack { Events, Snapshots, Checkpoints,
             Commands, Queries, ReadModels, Bus }
         func (s *Stack) Close() error  // unified lifecycle
▲ composed from
Layer 1 — Backends (already exist)
storage.SQLBackend  ·  pebble.Backend  ·  turso.Backend
memory.*   (+ future persistent bus adapters)

Layers 0 and 1 are unchanged. Layer 2 is the new stack module. Layer 3 is a family of preset sub-packages. The deployer imports one sub-package from Layer 3; the app developer imports modules from Layer 0. Neither crosses into the other's territory.

Why this preserves “library, not framework”

The Stack is opt-in. Core types stay pure interfaces with no backend knowledge. A consumer who wants maximum control still wires stores by hand from Layer 1 — the current behaviour, fully supported and documented. Presets are the happy path, not the only path.

06Capability Inventory

A Stack holds seven capabilities. These are the only storage touchpoints in the entire library (documented in docs/research/storage-environment-mapping.md). Each maps to an existing interface — except the read model, which needs a new module.

# Capability Interface Status
1 Event Store event.Store Solid
2 Snapshot Store snapshot.SnapshotStore Solid
3 Checkpoint Store event.CheckpointStore Solid
4 Command Store command.Store Interface ready
5 Query Store query.Store Interface ready
6 Read Model Store readmodel.Store[T]  new Missing
7 Message Bus event.Bus In-memory

The read model store is the one capability with no formal module today. Every consumer reinvents it (example/todo/storage/). It is the single highest-impact addition, and it unblocks presets — because projections need somewhere to write their materialised views.

07Preset Catalog

Presets are convenience functions that produce a wired Stack. Each is a sub-package so a consumer only links the backend they actually use.

Preset Topology Best For Deps
memory.New() All in-memory Tests, CI, prototypes zero
sqlite.Open(dir) 1 SQLite file Local-first, single-process, MVP sqlite driver
pebble.Open(dir) 1 Pebble DB Embedded, write-heavy, single-process pebble
postgres.Open(dsn) 1 Postgres DB Managed prod, multi-process pgx
stack.Compose(...) Mixed / split Multiple stores by capability varies

Every preset returns the same *Stack type. Application code receives a *Stack and is oblivious to which preset built it. That polymorphism is the deployer's freedom.

08The Split-Topology Case

The most interesting design challenge — and the one the prompt specifically asks for — is running multiple databases: one for command + event sourcing, one for the query log, one for materialised views. This is where presets earn their keep, because the Stack must compose capabilities from different providers rather than inherit them from one backend.

The stack.Compose builder assembles a Stack capability-by-capability:

// Three SQLite databases, each tuned for its workload.
stk, err := stack.Compose(
    stack.WithEvents(sqlite.EventStore("data/events.db")),
    stack.WithCommands(sqlite.CommandStore("data/commands.db")),
    stack.WithReadModels(sqlite.ReadModels("data/views.db")),
    stack.WithBus(memory.Bus()), // transient, single-process
    stack.WithSnapshots(sqlite.SnapshotStore("data/events.db")),
    stack.WithCheckpoints(memory.CheckpointStore()),
)
defer stk.Close() // closes every provider that owns a resource

The same Compose API handles heterogeneous backends: events on Postgres, read models on Pebble, bus on NATS. The Provider interface — implemented by every backend facade — is the contract that makes this work: 

// Every backend facade implements the relevant Provide methods.
type Provider interface {
    ProvideEvents() event.Store
    ProvideSnapshots() snapshot.SnapshotStore
    ProvideCheckpoints() event.CheckpointStore
    ProvideReadModels() readmodel.Store
}

Get the Provider interface right here and the single-backend presets fall out for free — a preset is just Compose(WithProvider(backend)) with sensible defaults.

09Recommendations as Data

The prompt asks for recommendations: guidance that some data (projections, materialised views) may be better placed in a SQL, KV, columnar, or graph database. The research is already done in docs/research/storage-environment-mapping.md — a per-capability, per-environment matrix. The Stack layer surfaces it as a first-class reference rather than a buried research note.

Capability Local / embedded Managed prod Why
Event Store SQLite / Pebble PostgreSQL Append-only log; needs ordering + optimistic concurrency
Read Models SQLite / Pebble PostgreSQL / DynamoDB / Firestore Read-heavy; rebuildable from events; flexible queries
Snapshots / Checkpoints SQLite / Pebble etcd (K8s) / DynamoDB / Firestore Tiny KV; point lookups; frequent overwrites
Command / Query log SQLite PostgreSQL (shared) Audit trail; lower volume than events
Message Bus memory NATS / Redis / SNS+SQS Transient delivery; multi-node fan-out
Where recommendations live

In documentation (docs/PRESETS.md) and as structured comments in the preset packages — not as runtime code that adds imports and complexity. A preset's doc comment states its sweet spot and its limits. The deployer reads it; the app never executes it.

10Design Decisions

Naming: stack

A Stack is literally a stack of capabilities wired to one topology. The name Backend is already taken by per-DB facades (pebble.Backend, storage.SQLBackend), so stack sits one layer above cleanly. Alternatives app, runtime, preset either lie about scope or collide with existing vocabulary.

Module topology: one module, sub-packages

One stack/ module with preset sub-packages (stack/sqlite, stack/pebble, stack/postgres, stack/memory). Single import root, but each sub-package is its own compilation unit — a consumer using only stack/sqlite never links Pebble. This mirrors the existing catalog/asyncapi, catalog/openapi pattern in this repo and avoids the over-modularization the project's own docs warn against.

Read model: generic, both adapters from day one

readmodel.Store[T any] with a KV-shaped contract (Get / Put / Delete / Iter) plus an SQL adapter for filtered-list queries. The KV contract covers 90% of projection needs and has three ready adapters (Pebble via kv.Store, memory, future Redis). Define the generic once; ship both adapters.

All capabilities are first-class

Every backend should eventually provide all seven capabilities. No capability is treated as “probably unused.” This is a public library; its consumers are external and invisible. A missing implementation is a real gap for someone, not a candidate for YAGNI.

11Honest Tradeoffs

What we gain

Deployer portability (one-line backend swap). Application code becomes backend-agnostic by construction. Dramatically simpler onboarding — the todo example shrinks from ~150 glue lines to ~10. A clear answer to “how do I run this in prod?”

What it costs

A new module (stack) plus a new module (readmodel) = surface area to maintain and test. Presets can hide power-user knobs — mitigated by the stack.Compose escape hatch and raw wiring remaining fully supported.

The constraint to respect

A generic readmodel.Store[T] will not fit every conceivable projection shape. Some consumers need columnar or graph storage for specific views. The answer is not to cram every storage model into one interface — it is to let those consumers implement readmodel.Store themselves (or bypass it) while the presets cover the common 90%. Presets serve the majority; the interface serves the rest.

12A Correction

An earlier draft of this proposal dismissed the command store gap with “zero consumers today for a reason” and recommended skipping it as YAGNI. That was wrong. This is a public library — its consumers live outside this repo and are invisible. The project's own AGENTS.md states it plainly:

“Zero internal consumers is the EXPECTED state. Deleting external-facing API is breaking the product.”

The command store and query store interfaces exist, are exported, and may well be implemented by external consumers right now. The correct posture is: every capability gap is a real gap, and the Stack layer should make it trivial for any backend to fill all of them. This proposal treats all seven capabilities as equally important.

13Non-Breaking Migration

The Stack layer is purely additive. Nothing about the existing modules, interfaces, or wiring changes. The migration is opt-in and gradual:

  1. Existing consumers keep their hand-wired main.go and it continues to work identically. Raw wiring remains documented as the power-user path.
  2. New consumers start with a preset. The happy path is now the default in docs and examples.
  3. Migrating consumers move their glue into a preset call at their own pace. No big-bang rewrite.

The proof is in the example: if rewriting example/todo on stack/sqlite does not produce a dramatically simpler main.go, the design is wrong and should be iterated before shipping.

14Execution Plan

Nine phases, ordered by what unblocks what. Each is independently shippable.

1

readmodel module

Define generic readmodel.Store[T] + memory adapter. This unblocks presets — projections need a write target. Highest impact, smallest scope.

2

stack core

Capabilities struct, Stack type, Provider interface, Compose builder, unified Close().

3

stack/memory preset

Fastest to build; validates the Stack shape with zero external deps.

4

stack/sqlite preset

The “one file for everything” MVP case. The most common deployment.

5

stack/pebble preset

Embedded KV, single-process prod. Shares the Provider contract with SQLite.

6

split topology

stack.Compose with per-capability providers — the 3-database case. This is where the Provider interface is stress-tested.

7

stack/postgres preset

Managed prod. Same shape as SQLite, different driver and dialect.

8

rewrite example/todo

Port example/todo to stack/sqlite. Add a split-topology example. Measure the line-count and clarity delta. If it's not dramatic, iterate.

9

docs + recommendations

docs/PRESETS.md reference. Update STORAGE_GUIDE.md and SKILL.md to lead with presets. Encode the recommendation matrix.

Where to start

Phase 1 (readmodel) and Phase 2 (stack core). Everything downstream is blocked until the read model exists and the Stack type is defined. The split-topology case (Phase 6) is the real design test — it forces the Provider interface to be a composition of parts, not a single backend. Get that right and the single-backend presets are trivial.
