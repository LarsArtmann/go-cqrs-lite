The Outbox Pattern

How to reliably publish events in a distributed system without losing them — even when the process crashes halfway through.

01The Problem

In CQRS + Event Sourcing, every state change produces an event. That event must be both persisted to the store and broadcast to subscribers. The naive approach looks like this:

1
💾 Save events to database
2
📡 Publish events to message bus
💥 process crashes between steps 1 & 2
3
Publish — never happened

If the process crashes after saving but before publishing, the event is permanently lost to subscribers. The data is in the store, but no projection, saga, or read model will ever see it. This violates the fundamental invariant of event-driven systems: every event must be delivered.

Common workarounds have their own flaws: two-phase commit is slow and complex, in-process buses couple store to transport, and change-data-capture (Debezium) requires external infrastructure.

02The Solution

The Transactional Outbox pattern writes events to the database and an outbox table in the same transaction. A background poller then reads pending entries and publishes them to the bus. If it crashes, the entry remains "pending" and gets retried.

💾
Save Events
Write to event store table
→
📤
Outbox.Append
Same transaction — atomic!
→
🔄
Poller
Background goroutine polls pending
→
📡
Bus.Publish
Broadcast to subscribers

The key insight: the outbox entry lives in the same database as the event store. This means a single SQL transaction guarantees atomicity — either both commit or neither does. No distributed coordination needed.

03The Interface

The core abstraction is event.Outbox — three methods, one purpose:

core/event/outbox.go
Append (ctx, []Event) → error Stage events inside the save transaction
PollPending (ctx, limit) → []OutboxEntry Fetch unacknowledged entries, oldest first
Ack (ctx, []OutboxID) → error Mark entries as successfully published

Each entry wraps a batch of events with a unique ID and timestamp. The poller reads them in order, publishes via the bus, and acknowledges on success. Failed entries stay pending for the next poll cycle.

04Database Schema

Under the hood, the SQLOutbox stores event batches as JSON in a single table:

Column Type Description
id text OutboxID (event batch identifier)
status text "pending" or "acknowledged"
events jsonb Serialized event batch
created_at timestamptz When the entry was created

The status column drives the entire lifecycle. pending entries are picked up by the poller. After successful publishing, they become acknowledged (and are deleted, not updated — keeping the table small).

05The Lifecycle

Here's exactly what happens from command to subscriber — step by step:

Save + Outbox TransactionalSink.SaveWithOutbox()

A single SQL transaction inserts events into the event store and appends them to the outbox table. If either fails, the entire transaction rolls back. No partial state.

Poll Outbox.PollPending(ctx, limit)

A background goroutine (the OutboxPublisher) periodically queries for entries with status = 'pending', ordered by created_at.

Publish Bus.Publish(ctx, events...)

For each pending entry, the poller publishes its events through the event bus. If publishing fails for one entry, the remaining entries in the batch are still published. The failed entry stays pending and will be retried on the next poll cycle.

Acknowledge Outbox.Ack(ctx, ids)

Successfully published entries are acknowledged — which deletes them from the outbox table. If the process crashes before ack, the entry remains pending and gets republished (subscribers must be idempotent to handle this).

06Usage

Setting up the outbox in your application takes three pieces:

// 1. Create the outbox alongside your event store
var db *sql.DB = /* your database */
store, _  := storage.NewSQLEventStore(db)
outbox, _ := storage.NewSQLOutbox(db)
txStore, _ := storage.NewSQLTransactionalStore(store, outbox)

// 2. Wire the background publisher
publisher, _ := event.NewOutboxPublisher(outbox, bus,
    event.WithPollInterval(5 * time.Second),
    event.WithBatchSize(100),
)
publisher.Start()  // begins background polling
defer publisher.Close()

// 3. Use SaveWithOutbox instead of Save
err := txStore.SaveWithOutbox(ctx,
    event.AggregateRef{"User", userID},
    events,
    expectedVersion,
)

For a lower-level approach, the storage.OutboxPoller provides a standalone Run(ctx) method with configurable interval and batch size, without the lifecycle management of OutboxPublisher.

07Why It Works

The entire pattern hinges on one property: atomicity. The SaveWithOutbox method opens a single SQL transaction that:

T
💾 INSERT INTO events ...
T
📤 INSERT INTO outbox (status='pending', events=...)
T
✓ COMMIT — both succeed, or neither does

If the INSERT into events succeeds but the outbox INSERT fails, the entire transaction rolls back. If the process crashes before COMMIT, the database rolls back automatically. There is no window where events are saved but not outboxed.

This is why the outbox lives in the same database as the event store — it piggybacks on the database's existing ACID guarantees instead of requiring distributed coordination.

08Tradeoffs

+ Advantages

  • Exactly-once storage — events are atomically stored and outboxed
  • Crash-resilient — pending entries are retried on restart
  • Minimal infrastructure — single SQL table, no Debezium or Kafka required
  • Decoupled — poller runs independently, async consumers supported
  • Observable — poll metrics, pending counts, processing rates
  • Works with PostgreSQL, SQLite, and Turso

− Considerations

  • Slight latency — events arrive after poll interval (default: 1s), not instantly
  • At-least-once delivery — ack before crash means republish; subscribers must be idempotent
  • Storage overhead — outbox entries exist until acknowledged and deleted
  • Batch-level ack — partial failure retries the entire batch
  • Requires wiring — Outbox + Publisher + Bus must be composed by the consumer

09Implementations

The library provides three event.Outbox implementations:

SQLOutbox

Production implementation backed by PostgreSQL or SQLite. Supports the full lifecycle with transactional co-participation via SQLTransactionalStore.

MemoryOutboxStore

In-memory implementation in the memory module. Perfect for testing without a real database. Thread-safe with mutex protection.

FakeOutbox

Test double in testhelpers. Records calls for assertion. No actual persistence.

OutboxPublisher

Not an Outbox itself — the background poller that drives the lifecycle. Configurable poll interval, batch size, and graceful shutdown via Close().

10Why Do We Need An Outbox?

A fair question. Your event store already persists events. Your bus already publishes them. Why add a third component?

The answer is a single word: atomicity.

Without the outbox, you have two separate systems — a database and a message broker — and no transaction that spans both. There is no way to atomically commit to PostgreSQL and publish to NATS/Kafka/Redis in a single operation. The moment you do them sequentially, you have a window where the process can crash between the two — and that window is always open.

Two-Phase Commit

Technically solves it. But 2PC is slow, complex, and not supported by most message brokers. It also creates tight coupling between your database and your broker — exactly what you want to avoid in a CQRS system.

Change Data Capture

Run Debezium to tail the WAL. Works, but now you have external infrastructure — Kafka Connect, Debezium connectors, schema registry. You went from "I need to publish events" to "I need a platform team."

Outbox Pattern

One extra table in your existing database. One background goroutine. No new infrastructure. Uses the ACID guarantees you already have. Events and outbox entry commit together, or not at all.

The outbox pattern is the simplest solution that actually works. It doesn't require distributed transactions, external CDC pipelines, or message broker XA support. It just uses your database — which already knows how to commit atomically.

In go-cqrs-lite, the outbox is opt-in. If you only use the in-process MemoryBus, you don't need it — bus.Publish happens synchronously inside the same process. But the moment you publish to an external broker (NATS, Kafka, Google PubSub, RabbitMQ), the outbox becomes essential.

11How Watermill Handles It

Watermill is a Go library for event-driven applications with built-in CQRS, routing, and middleware. It solves the same problem with a component called the Forwarder — Watermill's name for the outbox pattern.

The Forwarder

Watermill's approach is architecturally identical to go-cqrs-lite's outbox, but the mechanics differ:

go-cqrs-lite Outbox Watermill Forwarder
Storage Dedicated outbox table (id, status, events JSON, created_at) Watermill's built-in SQL Pub/Sub (a separate messages table)
Write path SaveWithOutbox() — single tx inserts into events + outbox sql.NewPublisher(tx, ...) — publisher decorated to write to SQL instead of broker
Read path PollPending() — explicit poll with status column SQL Subscriber listens on an intermediate topic; Forwarder subscribes and forwards
Ack model Explicit Ack(ids) deletes entries Watermill's standard Ack/Nack on messages
Scope Domain-aware — stores typed events with aggregate metadata Generic — wraps any message.Message (topic + payload + metadata)
Event store coupling Tight — outbox is co-located with the event store in the same tx Loose — Forwarder is broker-agnostic, works with any SQL Pub/Sub

How Watermill's Flow Works

1
App code writes to DB + publishes via decorated Publisher (writes to SQL table instead of broker)
2
Forwarder subscribes to the SQL Pub/Sub's intermediate topic
3
Forwarder unwraps the enveloped message and publishes to the real broker (NATS, Kafka, etc.)
4
On success, SQL subscriber acks → message removed from SQL table

The Key Difference

Watermill's Forwarder is a generic message relay — it sits between any SQL-backed Pub/Sub and any broker-backed Pub/Sub. It doesn't know about event sourcing, aggregates, or domain events. It just forwards opaque messages.

go-cqrs-lite's outbox is domain-aware — it stores typed events with aggregate IDs, versions, and metadata. It's co-designed with the event store, so the SaveWithOutbox method is a single atomic operation that inserts into both tables in one transaction.

They solve the same fundamental problem — "don't lose events between database and broker" — with different tradeoffs. Watermill is more generic and broker-agnostic. go-cqrs-lite is more integrated with the event sourcing lifecycle.

Using Them Together

In go-cqrs-lite, the watermill module provides adapters: PublisherAdapter and SubscriberAdapter that bridge go-cqrs-lite's event.Bus with Watermill's message.Publisher / message.Subscriber. If you want to use Watermill's Forwarder instead of the built-in outbox, you can — the adapters make the two libraries interoperable.
