01 — What you got right

The patterns are beautiful

project-discovery-sdk enriches projects by calling GitHub, GitLab, Bitbucket, and Gitea APIs. It checks NPM, PyPI, Cargo, and four other registries. Every single one of those calls has zero retry, zero backoff, and zero circuit breaking.

Your middleware module solves exactly this problem. The retry with exponential backoff and jitter. The circuit breaker with three-state machine. The structured logging with duration. I look at my enrichment pipeline and I see a 1:1 mapping to your middleware chain.

The Enricher interface in project-discovery-sdk is a single-method interface — Enrich(ctx, *Project) error — the textbook Go shape for decoration. Your middleware pattern would wrap it perfectly. The fit is so natural it feels like the SDK was designed for it.

Your error taxonomy — Rejection, Conflict, Transient, Infrastructure, Corruption — would let me classify "404 not found" (permanent, don't retry) vs "connection refused" (transient, retry with backoff) vs "GitHub rate limit" (transient, retry after reset). Right now I treat them all identically.

And the Decider pattern — load→fold→decide→save→publish — is the cleanest implementation of functional event sourcing I've seen in Go. The ISP-compliant interfaces (Publisher, Subscriber, EventSink, EventSource) show real architectural thought.

You built the right abstractions. The problem is purely in how they're packaged.

03 — The root cause

event/v2 is a hub, not a leaf

In a healthy dependency graph, the most-used module is the lightest — a leaf that everything else depends on. In go-cqrs-lite, the most-used module is the heaviest — a hub that depends on everything else.

Current — event/v2

// event/v2 depends on 7 siblings
event/v2
├── command/v2    // I don't dispatch commands
├── query/v2      // I don't dispatch queries
├── memory/v2     // I don't need memory store
├── schema/v2     // I don't generate schemas
├── snapshot/v2   // I don't snapshot aggregates
├── codec/v2      // I don't encode payloads
└── id/v2         // I already use go-branded-id

Proposed — event/core

// event/core depends on nothing
event/core
└── (stdlib only)

// Optional layers, imported separately
event/bus       → event/core
event/store     → event/core, codec
event/snapshot  → event/core
middleware/retry → stdlib  // no CQRS deps
middleware/cb    → stdlib  // no CQRS deps

The core event types — Event, Type, Version, Metadata — should have zero dependencies. They're value types. A struct with an ID, a timestamp, a byte slice, and a version number. The fact that importing them pulls in a command dispatcher and a query dispatcher is an architectural accident, not a necessity.

Similarly, the retry logic — exponential backoff with jitter, context-aware cancellation — is pure algorithmic code. It operates on func() error. It has no business knowing about events, commands, queries, or OpenTelemetry.

04 — What would make me adopt it

Six changes that unlock adoption

These are ordered by impact. P1 and P2 would make me adopt go-cqrs-lite immediately. P3 turned out to be weaker than expected (P1 already solves it). P5 was withdrawn — the wrong problem. P4 and P6 would make me recommend it to everyone.

P1

Extract generic middleware — zero CQRS deps

Create middleware/retry and middleware/circuitbreaker as standalone modules with zero internal sibling dependencies. No event types, no command types, no OTel. Just pure algorithms: 

// middleware/retry — stdlib only
package retry

type Config {
    MaxAttempts  int
    InitialDelay time.Duration
    MaxDelay     time.Duration
    Multiplier   float64
    IsRetryable  func(error) bool
}

// Do retries fn with backoff and jitter. Pure algorithm.
func Do(ctx context.Context, cfg Config, fn func() error) error

Then the existing CQRS-specific middleware becomes thin wrappers:

// middleware/v2 keeps the typed adapters
func CommandRetry(cfg retry.Config) Middleware {
    return func(h Handler) Handler {
        return func(ctx context.Context, cmd Command) error {
            return retry.Do(ctx, cfg, func() error { return h(ctx, cmd) })
        }
    }
}

Why this matters: 90% of the value of your middleware module is the retry/backoff/circuit-breaker logic. Today it's locked behind 40+ transitive deps. Freed from the CQRS types, it becomes useful to any Go project making network calls.

P2

Split event/v2 into layered leaves

Break the hub module into three layers, each independently importable:

event/core    // Event, Type, Version, Metadata, AggregateRef — stdlib only
event/bus     // Bus, Publisher, Subscriber interfaces — depends on core only
event/store   // Store, EventSink, EventSource — depends on core + codec
event/journal // Journal, SeekableJournal — depends on core

The event/core module contains only value types. No interfaces, no behavior, no codec, no ULID dependency (the EventID can be a plain string in core). Projects that only need to reference event types (like middleware) import core and get nothing else.

Why this matters: The current event/v2 is the #1 transitive dependency in the entire repo. Everything depends on it, and it depends on everything. Splitting it turns the dependency graph from a tangled web into a clean tree.

P3

Make OTel optional, not structural weaker than P1

Today, decider/v2, projection/v2, storage/v2, and middleware/v2 all directly import OTel packages. The heavy ones are otel/sdk and otel/sdk/metric in middleware/v2 — the trace API alone (otel/trace) is relatively lightweight.

Honest pushback: the OTel trace API is the Go ecosystem standard. Shimming Tracer/Span behind custom interfaces adds maintenance burden — every new OTel feature (links, events, status codes) requires updating the shim. This proposal is weaker than it appeared because:

P1 already solves this. Extracting generic middleware as stdlib-only removes the OTel dependency for external consumers entirely. The remaining modules (decider, projection, storage) are CQRS-internal — their OTel usage is justified for the audience that imports them. Only middleware was the problem, and P1 fixes it.

P4

Generic decorator pattern

The retry and circuit breaker don't operate on CQRS types. They operate on func(ctx) error. Expose this explicitly: 

// middleware/retry
func Do(ctx context.Context, cfg Config, fn func() error) error

// middleware/circuitbreaker
type Breaker struct { ... }
func (b *Breaker) Do(fn func() error) error

// middleware/timeout
func Do(ctx context.Context, timeout time.Duration, fn func() error) error

The CQRS-specific adapters (CommandRetry, EventRetry, QueryRetry) become one-liners that call the generic implementations. Non-CQRS consumers use the generic functions directly.

Why this matters: This is the difference between "a CQRS library with middleware" and "a middleware library that also works for CQRS". The second formulation has 100x the potential user base.

P5

Configurable ID backing type withdrawn — wrong problem

Original proposal: make id.Of[T] accept a configurable backing type so non-ULID use cases (file paths, project names) could use the same module.

Withdrawn. ULID backing is a deliberate, correct choice for event-sourced systems — time-ordered, globally unique, binary-sortable, extractable timestamp. Making it string-backable would dilute these guarantees.

This was the wrong problem. project-discovery-sdk already uses go-branded-id directly for its string-backed needs. go-cqrs-lite's id/ module serves a different domain (event identifiers) where ULID is the right answer. No change needed — the two projects already share the underlying go-branded-id library and specialize appropriately.

P6

Dependency budget per module

Add a mechanical rule: every module must declare its dependency budget, and CI enforces it. This prevents the graph from re-tangling:

Layer Max external deps Max internal siblings Examples
Core (leaf) ≤ 2 0 event/core, middleware/retry, id
Protocol ≤ 3 ≤ 2 event/bus, event/store
Implementation ≤ 5 ≤ 4 memory, storage/sqlite
Integration unlimited unlimited middleware, catalog, otel

Why this matters: "Lite" is not a branding exercise — it's a structural property that must be enforced mechanically, not by convention. A dependency budget in CI would have caught the event↔memory circular dependency before it formed.

With go-cqrs-lite

import "go-cqrs-lite/middleware/retry"
import "go-cqrs-lite/middleware/circuitbreaker"

func (e *enricher) Enrich(
    ctx context.Context,
    p *Project,
) error {
    // 3 attempts, exponential backoff,
    // circuit breaker prevents flood.
    return cb.Do(func() error {
        return retry.Do(ctx, cfg, func() error {
            result, err := checker.Check(ctx, slug)
            if err != nil {
                return errclassify.Wrap(err)
            }
            p.Visibility = &RepositoryVisibility{...}
            return nil
        })
    })
}
// deps: 0 CQRS modules. Just retry + cb.

Notice what's not imported: no command dispatcher, no query dispatcher, no event store, no memory bus, no snapshot, no schema, no OpenTelemetry SDK. Just two tiny packages doing one job each.

That's what "lite" means. I get exactly what I need and nothing I don't. Two imports. Zero transitive CQRS deps. And my enrichment pipeline goes from "fails on every transient network blip" to production-grade resilience.

06 — Suggested sequence

How to get there incrementally

This isn't a rewrite. It's a sequence of extractions that leave the existing API untouched while creating new, lighter import paths.

Extract retry + circuit breaker as standalone

Move the core algorithms from middleware/v2 into middleware/retry and middleware/circuitbreaker. The existing CQRS middleware becomes thin wrappers. Zero breaking changes. New modules are additive.

Extract event/core from event/v2

Move Event, Type, Version, Metadata, AggregateRef into event/core. The full event/v2 re-exports everything from core. Zero breaking changes. Existing imports keep working.

Revisit OTel coupling if needed

After P1, the OTel problem is largely solved for external consumers (generic middleware is stdlib-only). If CQRS-internal consumers still need lighter OTel integration, the shim pattern can be evaluated then — but it's no longer a blocker for adoption.

Update sibling deps to use core

Point command/v2, query/v2, decider/v2 at event/core instead of event/v2. Each sheds unnecessary siblings from its transitive graph.

Document dependency budgets in CI

Add a linter that checks each module's dependency count against its budget. Prevents regression.
