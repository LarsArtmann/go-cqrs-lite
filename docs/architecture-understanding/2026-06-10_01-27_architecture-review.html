Executive Summary

The go-cqrs-lite library has excellent modular structure at the macro level — 22 independently versioned library modules with clear layer separation. The ISP-split interfaces, pure-function decider pattern, and composition-over-inheritance design are textbook examples of Go library architecture.

However, 4 circular dependencies between core modules (event, command, memory, snapshot) prevent true independent compilation and versioning. Additionally, 12 of 22 modules have test-only dependencies in their production go.mod files, causing unnecessary binary bloat for consumers.

The most impactful improvement would be breaking the event ↔ command cycle by extracting shared types (AggregateRef, Metadata) into a thin shared module.

Circular Dependencies CRITICAL

Four bidirectional import cycles exist in the core module graph. These prevent independent compilation and versioning of the affected modules.

#CycleImpact
1event ↔ commandCore event types coupled to command dispatch; shared types (AggregateRef, Metadata) live in wrong module
2event ↔ memoryEvent test suite imports memory; memory implements event interfaces — should be one-directional
3memory ↔ snapshotIn-memory store depends on snapshot abstractions AND snapshot depends on memory types
43-node: memory → command → event → memoryTransitive cycle through the bidirectional edges above

Root Cause

The primary issue is that event is both a domain types module AND a test infrastructure module. Its eventtest sub-package depends on memory (for shared store suite), and its main package depends on command and query (for CatalogDispatcher integration).

Fix Strategy

  1. Extract eventtest from event go.mod — move to its own module (it already has its own directory). This breaks event ↔ memory.
  2. Extract shared types (AggregateRef, Metadata) from command into event, then remove event → command dependency. CatalogDispatcher should be in command, not event.
  3. Unidirectional snapshot: snapshot should depend on event only, not memory. Move memory snapshot implementation's interface dependency.

Test Dependencies in Production go.mod MEDIUM

12 of 22 modules list test-only libraries (ginkgo, gomega, rapid, go-sqlmock) as direct dependencies in their production go.mod. This means consumers who import these modules transitively pull in the entire test framework at runtime.

Impact

Go does not have a separate test-only require block. However, these deps should be listed as // indirect or moved to a separate test module. The current setup means go mod tidy won't remove them because they ARE used in _test.go files. The real fix is to move test suites into separate test modules or use Go 1.26's improved test dependency handling.
