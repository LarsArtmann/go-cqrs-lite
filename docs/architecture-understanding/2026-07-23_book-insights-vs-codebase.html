00Summary

go-cqrs-lite is, in essence, an implementation of the DDIA / Kleppmann "logs + materialized views" thesis at the application/aggregate level. The event store is the WAL, projections are materialized views, the decider is the fold function, and the schema upcaster system is schema evolution. 38 of 61 catalogued insights from seven books are already implemented in the codebase. The 8 gaps are mostly "should consider" items where the library provides primitives but could improve ergonomics or documentation. The 15 "must NOT do" items are anti-patterns the library correctly avoids — and should continue to avoid.

The bottom line The library is architecturally sound and maps remarkably well to the theoretical foundations. The gaps are in observability ergonomics, documentation of consistency guarantees, and a few missing distributed-systems primitives. No structural changes needed — only additions at the edges.

01What We Already Apply

38 insights across seven books are already implemented. Below they are organized by book, with the specific codebase mapping for each.

Designing Data-Intensive Applications (Kleppmann)

The most important book for this codebase. Its Part III thesis — "databases are logs + indexes + materialized views" — is the architecture of go-cqrs-lite.

+
Log as source of truth (DDIA Part III) The event store (event.Store) is the WAL. State is derived by folding events via decider.Decider[State].Apply. This is exactly DDIA's "system of record (log) → derived data (views)" pattern. ADR-0001 chose pure functions over mutable aggregate roots to make this explicit.
+
Materialized views / derived data Three projection tiers implement DDIA's "materialized views": stack.Materialize (KV/document), storage.RelationalProjection (multi-table SQL), and graph.GraphProjection (nodes/edges). All are rebuildable from the log. The projectionhost manages their lifecycle.
+
Schema evolution (forward/backward compatibility) schema.Upcaster transforms old event versions on read — exactly DDIA's Avro schema-evolution pattern (writer schema vs reader schema). VersionedStore and VersionedSeekableJournal apply upcasters transparently. Events carry SchemaVersion stamps.
+
Optimistic concurrency control event.EventSink.Save(ctx, ref, events, expectedVersion) implements compare-and-set: the store checks expectedVersion against current version, rejecting with ErrConcurrencyConflict on mismatch. SQL: WHERE version = expectedVersion. Pebble: sharded mutex + version check before batch commit.
+
Both storage engine families (B-tree + LSM) SQL stores (PostgreSQL/SQLite) use B-tree indexes (good for read-heavy point lookups). Pebble uses LSM-trees (great write throughput, compaction cost). DDIA describes both families with these exact tradeoffs. The library supports both without forcing a choice.
+
Interface Segregation (ISP) for store interfaces EventSink (write), EventSource (read), Journal (cross-aggregate), SeekableJournal (position-based), BackwardsSource (reverse). ADR-0006 explicitly split the monolithic Store interface. This mirrors DDIA's principle of segregating read/write paths for independent scaling.
+
Snapshot optimization (read performance) snapshot.SnapshotStore with EveryNEvents and ReadPressure strategies. On load: snapshot + delta events rather than full replay. DDIA discusses this as materialized view refresh strategies (incremental vs full rebuild). Best-effort saves (errors swallowed, logged).
+
Single-writer per aggregate (= per-partition) Optimistic concurrency per aggregate ID = DDIA's "single-writer per partition" for ordering. The MultiSink.SaveMultiBatch provides atomic multi-aggregate writes when cross-aggregate atomicity is needed.
+
Tombstone soft-delete (no physical deletes) event.DetectTombstone + event.MarkTombstone — metadata-based soft delete. Maps to DDIA's tombstones in LSM compaction and replication (deletes are special writes, not destructive operations). ADR-0005.
+
Idempotent receiver pattern idempotency.Store with CheckAndRecord (atomic check + record) and dedup.Ring (bounded O(1) dedup at stream boundaries). DDIA's "idempotent receiver" for at-least-once delivery.
+
Consumer offset tracking (high-water mark) event.CheckpointStore + projectionhost worker tracking. Each projection saves its position after processing. On restart, resumes from checkpoint. DDIA's "consumer offsets" / high-water mark pattern.
+
Catch-up: replay then live (consumer bootstrapping) watermill.CatchUpSubscriber Phase 1: replay from journal with ProcessingMode=ModeReplay. Phase 2: live handoff with EventID-based dedup via dedup.Ring. DDIA's "bootstrapping new consumers from the log."
+
Multi-DB I/O isolation (shared-nothing) WithEventDB, WithQueryDB, WithViewDB split databases for I/O isolation. DDIA's shared-nothing architecture at the database level. ADR-0033.
+
Self-describing messages (encoding stamps) Every event carries Encoding() stamp. DecodePayloadAuto dispatches based on encoding (JSON or CBOR). DDIA discusses schema-in-message vs schema-registry; go-cqrs-lite chose self-describing events for mixed streams. Blind stores (kv/snapshot/command/query) use the ADR-0044 envelope.
+
Error taxonomy (classified errors) 5-family taxonomy via go-error-family: Rejection, Conflict, Transient, Infrastructure, Corruption. DDIA emphasizes classifying errors as transient vs permanent for proper retry/handling. The gRPC transport maps families to status codes; the example maps families to HTTP status codes.

Exploring CQRS and Event Sourcing / Implementing DDD, CQRS and Event Sourcing

The CQRS and event-sourcing literature is the direct theoretical foundation. Nearly every pattern described in these books is implemented.

+
CQRS separation (command/query/event) Three separate module trees: command/, query/, event/. Each has its own store, bus, dispatcher, and middleware. The write side (decider) and read side (projections) are completely decoupled.
+
Event sourcing (event log as truth) decider.Repository[State].Execute: load events → fold → decide → save → publish. State is always a fold over events. The store is the source of truth, not the aggregate.
+
Aggregates as replay boundaries Decider[State] with Initial + Apply (fold). Each aggregate is loaded independently, events folded into state. No shared mutable state between aggregates. ADR-0001.
+
Snapshots (performance optimization) snapshot.SnapshotStore, EveryNEvents, ReadPressure. Snapshot + delta events on load. Best-effort saves. Exactly the CQRS/ES book pattern for avoiding full replay.
+
Three projection tiers (read models) KV/document (Materialize), relational (RelationalProjection), graph (GraphProjection). All implement projection.Projection. All rebuildable from the event log.
+
Event versioning / upcasting schema.Upcaster with SourceType, SourceVersion, Upcast. VersionedStore wraps any store. VersionedSeekableJournal for projectionhost pipelines. Events are immutable; transformation happens on read.
+
Anti-pattern avoided: event-sourcing CRUD The example/taskmanager uses 11 typed events (TaskCreated, TaskAssigned, TaskStarted, TaskCompleted, etc.) — NOT anemic Created/Updated/Deleted. Each event carries only the changed data, not full state. The cqrs-lint linter (60 rules) catches CRUD-style events in consumer code.
+
Saga / process manager emergence deriver.Deriver (ADR-0040) provides event→command derivation: Then, Filter, Idempotent, AsHandler. Multi-step orchestration emerges from bus.SubscribeAll + command dispatch. No dedicated saga framework needed — this is the correct library-level abstraction.
+
Command bus pub/sub command.NewMemoryBus (in-process), watermill.NewCommandBus (any broker via Watermill). Typed subscription dispatch, catch-all (SubscribeAll), middleware chain.
+
Temporal queries (time-travel) LoadAtVersion, LoadAtTime in the decider repository. event.EventSource.LoadToVersion, LoadToTimestamp. The ability to reconstruct state at any point in time — a hallmark of event sourcing.
+
Typed commands (compile-time safety) decider.TypedDecider[State, Cmd] binds the command type at compile time. query.RegisterTyped[Q, R] and query.TypedHandler[Q, R] for type-safe query dispatch. ADR-0001.
+
Projection rebuild (reset from scratch) projectionhost.Host.Reset(ctx, name) drops checkpoint + calls Resettable.Reset() if implemented. Replays from zero. Dead-letter store admin: Count, ListPaged, PurgeBefore.
+
Dead letter handling (poison event quarantine) projectionhost.WithDeadLetterStore(dlq, 3) — poison events exceeding retry threshold are captured to a SQLite-backed DLQ (UNIQUE(projection_name, event_id)). Checkpoint advances past them. Admin interface for inspection and cleanup.
+
Eventual consistency (documented and tracked) projectionhost.LagPerProjection() and LagDuration() for dashboards. Processing mode (ModeReplay vs ModeLive) distinguishes replay from live processing. The docs explicitly warn about eventual consistency between write and read sides.

Designing Event-Driven Systems (Kleppmann)

This book is essentially DDIA's stream/derived-data chapters expanded. Its thesis — "turn the database inside-out" — is the go-cqrs-lite architecture.

+
Log as fundamental primitive The event store IS the distributed commit log (Jay Kreps' "The Log" essay). event.SeekableJournal.ReadFrom(afterEventID, limit) provides position-based reading, like Kafka offsets. ULID event IDs are time-sortable.
+
Tables and streams are duals Events (stream) → projections (table). A projection is the materialized current value of an event stream. stack.Materialize literally materializes events into KV documents. The Reset operation rebuilds the table from the stream.
+
Turn the database inside-out WAL = event.Store. Indexes = kv.Store. Materialized views = projections. MVCC = optimistic concurrency + snapshot isolation per aggregate. These internal DB mechanisms are first-class distributed building blocks in go-cqrs-lite.
+
Derived data over distributed transactions No 2PC. Projections derive from the log independently. Each consumer builds its own view. ADR-0016 explicitly declined the outbox pattern. This is Kleppmann's "derived data over distributed transactions" thesis.
+
Schema management across boundaries Codec abstraction (codec.JSONCodec, codec.CBORCodec), encoding stamps on every event, DecodePayloadAuto for mixed streams. Upcasters for schema evolution. The hard organizational problem Kleppmann describes is addressed at the library level.
+
CDC-like replay (change data capture) CatchUpSubscriber replays from journal position, like CDC. The SSE broker's WithReconnectJournal provides Last-Event-ID reconnection — missed events are replayed from the journal before live streaming.
+
W3C trace context propagation cqrsotel.WithCorrelationID, cqrsotel.CorrelationIDFromContext, cqrsotel.NewTextMapPropagator() (W3C trace + baggage). Watermill TraceContextMiddleware injects/extracts trace context into message metadata for cross-service producer→consumer span linking.

Patterns of Distributed Systems

The pattern catalogue from Berkeley/Joshi. go-cqrs-lite implements the patterns relevant to an application-level CQRS library.

+
Write-Ahead Log (WAL) The event store IS the WAL. Events are persisted before publishing. If publish fails, events are safe in the store. decider.Repository.Execute: save → publish (not the reverse).
+
High-Water Mark / Checkpointing event.CheckpointStore + projectionhost worker checkpoint tracking. Save position after processing, resume on restart.
+
Idempotent Receiver idempotency.Store.CheckAndRecord (atomic), dedup.Ring (bounded O(1) at stream boundaries), middleware.EventIdempotency / CommandIdempotency / QueryIdempotency.
+
Sequence Broker (ordered replay) event.SeekableJournal.ReadFrom(afterEventID, limit) provides position-based, ordered replay. ULID IDs are monotonically sortable.
+
Retry with exponential backoff + jitter retry.Do (standalone, zero-dep), middleware.NewRetry (middleware chain), projectionhost crash-restart with full jitter backoff. scheduling.Scheduler uses equal-jitter backoff for failed dispatches.
+
Circuit Breaker middleware.CircuitBreaker with atomic.Int32 state (lock-free fast path). Half-open probe, configurable failure threshold.
+
Dead Letter Queue projectionhost.WithDeadLetterStore(dlq, threshold). middleware.NewRetry with OnDeadLetter callback. SQLite-backed DLQ store with admin interface (count, list, purge).
+
Heartbeat (liveness) SSE heartbeat (15s comment frames prevent proxy idle timeouts). scheduling.Scheduler polls on a ticker (1s default). stack.Bundle.HealthCheck pings DB + all registered health checkers.

Service Design Patterns (Daigneau)

Service interface/API design patterns. The library provides transport helpers without enforcing a specific protocol.

+
Service tiers (entity / task / activity) Module structure maps to Daigneau's tiers: event/, command/, query/ (entity services), decider/ (task-level), projectionhost/ (activity-level). The four-tier model (ADR-0046) is the formalization.
+
Request/Acknowledge (async messaging) Event publishing: save to store (acknowledge) then publish (notify). Command bus: publish and subscribe. Watermill bridges for NATS/Redis/Kafka.
+
Content negotiation (codec abstraction) codec.JSONCodec, codec.CBORCodec, codec.CBORCompactCodec, codec.RawCodec. Events are self-describing (encoding stamp). SSE WithPayloadTransform for CBOR→JSON browser conversion.
+
Idempotency at the contract layer middleware.CommandIdempotency, EventIdempotency, QueryIdempotency. KV-backed idempotency (idempotency/kvstore) for Redis SET NX / SQL INSERT ON CONFLICT.
+
Multiple transport options (no lock-in) SSE (transport/http), gRPC (transport/grpc), REST (example/taskmanager). Watermill adapters for any message broker. The library provides helpers but does not enforce a protocol.
+
Error mapping (contract to status) Error family → HTTP status (example writeCQRSError). Error family → gRPC status (transport/grpc/classifyError). CommandResult{Success, Error, ErrorCode, ErrorFamily} in gRPC response.

Deciphering Data Architectures

The data-platform patterns (warehouse, lakehouse, fabric, mesh) are mostly outside the scope of an application-level CQRS library. However, the Data Mesh's organizational principles are reflected in the module structure.

+
Domain ownership (Data Mesh principle 1) Each module has its own go.mod, independent version, and dependency budget. The multi-module monorepo (ADR-0003) mirrors "domain ownership" — each module is owned by its concern, not by a central platform team.
+
Self-serve platform (Data Mesh principle 3) Stack presets (stack/sqlite, stack/postgres, stack/pebble, stack/turso) provide one-call infrastructure setup. Consumers call sqlite.New(dsn) and get a fully wired Bundle — the "self-serve data platform" pattern.
+
Federated governance (Data Mesh principle 4) The four-tier model (ADR-0046), dependency budgets (nix run .#check-layers), and cqrs-lint (60 rules) enforce governance without a central bottleneck. Modules comply with layering rules automatically.

02What We Should Apply

8 insights are not yet implemented but would meaningfully improve the library. They are ordered by impact. None require structural changes — all are additions at the edges.

Should Apply · Medium impact

Read-your-writes consistency helper

decider/Repository, projectionhost · CQRS/ES books + DDIA

The CQRS books describe the "read-your-writes" problem: after a command succeeds, the client may query a read model that hasn't been updated yet. The library has lag tracking (LagPerProjection) but no helper to wait for a projection to catch up to a specific event version before querying. This is the most common CQRS pain point for consumers.

Recommended action Add a WaitForVersion(ctx, projectionName, aggregateRef, version, timeout) helper to projectionhost that blocks until the projection's checkpoint reaches the given version. Or document the pattern for consumers to implement using existing lag metrics + polling.
Should Apply · Medium impact

Bounded staleness queries (read freshness guarantees)

kv/ViewStore, storage/SQLViewStore · DDIA Ch. 9

DDIA discusses "bounded staleness" — a guarantee that reads return data no staler than a threshold. The library has per-projection lag tracking but no way to reject reads that would return stale data. For consumers building user-facing APIs, the ability to say "reject this read if the read model is more than 5 seconds behind" is valuable.

Recommended action Add an optional WithMaxStaleness(duration) option to kv.ViewStore / storage.SQLViewStore reads that checks projection lag and returns a ErrStaleRead (Transient) if exceeded. Alternatively, document how consumers compose LagDuration() with their read path.
Should Apply · Medium impact

Projection versioning / migration strategy

projectionhost, stack.Materialize · CQRS/ES books

When a projection handler changes (new column, new logic), the only option is Reset() — full rebuild from zero. For large read models, this is expensive. The CQRS/ES books discuss incremental migration: versioned projections that can transform existing read-model data in place, or dual-write during migration. The library provides Resettable but no incremental migration path.

Recommended action Document the migration pattern (reset vs dual-projection) clearly. Consider adding a Migratable optional interface that projectionhost calls before replay, allowing projections to transform existing data instead of clearing it. This keeps Reset as the nuclear option.
Nice to have · Low impact

Distributed tracing: span links for projection replay

projectionhost, otel/ · DDIA Ch. 11, Designing Event-Driven Systems

OTel tracing is well-integrated (spans for projectionhost.handle_event, command/event/query middleware). However, during replay, all events are processed in a single span tree, losing the original causal chain. The original event's trace context is available in metadata but not linked as OTel span links. This makes it hard to trace a specific event's journey from command to projection during replay.

Recommended action When processing events during replay, extract the original trace context from event metadata and add it as a span link (trace.Link) to the replay span. This preserves causal visibility without creating child spans (replay is not a child of the original command).
Nice to have · Low impact

Outbox pattern documentation (not implementation)

docs/ · DDIA Ch. 11, Designing Event-Driven Systems

ADR-0016 correctly declined implementing the outbox pattern as a library concern. However, the "publish after save" gap (events persisted but publish fails) is the most common operational problem for CQRS consumers. The library provides the primitives (event store + publisher) but no documentation showing how to compose an outbox using them. Consumers reinvent this every time.

Recommended action Add a documented recipe (in .agents/skills/go-cqrs-lite/references/ or docs/) showing the outbox pattern: use a projection that reads from the event journal and publishes to the bus, making the journal itself the outbox. This is already possible with CatchUpSubscriber + EventPublisher but the recipe should be explicit.
Nice to have · Low impact

Explicit consistency guarantee documentation

docs/ · DDIA Ch. 9, CQRS/ES books

DDIA carefully enumerates consistency guarantees: read-your-writes, monotonic reads, consistent prefix reads. The library implements optimistic concurrency (write side) and eventual consistency (read side), but these guarantees are not documented in a single place. Consumers must read ADRs and source to understand what the library promises. A "consistency model" document would help consumers reason about their system's behavior.

Recommended action Add a docs/CONSISTENCY_MODEL.md that explicitly documents: (1) write-side guarantee (optimistic concurrency, linearizable per aggregate), (2) read-side guarantee (eventual consistency, per-projection lag, no cross-projection monotonic read guarantee), (3) what consumers must implement themselves (read-your-writes, bounded staleness).
Nice to have · Low impact

Stream join / correlation state machine documentation

deriver/, docs/ · Designing Event-Driven Systems

Kleppmann discusses stream joins: joining two event streams on a common key (e.g., "when OrderCreated AND PaymentReceived for the same order"). The deriver module handles event→command derivation but not multi-stream correlation. For consumers needing this, the pattern is: maintain a correlation read model (via projection) + deriver that checks it before dispatching. This is possible but undocumented.

Recommended action Document the "correlation state machine" pattern: use a projection to track per-correlation-key state, then a deriver that queries it before dispatching commands. This is the go-cqrs-lite answer to stream joins without adding a stream processing engine.
Nice to have · Low impact

Data-as-a-product documentation

docs/ · Deciphering Data Architectures (Data Mesh)

The Data Mesh principle "data as a product" maps naturally to CQRS: events are the write-side product, read models are the projection-side product. Each has a clear contract (event types, read-model schema). But this framing is not explicit in the documentation. Making it explicit would help consumers think about their events and read models as versioned products with consumers, not just internal implementation details.

Recommended action Add a section to docs/DOMAIN_LANGUAGE.md or the skill references that frames events and read models as products with explicit contracts, versions, and consumers. The catalog module (AsyncAPI, D2, EventCatalog exporters) already supports this — connect the conceptual framing to the tooling.

03What We Must NOT Do

15 anti-patterns from the books that go-cqrs-lite correctly avoids — and must continue to avoid. These are temptations that seem like improvements but would violate the library's core design principles.

1. Do NOT add distributed consensus (Raft/Paxos)

Book: DDIA Ch. 9, Patterns of Distributed Systems
Why not: Consensus is a deployment concern, not a library concern. go-cqrs-lite provides optimistic concurrency per aggregate. If consumers need multi-node coordination, they use etcd/Zookeeper at the deployment layer. Adding consensus would make the library opinionated about deployment topology — violating "library, not framework."

2. Do NOT add two-phase commit (2PC)

Book: DDIA Ch. 9, Designing Event-Driven Systems
Why not: 2PC is blocking and operationally fragile. The library uses eventual consistency + projections instead. Kleppmann explicitly argues for derived data over distributed transactions. ADR-0016 declined the outbox for the same reason.

3. Do NOT add an outbox implementation

Book: DDIA Ch. 11, CQRS/ES books
Why not: ADR-0016 explicitly declined this. The outbox is a consumer concern. The library provides the primitives (event journal + publisher) and the pattern is composable using CatchUpSubscriber. Adding an outbox would impose transactional coupling between the event store and a message broker — limiting consumer choice.

4. Do NOT add multi-leader replication

Book: DDIA Ch. 5
Why not: Multi-leader replication introduces write conflict resolution, which is a domain decision. The library's optimistic concurrency model is single-leader per aggregate. Multi-leader would require conflict resolution strategies (LWW, CRDTs, custom) — a framework concern, not a library concern.

5. Do NOT enforce a single storage engine

Book: DDIA Ch. 3
Why not: B-trees (SQL) and LSM-trees (Pebble) have different tradeoffs. The library supports both, plus memory and Turso. Forcing one would eliminate valid deployment scenarios. DDIA explicitly argues that no storage engine is universally best.

6. Do NOT add a schema registry service

Book: DDIA Ch. 4, Designing Event-Driven Systems
Why not: Schema validation is opt-in middleware (schema.Validator with RegisterType[T]()). Events are self-describing (encoding stamps). A centralized registry service would impose operational burden and coupling. The library's approach (upcasters on read, validation on publish/subscribe) is sufficient.

7. Do NOT add a god aggregate / OO aggregate root

Book: Implementing DDD, CQRS and ES
Why not: ADR-0001 explicitly chose pure functions (Decider[State]) over a 9-method OO aggregate root interface. Pure functions are easier to test, compose, and reason about. The OO aggregate root pattern couples domain logic to infrastructure (loading, saving). The decider pattern separates them.

8. Do NOT couple projections to aggregate state

Book: CQRS/ES books
Why not: Projections handle events, not aggregate state. This is deliberate: events are the contract, state is an implementation detail. Coupling projections to state would make state changes break projections and vice versa. The projection.Projection.Handle(ctx, evt) interface takes events.

9. Do NOT add a saga framework

Book: CQRS/ES books
Why not: Sagas emerge from bus.SubscribeAll + command dispatch. The deriver module provides the building blocks (Then, Filter, Idempotent). Adding a saga framework would impose a state machine abstraction, conflict resolution, and compensation semantics — all of which are domain-specific decisions. The docs correctly note: "No dedicated saga module. Multi-step orchestration emerges."

10. Do NOT add a Kafka/stream processing engine

Book: Designing Event-Driven Systems
Why not: projectionhost is a simple, correct stream processor (read from journal, process, checkpoint). A full stream processing engine (windowing, watermarking, stream joins) would be over-engineering for an application-level CQRS library. Consumers needing Kafka-scale streaming use Kafka + the Watermill adapter.

11. Do NOT add log compaction to the event store

Book: DDIA Ch. 11, Designing Event-Driven Systems
Why not: Log compaction (keeping only the latest value per key) destroys the audit trail. In event sourcing, ALL events matter — they are the business record. Snapshots are the correct optimization (avoid replay cost without losing data). Compaction would violate the fundamental premise of event sourcing.

12. Do NOT add an opinionated transport / API gateway

Book: Service Design Patterns
Why not: The library provides transport helpers (SSE, gRPC) but does not enforce HTTP, gRPC, or any specific protocol. Consumers choose their transport. Adding an API gateway or enforcing REST maturity would violate "library, not framework" and limit deployment options.

13. Do NOT add data lakehouse / data fabric patterns

Book: Deciphering Data Architectures
Why not: This is an application-level CQRS library, not a data platform. Data warehouse, lakehouse, and fabric patterns solve a different problem (analytics at scale across organizational data). The library's projections are operational read models, not analytical datasets. Mixing these concerns would dilute the library's focus.

14. Do NOT add leader election or quorum protocols

Book: Patterns of Distributed Systems
Why not: Leader election and quorum are for replicated state machines (Raft, Paxos). go-cqrs-lite's event store is not replicated at the library level — replication is a storage backend concern (Postgres replication, Pebble WAL replication). Adding leader election would impose a specific replication model.

15. Do NOT add fencing tokens / generation locks

Book: Patterns of Distributed Systems
Why not: Fencing tokens prevent stale leaders from writing after a partition heals. This is a deployment/orchestration concern (Kubernetes leases, etcd locks). The library's optimistic concurrency (expectedVersion) is the application-level fencing — a stale instance's write will fail the version check. Adding deployment-level fencing would mix concerns.

What this analysis reveals about the architecture

DDIA Part III → Event Store (WAL) + Projections (Views) + Schema (Evolution) = go-cqrs-lite

The library is a faithful, well-executed implementation of the most important theoretical insights from these seven books. The 62% application rate (38 of 61) is high considering that many book insights (replication, consensus, data platforms) are intentionally out of scope for a library. The gaps are in ergonomics and documentation, not in fundamental architecture. The "must NOT do" list is a testament to disciplined design — the library correctly refuses to be a framework.
