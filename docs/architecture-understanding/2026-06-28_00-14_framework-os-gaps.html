What's missing to be a superb Event-Sourcing Framework/OS?

Not a list of forgotten features. A deliberate framing of two very different buckets of gaps — one on-mission for a library, one that requires becoming a different product entirely. Verified against the v3.1.0 source.

00The Thesis

The single most important fact about this question: this project is explicitly, repeatedly, deliberately a library/SDK, not a framework (AGENTS.md principle #1, the repo's own warning table, the litmus test “Would ANY Go app potentially use this?”). Almost everything perceived as “missing” is not an oversight — it is the consequence of that choice. Frameworks and operating systems own a runtime and a control plane; libraries provide importable primitives.

Two buckets, two destinies

Split the gaps cleanly. Bucket A = composable building blocks a complete library could still ship (embed-in-process, no opinionated server). These are on-mission and high-leverage. Bucket B = a runtime process + a control plane — the things that make something an “OS.” Shipping these means crossing the line the project refuses to cross, which is exactly why they're absent.

♦What's already genuinely superb

A credible answer must first acknowledge what's done well, because much of the “framework” surface is already here and best-in-class for Go.

+
Primitive surface is best-in-class Immutable events (concrete alias, zero-copy reads), branded IDs, ISP-split store/bus interfaces, SeekableJournal, BackwardsSource, tombstone soft-delete, causality/correlation, time-travel loads, streaming sources.
+
Real multi-backend storage Postgres / SQLite / Turso / Pebble + KV + SQLViewStore + RelationalProjection + a new graph/ tier. Not just an interface — working implementations with optimistic concurrency.
+
Auto-documentation is rare and excellent catalog → AsyncAPI / OpenAPI / D2 / EventCatalog / docs-server from the same registry. Most ES libraries have nothing like this.
+
Security primitives baked in Signing (HMAC/Ed25519/multisig), encryption (XChaCha20/AES-GCM/HKDF), schema upcasting + validator, error taxonomy, defensive clones everywhere.
+
Observability + transport + tooling OTel re-exports, Prometheus bridge, Watermill adapter, SSE (Last-Event-ID reconnect), gRPC, cqrs-gen / api-stability / doc-check tooling.
Verdict so far. As a library of ES primitives, this is arguably the most thoughtfully architected in the Go ecosystem. The hard parts are solved. What's missing is not more primitives — it's the tier above them.

02Bucket A — Library-tier gaps (on-mission)

These could ship as composable modules and the project would still be a library. Each removes a chunk of hand-rolled glue a consumer currently writes themselves. Ordered by leverage.

Highest leverage

A1. Managed Projection Host (runtime/ or revive projection/)

ADR-0030 deleted the projection module; watermill/catchup_subscriber.go + stack/materialize.go are the raw pieces

Today every consumer hand-assembles CatchUpSubscriber + Projection + checkpoint + lifecycle. There is no batteries-included host that does: per-projection goroutines, crash auto-restart with exponential backoff, health/liveness exposure, ordered vs parallel routing policy, and graceful drain on shutdown. This is the single component that turns a library into an ES runtime — Marten's “async daemon” and Axon's tracking-event-processor are exactly this. It is still embeddable in your own process, so it stays a library.

Why it's the #1 gap. It is the last “loop” every consumer rewrites, and it's where production failure modes (restart storms, lost checkpoints, ordering bugs) live.
Strong

A2. Transactional Outbox (outbox/)

0 outbox references in *.go; docs/outbox-explained.html argues the relay replaces it

The dual-write problem is real: Repository.Execute saves to the store and publishes to the bus as two separate operations. A crash between them means an event is persisted but never published until a relay notices it. The CatchUpSubscriber is a subscriber-side relay; an outbox is the publisher-side atomic guarantee (write the outbox row in the same TX as the aggregate, a relay drains it). The project chose relay-over-outbox to avoid a secondary table — a defensible call, but it is the textbook “reliability” gap a superb framework closes.

Strong

A3. Command Idempotency (idempotency/ or a middleware)

grep idempoten|dedup: dedup exists at the event tier (CatchUp, SSE) and projection sinks; nothing on the command path

Delivery is at-least-once. With no command-id / idempotency-key dedup, a retried command produces duplicate events and duplicate side effects. A small idempotency-key store + a command middleware (check-seen, store-result-on-success) is a classic framework primitive that's small to build and large in value.

Strong

A4. Dead-Letter / Poison-Message sink

0 DeadLetter|DLQ|poison matches in *.go

A projection that repeatedly fails on one event will either block the stream or skip it forever. A DLQ wrapper (capture failing event + error to a store, advance checkpoint, expose for replay) is essential operability. Pair it with the Projection Host (A1).

Nice multiplier

A5. Scenario-testing DSL (testing/)

“toward-perfect” flagged AggregateTester/ProjectionTester/BusTester as thin; eventtest exists but no fluent harness

A first-class decider.Given(evts...).When(cmd).Then(expected, state) harness and a projection-replay assertion kit. The decider has property tests, but no consumer gets a one-liner BDD scenario harness. This is the “DX multiplier” that makes adoption stick.

Nice multiplier

A6. Scheduled commands / durable deadlines (scheduling/)

no scheduler; common ES need (“cancel order after 30 min unpaid”)

A durable timer store (events written at a future time, a dispatcher polls them) is a primitive, not a runtime. It unlocks time-based business logic that today every consumer bolts on with cron + an external queue.

03Bucket B — Runtime/OS gaps (a different product)

These exist only as a running process with a control plane. Shipping them violates principle #1. The honest move is a sibling product (as EventStoreDB relates to a client SDK), not bolting a server onto this repo.

B1. Control-plane CLI (cqrsctl)

Rebuild a projection, list aggregates, inspect checkpoints, replay/reset, view lag. cqrs-gen is codegen only — there is no operational CLI.

B2. Admin / ops dashboard

Only a docs server exists (catalog/docserver). No live ops UI: event browser, aggregate inspector, projection-lag graphs, replay trigger. A design doc exists; no code.

B3. Replication / clustering / consumer groups

Single-node only. DistributedRunner gives leader-election active/passive failover — not partitioned reads, competing consumers, or a sharded event store. This is the “OS” scale tier.

B4. Log compaction / archival lifecycle

Streams grow forever. Compaction, truncation, and S3/GCS archival are raw ideas with design docs and no code. An OS manages its own log lifecycle.

B5. Cross-service schema-registry service

schema.Validator enforces at publish + load time in-process. A superb OS runs a contract registry with BACKWARD/FORWARD/FULL compatibility checks and version negotiation across services (Confluent-style). That is a server, not a library.

The line you must not blur. Mixing B-tier features into this repo is how a clean library becomes a half-framework nobody trusts. Keep the library pure; build the runtime as a separate, optional product that consumes these primitives.

05Pareto roadmap (20% effort → 80% of “superb”)

Ordered for compounding impact. The first three deliver most of the perceived “framework” feel while staying a library.

1

Ship the Projection Host (A1)

Wrap CatchUpSubscriber + Materialize + checkpoint into a managed host: restart, backoff, health, graceful drain, DLQ hook. This alone closes the biggest gap and is still embeddable.

impact: huge · effort: medium · stays a library: yes

2

Add the DLQ + Idempotency pair (A3 + A4)

Small primitives, disproportionate reliability win. Both are middleware/sinks that compose into the host from step 1.

impact: high · effort: low–medium · stays a library: yes

3

Optional Outbox sink (A2)

Offer it as an opt-in EventSink for the shared-DB case; keep the relay as the default. Let consumers pick atomicity vs. no-secondary-table.

impact: high (for those who need it) · effort: medium · stays a library: yes

4

Scenario-testing DSL (A5)

Fluent Given/When/Then for deciders, projections, buses. The adoption multiplier.

impact: medium–high (DX) · effort: low · stays a library: yes

5

Draw the product line, then maybe build a sibling runtime (B1–B2)

Do not add a server/dashboard to this repo. If “OS” is the goal, start a separate go-cqrs-runtime (or similar) that embeds this library and adds cqrsctl + dashboard + replication. Keeps the library trustworthy and the runtime optional.

impact: transforms the product · effort: large · stays a library: no — new product

06Strategic verdict

As a library, it's already superb — finish Bucket A.

The missing piece is not “more ES primitives.” It is the managed projection host plus the reliability trio (DLQ, idempotency, optional outbox). Build those four and consumers can assemble a complete, production-grade ES system using only library modules, with zero hand-rolled infra loops. That is the legitimate ceiling for a project that insists on being a library.

“OS” is a different company.

The control plane, dashboard, replication, and log-lifecycle services are what make EventStoreDB a product. They cannot be a module here without breaking the library's core promise. Pursue them only as a deliberate, separate bet — and only if a concrete consumer need outgrows single-machine. Until then, “single-machine is sufficient” is the correct, honest position the project already holds.
