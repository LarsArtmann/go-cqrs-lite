Metaengine: How close to the "deployer-decides" goal?

Evidence-based assessment of the metaengine/ module against Lars's stated goal: consumers declare Commands + Events + Queries; the deployer picks infrastructure; the optimizer builds superb projections. Verdict: the engine is research-grade and feature-complete on the optimizer side, but the developer/operator ergonomics gap is the binding constraint on the goal.

00Verdict

The metaengine is the strongest, most ambitious part of go-cqrs-lite and is genuinely novel: a cost-based optimizer that distributes event-sourced projections across N heterogeneous engines at deploy time. The optimizer itself largely delivers the goal. What does not yet deliver the goal is the layer above the optimizer: the developer/operator API. The flagship example proves it — to use the metaengine today the consumer writes ~140 lines of taskEventDecoder, hand-wraps every event in eventWithID[P], opens the *sql.DB itself, and hardcodes the engine list. That is the opposite of "the deployer decides; the consumer declares query patterns only."

The bottom line Optimization engine: ~90% to the goal. Developer/operator ergonomics: ~40%. The single highest-leverage next step is an operator-driven engine path (bundle supplies engines, consumer never touches *sql.DB) plus folding the event-decoder into the declaration. Harvested to ROADMAP.md → Theme 1.

◆What's already excellent

These are real, verified capabilities — not aspirational. Each maps directly to a clause of the goal.

+
5 cross-parity engines, dependency-isolated Memory, SQLite, Pebble, DuckDB, Postgres — each its own module so a consumer who imports one never pays for the others' deps (CGo for DuckDB, pgx for PG, Pebble for LSM). adttest.RunMatrix enforces 10/10 ADT parity.
+
The fold-return-type-IS-the-ADT insight Developers never write "I need a Map." func(e)(K,V) → Map, func(e) Delta → Counter, etc. This is the cleanest realization of "declare intent, not mechanism" in the codebase.
+
Typed filter/sort with real pushdown FilterOnField/SortOnField become SQLite json_extract(), PG JSONB ->>, DuckDB json_extract() WHERE/ORDER BY — O(logN) not O(N). Pebble gets a secondary index (108x) and sort index (1,233x).
+
"Recommendations" exist — as diagnostics The goal asks for storage recommendations. store.ExplainPlan(), store.Doctor(), degradation WARNs, scale-threshold WARNs, and write-amp budgets are exactly that — advisory, not silent.
+
Materialize-vs-replay: the ES-specific killer feature Because the source of truth is an event log, the planner can advise whether to materialize a projection or replay on read. No general-purpose DB planner can do this.
+
SQLite+Memory minimal path works The taskmanager example runs end-to-end on Memory + SQLite — one clause of the goal ("run fully with just SQLite + Memory") is met today.
+
Replication model laid (DDIA Ch5) Replication/ReplicationLag/NetworkRTT on EngineProfile + replicationRule diagnostics. Foundation for the Iroh distributed engine (ADR-0096) and the multi-machine deployments the goal implies.

01Where the goal is NOT yet met

Ordered by impact on the stated goal. Each cites the evidence in the flagship example.

Blocking · High impact

The consumer, not the deployer, picks and wires the infrastructure

example/taskmanager/setup.go:83-102 · metaengine.go:163-193

The goal: "consumers should NOT decide on infrastructure … the person deploying the App decides." Reality: setupMetaEngine calls sql.Open("sqlite", dsn), sets WAL/busy_timeout pragmas, SetMaxOpenConns(1), constructs metaengine.NewSQLiteEngine(meDB), and hardcodes []Engine{NewMemoryEngine(), sqliteEng} into Plan(). stack.WithMetaEngine only registers an already-built store for Close + benchkit discovery. Swapping Memory→Pebble requires editing consumer code, not config. There is no operator config/registry at all. 

// What the consumer writes today (example/taskmanager/setup.go)
meDB, _ := sql.Open("sqlite", dsn)
meDB.SetMaxOpenConns(1)
for _, p := range []string{"PRAGMA journal_mode=WAL", "PRAGMA busy_timeout=5000"} { meDB.Exec(p) }
sqliteEng, _ := metaengine.NewSQLiteEngine(meDB)
store, _ := metaengine.Plan([]metaengine.Engine{metaengine.NewMemoryEngine(), sqliteEng}, ...)
Fix direction A stack.WithMetaEngineQueries(queries...) path where the Bundle (which already owns the backend/DSN) supplies the engine list from its own capabilities, and the consumer passes only query declarations. The deployer's preset choice (sqlite.New vs pebble.New) then decides engines with zero consumer-code change.
Blocking · High impact

The event→projection bridge is hand-written per event type

example/taskmanager/metaengine.go:75-151 (taskEventDecoder, 77 lines)

The goal: "knowing ONLY the Commands + Events + Queries … build superb projections." But the consumer maintains a second source of truth about every event type — a 77-line switch that re-decodes each payload and wraps it in eventWithID[P]{ID: evt.StreamID(), Payload: p}. The fold handlers (metaengine.go:200-299) already encode event→view logic; the decoder duplicates that event knowledge. Adding an event means touching two places, and the ID-from-StreamID wrapper is pure boilerplate (the entity key for an event-sourced Map is always the stream ID).

Fix direction Let fold handlers be keyed by the CQRS event-type string and receive the raw payload + stream ID directly (the onTyped helper is a local workaround for this exact gap). An EventDecoder that defaults to "JSON-unmarshal into the fold's sample type + attach StreamID" removes the parallel switch for the common case.
Important · Medium impact

The vision's declarative projection API (projection.Declare) does not exist

docs/planning/meta-engine-design.md:6-9, 385-411 · shipped: metaengine.Query

The design doc is explicit: projection.Declare[V,K]("users", …, projection.Lookup(), projection.Filter("status"), projection.Sort("joined_at"), projection.Count("status")) and generated accessors store.Users.ByStatus() are NOT shipped. What shipped is the lower-level metaengine.Query[Input, Result]("name", folds..., FilterOnField(...), SortOnField(...)) + reflective ExecuteTyped[In,Out]/TypedReader[V].Scan. Powerful, but more mechanism than the "declare operations, get typed accessors" vision. metaengine-gen (ROADMAP) would close the accessor half.

Important · Medium impact

Only 1 of 3 examples uses the metaengine

example/getting-started, example/readme-quickstart

getting-started uses stack.NewMaterialize + kv.MemStore; readme-quickstart uses no projection at all (replays the aggregate). If the metaengine is "THE STRATEGIC FUTURE," the on-ramping example teaches the older, more boilerplate-heavy Materialize path instead. New consumers learn the pattern the goal is meant to replace.

Nice to have · Low impact

Multi-SQLite-DB goal clause: stack has it, metaengine re-opens its own DB

stack multi-DB (WithEventDB/WithQueryDB/WithViewDB) vs example/taskmanager/setup.go:167

The goal explicitly wants "multiple SQLite DBs e.g. 1 for Command+ES, 1 for Query logs, 1 for materialized views." The stack supports this, but the metaengine bypasses it and opens its own separate connection to the same DSN. Not wrong (separate tables: meta_map, meta_counter), but the metaengine isn't a first-class citizen of the multi-DB layout.

02How well is the metaengine integrated?

Honest answer: lifecycle-deep, semantically-shallow.

Integration edge Depth Evidence
metaengine → stack.Bundle Lifecycle only WithMetaEngine registers a pre-built Store for Close + benchkit. No auto-wiring of engines from the bundle's backend.
metaengine → projectionhost Functional projectionadapter wraps Store as projection.Projection; used in taskmanager. Works, but the EventDecoder is manual.
metaengine ↔ event Manual bridge Consumer writes the decoder switch. No first-class "fold by CQRS event type + StreamID" path.
metaengine → catalog/docs Deferred (YAGNI) ROADMAP: catalogbridge deferred until a consumer asks. Query collections are undocumented in OpenAPI/AsyncAPI.
metaengine → benchkit Auto-discovered Bundle.MetaEngine() accessor; benchkit measures Apply throughput + ExecuteTyped latency.
Examples adoption 1 of 3 Only taskmanager. The two on-ramping examples teach different (older) read-model patterns.
Interpretation The metaengine is wired in enough to run, but not enough to realize the goal. The integration is "consumer does the wiring, bundle closes it." The goal wants "deployer does the wiring, consumer declares intent." That inversion is the work.

03Target state (the goal realized)

If the binding-constraint gaps close, consumer code shrinks from ~150 lines of wiring to this: 

// CONSUMER declares ONLY events, queries, and folds.
type TaskCreated struct{ ... }
type TaskView struct{ ... }

taskViews := metaengine.Query[ListTasks, TaskView]("task_views",
    metaengine.OnEvent("task.created", TaskCreated{},    // keyed by CQRS type string
        func(s id.StreamID, e TaskCreated) (string, TaskView) { return s.String(), TaskView{...} }),
    metaengine.OnEvent("task.deleted", TaskDeleted{}, metaengine.Remove[TaskView]()),
    metaengine.FilterOnField[TaskView]("status", metaengine.FilterEq),
)

// DEPLOYER picks the preset (one line). Bundle supplies engines from its backend.
bundle, _ := sqlite.New(dsn,
    stack.WithMetaEngineQueries(taskViews, taskCounts), // no *sql.DB, no engine list
)
host.Register(bundle.MetaEngineAdapter())              // adapter built from the bundle
This is the target The consumer never imports database/sql, never constructs an engine, never writes an event decoder. The deployer's sqlite.New vs pebble.New vs a future multi-engine registry decides where data lives. That is the goal, verbatim. Two design pieces unlock it: (1) OnEvent(typeString, sample, fn) that injects StreamID; (2) WithMetaEngineQueries that derives engines from the bundle.
