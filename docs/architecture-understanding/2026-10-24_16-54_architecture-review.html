Architecture review · modularity & service orientation

Strong bones, one god package, and two architectures at once

101 Go modules with zero production import cycles and an enforced layer gate. The structural debt is concentrated in two places: a single metaengine package that carries 13% of the entire exported API, and a v4/v5 dual track that makes every fix a two-copy decision.

00Verdict

Measured against the seven-dimension rubric, go-cqrs-lite is a good architecture with two structural bills coming due. The parts that usually rot first have not rotted: there are zero production import cycles across 101 modules and 322 production edges, the module-layer gate passes (scripts/check-module-layers.sh, 100 layer entries), and the domain tier imports nothing but Tier 0/1 primitives (the vocabulary modules event, command and query each import only dispatcher, id, metadata and record; decider reaches upward only to snapshot and the zero-dependency otel facade). Composability is genuinely best-in-class: a new engine is a module plus init() -> metaengine.RegisterDriver, and a new read model is a fold declaration.

The bills are cohesion and dual-track cost. One package, metaengine, holds 166 production files, 27,701 LOC and 829 exported symbols, which is 13% of the entire tracked API in a single Go package, spread across nine separable concerns. And the repo is now maintaining two architectures: v4 (101 modules, 214 // Deprecated: markers) and v5 (core/v5, 9 of 32 packages), with byte-identical mirror twins such as event and core/v5/event both exporting exactly 253 symbols.

The bottom line Do not start another structural program in v4. Make the v5 package split the only structural program (metaengine as five packages, memory engine as its own module), keep v4 fix-only, and ship the missing cqrs-upgrade --to-v5 import rewrite so the 23 remaining copy-forwards actually reach the fleet. That converts duplicate maintenance into a one-time migration instead of an endless tax.

03What is already excellent

+
Zero production import cycles, mechanically enforced 322 production edges over 101 modules, no cycle. The one layer-gate script parses every go.mod and rejects upward dependencies; it currently reports "Module layer check passed" (100 layer entries).
+
Dependency direction is textbook Domain modules import only Tier 0/1: event -> dispatcher, id, metadata, record; command and query mirror that. Telemetry goes through the zero-dependency otel facade, so no domain module imports OpenTelemetry.
+
Capability interfaces instead of fat interfaces 225 exported interfaces, and the load-bearing ones are optional capabilities the planner probes: AtomicAppender, Transactional, EngineResetter, DedupStore, DueClaimer, FactSink, Prober, VectorPathReporter.
+
A real composition root, not a god New() system.New(DomainConfig, DeploymentConfig) enforces the consumer/operator split: the consumer never touches infrastructure, the operator never writes domain code. The coeffect gate (DomainConfig.Events) and the safety check run before wiring.
+
Plugins are the design, not an afterthought 11 engine modules plus the in-core memory engine, each dependency-isolated (CGo only for DuckDB, heavy clients only where needed), each registering itself with init(). Consumers that import one engine never pay for another's dependencies.
+
Wrapping that cannot silently drop capabilities event.DecorateStore / event.DecorateJournal with sink/source transforms replaced hand-written wrappers (which had already lost MultiSink and StreamingJournal once). This is the right fix for a whole bug class.
+
One wire vocabulary across modules event.Type, command.Type and query.Type are aliases of record.Type, pinned by cross-type comparison tests. The classic event-vs-command split brain is gone.
+
Verification depth that most libraries never reach 1,783 test files against 1,764 production files; an API golden (6,301 symbols), a duplication gate, a file-size ratchet, an error-taxonomy drift gate, a doc gate that fails on any warning, and 207 cqrs-lint rules for consumers.
+
Deletion discipline exists and is exercised transport/http, transport/grpc and idempotency/kvstore were deleted at zero fleet consumers (ADR-0152 addendum), with pinned tags left resolvable and migration notes written. That is rarer than any feature on this list.

04Findings

Critical · cohesion

One package holds nine concerns and 13% of the entire API

metaengine/ (166 production files, 27,701 LOC, 829 exported symbols)

The metaengine root package contains the engine contract, the registry, the health/quarantine machinery, the cost planner, the layout/calibration logic, the execution runtime, the store and collection layer, the fold inference, the ADT implementations (vector, graph, spatial, as-of), the SQL scan and dialect helpers, the diagnostics surface, the typed readers, and the memory engine itself. Cluster counts from file ownership: store/collections/folds 48 files, engine contract 28, planner 16, execution 16, diagnostics 13, ADTs 13, SQL helpers 11, memory engine 8, and 13 residual files (types, error vocabulary, capability adapters). All of it shares one namespace and one 829-symbol stability promise.

Two symptoms prove this is not cosmetic. First, the only engine that lives inside the core is the memory engine (memory_*.go), while the other eleven are dependency-isolated modules; the asymmetry exists because the package boundary is the module boundary. Second, every consumer that imports metaengine to touch one fold or one engine profile inherits the whole surface in godoc, and every internal change regenerates a golden entry inside the largest block of docs/api_surface.txt.

Fix: split in v5, not in v4 Create core/v5/metaengine/{engine,plan,exec,collection,diagnostic} with an enforced rule (collection -> engine <- plan/exec, diagnostic on top, nothing depends on it), move memory_*.go to metaengine/memoryengine, and cap packages at ~300 exported symbols. Doing this in v4 would be a breaking change with no consumer benefit; doing it in v5 costs one migration and prevents a second re-split later.
Important · dual track

Two architectures are being maintained at once, and the bridge does not exist

core/v5 (9 of 32 packages) · 214 Deprecated markers · cmd/cqrs-upgrade

core/v5 mirrors record, id, dedup, kv, dispatcher, metadata, event, command and query by hand. The mirrors are byte-identical in surface: event and core/v5/event both export 253 symbols, id and core/v5/id both 94. The 23 missing packages include every load-bearing one: decider, middleware, system, metaengine, storage, projectionhost. Meanwhile cmd/cqrs-upgrade has no core/v5 awareness at all, so even a completed fork could not be adopted by the ~35 fleet repos without hand edits.

The cost is not theoretical: every bug fixed in a mirrored package must be fixed twice or consciously dropped on one side, and every new feature forces that same decision. 214 // Deprecated: markers show how much surface is already scheduled to disappear.

Fix: fork less, migrate more Freeze v4 structurally (fix-only), finish the copy-forwards in the post-split package shape, and make cqrs-upgrade --to-v5 the gating deliverable: rewrite imports, bump pins, and report decorator/config changes. Until that exists, the v5 fork is pure cost with no consumer.
Important · gate health

The file-size ratchet is red right now

scheduling/sqlstore/store.go:363 (382 an hour later, in flight) · system/adapter_event.go:351 · metaengine/layout.go:360

bash scripts/check-file-size.sh reports three new offenders against the 350-line maximum, all committed on 2026-10-23 and 2026-10-24 by the auto-commit daemon. The gate fails, which means #verify and CI are red for reasons unrelated to any feature. A ratchet that is allowed to stay red stops being a ratchet: the next contributor learns that red is normal.

This is also the cheapest possible proof of the review's own thesis: the offenders are small, the fixes are mechanical, and leaving them open is a choice. One of them grew by 19 lines while this review was being written, which is what an unguarded gate buys you.

Fix: split the three files before anything else 363, 351 and 360 lines at measurement: each needs one extraction. Small effort, immediate green, and it restores the "green means green" contract that every other gate depends on.
Important · gravity

The largest module in the library is now a linter

cmd/cqrs-lint: 48,721 production LOC · catalog: 22,246 · analyzer package: 187 symbols

Tooling and documentation machinery is 32.8% of production LOC. cmd/cqrs-lint alone is 1.4x the size of metaengine and 7x system. That is a maintenance-unit problem, not a module problem: the repo's review attention, CI budget and release coordination are shared between a runtime SDK and two developer tools that have independent lifecycles and independent consumers.

Fix: separate product lines Move cmd/cqrs-lint and the catalog exporters into their own repositories (or at minimum a tools/ product line with its own release cadence and CI triggers). The core keeps thin gates; the tools stop competing with the SDK for structural care.
Medium · API economics

6,301 exported symbols, all equally promised, with no stability tiers

docs/api_surface.txt · 82 tracked modules · median 69 symbols per module

The API golden treats every exported symbol as a compatibility promise, which is admirable and correct for a library. But it makes no distinction between the ten symbols a consumer actually calls (system.New, RegisterDecider, Lookup, QuerySet, Evolution, decider.Execute) and the 829 inside metaengine that are mostly planner and engine machinery. The metaengine family carries an "# Experimental" doc stamp, but the golden and the release rules do not encode that difference, so the stamp is advisory only.

Fix: make stability structural Split the golden into a stable-core set and an experimental set, derive it from the package layout after the metaengine split, and let release policy follow the sections. A doc stamp that the tooling ignores is a comment; a golden section is a contract.
Medium · release scale

101 modules means 101 version trains to coordinate

100 layer entries · 112 published trains in versions.json · 92-tag release waves

Adding or removing a module requires six registration points (go.work, flake testModules, api-stability list, module layers + dependency budget, cqrs-lint module catalog, versions manifest). Releases happen in tag waves (a recent one was 90 tags), and batch-release.sh's verify=ok builds but does not test, so a wave's real verification is a separate per-module sweep. None of this is wrong; it is simply the price of one module per engine and per concern, and the price grows with every split.

Fix: collapse the domain core, keep drivers separate v5's one-core-module shape is the right answer: one train for the domain, eleven for the drivers, separate trains for products. Also retire the require-dead presets (8 of the 9 stack/* presets have zero fleet requires; only stack/sqlite is used) instead of carrying them.
Low · duplication hygiene

The accepted-clone baseline is large, and templ files cannot opt out

.art-dupl-baseline.json: 189 accepted groups

The concentration is where you would predict: pgengine (9 groups), badgerengine (7 + 6), metaengine/memory_stream_log.go (6), duckdbengine (5), mysqlengine/vector.go (5). Most are deliberate dialect seams, several carry //art-dupl:accept directives, and templ files cannot carry directives at all (HTML comments do not parse), so three docserver templ groups live permanently in the baseline.

Fix: annotate on touch, document the seam Keep the engine clones, add directives when a file is touched anyway, and write one short "dialect seam" note per engine family so the next reader knows the duplication is a decision rather than an accident.

Split-brain audit

Eliminated: type vocabulary

event.Type, command.Type and query.Type are aliases of record.Type, and the lockstep tests compare across modules. This was a real split brain two years ago and is now structurally impossible.

Deliberate but time-bounded: v4 vs v5

The fork means every mirrored package exists twice. Within a package the design is single-sourced; across v4/v5 it is not. The exit is the codemod plus the remaining copy-forwards, not a change of mind.

Two persistence vocabularies, both legitimate

Event streams (event + storage adapters) and planner-managed collections (metaengine) are two models of storage coexisting. This is documented (docs/architecture-understanding/ANALYTICAL-VS-TRANSACTIONAL.md) and is a strength, but it is the first thing a new contributor misreads.

"Engine" means two different things

metaengine.Engine is a storage backend; scheduling/engine is a TimerStore facade, and scheduling/engine is a module while metaengine/engine.go is a file in a package. Cheap to fix in DOMAIN_LANGUAGE.md, expensive to leave ambiguous.

07Scale and service shape

This is a library, so "service orientation" means: does each module own its data and contract, and could it be extracted or deployed independently if the consumer needed it? The answer is mostly yes, with one honest caveat.

Scale axis Verdict Evidence
New feature (new read model) Excellent a fold declaration plus an Evolution; no new package
New backend Excellent new module + init() registration; 11 exist
Traffic / data growth Good cost planner, health quarantine + reprobe, calibration, reset-and-replay ladder
API growth Strained 6,301 symbols, one undifferentiated golden, 214 deprecations pending removal
Team / contributor growth Strained 101 module boundaries, six registration points per module, tag-wave releases
Deployment independence Good engines and drivers are separate modules, but core and tooling share one repo and one release process
The service-orientation read Module boundaries align with bounded contexts far better than most libraries of this size manage. The weakness is not conceptual coupling; it is that the maintenance unit (repo, CI, release train) is one mixed bag of runtime core, linter, and docs renderer. Splitting the product lines would raise this dimension more than any code change.

09Action roadmap

Ordered by leverage and by dependency, not by enthusiasm. Steps 1-2 are days; steps 3-6 are the v5 program; 7-9 are what makes the result stay good.

1

Make the quality gate green again P0 · S

Split scheduling/sqlstore/store.go (363), system/adapter_event.go (351) and metaengine/layout.go (360) to 350 lines or fewer. Nothing else in this roadmap matters while #verify is red. Dependency: none. Verification: bash scripts/check-file-size.sh exits 0.

2

Declare v4 a fix-only line P0 · decision

No new packages, no new exported symbols, no structural splits in v4. Every structural change goes into core/v5. This is a one-paragraph decision with zero implementation cost, and it is the precondition for steps 3-6 not being done twice.

3

Split metaengine into five v5 packages P1 · L

engine (SPI, registry, capability audit, health), plan (cost, layout, calibration, replan), exec (execute, dispatch, tx, SSE, catch-up), collection (store, folds, ADTs, cursors, typed readers), diagnostic (explain, doctor, DX). Rule: collection -> engine <- plan/exec, diagnostics on top only. Cost driver: the 48-file store/collection cluster must be moved without dragging the other four. Dependency: step 2.

4

Extract the memory engine P1 · S-M

Move memory_*.go (8 files) to metaengine/memoryengine in v5. Symmetry is the point: it removes the last reason for a driver to live inside the core package, and it shrinks the core by 1,382 LOC. Dependency: step 3 (the engine SPI must already be its own package).

5

Ship cqrs-upgrade --to-v5 P1 · L

Import rewrite (/v4 to core/v5/...), pin bumps, decorator and config migrations, and a V007-class report for deleted APIs. This is the difference between a fork and a migration. Dependency: none; can run in parallel with steps 3-4, but must land before step 6's fleet waves.

6

Finish the remaining 23 copy-forwards, then migrate in waves P1 · L

Copy forward decider, middleware, system, storage, projectionhost and the rest in the post-split package shape, then run fleet waves in the documented order: cqrs-htmx (73% of indirect edges), go-appkit (18%), then the app residue. Each migrated repo raises the delete-at-zero counter for its v4 modules. Dependency: steps 3, 4, 5.

7

Split the tooling into its own product line P2 · M-L

cmd/cqrs-lint (48.7k LOC, 207 rules) and the catalog exporters (22.2k LOC) get their own repo or at least their own release cadence and CI triggers. Keep the in-repo gates thin. Dependency: step 6 (tooling must know the v5 module layout before it moves).

8

Tier the API golden P2 · M

Two sections: stable core (composition root, decider, event, command, query, record, id) and experimental (metaengine family, catalog exporters). Derive membership from package boundaries so it cannot drift; let release policy follow the sections. Dependency: step 3 (the split defines the boundaries).

9

Retire the require-dead modules P2 · S

Eight of the nine stack/* presets have zero fleet requires (only stack/sqlite is used). Apply the existing delete-at-zero rule to them and to any module whose census count reaches zero, instead of carrying them into v5. Dependency: step 6 (fleet migration first, so the census is final).

10

Keep the deliberate duplication deliberate P3 · S

Add //art-dupl:accept directives to the remaining engine families when those files are touched anyway, and write a one-page "dialect seam" note per engine family (pg, badger, duckdb, mysql, memory) explaining which duplication is a decision. Also document the two meanings of "engine" in DOMAIN_LANGUAGE.md.
