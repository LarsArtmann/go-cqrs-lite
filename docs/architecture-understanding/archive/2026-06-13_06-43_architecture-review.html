2. Strengths

ISP Split (Sink/Source)

Store = EventSink + EventSource is the single best architectural decision in this codebase. Consumers who only read events never see write methods. This is textbook Interface Segregation.

Layer 0 Zero-Dep Modules

id/, dispatcher/, codec/ have no internal dependencies. They are perfectly composable atoms. This is the Unix philosophy applied to Go modules.

OTel Abstraction Layer

otel/ re-exports OTel types so consumers of event/storage/projection don't need direct OTel imports. This is the right pattern — mechanism, not policy.

Tombstone Over Delete

Soft-delete via metadata is a domain-aligned pattern. Three-state enum (Active/Tombstoned/Undetermined) prevents boolean ambiguity.

3. Issues and Recommendations

Strong command/ Re-exports event.Metadata

Problem: command.Metadata = event.Metadata creates a cross-module type alias. Consumers importing command/ get event.Metadata transitively. This is a module boundary violation.

Solution: Either (a) accept the coupling (it's the same domain concept), or (b) move Metadata to a shared types/ module. Option (a) is acceptable given these are both Layer 1 modules.

Impact: Low — doesn't cause bugs, but violates the "do one thing well" principle slightly.

Explore Reactive Streams Not Wired Into Dispatchers

Problem: EventBus = ro.Subject[Event] exists but the classic event.Bus interface doesn't bridge to it. Consumers must choose imperative Bus or reactive EventBus — no unified API.

Solution: Consider a BridgingBus that implements event.Bus and delegates publish to ro.Subject[Event].Next(). This gives reactive semantics to the imperative API.

Impact: Medium — limits reactive adoption without sacrificing existing API.

Explore 8 Clone Groups (dupl ≥80 tokens)

Problem: encryption/signing share identical base64 decode patterns. storage/ has near-duplicate SQL load methods. encryption/ has identical AES-GCM/XChaCha20 structures.

Solution: Extract shared internal/encoding helper for base64 decode. Parameterize SQL load helpers with operator. The encryption structural duplication is acceptable (algorithm differences justify it).

Speculative Catalog Module Complexity

Problem: catalog/ has 6 sub-packages (asyncapi, openapi, d2, eventcatalog, schema, docserver) plus internal packages. It's the largest module. The Builder and Registry are separate but serve similar purposes.

Solution: Consider splitting exporters into standalone modules if consumers typically only need 1-2 formats. Keep catalog core as registry + types.

6. Summary

go-cqrs-lite is an architecturally excellent Go library. The module boundaries are clean, the dependency graph is a proper DAG, ISP splits are textbook, and composability is first-class. The main areas for improvement are:

  1. command/ type alias coupling — low priority, acceptable as-is
  2. Reactive stream bridging — medium priority, would unify imperative and reactive APIs
  3. Duplication cleanup — low priority, 8 clone groups in non-critical paths
  4. Catalog complexity — speculative, consider splitting exporters
  5. README completeness — missing encryption/turso module sections
