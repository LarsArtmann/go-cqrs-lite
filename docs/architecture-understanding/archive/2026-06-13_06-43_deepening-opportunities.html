Architecture Deepening Opportunities

2026-06-13 · go-cqrs-lite v2.3.0 · 22 library modules

Candidate 1: Shared Base64 Decode for signing/encryption

Files: signing/signature.go, encryption/ciphertext.go, signing/event.go, encryption/event.go

Problem: Both modules implement identical base64 URL-safe→Standard fallback decode in UnmarshalJSON and Extract*() functions. This is a shallow module — the implementation is duplicated, not abstracted.

Solution: Create a shared internal/encoding package (internal to each module, or a new shared module) with DecodeBase64(raw string) ([]byte, error) that tries URL-safe then Standard encoding.

Benefits: Locality — bug fixes in one place. Leverage — both modules get the improvement. Depth — the decode logic gets a deeper, well-tested interface.

Worth Exploring

Candidate 2: Reactive Bus Bridge

Files: event/bus.go, event/reactive.go

Problem: event.Bus (imperative) and event.EventBus = ro.Subject[Event] (reactive) are separate APIs with no bridge. Consumers must choose one. The reactive API is powerful (filter, map, scan) but only available if you abandon the imperative Bus interface.

Solution: A BridgingBus that implements event.Bus and delegates Publish() to ro.Subject.Next() and Subscribe() to ro.Observable.Subscribe(). This gives reactive semantics through the standard interface.

Benefits: Depth — the Bus interface becomes a deep seam. Reactive operators (Filter, Map, Scan) become available to all Bus consumers without API change.

Strong

Candidate 3: Parameterized SQL Load Helpers

Files: storage/event_store_load.go, storage/command_store_load.go

Problem: LoadFromVersion and LoadToVersion are near-identical methods that differ only in SQL operator (> vs <=). Similarly LoadFromTimestamp/LoadToTimestamp. Each pair is 13-15 lines of boilerplate.

Solution: A loadRange(ctx, ref, op string, value any, requireHit bool) helper that takes the operator as a parameter. Public methods become one-liners.

Benefits: Locality — SQL logic in one place. Simpler maintenance. Shallow → Deep.

Speculative

Candidate 4: Catalog Exporter Module Split

Files: catalog/asyncapi/, catalog/openapi/, catalog/d2/, catalog/eventcatalog/, catalog/docserver/

Problem: Catalog has 6 sub-packages. If a consumer only needs AsyncAPI export, they still transitively depend on the D2 and EventCatalog packages (via the catalog root). The module is a bit shallow — the interface is "build catalog, export to format" but the implementation sprawls across 6 packages.

Solution: Keep catalog core (Registry, Builder, Catalog types) as-is. Consider making each exporter its own module: catalog-asyncapi/v2, catalog-openapi/v2, etc. Each depends only on catalog core.

Benefits: Dependency isolation — consumers only import the formats they need. Smaller dependency trees.

Risk: May be over-modularization at current scale. 6 exporter modules is a lot. The sub-packages already provide good isolation within the single module.

Speculative

Top Recommendation

Candidate 2: Reactive Bus Bridge is the highest-impact deepening opportunity. It would:

  • Unify the imperative and reactive event APIs without breaking changes
  • Enable reactive operators (Filter, Map, Scan, Tap) through the standard Bus interface
  • Add depth to the event/ module — the Bus seam would hide significant reactive behavior
  • Align with the Go ecosystem trend toward reactive streams (samber/ro)
