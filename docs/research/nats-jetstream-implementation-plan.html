NATS JetStream
Implementation Plan

Module: jetstream/ · Date: 2026-05-29 · Status: Planning

A native NATS JetStream backend for go-cqrs-lite — replacing both the SQL database and the message broker with a single system. One binary for embedded, one URL for distributed.

Why Native?

The existing watermill/ adapter bridges go-cqrs-lite events to Watermill's message model, which then talks to NATS. A native module eliminates the Watermill dependency and the double-serialization overhead, while unlocking JetStream-specific features (KV for snapshots/checkpoints, direct get, subject-based filtering).

Why JetStream?

One system covers all five go-cqrs-lite storage needs: Event Store (Stream), Snapshot Store (KeyValue), Checkpoint Store (KeyValue), Bus (NATS Core pub/sub), and Journal (Consumer with replay). Embedded or distributed — same Go code, different config.

Part 2

Primitive Mapping: JetStream ↔ go-cqrs-lite

Every go-cqrs-lite operation maps to a concrete JetStream API call. This section defines the exact mapping and the subject/key conventions.

01

Event Store → JetStream Stream

Stream 
Stream name:    "CQRS_EVENTS"
Subjects:       "cqrs.events.{aggregateType}.{aggregateID}"
Retention:      limits (append-only replay)
Storage:        file (or memory for testing)
MaxMsgsPerSubject: 0 (unlimited per aggregate)
Duplicates:     msg-id header = EventID for exactly-once
go-cqrs-lite JetStream API Mechanism
Save(ref, events, version) js.PublishAsync() Optimistic concurrency via stream state check + msg-id dedup
AppendBatch(ref, events) js.PublishAsync() × N Same as Save but skip version check
Load(ref) consumer.Fetch() with filter Ordered consumer on cqrs.events.{type}.{id}.>
LoadFromVersion consumer with start-sequence Map version → stream sequence via subject lookup
LoadToVersion consumer.Fetch() + early stop Read all, filter by version client-side
LoadToTimestamp consumer with start-time=0 + filter Fetch all, filter by timestamp client-side
Subject design: cqrs.events.{aggregateType}.{aggregateID} — subject-partitioned stream. One stream holds ALL aggregates. Per-aggregate reads use consumer with FilterSubject. This avoids N streams for N aggregates.
02

Journal → Ordered Consumer

Consumer 
ReadAll()  → ephemeral ordered consumer, start from seq 1
ReadFrom() → ephemeral ordered consumer, start after mapped sequence
go-cqrs-lite JetStream API Mechanism
ReadAll(ctx) s.Consumer() + Fetch(batch) Ordered consumer from beginning, fetch in batches
ReadFrom(ctx, afterEventID, limit) s.Consumer() + Fetch(limit) Map EventID → stream sequence via GetMsg(), then fetch from seq+1
EventID → Sequence mapping: Store a mapping of EventID → stream sequence in the message header. For ReadFrom, use stream.GetMsg() to find the sequence by EventID stored in header, then create consumer starting from seq + 1.
03

Event Bus → NATS Core Pub/Sub

NATS Core 
Publish subject:  "cqrs.events.{eventType}"
Subscribe filter:  "cqrs.events.{eventType}"
SubscribeAll:      "cqrs.events.>"
go-cqrs-lite JetStream / NATS API Mechanism
Publish(events) nc.Publish() + js.PublishAsync() Dual write: NATS core for real-time delivery + stream for durability
Subscribe(type, handler) js.Subscribe(subject) Push consumer with FilterSubject on event type
SubscribeAll(handler) js.Subscribe("cqrs.events.>") Push consumer on wildcard subject
Use(middleware) Internal handler chain Same pattern as MemoryBus — wrap handlers in middleware
Dual-write strategy: Publish goes to both NATS core (instant delivery to subscribers) AND JetStream stream (durability for replay). Subscribers use push consumers backed by the stream, so they get at-least-once delivery with replay capability.
04

Checkpoint Store → KeyValue Bucket

KeyValue 
Bucket name: "CQRS_CHECKPOINTS"
Key format:  "{projectionName}"
Value:       JSON(eventID + processedAt)
go-cqrs-lite KeyValue API Mechanism
Load(ctx, name) kv.Get(ctx, name) Deserialize JSON → Checkpoint{EventID, ProcessedAt}
Save(ctx, name, cp) kv.Put(ctx, name, json) Serialize checkpoint → JSON bytes, put in bucket
Perfect fit. KeyValue's Get/Put semantics map exactly 1:1 to CheckpointStore. Revision-based Update() is available for CAS if needed later. History is optional (set History: 1 to keep only latest).
05

Snapshot Store → KeyValue Bucket

KeyValue 
Bucket name: "CQRS_SNAPSHOTS"
Key format:  "{aggregateType}:{aggregateID}"
Value:       JSON(snapshot struct)
go-cqrs-lite KeyValue API Mechanism
Save(ctx, snapshot) kv.Put(ctx, key, json) Serialize Snapshot → JSON (ID, Type, Version, State, CreatedAt)
Load(ctx, ref) kv.Get(ctx, key) Deserialize JSON → Snapshot. Return ErrSnapshotNotFound if key missing
LoadAtVersion(ctx, ref, v) kv.Get(ctx, key) Load latest, check version >= requested. Only latest per key.
Delete(ctx, ref) kv.Delete(ctx, key) Soft delete (adds delete marker). Optionally kv.Purge() for hard delete.
LoadAtVersion limitation: KeyValue stores only the latest value per key by default. Setting History: 64 enables historical revisions, allowing kv.History(key) for version lookups — but this is over-engineering. Recommend: store only latest snapshot per aggregate (same as SQLSnapshotStore upsert behavior).
06

Subject & Key Conventions

Convention 
Event Stream subject:  cqrs.events.{aggregateType}.{aggregateID}
Bus publish subject:    cqrs.bus.{eventType}
Checkpoint KV bucket:  CQRS_CHECKPOINTS
Checkpoint KV key:     {projectionName}
Snapshot KV bucket:    CQRS_SNAPSHOTS
Snapshot KV key:       {aggregateType}:{aggregateID}
Convention Pattern Rationale
Stream subjects cqrs.events.*.* Two-level partitioning by type + ID for per-aggregate consumer filtering
Bus subjects cqrs.bus.* Separate namespace from stream — bus is fire-and-forget pub/sub
KV bucket names CQRS_* Uppercase prefix for go-cqrs-lite buckets, avoiding collision with user buckets
KV keys Natural key strings Projection names, aggregate stream keys — human-readable
Configurable prefix WithPrefix("myapp") Default cqrs, configurable for multi-tenant isolation

Part 4

Detailed Interface Implementation

Method-by-method design for each type. Pseudocode showing the JetStream API calls, error handling, and edge cases.

07

StreamEventStore — Save

Step
// Save persists events with optimistic concurrency control func (s *StreamEventStore) Save(ctx context.Context, ref AggregateRef, events []Event, expectedVersion Version) error { // 1. Read current state from stream for this aggregate subject := fmt.Sprintf("cqrs.events.%s.%s", ref.Type, ref.ID) info, _ := s.stream.Info(ctx, jetstream.WithSubjectFilter(subject)) // 2. Count existing messages for this subject (= current version) currentVersion := info.State.Msgs // msgs per this subject if currentVersion != expectedVersion.Int() { return event.WrapConflict(ErrVersionMismatch, ...) } // 3. Publish each event with msg-id for dedup for i, evt := range events { msg, _ := eventToMsg(evt) msg.Subject = subject msg.Header.Set("Nats-Msg-Id", evt.ID().String()) // exactly-once dedup _, err := s.js.PublishMsg(ctx, msg) if err != nil { return event.WrapInfrastructure(err, ...) } } }
Concurrency control: Check stream.Info() with subject filter to get per-aggregate message count. If it doesn't match expectedVersion, return ErrVersionConflict. This is analogous to SQLEventStore's SELECT MAX(version) check inside a transaction.
08

StreamEventStore — Load Methods

Step
// Load returns all events for an aggregate func (s *StreamEventStore) Load(ctx context.Context, ref AggregateRef) ([]Event, error) { subject := fmt.Sprintf("cqrs.events.%s.%s", ref.Type, ref.ID) consumer, _ := s.stream.CreateConsumer(ctx, jetstream.ConsumerConfig{ FilterSubject: subject, DeliverPolicy: jetstream.DeliverAllPolicy, AckPolicy: jetstream.AckExplicitPolicy, }) defer consumer.Delete(ctx) msgs, _ := consumer.Fetch(1024) // batch fetch // Convert msgs → Events, return ErrAggregateNotFound if empty } // LoadFromVersion: start after a specific version // Map version → stream sequence, create consumer with StartSequence // LoadToVersion: fetch all, filter client-side by version header // LoadToTimestamp: fetch all, filter client-side by occurred_at header
Version → Sequence mapping: JetStream sequences are global per-stream, not per-subject. To implement LoadFromVersion, we need a mapping. Options: (a) store version in message header and scan, (b) maintain an in-memory cache, or (c) use stream.GetMsg() to find sequence by version header. Recommend option (a) for correctness — ephemeral consumer fetching all messages for the subject, then skipping until version > requestedVersion.
09

StreamEventStore — Journal (ReadAll / ReadFrom)

Step
// ReadAll returns all events in global order func (s *StreamEventStore) ReadAll(ctx context.Context) ([]Event, error) { consumer, _ := s.stream.OrderedConsumer(ctx, jetstream.ConsumerConfig{ DeliverPolicy: jetstream.DeliverAllPolicy, AckPolicy: jetstream.AckExplicitPolicy, }) // Fetch in batches of 256 until exhausted var all []Event for { batch, _ := consumer.Fetch(256) events := msgBatchToEvents(batch) if len(events) == 0 { break } all = append(all, events...) } return all, nil } // ReadFrom: find sequence by EventID, create consumer from seq+1 func (s *StreamEventStore) ReadFrom(ctx context.Context, afterEventID EventID, limit int) ([]Event, error) { // Search for EventID in message headers // Option A: iterate from start, compare headers (slow) // Option B: maintain EventID→seq index in a KV bucket (fast) // Option C: store EventID in Nats-Msg-Id, use GetMsg (medium) }
ReadFrom strategy: The most efficient approach is Option B — maintain a small KV bucket CQRS_SEQ_INDEX mapping EventID → streamSequence. Every Save/ Publish writes the mapping. ReadFrom looks up the sequence in O(1), creates a consumer starting from seq + 1, and fetches limit messages. This avoids scanning the entire stream.

Serialization — Event ↔ nats.Message

Step
// Headers for event metadata (following watermill/ pattern) "event_id" → evt.ID().String() "event_type" → evt.Type().String() "aggregate_id" → evt.AggregateID().String() "aggregate_type" → evt.AggregateType().String() "version" → fmt.Sprintf("%d", evt.Version()) "schema_version" → fmt.Sprintf("%d", evt.SchemaVersion()) "occurred_at" → evt.OccurredAt().Format(time.RFC3339Nano) "encoding" → evt.Encoding().String() "correlation_id" → evt.Metadata().CorrelationID "causation_id" → evt.Metadata().CausationID "user_id" → evt.Metadata().UserID "request_id" → evt.Metadata().RequestID "source" → evt.Metadata().Source "ip_address" → evt.Metadata().IPAddress "user_agent" → evt.Metadata().UserAgent "custom.{key}" → evt.Metadata().Custom[key] // Payload msg.Data = evt.Payload() // raw bytes, no base64 encoding needed
Direction Function Error Category
Event → nats.Msg eventToMsg(evt) (*nats.Msg, error) Corruption
nats.Msg → Event msgToEvent(msg) (Event, error) Corruption
Event → KV value marshalCheckpoint(cp) []byte —
KV value → Checkpoint unmarshalCheckpoint(data) (Checkpoint, error) Corruption
Key difference from watermill/: NATS messages have native Header support (HTTP-style headers), so metadata goes in headers (not message metadata map). Payload is raw bytes on msg.Data — no double-encoding.

Embedded Server Mode

One of JetStream's killer features: the server can run in-process. Same code for edge/testing and production.

Embedded Server Lifecycle embedded.go

The embedded server is a test/dev convenience — production uses a remote cluster. The module provides helper functions to spin up an in-process NATS server with JetStream enabled.
// NewEmbeddedServer starts an in-process NATS server with JetStream func NewEmbeddedServer(opts ...EmbeddedOption) (*EmbeddedServer, error) { options := &server.Options{ JetStream: true, StoreDir: os.TempDir(), // file-based for durability in tests Port: -1, // random available port NoLog: true, } for _, opt := range opts { opt(options) } srv, err := server.NewServer(options) if err != nil { return nil, err } go srv.Start() // Wait for server to be ready if !srv.ReadyForConnections(10 * time.Second) { return nil, ErrServerStartTimeout } return &EmbeddedServer{ server: srv, url: fmt.Sprintf("nats://127.0.0.1:%d", srv.Addr().(*net.TCPAddr).Port), }, nil } // EmbeddedServer wraps the in-process server type EmbeddedServer struct { server *server.Server url string } func (e *EmbeddedServer) URL() string { return e.url } func (e *EmbeddedServer) Close() { e.server.Shutdown() }
Design decision: nats-server is a test-only dependency — it goes in go.mod with the // indirect tag. Production code only imports nats.go. The embedded.go file uses build tags or is always available (since nats-server is pure Go, no CGO).

Part 6

Event Bus Implementation

The bus is the trickiest component — it must support both real-time delivery and middleware chains, while leveraging NATS pub/sub.

11

Bus — Publish & Subscribe

Bus
type Bus struct { nc *nats.Conn js jetstream.JetStream stream jetstream.Stream prefix string handlers map[Type][]Handler allHandlers []Handler middleware []Middleware pubMw []PublishMiddleware mu sync.RWMutex closed bool cancel context.CancelFunc } // Publish: dual-write to NATS core + stream func (b *Bus) Publish(ctx context.Context, events ...Event) error { for _, evt := range events { msg, _ := eventToMsg(evt) // 1. Persist to stream (durability) msg.Subject = fmt.Sprintf("%s.events.%s.%s", b.prefix, evt.AggregateType(), evt.AggregateID()) msg.Header.Set("Nats-Msg-Id", evt.ID().String()) b.js.PublishMsg(ctx, msg) // 2. Notify via NATS core (real-time delivery) notifySubj := fmt.Sprintf("%s.bus.%s", b.prefix, evt.Type()) b.nc.Publish(notifySubj, msg.Data) // fire-and-forget notification // 3. Dispatch to local handlers (in-process) b.dispatch(ctx, evt) } } // Subscribe registers a handler for a specific event type func (b *Bus) Subscribe(eventType Type, handler Handler) error { b.mu.Lock() b.handlers[eventType] = append(b.handlers[eventType], handler) b.mu.Unlock() } // SubscribeAll registers a handler for all event types func (b *Bus) SubscribeAll(handler Handler) error
Design decision — local handlers only vs. NATS consumers: The simplest v1 implements Subscribe as a local handler registry (like MemoryBus). NATS consumer-based subscriptions are a v2 enhancement for distributed deployments. This matches the library's philosophy: consumers compose their own stack.
12

Bus — Middleware Chain

Bus
// Middleware chain (same pattern as MemoryBus) func (b *Bus) Use(mw ...Middleware) error { b.middleware = append(b.middleware, mw...) } func (b *Bus) UsePublish(mw ...PublishMiddleware) error { b.pubMw = append(b.pubMw, mw...) } // Apply middleware in reverse order (outer-first) func (b *Bus) dispatch(ctx context.Context, evt Event) error { handler := func(ctx context.Context, evt Event) error { // Invoke SubscribeAll handlers first, then type-specific for _, h := range b.allHandlers { if err := h(ctx, evt); err != nil { return err } } for _, h := range b.handlers[evt.Type()] { if err := h(ctx, evt); err != nil { return err } } return nil } // Wrap with middleware (reverse order) for i := len(b.middleware) - 1; i >= 0; i-- { handler = b.middleware[i](handler) } return handler(ctx, evt) }
Middleware reuse: All existing middleware/ module handlers (Logging, Retry, Recovery, Validation, Metrics, OTel Tracing) work out of the box — they operate on event.Handler and event.Publisher, which the Bus implements.

KVSnapshotStore

type KVSnapshotStore struct { kv jetstream.KeyValue closed bool mu sync.Mutex } func (s *KVSnapshotStore) Save(ctx context.Context, snap Snapshot) error { key := fmt.Sprintf("%s:%s", snap.AggregateType, snap.AggregateID) data, _ := marshalSnapshot(snap) _, err := s.kv.Put(ctx, key, data) // kv.Put overwrites existing → upsert behavior (like SQL ON CONFLICT) } func (s *KVSnapshotStore) Load(ctx context.Context, ref AggregateRef) (*Snapshot, error) { key := fmt.Sprintf("%s:%s", ref.Type, ref.ID) entry, err := s.kv.Get(ctx, key) if errors.Is(err, nats.ErrKeyNotFound) { return nil, event.WrapRejection(snapshot.ErrSnapshotNotFound, ...) } return unmarshalSnapshot(entry.Value()) } func (s *KVSnapshotStore) LoadAtVersion(ctx, ref, version) (*Snapshot, error) { snap, err := s.Load(ctx, ref) // Load latest if snap.Version < version { return nil, ErrSnapshotNotFound } return snap, nil } func (s *KVSnapshotStore) Delete(ctx context.Context, ref AggregateRef) error { key := fmt.Sprintf("%s:%s", ref.Type, ref.ID) return s.kv.Delete(ctx, key) // Soft delete (marker) } var ( _ snapshot.SnapshotSink = (*KVSnapshotStore)(nil) _ snapshot.SnapshotSource = (*KVSnapshotStore)(nil) )

Part 9

Risks, Open Questions & Mitigations

R1

Version → Sequence Mapping

Risk
JetStream stream sequences are global (1, 2, 3, ...) across all subjects. go-cqrs-lite versions are per-aggregate (each aggregate starts at 1). Mapping between them is the hardest problem.
Approach Pros Cons
A: KV index (recommended) O(1) lookup, fast ReadFrom Extra write on every Save, storage overhead
B: Linear scan with header check No extra storage O(n) for ReadFrom, slow for large streams
C: Per-aggregate streams Natural version = sequence N streams for N aggregates, management overhead, doesn't scale
D: Store version in header, scan per subject No extra storage, per-subject consumer Still O(n) for LoadFromVersion with high version numbers
Mitigation: Start with Approach D (version in header + per-subject ephemeral consumer). Add KV index (Approach A) if benchmarks show unacceptable latency. The KV index is an optimization, not a prerequisite.
R2

Per-Subject Message Counting for OCC

Risk
Optimistic concurrency requires knowing how many events exist for an aggregate. stream.Info() with subject filter might not give per-subject message counts in all JetStream versions.
Fallback How
Ephemeral consumer + count Create consumer on subject, fetch all, count messages. Works but O(n).
Last message by subject stream.GetLastMsgForSubject(subject) returns the last message. Version in header = current version.
External counter in KV Maintain CQRS_VERSIONS:{type}:{id} → currentVersion in a KV bucket. CAS via kv.Update().
Mitigation: Use GetLastMsgForSubject() to get the current version — it returns the last message for the aggregate's subject, from which we extract the version header. This is O(1) and doesn't require scanning. If the subject has no messages, the aggregate doesn't exist (version 0).
R3

nats-server Dependency Size

Risk
nats-server is a substantial dependency (~150K LOC). Even as a test-only dependency, it bloats the module's go.sum.
  • Mitigation: nats-server is a test dependency only (// indirect in go.mod). Production code imports only nats.go (~15K LOC).
  • Alternative: Use testcontainers + Docker for integration tests instead. But embedded is faster and simpler for unit tests.
  • Recommendation: Keep embedded for now. The test ergonomics are worth it.
R4

LoadBackwards Not Feasible

Risk
JetStream doesn't natively support reverse-ordered message consumption. The BackwardsSource interface (LoadBackwards) may not be satisfiable efficiently.
  • Option A: Don't implement BackwardsSource. Not all stores do (pebble/ doesn't).
  • Option B: Fetch all events for the aggregate, reverse in-memory. Works but loads everything.
Decision: Don't implement BackwardsSource. It's optional (neither pebble nor memory require it). Document as a known limitation.

Unique Value

JetStream is the only module that provides all 5 interfaces (Store, Journal, Bus, Checkpoint, Snapshot) in both embedded and distributed modes. memory/ does all 5 but single-process only. storage/ does 3 but needs an external broker for Bus.

When to Use

Use jetstream/ when you want a single system for CQRS+ES without managing separate PostgreSQL + NATS/Kafka. Ideal for edge computing, embedded systems, and teams wanting operational simplicity.

When NOT to Use

Stick with storage/ (SQL) when you need complex ad-hoc queries, strong SQL ecosystem tooling, or already have PostgreSQL operational expertise. JetStream's query capabilities are limited to subject-based filtering.

Usage Examples

EX1

Embedded Mode (Edge / Testing)

Example
import jetstream "github.com/larsartmann/go-cqrs-lite/jetstream" // Start embedded NATS server + create all stores backend, err := jetstream.NewBackend( jetstream.WithAutoCreate(), jetstream.WithMemoryStorage(), ) if err != nil { panic(err) } defer backend.Close() // Use event store store := backend.EventStore() ref := event.NewAggregateRef("User", userID) evt, _ := event.NewEvent("user.created", userID, "User", 1, payload) store.Save(ctx, ref, []event.Event{evt}, 0) // Use bus with existing middleware bus := backend.Bus() bus.Use(middleware.Logging(logger)) bus.Use(middleware.Recovery()) bus.Subscribe("user.created", func(ctx context.Context, evt event.Event) error { fmt.Println("User created:", evt.AggregateID()) return nil }) bus.Publish(ctx, evt)
EX2

Remote Mode (Production)

Example
// Connect to existing NATS cluster backend, err := jetstream.NewBackend( jetstream.WithURL("nats://nats.prod:4222"), jetstream.WithPrefix("myapp"), // Streams/buckets pre-created by ops team ) if err != nil { panic(err) } defer backend.Close() // Use projection runner with JetStream checkpoint store runner := projection.NewRunner( backend.EventStore(), // Journal backend.Bus(), // Subscriber backend.Checkpoints(), // CheckpointStore projection.WithRetry(3, time.Second), ) runner.Register(myProjection) go runner.Run(ctx)
EX3

Individual Stores (Composable)

Example
// Use only what you need — library, not framework nc, _ := nats.Connect(nats.DefaultURL) js, _ := jetstream.New(nc) // Just the event store stream, _ := js.Stream(ctx, "CQRS_EVENTS") store, _ := jetstream.NewStreamEventStore(js, stream, jetstream.WithPrefix("myapp")) // Just the checkpoint store kv, _ := js.KeyValue(ctx, "CQRS_CHECKPOINTS") checkpoints := jetstream.NewKVCheckpointStore(kv) // Mix with storage/ for SQL snapshots + JetStream events sqlSnapStore, _ := storage.NewSQLiteSnapshotStore(db) // → Use JetStream for events + bus, SQL for snapshots
Composability: Every store can be constructed independently. Mix JetStream events with SQL snapshots, or use JetStream checkpoints with a Pebble event store. The library doesn't force an all-or-nothing choice.
