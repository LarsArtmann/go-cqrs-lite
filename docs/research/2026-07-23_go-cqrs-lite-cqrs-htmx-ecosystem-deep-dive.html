go-cqrs-lite & cqrs-htmx Ecosystem Audit

A cross-project analysis of how 22+ consumer applications use the go-cqrs-lite CQRS/Event-Sourcing library and the cqrs-htmx HTTP binding. We identify what is used well, what is underused, what is misused, and what should be avoided.

Scope: 22+ consumer projects go-cqrs-lite v4.0.x cqrs-htmx v4.3.0 Ecosystem Adoption Score: 58/100

01Summary

The bottom line. The ecosystem has strong adoption of the core go-cqrs-lite event-sourcing/decider loop, but weak adoption of the higher-level cqrs-htmx HTTP binding. Most web projects import cqrs-htmx only for its middleware chain (security headers, recovery, HTMX detection) and leave the declarative app.Command / app.Query routing, CSRF, rate limiting, typed decoders, and SSE/WebSocket bridges on the table. Version drift is also a real problem: the dependency graph shows 76 version conflicts and 532 outdated consumers, with several projects mixing go-cqrs-lite v3 and v4 submodules or pinning local replace-only pseudo-versions.
✓
Core CQRS/ES is well understood bank-sync, Standup-Killer, Zlota44, github-local-sync, browser-history, and go-localsync all use deciders, event stores, and projections correctly.
✓
Advanced production features are exercised bank-sync uses encryption, snapshots, and upcasting; Standup-Killer uses SSE and idempotency; browser-history uses WebAuthn/usermgmt.
✓
Middleware awareness is growing Recovery, security headers, and HTMX detection are being adopted through cqrs-htmx.Chain in Standup-Killer, github-local-sync, PapDashboard, and crush-daily.

04Capability Gaps

The go-cqrs-lite suite exposes roughly 28 independent modules (event, command, query, decider, id, storage, projections, snapshots, schema, signing, encryption, middleware, otel, catalog, watermill, transport/http, scheduling, deriver, graph, kv, listing, idempotency, projectionhost, etc.). cqrs-htmx adds declarative HTTP handlers, middleware, auth/usermgmt, SSE/WebSocket bridges, typed decoders, and more. The sections below grade real-world adoption of the most important capabilities.

Fully Leveraged

Decider / event-sourcing core

bank-sync, Standup-Killer, Zlota44, github-local-sync, browser-history, standard-bug-tracking-schema, accountability-system, go-localsync

The decider pattern is the most-adopted capability. Multiple projects use decider.NewRepository, typed command handlers, and event buses correctly. This is the primary strength of the ecosystem.

Partially Used

cqrs-htmx declarative HTTP routing

crush-daily/internal/server/server.go:196, github-local-sync/internal/server/server.go:78-96

Only crush-daily (one app.Command) and github-local-sync (four app.Query routes) actually use cqrs-htmx for routing. Standup-Killer, Zlota44, accountability-system, KeyCountdown, KeyHolderAI, PapDashboard, timesheets, and overview import the library but wire their endpoints manually. They still pay the dependency cost without gaining the decoding, validation, auth, and error-mapping benefits.

Recommendation. For any state-changing POST/PUT route, prefer app.Command with DecodeJSON or DecodeForm plus Authorize and NotifySuccess. For read routes, use app.Query with RenderJSON or RenderTemplResult.
Missed Opportunity

CSRF, rate limiting, and security headers

Standup-Killer, Zlota44, bank-sync, accountability-system, KeyCountdown, KeyHolderAI, PapDashboard

cqrs-htmx ships CSRFMiddleware, RateLimiterMiddleware, and SecurityHeadersMiddleware with sensible defaults. Most web projects use only SecurityHeadersMiddleware (and sometimes only with empty fields). CSRF and rate limiting are rarely applied, even on state-changing endpoints.

Recommendation. Wrap the production mux with: 
return cqrshtmx.Chain(
    cqrshtmx.RecoveryMiddleware,
    cqrshtmx.SecurityHeadersMiddleware,
    cqrshtmx.CSRFMiddleware(cqrshtmx.CSRFConfig{}),
    cqrshtmx.RateLimiterMiddleware(cqrshtmx.DefaultRateLimiterConfig()),
    cqrshtmx.HTMXMiddleware,
    app.Middleware(),
)(mux)
Partially Used

Idempotency

Standup-Killer/domain/cqrs/handlers.go, Zlota44

Standup-Killer and Zlota44 wire idempotency stores, but most other state-changing projects — including bank-sync — do not. For financial/banking commands this is a high-value gap: duplicate imports could create duplicate transactions.

Recommendation. Add go-cqrs-lite/idempotency and middleware.CommandIdempotency to the command dispatcher in projects with non-idempotent state changes.
Misused / Risk

Version drift and replace-only pseudo-versions

SEC/go.mod:10-29, browser-history/cmd/server/go.mod:11-32

SEC pins every go-cqrs-lite and cqrs-htmx submodule to v4.0.0-00010101000000-000000000000 and replaces them all with local paths. This only builds inside the monorepo; a fresh checkout or CI outside the workspace will fail because the pseudo-versions are not fetchable.

browser-history has both v3 and v4 submodules in the same go.mod (e.g. command/v3 alongside metadata/v4). This is a latent compilation and type mismatch risk.

Recommendation. Publish stable go-cqrs-lite/cqrs-htmx tags and switch SEC to published versions. For browser-history, run go get on every go-cqrs-lite submodule to v4 and delete v3 replaces.
Partially Used

Projections and read-model tiers

bank-sync, Standup-Killer, DiscordSync, browser-history, InboxClean, go-localsync

Projections are used well in some projects, but many apps still build read models by hand-rolling SQL over the event store or by loading full aggregate histories. The library offers three projection tiers (KV/Document, Relational, Graph) and projectionhost for crash-restart + checkpoint + DLQ, but most projects stop at the simplest in-memory projection.

Recommendation. For cross-aggregate lists with status, use listing. For complex relational read models, use storage.RelationalProjection. For long-lived projections, wire a projectionhost.Host with a checkpoint store.
Missed Opportunity

OpenTelemetry and Prometheus

bank-sync, crush-daily, DiscordSync, Kernovia, KeyHolderAI

Only a handful of projects import go-cqrs-lite/otel or prometheus. Most projects have no distributed tracing or CQRS-specific metrics around command/query dispatch latency, event throughput, or projection lag. Given the library's built-in OTel middleware, this is low-hanging fruit.

Missed Opportunity

Signing, encryption, scheduling, deriver, graph, catalog

Ecosystem-wide

High-value features are almost entirely unused: signing (only Kernovia imports it), encryption (only bank-sync), scheduling (only Standup-Killer indirectly), deriver (event-to-command pipelines), graph (graph read models), and catalog (AsyncAPI/OpenAPI/EventCatalog generation). These are not needed everywhere, but several projects would benefit from them.

Misused / Risk

Dead imports and framework mismatch

KeyHolderAI/go.mod:65, KeyHolderAI routing uses Gin

KeyHolderAI imports cqrs-htmx/v4 but uses Gin for HTTP routing. No app.Command / app.Query usage is visible. This is a wasted dependency that also complicates the module graph. Either migrate to cqrs-htmx (net/http or Chi) or drop the import.

07Per-Project Notes

Condensed findings for the most important consumers. The full import matrix is available from the dependency graph tool.

Good examples

bank-sync

The most complete adoption: decider, SQLite event store, projections, snapshots every 50 events, AES-256-GCM encryption at rest, schema upcasting, and middleware. Uses cqrs-htmx for query fragments and middleware. A natural next step is adding idempotency to the sync/import command path.

github-local-sync

Clean cqrs-htmx usage: app.Query for stats, branches, flows, and health; middleware chain; SSE progress stream. Also uses the stack/sqlite preset and scenario tests. The sync trigger is intentionally a plain handler because it is a long-running process, not a domain command.

Partial / underusing

Standup-Killer

Excellent CQRS core (3 deciders, idempotency, projections) but cqrs-htmx is only used for the middleware chain and SSE broadcaster. All HTTP routes are custom handlers. Migrating the POST/GET routes to app.Command / app.Query would remove a lot of boilerplate and add CSRF/rate-limiting for free.

Zlota44

Strong decider and typed command/query setup with idempotency and retry middleware. No visible projection/read-model layer; dashboard queries appear to load aggregate histories. cqrs-htmx is imported but routes are custom.

crush-daily

Builds a full cqrs-htmx App with Prometheus/OTel integration, but only POST /api/collect uses app.Command. All other routes are hand-rolled. Snapshots are wired through the SQLite-backed snapshot store.

PapDashboard

Uses cqrs-htmx.Chain for middleware and Huma for API routing. Does not use app.Command / app.Query. Decider usage is mostly in tests; runtime adoption is unclear.

Problematic

SEC

All go-cqrs-lite and cqrs-htmx dependencies are pinned to non-fetchable pseudo-versions and replaced with local paths. This is a build-time landmine outside the monorepo. It also uses only in-memory storage, losing persistence benefits.

browser-history

Multi-module architecture is sound, but cmd/server/go.mod mixes go-cqrs-lite/.../v3 and go-cqrs-lite/.../v4 submodules. Must be migrated fully to v4 to avoid type collisions and compilation surprises.

KeyHolderAI

Uses Gin for routing and cqrs-htmx only for helper utilities (HTMX response builders, context enrichment, HTMX detection, error mapping) and middleware. It creates a cqrs-htmx App via DI but does not use app.Command / app.Query for routing. Decision needed: either migrate routes to cqrs-htmx or drop the dependency and use smaller helper imports.

overview

Imports cqrs-htmx only for middleware/SSE helpers. go-cqrs-lite is an indirect dependency. If the project is purely a dashboard, it should either start using CQRS or depend on a smaller middleware-only surface to reduce coupling.

08Conclusion

The go-cqrs-lite / cqrs-htmx ecosystem is healthy at the core but underutilized at the HTTP layer. The projects that "go deep" on event sourcing (bank-sync, Standup-Killer, Zlota44, github-local-sync) demonstrate the library's power. The missed opportunity is that most web projects still hand-roll HTTP handlers despite importing cqrs-htmx, leaving security, decoding, validation, and error-mapping benefits on the table.

The two highest-impact fixes are: (1) stabilize dependency wiring in SEC and browser-history, and (2) migrate web routes to app.Command / app.Query in the major web projects. After that, rolling out CSRF, rate limiting, and idempotency across the web surface will raise the ecosystem's production maturity significantly.

Next step. Run the dependency-graph update plan for go-cqrs-lite and cqrs-htmx to align patch versions, then pick one representative project (e.g. Standup-Killer) to migrate its routes to cqrs-htmx declarative handlers. Use that migration as a template for the others.
