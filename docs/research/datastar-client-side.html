Datastar, Client-Side

00Summary

Datastar is not a JavaScript framework in the Svelte/React sense. It is a wire protocol plus a 33 KB attribute interpreter: the server sends HTML fragments and JSON "signals" over SSE, the browser morphs them into the DOM. There is no client-side state machine to write, no API layer to shape, and no build step.

For this repository that lands in a very specific place. go-cqrs-lite already owns the one thing Datastar needs — a Watcher[V] over a materialized read model, with replay, backpressure, and heartbeats, exposed as metaengine.ServeSSE at metaengine/sse.go:111. Today that endpoint emits unnamed SSE events carrying JSON, which is the lowest-value possible contract: every consumer writes the same JSON→DOM renderer again. Datastar replaces exactly that step.

The bottom line Adopt Datastar as one more encoder on top of the existing SSE machinery, not as a rewrite. Ship it as a Tier 4 sibling module (metaengine/datastaradapter, beside projectionadapter), and stop there. Do not move HTML rendering into metaengine core, and do not convert the offline catalog/architecture export — that artifact's whole reason to exist is that it works with no server.

The single highest-leverage change is small: teach the SSE writer to emit event: datastar-patch-elements with a rendered fragment instead of a JSON blob. Everything downstream — replay, Last-Event-ID resume, drop-old backpressure, timeouts — is already implemented and already correct.

01What Datastar actually is

The project is by Star Federation (Delaney Gillilan), MIT licensed. 1.0 GA landed 2026-04-16; the current client release is v1.0.4, published 2026-09-21. You load one ES module; everything else is attributes on the HTML you were already sending. A commercial Pro tier ($349 solo / $1,299 team) gates about a dozen attributes and actions — the design below avoids all of them.

The distinction that matters here htmx swaps HTML on request. Datastar patches DOM on a standing stream. A CQRS library's core value proposition — a read model that changes as events land — is precisely a standing stream. That is why this question is worth a report: the fit is structural, not cosmetic.

Credibility check, since "new framework" is a fair objection: the documented production case is Instabooks, a QuickBooks-Online competitor rewritten from React to Datastar by a team including David Nolen (long-time ClojureScript lead) and Anders Murphy. Beyond that the project publishes no customer list, so treat any broader adoption claim as unverified. The 1.0 line, a cross-SDK conformance suite, and 15+ backend SDKs are the substantive signals.

The obvious alternative is htmx — and the fleet already ships a full htmx integration. The difference that matters for a CQRS backend:

htmx 2.x Datastar 1.0
Morphing extension (idiomorph) built in, outer is the default
Server→client state no — you swap an HTML chunk and stash values in hidden inputs datastar-patch-signals, RFC 7386 merge patch
Client→server payload form encoding one JSON {datastar: …} object, decoded into a Go struct
Stream-first ergonomics SSE is an extension (hx-ext, sse-swap) SSE is the primary transport

02The protocol, precisely

Three things make up Datastar: signals (reactive state), attributes (declarative bindings), and the patch events (how the server mutates both). Everything else is convenience.

The two patch events, verbatim

This is the entire server→client contract. Your backend writes these bytes and nothing else: 

event: datastar-patch-elements
data: selector #feed
data: mode prepend
data: useViewTransition true
data: viewTransitionSelector #main
data: elements <tr id="user-42">
data: elements   <td>ada@example.com</td>
data: elements </tr>

event: datastar-patch-signals
data: signals {projectionLagMs: 12, backlog: 0}

Two newlines terminate each event. The elements line is the only required field for the first event; every option has a default. Modes: outer (default, morph), inner, replace, prepend, append, before, after, remove. Extra data lines: namespace svg|mathml, useViewTransition, viewTransitionSelector. Signals are removed by setting them to null; onlyIfMissing true makes a patch a default-only seed.

Morphing is ID-based — this is the one rule to obey "Morphs elements by matching top-level elements based on their ID." Put a stable id on every top-level patched element, and on any descendant whose state (focus, listeners, CSS transitions) must survive. A table row without an id will be torn down and rebuilt on every patch.

Actions

@get, @post, @put, @patch, @delete, plus @query (RFC 10008 QUERY: signals in the body, safe and idempotent — a genuinely good fit for CQRS queries). Helpers: @peek() (read without subscribing), @setAll(), @toggleAll().

Every action takes one options object, and the response Content-Type decides everything else:

Response type Interpretation Optional headers
text/event-stream Datastar patch events (the normal streaming case) —
text/html elements to patch, one-shot datastar-selector, datastar-mode, datastar-use-view-transition
application/json signals to patch datastar-only-if-missing
text/javascript code to execute datastar-script-attributes

Fetch reliability is built in and configurable per call: retry (auto|<code>error</code>|<code>always</code>|<code>never</code>), retryInterval (1s), retryScaler (2), retryMaxWait (30s), retryMaxCount (10), requestCancellation (auto|<code>cleanup</code>|<code>disabled</code>|AbortController), and openWhenHidden. Lifecycle events (datastar-fetch with started, finished, error, retrying, retries-failed) make error UX possible without custom JS.

Resume works — and that is the whole reason a CQRS bridge is cheap

Datastar is fetch-based, so it cannot inherit EventSource's automatic Last-Event-ID behaviour. It reimplements it instead. The v1.0.4 bundle tracks the SSE id: field and replays it as a last-event-id request header on the next attempt: 

// minified, deobfuscated shape — datastar.js v1.0.4
W ? _["last-event-id"] = W : delete _["last-event-id"]

That single detail is what makes the existing replay path reusable unchanged. metaengine already writes id: <seq> on every event when a replay journal is attached (metaengine/sse.go:227) and already honours the request header (metaengine/sse.go:252). A Datastar client speaking to that endpoint gets the same resume a browser EventSource gets today.

The trap: a clean close does not reconnect Datastar retries on a thrown fetch error, on a retryable HTTP status, and when a hidden tab becomes visible again. It does not reconnect when the server closes the stream politely — the fetch resolves and the stream just ends. That collides directly with metaengine.WithSSETimeout (metaengine/sse.go:49): a timeout closes the connection with no error, so a Datastar client would sit on a dead stream with no indication. The adapter must either default the timeout to zero or send a final patch whose data-init re-opens the stream. This is a real footgun, not a theoretical one, and it must be a test.

03The Go half — what the fleet already owns

The most important finding of this study is that adopting Datastar here is not a greenfield decision. Four layers already exist in the sibling fleet, and this repository already depends on two of them.

go-sse v0.6.2 → go-datastar v0.6.3 → cqrs-htmx/datastar → your handlers
Layer Module What it gives you In-go-cqrs-lite today

Consequence: the dependency cost of a Datastar docserver is one module templ-components/utils/wire is in templ-components/utils, which catalog/go.mod already requires. templ-components/datastar requires only templ, templ-components/utils, and go-datastar/static — and that last one is a 58-byte go.mod wrapping one 33 KB JS file. Total new transitive surface: essentially zero.

There is also a design precedent worth copying: go-datastar chose patches as values over the official SDK's connection-bound method calls, precisely so a patch can be broadcast, stored, filtered, and replayed. The official datastar-go v1.2.2 cannot do that: datastar.NewSSE(w, r) writes straight to the wire. For a library whose whole architecture is "events are values, projections are values, replays are values", the fleet's own library is the correct dependency, and its wire output is golden-tested to be byte-identical to the official one.

The SSE contract being emitted today

metaengine/sse.go is a genuinely careful piece of engineering: subscribe-before-commit ordering so a client that has seen 200 can never miss a raced write, replay with dedup against the live handoff, drop-old backpressure, heartbeats, X-Accel-Buffering: no. The output, though, is deliberately minimal: 

// metaengine/sse.go:173 — the entire client-facing contract
data: {"ID":"user-42","Email":"ada@example.com","Plan":"pro"}

Unnamed event, JSON payload, no semantics. Every consumer — a dashboard, an admin panel, a live table — must rebuild the renderer. That is the gap Datastar fills, and the gap is exactly one function wide.

And the one place Datastar must never go

catalog/architecture/assets/reference.js opens with a sentence that is a design constraint, not a comment: 

There is no fetch, no framework and no build step: the whole point of
this export is that it keeps working from an email attachment years from now.

Datastar is structurally the opposite: it needs a live server, a stream, and an interpreter. Any proposal to "modernize" that artifact with Datastar destroys its only differentiator. It renders through architectureCache and is served with its own CSP deliberately not applied (catalog/docserver/architecture.go:44-48). Leave it alone.

05Six opportunities, ranked

Ordered by payoff per unit of risk. Item 0 is the one that will still matter in two years.

Highest leverage · library surface

0. A Datastar encoder beside ServeSSE

new module metaengine/datastaradapter/ · sibling of projectionadapter/, graphadapter/, keycodec/, otelobserver/

A consumer with a live read model currently gets JSON and writes a renderer. Give them a second encoder that takes the same *Watcher[V] and the same options, and emits Datastar patches built from a caller-supplied render function. Every hard problem — ordering, replay, dedup, backpressure, timeouts, heartbeats — is already solved in metaengine/sse.go and is reused verbatim. 

// metaengine/datastaradapter/datastar.go — the whole idea
type Renderer[V any] func(v V) string

// ServeDatastar streams read-model changes as datastar-patch-elements.
func ServeDatastar[V any](
    w http.ResponseWriter, r *http.Request,
    watcher *metaengine.Watcher[V],
    render Renderer[V],
    opts ...metaengine.SSEOption,
) error

// EventsPatch turns HTML into the wire payload go-sse already knows
// how to split: one `elements ` prefix per line.
func ElementsPatch(html string, id sse.EventID) sse.Event

Why a sibling module and not a new option on ServeSSE: metaengine is a storage/query planner and must not learn what HTML is. The four existing adapters set the pattern; this is the fifth. Dependency budget: metaengine + go-sse + go-datastar, nothing else.

Test contract to ship with it Mirror systemscenario/sse.go: boot an in-process server, connect as a real client, assert the parsed patch events. Then pin the bytes with a golden — and do not invent the goldens. Upstream ships a cross-SDK conformance corpus at sdk/test/get-cases/*/{input.json,output.txt} precisely so every SDK emits identical bytes; adopting those fixtures as the adapter's golden makes the output verifiable against starfederation/datastar-go instead of against our own opinion of the spec.
Biggest in-repo UX win

1. Make the event catalog searchable without page reloads

catalog/docserver/eventcatalog_handlers.go · GET {docs}/eventcatalog + 5 detail routes

The catalog surface is today a set of full-page navigations: filter a list, click a message, lose the filter, press back. With signals the filter becomes a data-bind on one input, and the result list becomes a server-rendered fragment patched into #results. Server-side filtering stays authoritative (no catalog JSON shipped to the browser), which also keeps the page small on large catalogs. 

<input type="search"
       data-bind:q
       data-on:input__debounce.250ms="@get('/docs/eventcatalog/results')"
       data-indicator:searching>

<div id="results" data-show="!$searching">
  <!-- server-rendered rows, morphed in -->
</div>

The handler returns text/html plus datastar-selector: #results and datastar-mode: inner — which is exactly what wire.Handler(PatchTarget{...}) in templ-components/utils/wire already emits, and the catalog module already depends on that module.

Near-zero code

2. Flip the docserver transport with wire.Action

catalog/docserver/*.templ · docsPageProps

templ-components already renders one typed wire.Action as either htmx attributes or Datastar attributes, selected by Transport: TransportDatastar (ADR-0030 in that repo). The docserver currently opts out of both runtimes (HTMXSrc = HTMXNone), so turning on Datastar means: serve the runtime via datastar.SDKScript, pass Transport: wire.TransportDatastar, and keep every other component byte-identical. This is the cheapest possible pilot and it de-risks opportunity 1.

One CSP detail, and it is good news docserver ships script-src 'self' 'nonce-…' with no 'unsafe-eval' (catalog/docserver/csp.go:50-66). Datastar's default expression mode uses the Function() constructor and would be blocked. Its CSP mode needs no eval: put data-nonce="<same nonce>" on the <html> element and Datastar applies that nonce when compiling expressions. layout.PageProps has HTMLDataAttrs templ.Attributes documented for exactly this. The existing per-request nonce plumbing (templ.GetNonce) is the same value — no second nonce system.
Documentation value

3. One reference consumer app

example/ · next to goal-shaped-app

The repo has zero HTML examples. A small example/live-dashboard that wires system.New + one metaengine.Watcher + ServeDatastar + a 30-line templ page would do more for adoption than any amount of prose — and it becomes the fixture that keeps the adapter honest. Register it under examplePaths (build-only), never testModules.

Small but real

4. Publish the wire contract in the skill

.agents/skills/go-cqrs-lite/references/advanced.md §6.15

The SSE decision matrix in SKILL.md currently offers two browser options (raw events via go-sse, read-model values via ServeSSE) and one of them arrives as meaningless JSON. A third row — "browser needs a live view" → ServeDatastar — closes the matrix. Remember cmd/doc-check.

Explicit non-goal

5. Do not convert catalog/architecture

catalog/architecture/assets/reference.js

Recorded here so the question does not get re-asked in six months: the offline artifact wins by having no runtime. A "Datastar-powered" variant of the same reference (served, not attached) is defensible as a separate export mode, if a consumer ever asks for live catalog browsing without running docserver. Not before.

06Where it breaks — the honest list

+
Morphing is only as good as your IDs Rows without stable ids are destroyed and rebuilt, taking focus, listeners, and open <details> with them. The modern mitigation is the platform, not the framework: moveBefore() preserves state on a reparent (Chrome/Edge 133+, Firefox 144+; no Safari), with feature detection required. data-preserve-attr, data-ignore-morph, and per-row view-transition-name are the escape hatches to document. Two hard constraints if you enable useViewTransition: at most one element per name before and after a transition (a duplicate silently degrades to an instant swap, no error), and nothing routes focus for you — a transition that reveals a detail pane must move focus to its heading itself.
+
Signals are shipped on every request A @get puts every non-_ signal in the query string; other methods put them in the body. A naive implementation with a 5,000-row signal array will hurt. Server-side filtering (opportunity 1) avoids this by keeping the dataset out of signals entirely.
+
Expressions are JavaScript in attributes This is an XSS surface if user data is ever interpolated into an expression. The rule is the same one the fleet already applies to templ: static expressions, user values only through signals, and data-ignore as a last resort. CSP mode does not make untrusted expressions safe — the docs say so outright.
+
There is no client-side router data-replace-url and data-query-string are Pro. A multi-page admin UI stays multi-page (which is fine here: docserver's pages are documents, not views of an app).
+
Design the stream as idempotent state, not as a feed Because a hidden tab tears the stream down and re-issues it, and because a clean close is not retried, upstream's own guidance for CQRS is a "fat morph": send the complete desired state of the region on every patch instead of appending deltas. Our read-model watcher makes that natural — Watcher[V] hands you the current value, not a diff — but the adapter's documentation must say it, because append-shaped patches (mode append to an event log) will visibly duplicate after a reconnect.
+
Heartbeats: an advantage of our stack, not theirs The official SDK has no keepalive helper at all — its writer is unexported, so you cannot emit a bare : keepalive comment through it. go-sse has WriteHeartbeat, and metaengine.WithSSEHeartbeat already wires it. Another reason to build on go-datastar + go-sse rather than the upstream SDK.
The one architectural boundary to defend Datastar makes it tempting to put HTML rendering inside metaengine. Resist. Rendering belongs to the adapter layer for the same reason projectionadapter exists: the substrate must stay JSON-shaped, engine-agnostic, and testable without a browser.

Protocol cheat sheet for a Go handler

// 1. headers + flush
w.Header().Set("Content-Type", "text/event-stream")
w.Header().Set("Cache-Control", "no-cache")
w.Header().Set("X-Accel-Buffering", "no")
w.WriteHeader(http.StatusOK)
w.(http.Flusher).Flush()

// 2. read signals (POST body / GET query param)
var sig struct { Q string `json:"q"` }
_ = datastar.ReadSignals(r, &sig)

// 3. patch — or, in this repo, hand a Patch to the broadcaster
sse.WriteEvent(w, patch.Event())

Open questions this study did not settle

  • Whether the adapter should also offer a signal encoder (JSON value → datastar-patch-signals) for consumers who want client-side rendering with server-side truth. Cheap to add, but two encoders need two contracts.
  • Whether cqrs-htmx/datastar's EventBridge should move down into the adapter, or stay a handler-layer convenience. Duplicating the bridge in two repos is the failure mode to avoid.
  • How a Datastar client behaves against WithSSEReplayLimit-capped replay when the missed window is larger than the cap: silent gap or full re-fetch. Needs a browser test, not a reading of the code.
