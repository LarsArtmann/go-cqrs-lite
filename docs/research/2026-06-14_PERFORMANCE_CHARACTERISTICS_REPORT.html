Executive Summary

Scorecard across all resource dimensions

go-cqrs-lite is a library, not a runtime service — so "performance" means: how cheaply can a consumer create, route, persist, and replay events? Every nanosecond and allocation compounds because consumers call these paths in tight loops under their own load. The analysis below covers every module with production benchmarks.

Good10M cmd/sec concurrent

Excellent sharded-lock design in Pebble. CircuitBreaker mutex is a bottleneck. SSE broker has a goroutine leak.

What's excellent

Command/query dispatch at 52–55 ns/op, zero-allocation Fold at 255 ns/op, pre-wrapped middleware at registration time, zero-copy PayloadReadOnly() fast path, and CBOR codec modes cached at package init. The pure-function decider design means the hot fold loop has zero allocations.

What needs attention

Pebble writes every event twice (double serialization + 2× disk bytes). SQL saves fire one INSERT per event with no multi-row batching. NewMetadata() unconditionally allocates a map for every event even when unused. The MemoryBus holds an RLock for the entire duration of handler execution. The projection pipeline allocates a new handler slice per event.

HMAC-SHA256

Hardware-accelerated (SHA-NI). Canonical buffer is compact: 4-byte big-endian length prefixes, 8 fields + optional 32-byte payload digest. Only the digest is signed, not the raw payload — good design.

Throughput ceiling: ~1.5M events/sec for signing alone.

Ed25519

Pure-Go crypto/ed25519. Verify is 45× slower than HMAC. For high-volume verification (projection replay), this is the CPU bottleneck. Consider batch verification (ed25519.VerifyBatch) for multi-sig scenarios.

Throughput ceiling: ~33K verifies/sec.

AEAD Encryption

AES-256-GCM uses AES-NI hardware acceleration. XChaCha20-Poly1305 is constant-time (no hardware dependency) — preferred for cross-platform consistency. Both issue crypto/rand.Reader per encrypt = 1 kernel syscall per event.

Reflection Cost (Catalog)

The catalog/ module performs heavy reflection (7+ struct-tag lookups per field, recursive type walks) — but only at build time. The schemaCache sync.Map (schema/reflect.go:58) caches reflect.Type → *Schema, making subsequent calls O(1). The built Catalog is immutable and lock-free at runtime.

CPU Summary

The library's CPU profile is dominated by serialization (JSON/CBOR marshal), cryptography (HMAC/AES/Ed25519), and map operations (metadata clone, dispatch lookup). Core dispatch and fold paths are essentially optimal. The single biggest CPU waste is the pebble double-serialization (every event encoded twice on save) and the SQL per-row timestamp string parsing on SQLite/Turso.

Defensive Cloning — The Design Philosophy

Every public accessor on ImmutableEvent returns a clone: 

event/event.go:129-137
func (e *ImmutableEvent) Payload() []byte {
    return slices.Clone(e.payload)   // allocates a NEW []byte every call
}
func (e *ImmutableEvent) Metadata() Metadata {
    return e.metadata.Clone()        // allocates a new map every call
}

This is correct for immutability safety — a consumer cannot mutate internal state through a returned reference. But it means tight read loops that call Payload() or Metadata() allocate on every iteration. The library provides a deliberate escape hatch: 

event/codec.go:63-65
func PayloadReadOnly(evt Event) []byte {
    return payloadForDecode(evt)    // type-asserts to *ImmutableEvent, returns raw slice
}

This zero-copy path is used internally by signing (SHA-256 hashing), pebble (json.Marshal), storage/sql (ExecContext), and middleware/sse. It is the single most important allocation optimization in the codebase.

Unconditional Metadata Map Allocation

NewMetadata() (metadata.go:22) allocates make(map[MetadataKey]string) for every event, even when no custom metadata is ever set. This is the most common allocation in the event module. A lazy-init pattern (nil map until first write) would eliminate it for the majority of events.

Full Pipeline Allocation Budget

For a fully-loaded write path (command → decider → event creation → signing → encryption → bus publish), the per-event allocation budget is approximately:

Stage Allocs ~Bytes Key Sources
Event construction 2–8 304–737 struct + payload clone + metadata map + ULID
HMAC signing 11 848 canonical buffer + HMAC + base64 + clone
AES-256-GCM encryption 7–8 2,320 nonce + Seal + result + base64 + clone
Bus publish 3 48 middleware chain rebuild + handler dispatch
OTel tracing 2 ~200 span + attrs slice
Total per event ~25 ~4,500 + 1 kernel syscall (getrandom)

At 10K events/sec sustained, this is ~45 MB/sec of short-lived garbage. Go's concurrent GC handles this, but at 100K events/sec, GC pauses become measurable without GOGC tuning.

Why sync.Pool Was Rejected

Design Decision — Documented & Intentional

sync.Pool requires a Reset() method that mutates the object. ImmutableEvent is immutable by contract — a pooled event with stale metadata from a previous use would be a data leak vulnerability (one event's metadata appearing in another). The team explicitly rejected pooling as documented in multiple status reports. The 304B/2-allocs cost at 182ns is the "honest cost of immutability."

Issues Identified

One INSERT per event

SharedInsertEvents (sql/helpers.go:57) loops over events and runs one tx.ExecContext per event. A batch of N events = N INSERT statements = N network round-trips. A single multi-VALUES INSERT would amortize protocol overhead.

SQL rebuilt per call

fmt.Sprintf rebuilds the INSERT/SELECT template on every Save/Load (event_store_scan.go:86). The result is identical for a given dialect — should be a const. database/sql caches the prepared statement internally, but the string allocation is wasted.

6-layout timestamp parse

SQLite/Turso parses timestamps by trying 6 format layouts in a loop (sql/sqlite.go:10). For a 10K-event Load, this is up to 60K parse attempts. Pebble stores nanos as int64 — far more efficient.

MaxOpenConns(1) for SQLite

ConfigureSQLitePool forces a single connection (sqlite_helpers.go:57). All reads and writes serialize. WAL is opt-in. The pool config is advisory — users who forget to call it get unsafe concurrency.

Good design: Streaming + Keyset Pagination

The SQL module has the only true streaming interface: LoadStream (stream.go:15) wraps *sql.Rows and scans one row at a time. The aggregate listing reader uses proper keyset pagination (aggregate_id > ? with LIMIT N+1 has-more trick). Indexes are well-designed: the UNIQUE(aggregate_type, aggregate_id, version) constraint doubles as a covering index and optimistic-concurrency guard.

Strengths

  • Atomic batch writes — every Save goes through db.NewBatch() + batch.Commit(). Correct LSM-level atomicity.
  • O(log n) version check — iter.Last() seeks directly to the latest version key. Zero-padding (%010d) ensures correct lexicographic ordering.
  • 256-shard mutex pool — FNV-hash over type+ID distributes per-aggregate locks. Collision probability is low.
  • Early termination — LoadToTimestamp breaks as soon as the predicate fires (10× faster than full scan).
Critical: Double Serialization on Save

writeEventsToBatch (save.go:109) serializes every event via serializeAndAddToBatch, then appendToJournal (journal.go:25) re-serializes every event from scratch for the journal key. This means 2N CBOR encodings + 2N batch.Set calls, writing the same bytes under two keys. Storage cost is exactly 2× the event payload size per event. Fix: serialize once, call batch.Set twice with the same data slice.

Quadratic ReadFrom

ReadFrom(afterEventID) (journal.go:79) iterates from iter.First() and linearly skips every event until the cursor is found — deserializing and discarding each. For projection catch-up over millions of events, total work is O(cursor_pos × pages). The SQL backend avoids this with a self-join; pebble could use an event-ID → journal-key reverse index.

Metadata JSON Round-Trip on Read

Deserialization (serialization.go:95) CBOR-decodes metadata into event.Metadata, then re-encodes it to JSON via MarshalMetadataJSON, then passes the JSON to ReconstructEventFromFields which parses it again. This JSON round-trip is wasted work on every read.

Turso inherits all SQLite storage behavior (1 INSERT/event, 6-layout timestamp parse, MaxOpenConns(1)). Its distinguishing features are:

Runs EXPLAIN QUERY PLAN and classifies plans as full-scan vs index-seek vs covering-index. Recommends 5 production-tuned CQRS covering indexes including idx_events_cursor (occurred_at, id) for cursor pagination.

Network Performance

Transport adapters, serialization overhead, and remote sync

go-cqrs-lite is transport-agnostic by design — it does not include an HTTP server, gRPC service, or message broker. All network characteristics are inherited from the consumer's chosen transport. The library provides adapters for Watermill (message broker) and Turso (remote database sync).

The adapter converts between CQRS events and Watermill messages. BuildMetadata is zero-allocation — excellent. The serialization path (EventToMessage) pays the JSON marshal + base64 + metadata map costs inherent to the event model. Actual network latency depends on the Watermill publisher implementation (NATS, Kafka, etc.) — not measured here.

Turso Remote Sync

The Turso connector provides Push, Pull, and Checkpoint operations for syncing local LibSQL state with a remote server:

  • Push — ships local WAL frames to the remote server. Bounded by network bandwidth and WAL size.
  • Pull — fetches remote changes. Returns whether anything changed for conditional sync.
  • Checkpoint — flushes the WAL into the main DB file (analogous to PRAGMA wal_checkpoint).
Pool Starvation Under Sync

ConfigureTursoPool forces MaxOpenConns(1). Background sync traffic (Push/Pull) competes with foreground reads/writes on the same single connection. Under high write throughput with frequent sync, this creates head-of-line blocking.

SSE (Server-Sent Events) Middleware

The SSE broker (middleware/sse.go) provides real-time event push to HTTP clients. Each connected client gets a buffered channel (make(chan event.Event, 100)) and a dedicated goroutine.

GPU

Applicability and theoretical opportunities
Verdict: Not Applicable

go-cqrs-lite is a pure-CPU Go library with no GPU-offloadable workloads. The operations it performs — map lookups, JSON/CBOR serialization, HMAC/AES cryptography, SQL queries — are all either latency-bound (not throughput-bound) or hardware-accelerated on CPU (SHA-NI, AES-NI). GPU offloading would add PCIe transfer overhead that exceeds the compute savings for every operation in this library.

Why GPU Doesn't Help Here

🔬 Cryptography

HMAC-SHA256 and AES-256-GCM are already hardware-accelerated on CPU (SHA-NI: ~3 cycles/byte, AES-NI: ~1 cycle/byte). GPU crypto would require a PCIe round-trip (~5–10 µs) that exceeds the CPU cost (669 ns for HMAC, 777 ns for AES). Only Ed25519 verify (30µs) is slow enough to theoretically benefit, but batch verification is a better CPU-side fix.

📦 Serialization

JSON/CBOR marshaling is branch-heavy (type switches, field iteration, escape analysis). GPUs excel at SIMD-parallel work on regular data layouts; serialization is inherently sequential per-event and latency-bound. The Go encoding/json encoder is not GPU-portable without a CGO bridge.

🗂️ Map Operations

Dispatch and metadata operations are O(1) hash-map lookups at 7–55 ns. The CPU L1/L2 cache hit rate is effectively 100% for these small, hot maps. GPU memory latency (400+ cycles for global memory) is orders of magnitude worse.

💾 Database I/O

SQL queries and Pebble scans are I/O-bound, not compute-bound. The bottleneck is disk seek time (µs–ms range), not CPU computation. A GPU cannot make a disk seek faster.

Theoretical GPU Opportunities (If Scale Demanded It)

Workload Current CPU Cost GPU Potential Verdict
Ed25519 batch verify (1000+ events) 30 µs × 1000 = 30 ms Parallel verify on GPU cores Marginal — ed25519.VerifyBatch on CPU is better
Catalog schema reflection (startup) 100 ms (full export) None — single-threaded by nature No benefit
Projection replay (1M+ events) ~4 sec (benchmark) Decode payloads in parallel Plausible for decode only, but handler logic is sequential
Event signing (HMAC) 669 ns/event Already HW-accelerated No benefit

For any of these to be worth a CGO/PCIe bridge, the library would need to process millions of events per second in a single process — well beyond typical CQRS workloads.

CircuitBreaker: Mutex Serialization Bottleneck

The circuit breaker hot path (circuit_breaker.go:145,158) acquires sync.Mutex twice per message (once for allow(), once for recordSuccess()). Since Mutex is exclusive, this fully serializes all messages through the breaker. Under N concurrent goroutines, throughput is limited by hold_time × N. An atomic-based state machine (atomic.Int32 for state + failure count) would eliminate contention in the closed (happy) state.

MemoryBus: RLock Held During Handler Execution

MemoryBus.Publish (bus.go:92) holds an RLock for the entire duration of handler execution. Concurrent publishes share the RLock (fine), but any Subscribe/Use/UsePublish call is blocked until ALL in-flight handlers complete. The middleware chain is also rebuilt on every publish (bus.go:150) — closure allocation per event per publish.

SSE Broker: Vestigial Goroutine

SSEBroker (sse.go:56) spawns a goroutine that blocks on ctx.Done() and does nothing when cancelled. It exists solely to reference the context. It leaks until Close() calls b.cancel(). Removing it would have no functional effect. Additionally, fmt.Fprintf is called 3× per event per client for SSE formatting — a pooled bytes.Buffer + single write would reduce allocations.

Projection Parallelism

The projection runner supports optional bounded parallelism via errgroup.WithContext with g.SetLimit(parallelism) (runner_live.go:64). Parallelism is per-event across projections, not across events — events are still processed sequentially. Replay is fully sequential.

Projection Per-Event Allocations

HandlerRegistry.Lookup (handler.go:60) allocates a new []event.Handler on every event. builtProjection.EventTypes() (builder.go:80) calls slices.Clone on every call, which happens per live event in subscribesTo. For the 100K-event benchmark, this contributes to the 91M allocations total.

Allocation Reduction Opportunities

Pebble double serialization

Serialize once, batch.Set twice. Eliminates N CBOR encodings + N serializableEvent allocations per Save batch.

Lazy metadata map

Replace NewMetadata() unconditional map alloc with nil-map-until-first-write. Eliminates 1 alloc per event for the common case.

Projection handler slice cache

Cache the Lookup result or use a reusable buffer. Eliminates 1 alloc per event in the live projection pipeline.

SQL template constants

Hoist fmt.Sprintf INSERT/SELECT templates to package-level const strings. Eliminates per-Save string allocation.

ScanSlice capacity hint

Pre-allocate make([]T, 0, 64) instead of nil + append. Reduces log₂(N) slice growth copies during large Loads.

MemoryStore double-copy

Load (store_load.go:116+142) allocates + copies the event slice twice. The second copyEvents is pure defensive copying of an already-fresh slice.

What's Already Excellent

Zero-allocation Fold

The pure-function decider fold loop is 255 ns with 0 B / 0 allocs for 100 events. This is the hot read-path and it's optimal.

Pre-wrapped middleware

The dispatcher wraps middleware at registration time (dispatcher.go:88), storing the fully-wrapped handler. Hot dispatch has zero closure allocation.

Zero-copy PayloadReadOnly

The type-assertion fast path (codec.go:63) bypasses defensive cloning for internal read-only paths. Used by signing, pebble, storage, and SSE.

Sharded Pebble locks

256-shard FNV-hash mutex pool (store.go:15) distributes per-aggregate contention without unbounded sync.Map growth.

CBOR codec init caching

CBOR EncMode/DecMode are created once at package init (cbor.go:19) — not per-call. Codec dispatch is zero-overhead.

Snapshot acceleration

The decider loads a snapshot then only fetches events since snap.Version (load.go:176). Dramatically reduces fold iterations for long-lived aggregates.

Keyset pagination

The SQL aggregate reader uses aggregate_id > ? + LIMIT N+1 — proper keyset pagination that avoids OFFSET degradation.

Optimistic concurrency

No SELECT ... FOR UPDATE. Version checking via UNIQUE(agg_type, agg_id, version) constraint — correct and scalable.

Final Assessment

go-cqrs-lite is a well-engineered library with excellent core-path performance (dispatch at 24 ns, fold at 0 allocs). The primary performance debt is concentrated in three areas: (1) storage write paths (SQL batch inserts, pebble double serialization), (2) per-event defensive allocations (metadata map, projection handler slices), and (3) concurrency primitives under load (circuit breaker mutex, memory bus RLock duration). None of these are architectural — they are localized optimizations that can be applied incrementally without breaking the public API. The design philosophy of immutability-first and zero-copy internal reads is sound and well-executed.
