HMAC & SHA-256 — Hardware Acceleration Status

YES — SHA-NI is active at runtime.
Go 1.26's crypto/sha256 dispatches to blockSHANI() on this CPU — a hand-written assembly path using SHA256RNDS2, SHA256MSG1, SHA256MSG2 x86 instructions. This is the fastest SHA-256 path available in Go. HMAC-SHA256 calls sha256.Hash twice (inner + outer pad), both benefiting from SHA-NI.

How the dispatch works

// crypto/internal/fips140/sha256/sha256block_amd64.go
var useSHANI = cpu.X86HasAVX && cpu.X86HasSHA && cpu.X86HasSSE41 && cpu.X86HasSSSE3

func block(dig *Digest, p []byte) {
    if useSHANI {
        blockSHANI(dig, p)    // <-- WE HIT THIS PATH
    } else if useAVX2 {
        blockAVX2(dig, p)
    } else {
        blockGeneric(dig, p)
    }
}

Ed25519 is 16× slower because SHA-512 lacks hardware support and the elliptic curve math is inherently more expensive. No software optimization can fix this — it's a CPU limitation.

Go 1.26 SIMD — simd/archsimd (Experimental)

What's available

Go 1.26 introduces simd/archsimd via GOEXPERIMENT=simd. It provides:

  • 128-bit vectors: Int8x16, Float64x2, etc.
  • 256-bit vectors: Float32x8, Int64x4, etc.
  • 512-bit vectors: Float32x16, Int64x8, etc. (AVX-512)
  • Operations: Load, Store, Add, Sub, Mul, And, Or, Xor, Equal, Greater, Permute, Masked, Merge
  • Runtime CPU feature checks via archsimd.X86.HasAVX2(), etc.

Restrictions: amd64 only, not portable, not in public APIs, experimental (no Go 1 compatibility promise).

Code-Level Findings

1. Zero sync.Pool usage anywhere

event.NewEvent allocates ImmutableEvent + Metadata map + safePayload slice on every call (384 B / 3 allocs). Under sustained load (10k events/s), that's ~4 MB/s of short-lived garbage. A sync.Pool for ImmutableEvent would let the GC recycle these objects instead of allocating fresh ones. Expected impact: 30-50% fewer heap allocations under load.

2. Defensive payload copy on every event

event_construct.go:53-55 — make([]byte, len(payload)); copy(safePayload, payload) runs on every NewEvent, even when the caller is the sole owner (e.g., payload just marshaled from a struct). For event-loaded-from-DB paths, the defensive copy is pure overhead. An unsafe fast path or WithNoCopy() option for trusted callers would eliminate this.

3. probeCodec allocates a throwaway struct per event

event_new.go:43-50 — Creates a dummy ImmutableEvent{} just to check if WithNewCodec was passed. Runs on every event.New() call. Should iterate options directly or cache the result.

4. Storage benchmarks test a mock, not a real database

storage/benchmark_test.go uses sqlmock — the 119µs "load" is mock overhead, not PostgreSQL. One benchmark (BenchmarkSQLEventStore_Save) outright fails. The SQLite benchmarks in sqlite_bench_test.go are real and valid. The PostgreSQL mock benchmarks should be dropped or replaced with real PG (testcontainers).

5. Inconsistent benchmark style

signing/ uses legacy for i := 0; i < b.N; i++ + b.ResetTimer(). Most other files use modern b.Loop() (Go 1.26). No file calls b.ReportAllocs() — relying on the -benchmem flag instead.

6. No statistical rigor

benchmark-baseline.txt is a single-run snapshot. No benchstat-based comparison exists. Regression detection is impossible without -count=N runs and statistical analysis.

7. canonicalPayload — 10 allocations for string building

326 ns / 10 allocs just to concatenate strings. This is called before every sign/verify. Using strings.Builder (pre-sized) or []byte with sync.Pool would cut this to 1-2 allocs.

Answered Questions

How can benchmarks show 0 B/op?

Go's escape analyzer proves values never escape the stack frame. When all data is consumed locally — field reads, pure function returns, value-type computations — the compiler allocates on the stack. Zero heap pressure, zero GC cost. Examples:

  • Classify / IsRetryable (9 ns, 0 allocs) — reads a field from an interface, no allocation possible
  • Fold (281 ns, 0 allocs) — pure function, state is a value type returned on stack
  • CommandRecovery / Validation / Retry (5-6 ns, 0 allocs) — closure captures nothing, no escape

This is correct behavior, not a benchmark bug. It means the compiler is doing its job for these paths.

Is HMAC hardware-accelerated?

Yes. This CPU has sha_ni support. Go 1.26 dispatches crypto/sha256 to the blockSHANI assembly path, which uses SHA256RNDS2 / SHA256MSG1 / SHA256MSG2 x86 instructions. HMAC-SHA256 calls SHA-256 twice (inner + outer pad), both accelerated. The 818 ns result is near-optimal for the algorithm given the HMAC key setup overhead.

Why not SIMD everywhere?

Because most hot paths are allocation-bound, not CPU-bound. SIMD accelerates arithmetic; it doesn't reduce garbage. The highest-leverage improvements are all about reducing allocations (sync.Pool, strings.Builder, eliminating defensive copies). The one path where SIMD would genuinely help — pebble/LoadToTimestamp doing a linear timestamp scan — accounts for a tiny fraction of real-world usage.
