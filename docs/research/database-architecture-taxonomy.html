Database Architecture
Taxonomy

Date: 2026-05-29 · Scope: All known database architectures from interface and storage perspectives

Two axes of classification. A single interface model can be backed by many storage engines. A single storage engine can power many interface models.

Axis 1: Interface Model

What operations the database exposes to consumers — the API shape.

Axis 2: Storage Engine

How data is physically laid out on disk or in memory — the data structure.

Part 1

Interface Models

01

Key-Value

Interface 
Get(key) → value
Put(key, value)
Delete(key)
Dimension Detail
Operations Get, Put, Delete, Exists, Increment
Query model Exact key match only. No range, no filtering, no joins
Ordering None (hash) or lexicographic (ordered KV)
Schema None — opaque byte values
Transactions Optional — single-key atomic or multi-key batch
Notable Redis, etcd, DynamoDB, LevelDB, RocksDB, Pebble
  • Hash KV — O(1) point lookup, no range scan (Redis hash, Memcached)
  • Ordered KV — O(log n) lookup, range scan via iterator (Pebble, LevelDB, BadgerDB)
  • Distributed KV — Consensus-based, replicated (etcd, TiKV, FoundationDB)
02

Document

Interface 
Insert(collection, document)
Find(collection, query) → []Document
Update(collection, query, changes)
Delete(collection, query)
Aggregate(collection, pipeline) → []Document
Dimension Detail
Operations CRUD + rich query + aggregation pipeline
Query model Field matching, nested path queries, range, regex, geospatial
Schema Optional / flexible — documents can vary within a collection
Transactions Optional — MongoDB supports multi-document ACID
Notable MongoDB, CouchDB, Couchbase, Firestore, RethinkDB
Key property: A document is a self-contained unit (JSON/BSON). Queries address fields within documents. Indexes are on fields, not the whole document.
03

Relational (SQL)

Interface 
SELECT columns FROM table WHERE condition
    JOIN table2 ON ... GROUP BY ... ORDER BY ...
INSERT INTO table (columns) VALUES (...)
UPDATE table SET ... WHERE ...
DELETE FROM table WHERE ...
BEGIN / COMMIT / ROLLBACK
Dimension Detail
Operations Full relational algebra: select, project, join, aggregate, sort
Query model Declarative (SQL). Optimizer chooses execution plan
Schema Strict — typed columns, constraints, foreign keys, normalization
Transactions Full ACID — BEGIN/COMMIT/ROLLBACK, isolation levels
Notable PostgreSQL, MySQL, SQLite, Oracle, SQL Server, CockroachDB
Key property: Data is normalized across tables. Joins reconstruct relationships. The optimizer is the magic — consumers say WHAT they want, not HOW to get it.
04

Graph

Interface 
CreateNode(label, properties) → Node
CreateEdge(type, source, target, properties) → Edge
Traverse(start, pattern) → []Path
Query(cypher) → Result
ShortestPath(a, b) → Path
Dimension Detail
Operations Node/edge CRUD + traversal + pattern matching + path algorithms
Query model Graph traversal (Cypher, Gremlin, GQL). Pattern matching on topology
Schema Optional — labels/types with optional property constraints
Notable Neo4j, Neptune, JanusGraph, ArangoDB, TigerGraph
Key property: Relationships are first-class citizens. Multi-hop traversal is O(k) where k = path length, not O(n²) like SQL joins.
05

Time-Series

Interface 
Write(metric, tags, value, timestamp)
Query(metric, tags, timeRange) → []Point
Aggregate(metric, tags, window, fn) → []Bucket
Downsample(metric, targetResolution)
Dimension Detail
Operations Write (high-throughput ingest), Query (time range + aggregation)
Query model Time-bounded, tag-filtered, with windowed aggregation functions
Schema Metric name + tag set + field set. Often schemaless
Notable InfluxDB, Prometheus, TimescaleDB, TDengine, QuestDB, ClickHouse
Key property: Optimized for append-heavy time-ordered data. Reads are almost always range scans over time windows. Compression exploits temporal locality.
06

Search / Full-Text

Interface 
Index(document, fields)
Search(query, filters) → []Hit (ranked)
Suggest(prefix) → []Suggestion
Aggregate(query, facets) → FacetResults
Dimension Detail
Operations Index, Search (with relevance scoring), Facet, Autocomplete
Query model Full-text query DSL (boolean, phrase, fuzzy, proximity)
Schema Mapping definition (field types, analyzers)
Notable Elasticsearch, Solr, OpenSearch, Meilisearch, Typesense
Key property: Inverted index maps terms → documents. Relevance scoring is the differentiator. Not a primary store — usually sits alongside a source-of-truth database.
07

Wide-Column / Column-Family

Interface 
Put(rowKey, columnFamily, column, value)
Get(rowKey, columnFamily, column) → value
Scan(rowKeyRange, columnFamily, columns) → []Row
Dimension Detail
Operations Put, Get, Scan (range over row keys), Multi-Get
Query model Row-key based + column-family/column projection
Schema Column families defined at creation; columns within a family are flexible
Notable Cassandra, ScyllaDB, HBase, Bigtable, DynamoDB
Key property: A two-level map: RowKey → (ColumnFamily → (Column → Value)). Each row can have different columns. Optimized for write-heavy, wide-row access patterns.
08

Object Storage

Interface 
PUT(bucket, key, data, metadata)
GET(bucket, key) → data + metadata
DELETE(bucket, key)
LIST(bucket, prefix) → []ObjectInfo
Dimension Detail
Operations PUT, GET, DELETE, LIST, COPY. Versioning. Lifecycle rules
Query model Prefix-based listing only. No content query
Schema None — opaque binary blobs with user-defined metadata
Notable S3, GCS, Azure Blob, MinIO, Cloudflare R2
Key property: Infinite scale, eventual consistency, very high latency (100ms+). Not a database — a content-addressable file system. Used as a storage tier in many architectures.
09

Triple Store / RDF / SPARQL

Interface 
Assert(subject, predicate, object)
Retract(subject, predicate, object)
Query(sparql) → Result
Dimension Detail
Operations Assert/Retract triples, SPARQL queries, ontology reasoning
Query model Graph pattern matching via SPARQL. Logical inference over ontologies
Schema OWL ontologies / RDFS — formal semantic schema
Notable Virtuoso, Stardog, AllegroGraph, Jena, Neptune (RDF mode)
Key property: Every fact is a (subject, predicate, object) triple. Reasoning engine can derive new facts from rules. Used in knowledge graphs and semantic web.
10

Datalog

Interface 
Assert(fact)
Rule(head ← body)
Query(goal) → Result
Dimension Detail
Operations Fact assertion, rule definition, recursive query
Query model Declarative logic programming. Recursive rules
Schema Implicit — defined by fact structure and rules
Notable Datomic, Datahike, XTDB, Soufflé
Key property: Queries are logical deductions. Rules can be recursive. Datomic's "database as a value" — every query runs against an immutable snapshot. Natural fit for event sourcing.
11

Streaming

Interface 
Publish(topic, message)
Subscribe(topic, handler)
Process(stream → stream)
Window(stream, duration) → []Batch
Join(streamA, streamB) → streamC
Dimension Detail
Operations Publish, Subscribe, Transform, Window, Join, Aggregate
Query model Continuous queries over unbounded streams. Event-time processing
Schema Schema registry (Avro, Protobuf, JSON Schema)
Notable Kafka, Flink, Pulsar, NATS JetStream, Redpanda
Key property: Data flows continuously. No "load then query" — queries are always running. Kafka is both the database (log) and the transport.
12

Vector / Similarity

Interface 
Insert(id, vector, metadata)
Search(queryVector, k) → []Neighbor
Query(filter) → []Vector
Dimension Detail
Operations Insert, Search (k-NN), Filter, Hybrid search
Query model Approximate nearest neighbor (ANN) search
Schema Vector dimension + metadata schema
Notable Pinecone, Weaviate, Qdrant, Milvus, Chroma, pgvector
Key property: Queries find "things like this" rather than "things matching this exact key." Similarity replaces equality. The interface is fundamentally different from every other model.
13

Multi-Model

Interface 
SQL("SELECT ...")              // Relational
Cypher("MATCH ...")            // Graph
KV.Get(key)                    // Key-Value
Search(query)                  // Full-text
Vector.Search(embedding, k)    // Similarity
Dimension Detail
Operations Union of multiple interface models
Query model Unified query language (SurrealQL, AQL) or polyglot
Notable ArangoDB, SurrealDB, Fauna, Oracle, PostgreSQL (with extensions)
Key property: One database, multiple access patterns. Reduces operational complexity but may not excel at any single model.
14

Spatial / GIS

Interface 
INSERT INTO locations (name, geo)
  VALUES ('Berlin', ST_Point(13.4, 52.5))

SELECT * FROM locations
  WHERE ST_DWithin(geo, ST_Point(13.4,52.5), 5000)
Dimension Detail
Operations Spatial queries: nearest-neighbor, within-radius, within-polygon, intersection
Query model SQL extensions (PostGIS) or native spatial APIs with R-Tree indexing
Index R-Tree, Geohash, Z-order curve, H3 (hexagonal grid)
Notable PostGIS (#29), SpatiaLite (#141), GeoMesa (#204), Apache Sedona (#221)
Key property: Optimized for 2D/3D geometric queries. Usually a layer on top of relational or columnar, not a standalone engine. PostGIS is just a PostgreSQL extension.
15

Object-Oriented DBMS

Interface 
db.Store(&User{Name: "Alice", Address: &Address{City: "Berlin"}})
user := db.Load<User>(oid)
user.Address.City  // navigated transparently
Dimension Detail
Operations CRUD on object graphs with transparent navigation and lazy loading
Query model OQL, native language queries, or method-based APIs. No impedance mismatch
Schema Object types mirror application classes. Inheritance, polymorphism native
Notable ObjectBox (#171, Go-friendly), Db4o (#173), Objectivity/DB (#226), InterSystems IRIS (#118)
Key property: Eliminates object-relational impedance mismatch. Popular in embedded/mobile (ObjectBox). Lost the ORM war in enterprise but survives in niche domains (CAD, telecommunications, scientific).
16

Content Store

Interface 
session.getNode("/content/articles/2024/intro")
  .setProperty("title", "Hello World")
  .addMixin("mix:versionable")
session.save()
Dimension Detail
Operations Tree-structured content nodes with properties, versioning, access control
Query model XPath, SQL-2 (JCR standard). Full-text search built-in
Schema Node types and mixins (JCR) or flexible schema
Notable Apache Jackrabbit (#72, JCR reference impl), ModeShape (#279)
Key property: Tree-structured document management with built-in versioning, locking, and access control. The JCR (Java Content Repository) standard defines the interface. Niche — mostly CMS/ECM systems.
17

Native XML DBMS

Interface 
// XQuery across XML documents
for $book in doc("catalog.xml")/books/book
where $book/price < 30
return $book/title
Dimension Detail
Operations XQuery, XPath. XML as the native data model, not bolted on
Query model XQuery 3.1 (Turing-complete functional language), XPath 3.1
Schema XML Schema (XSD), DTD, or schema-less
Notable BaseX (#156), eXist-db (#222), Sedna (#201)
Key property: Stores and queries XML natively without relational mapping. Declining category — XML lost to JSON for APIs but survives in publishing, government, and legacy enterprise systems.
18

Navigational / Multivalue (Legacy)

Interface 
// Multivalue: multi-valued fields (arrays as first-class)
OPEN "CUSTOMERS" TO custs THEN
  READ cust FROM custs, "C12345"
  name = cust<1>      ; * attribute 1
  phones = cust<2>     ; * multi-valued
  phone1 = cust<2,1>   ; * first value
END
Dimension Detail
Operations Record-level access via IDs or hierarchical navigation (IMS). Multi-valued fields (Pick/MultiValue)
Query model Procedural navigation (IMS DL/I) or English-like query (Pick/UniQuery). No SQL
Schema Hierarchical (IMS) or dynamic multi-valued dictionaries (Pick/MultiValue)
Notable IMS (#148, 1966, still runs mainframes), Adabas (#97), UniData/UniVerse (#116), IDMS (#205)
Key property: Pre-relational models. IMS (1966) is the oldest DBMS still in production — handles 50B+ transactions/day at major banks. Multivalue/Pick systems run payroll and ERP for thousands of enterprises. Technically obsolete, practically irreplaceable.
Part 2

Storage Engines

01

B-Tree / B+Tree

Storage 
           [Internal Node: Keys + Child Pointers]
          /              |                \
  [Leaf: K,V,K,V]  [Leaf: K,V,K,V]  [Leaf: K,V,K,V]
       ↔ linked list for range scans ↔
Dimension Detail
Structure Balanced tree. Internal nodes: keys only. Leaves: key+value, linked for sequential scan
Read O(log n) point lookup. O(k) range scan via leaf links
Write O(log n) + possible node split/merge. Random I/O
Write amp Medium — page splits touch O(log n) pages
Best for Mixed read/write OLTP. Point lookups + range scans
Used by PostgreSQL (default), MySQL InnoDB, SQLite, LMDB, bbolt
B-Tree vs B+Tree: B-Tree stores values in internal nodes. B+Tree stores values only in leaves (denser internal nodes = shallower tree + leaf links for range scan). Most production databases use B+Tree.
02

LSM-Tree (Log-Structured Merge)

Storage 
Writes → [MemTable (sorted, in-memory)]
              ↓ flush when full
         [SSTable L0] → [SSTable L1] → [SSTable L2] → ...
              ↑ background compaction merges levels ↑
[WAL] → sequential log for crash recovery
Dimension Detail
Structure In-memory sorted table (memtable) + immutable sorted files on disk (SSTables) in levels
Read O(log n × L). Bloom filters skip empty SSTables
Write O(1) amortized — sequential append to WAL + memtable insert
Write amp High — data rewritten during compaction (10-30× for leveled)
Best for Write-heavy workloads. Time-series. Event logs. Large datasets
Used by RocksDB, LevelDB, Pebble, Cassandra, ScyllaDB, InfluxDB
Compaction Write Amp Read Amp Space Amp Best For
Size-tiered Low High High Write-heavy, bulk ingest
Leveled High Low Low Read-heavy, predictable latency
FIFO Lowest Medium Lowest Time-series, cache, TTL
Hybrid Medium Medium Medium Mixed workloads
03

Hash Index

Storage 
hash("user:123") → bucket 7 → [offset → disk position]
                                      ↓
                              [Log file: key, value, ...]
Dimension Detail
Structure In-memory hash map: key → disk offset. Data in append-only log
Read O(1) — hash lookup + single disk seek
Write O(1) — append to log + update hash map
Range scan ❌ Not possible — hash destroys ordering
Best for Pure key-value with no range queries. Caching
Used by Bitcask (Riak), Redis hash tables
04

Columnar Storage

Storage 
Row-oriented:  [id=1,name="Alice",age=30] [id=2,name="Bob",age=25]
Columnar:      id: [1, 2, 3, ...]
               name: ["Alice", "Bob", ...]
               age: [30, 25, ...]
Dimension Detail
Structure Each column stored separately. Per-column compression (RLE, dictionary, delta)
Read Only needed columns loaded. Vectorized processing (SIMD)
Write Slow — must update multiple column files. Batch writes mitigate
Space amp Very low — per-column compression is extremely effective
Best for OLAP. Analytics. Aggregation over many rows, few columns
Used by ClickHouse, DuckDB, Vertica, Parquet, Redshift, Snowflake
05

Append-Only Log / Event Store

Storage 
[Event 1] → [Event 2] → [Event 3] → ... → [Event N]
  ↑ immutable, never modified, only appended ↑
Dimension Detail
Structure Sequential, immutable records. Each record has a position/offset
Read O(n) scan, O(log n) with index. Replay from any position
Write O(1) — append to end. Fastest possible write pattern
Write amp Zero — no in-place updates, no compaction
Best for Event sourcing. Audit logs. CDC. Message queues. Kafka
Used by Kafka, EventStoreDB, go-cqrs-lite events table, Datomic
This is our model. go-cqrs-lite's event store is an append-only log per aggregate, with version as the sequence number.
06

Memory-Mapped (mmap)

Storage 
Process Virtual Memory:
[0x0000 ... Database File ... 0xFFFF]
     ↑ OS handles page faults ←→ Disk automatically ↑
Dimension Detail
Structure Entire database file mapped into virtual address space
Read Direct memory access — no system calls
Write Copy-on-write (LMDB) or in-place with write barriers
Currency Multiple processes can map the same file. Lock-free reads
Used by LMDB, bbolt, SQLite (WAL mode)
Key property: No buffer pool to manage — the OS IS the buffer pool. Reads are just memory dereferences. Writes are copy-on-write for crash safety.
07

Fractal Tree (Cache-Oblivious B-Tree)

Storage 
[Root with buffer] → [Internal with buffer] → [Leaf]
       ↓ flush              ↓ flush
  Messages buffered in internal nodes, flushed in batches
Dimension Detail
Structure B-Tree where internal nodes contain message buffers
Read O(log_B N) — must check buffers along the path
Write O(log_B N / B) — amortized, messages batched in buffers
Write amp Very low — messages flushed in bulk
Used by TokuDB (acquired by Percona, now EOL)
Key property: Combines LSM's write throughput with B-Tree's read performance. Writes accumulate in node buffers and flush in batches.
08

Adaptive Radix Tree (ART)

Storage 
Node4:  [≤4 children, compact]   → Node16: [≤16 children]
                                      → Node48: [≤48 children]
                                         → Node256: [256 children]
Dimension Detail
Structure Trie that adapts node size to occupancy (4 → 16 → 48 → 256 children)
Read O(k) where k = key length. Cache-friendly, SIMD-optimizable
Write O(k) — node type promotion/demotion as needed
Space Very compact — empty slots not allocated
Go impl github.com/plar/go-adaptive-radix-tree — production-ready, ~500★
Used by HyperLevelDB (index), Hyrise (in-memory DB), go-adaptive-radix-tree (Go)
09

BW-Tree (Latch-Free B-Tree)

Storage 
Page A → [delta 3] → [delta 2] → [delta 1] → [base page]
              ↑ CAS chain — updates without latches ↑
Dimension Detail
Structure B-Tree with latch-free updates via CAS delta chains
Read O(log n) — follow delta chain to base page
Write O(log n) — prepend delta via CAS. No latches
Currency Excellent — no lock contention on multi-core
Used by Microsoft Hekaton (SQL Server in-memory OLTP)
10

Time-Structured Merge Tree (TSM)

Storage 
[Cache] → flush → [TSM File: time-sorted, compressed per field]
                       ↓ compaction → [Larger TSM File]
Dimension Detail
Structure LSM variant: shard by time range, compress per-field
Read Time-range scan. Delta-of-delta + Gorilla float compression
Compression Exceptional — 10-20× on time-series data
Used by InfluxDB
11

Vector Index (HNSW / IVF)

Storage 
HNSW:                       IVF:
  Layer 2: [sparse]           [Centroid 1] → [vectors near 1]
  Layer 1: [medium]           [Centroid 2] → [vectors near 2]
  Layer 0: [dense]            [Centroid N] → [vectors near N]
Dimension Detail
HNSW Hierarchical navigable small world graph for ANN
IVF Inverted file index. Partition via centroids
Read O(log n) approximate. Recall vs speed tradeoff
Used by Pinecone, Weaviate, Qdrant, Milvus, pgvector
12

Copy-on-Write B-Tree (CoW)

Storage 
Write: Modify leaf → copy path to root → atomically swap root pointer
Old root still valid → readers see consistent snapshot
Dimension Detail
Structure B-Tree where every write creates new node copies up to root
Read O(log n) — no latches needed, consistent snapshot
Write O(log n) — copies O(log n) nodes per write
Currency Excellent — readers never block, single writer
Used by LMDB, ZFS (filesystem), bbolt

Relevance to go-cqrs-lite

What we use today

SQLEventStore

Ordered KV (keyed by aggregate+version) → B+Tree via PostgreSQL / SQLite / Turso

PebbleEventStore

Ordered KV (keyed by aggregate+version) → LSM-Tree via Pebble

SQLSnapshotStore

Simple KV (keyed by aggregate) → B+Tree

SQLCheckpointStore

Simple KV (keyed by projection name) → B+Tree

SQLOutbox

FIFO queue (status-filtered) → B+Tree

Our actual access pattern (despite using SQL as backend)

1. Event Store

Ordered KV with prefix scan (load all events for aggregate) + append (save events)

2. Snapshot Store

Simple KV — Get/Put by aggregate key

3. Checkpoint Store

Simple KV — Get/Put by projection name

4. Outbox

FIFO queue with status filter — poll pending, ack

Engines that fit our patterns

✓

LSM-Tree (Pebble, BadgerDB)

Fits
Append-heavy (events are append-only), prefix scan for aggregate loading. Trade-off: read amplification for large histories — mitigated by snapshots.
✓

B+Tree (PostgreSQL, SQLite)

Fits
Point lookup for snapshots/checkpoints, range scan for events. Trade-off: write amplification on high-ingest — acceptable for most workloads.
✓

Append-Only Log (Kafka-style)

Fits
Natural fit for event sourcing — events ARE append-only. Trade-off: no per-aggregate random access without secondary index.
✓

CoW B+Tree (LMDB)

Fits
Snapshot reads for free (time-travel), lock-free readers. Trade-off: single writer bottleneck — acceptable for embedded use.
★

Unified Backend

Part 5

Advanced / Hybrid Architectures

FoundationDB Layer Architecture

Storage: Ordered KV (serialized MVCC) + distributed consensus (Raft-like).
Interface: Raw KV is the only interface. SQL, Document, Graph — all built as layers on top.

Lesson: A single well-designed KV interface can power any higher-level model. This is the "data store aware but independent" principle taken to its extreme.

Datomic Database as a Value

Storage: Append-only transaction log (DynamoDB) + 5 sorted indexes (S3) + cache (EFS).
Interface: Datalog queries against immutable database values (snapshots).

Lesson: Every query sees a consistent point-in-time snapshot. "Time-travel" is free because history is never overwritten. This is the gold standard for event sourcing.

TigerBeetle Deterministic Single-Thread

Storage: LSM forest with direct I/O, no OS page cache.
Interface: Two-phase accounting transfers (debit + credit in one operation).

Lesson: Single-threaded deterministic execution eliminates entire classes of concurrency bugs. For financial data, this is worth the throughput trade-off.

SurrealDB Multi-Model Pluggable

Storage: Pluggable — RocksDB (embedded), TiKV (distributed), IndexedDB (browser).
Interface: SurrealQL covers document, graph, relational, vector in one query language.

Lesson: The "backend is pluggable" pattern is viable. Same query language, different storage. Aligns with our kv.Store abstraction approach.

NATS JetStream Potential go-cqrs-lite Backend

Storage: File (disk, RAFT-replicated) or Memory. Subject-partitioned append-only streams with configurable retention.
Interface: Three built-in data models on one server — Streams (append-only log), KeyValue (KV with history + CAS), ObjectStore (binary blobs).

// Go client: github.com/nats-io/nats.go/jetstream
js, _ := jetstream.New(nc)

// Event Store → Stream (append-only, per-aggregate via subjects)
stream, _ := js.CreateStream(ctx, jetstream.StreamConfig{
  Name: "events", Subjects: []string{"events.{type}.{id}"},
  Retention: jetstream.LimitsPolicy,
})
ack, _ := js.Publish(ctx, "events.User.01H4...", payload)

// Snapshot + Checkpoint → KeyValue bucket
kv, _ := js.CreateKeyValue(ctx, jetstream.KeyValueConfig{Bucket: "snapshots"})
rev, _ := kv.Put(ctx, "User:01H4...", snapshotBytes)
entry, _ := kv.Get(ctx, "User:01H4...")

// Outbox → WorkQueue Stream (exactly-once, auto-delete after ack)
outbox, _ := js.CreateStream(ctx, jetstream.StreamConfig{
  Name: "outbox", Retention: jetstream.WorkQueuePolicy,
})
consumer, _ := outbox.CreateOrUpdateConsumer(ctx, jetstream.ConsumerConfig{
  AckPolicy: jetstream.AckExplicit,
})
Why it matters for go-cqrs-lite: A single NATS server replaces PostgreSQL/SQLite (for SQL storage) + message broker (for outbox/bus). The KeyValue API is remarkably close to our proposed kv.Store interface — Get/Put/Delete/Watch with revision-based CAS and history. For edge deployments and single-binary scenarios, JetStream + Pebble covers the full spectrum from embedded to distributed.

Columnar OLAP — The Projection Powerhouses

Both are columnar OLAP engines. Both are wrong for the event store (row-level access). Both are phenomenal for the read side of CQRS — materialized views, projection stores, real-time analytics on event streams.

DuckDB Embedded OLAP — SQLite for Analytics

Storage: Columnar, vectorized execution (2,048-row batches), mmap-based, in-process (no server).
Interface: Full SQL, database/sql compatible Go driver. Reads Parquet, CSV, JSON, Arrow natively — no import needed.

// Go: github.com/duckdb/duckdb-go/v2 — full database/sql compat
db, _ := sql.Open("duckdb", "projections.ddb")

// Query Parquet event files directly — no import
rows, _ := db.Query(`SELECT aggregate_id, count() as events,
  max(timestamp) as last_event FROM read_parquet('events/*.parquet')
  GROUP BY aggregate_id`)

// Build projection table from event stream
db.Exec(`CREATE TABLE user_read_model AS
  SELECT aggregate_id, json_extract(payload, '$.name') as name,
    json_extract(payload, '$.email') as email,
    max(version) as current_version
  FROM read_parquet('events/*.parquet')
  WHERE event_type = 'UserCreated'
  GROUP BY aggregate_id`)

ClickHouse Distributed OLAP — Petabyte-Scale Analytics

Storage: Columnar, MergeTree engine family (ReplacingMergeTree, CollapsingMergeTree, AggregatingMergeTree, SummingMergeTree). RAFT-based replication.
Interface: Full SQL with materialized views. Go client: native API (clickhouse.Open) + database/sql (clickhouse.OpenDB).

// Go: github.com/ClickHouse/clickhouse-go/v2
conn, _ := clickhouse.Open(&clickhouse.Options{
  Addr: []string{"clickhouse:9000"},
})

// Event table — append-only, partitioned by month
conn.Exec(ctx, `CREATE TABLE events (
  event_id UUID, aggregate_id String, event_type String,
  version UInt32, payload String, timestamp DateTime64
) ENGINE = MergeTree()
  PARTITION BY toYYYYMM(timestamp)
  ORDER BY (aggregate_id, version)`)

// Materialized view — auto-projection on insert!
conn.Exec(ctx, `CREATE MATERIALIZED VIEW user_stats_mv
  TO user_stats AS
  SELECT aggregate_id, event_type, count() as cnt,
    max(timestamp) as last_seen
  FROM events GROUP BY aggregate_id, event_type`)

// Bulk insert — millions of events/sec
batch, _ := conn.PrepareBatch(ctx, "INSERT INTO events")
batch.Append(uuid.New(), "User:01H4", "UserCreated", 1, payload, time.Now())
batch.Send()

The MergeTree engine family handles deduplication (ReplacingMergeTree), state cancellation (CollapsingMergeTree), and pre-aggregation (AggregatingMergeTree). For enterprises running go-cqrs-lite at scale, a clickhouse/ projection module would complement the PostgreSQL event store with real-time analytics.

Event Sourcing, Bitemporal & Versioned — Directly Related to go-cqrs-lite

These databases share architectural DNA with go-cqrs-lite: immutable logs, time-travel queries, bitemporal tracking, or event-first design. Direct competitors or inspirations.

XTDB Bitemporal Datalog — Event Sourcing Competitor

Storage: Append-only transaction log + Lucene indexes + object store (S3/GCS). Documents are never updated — new versions are appended.
Interface: Datalog (Clojure), SQL:2023 (Java/XNode), XTQL. First-class bitemporal: valid-time + transaction-time on every document.

Why it matters: XTDB (formerly Crux) is the closest direct competitor to go-cqrs-lite in the event sourcing space. It's bitemporal (tracks both "when did this happen" and "when did we record it"), supports time-travel queries natively, and treats documents as immutable event streams. The Clojure ecosystem means it targets different users, but the architectural overlap is significant. #289 in DB-Engines ranking.

Dolt Git-for-Data — Versioned SQL

Storage: Prolly Trees (probabilistic B+Tree) — content-addressed, enabling structural sharing between versions like Git.
Interface: Full MySQL-compatible SQL. Git semantics: dolt commit, dolt diff, dolt merge, dolt revert on relational data.

Why it matters: Dolt applies Git's branching/merging model to relational data. Every table state is versioned, diffable, and mergeable. For event sourcing, this is fascinating — the event log IS the Git history. Prolly Trees achieve O(log n) reads with content-addressed deduplication. #190 in DB-Engines ranking.

Distributed SQL & Wide-Column — Scale-Out Architectures

For deployments where a single PostgreSQL instance isn't enough. These databases distribute data across nodes while maintaining SQL or wide-column interfaces.

TiDB Distributed HTAP — MySQL-Compatible

Storage: RAFT-replicated MVCC storage (TiKV, based on RocksDB) for OLTP + columnar (TiFlash) for OLAP. Separate engines, one SQL surface.
Interface: MySQL-compatible SQL. Transparent sharding. Go client via MySQL protocol.

Why it matters: TiDB proves the "HTAP" (hybrid transactional/analytical) model works at scale. For go-cqrs-lite, TiDB could use the MySQL dialect variant of our storage module. The TiKV layer (RocksDB-based) aligns with our Pebble adapter strategy. #84 in DB-Engines ranking.

ScyllaDB C++ Cassandra — 10× Latency

Storage: LSM-Tree (C++ rewrite of Cassandra's Java storage). Shard-per-core architecture. No JVM, no GC pauses.
Interface: Cassandra-compatible CQL. Same data model, 10× lower latency, same operational knowledge.

Why it matters: ScyllaDB demonstrates that the storage engine language matters. C++ with shard-per-core threading eliminates GC pauses and cross-core coordination. For event sourcing at scale, ScyllaDB's append-optimized LSM with tunable consistency is a viable event store backend. #69 in DB-Engines ranking.

CockroachDB / YugabyteDB Distributed PostgreSQL

Storage: Pebble (CockroachDB) or RocksDB (YugabyteDB) under the hood. RAFT-based replication. MVCC with hybrid logical clocks.
Interface: PostgreSQL-compatible SQL (YugabyteDB) or PostgreSQL-wire-protocol SQL (CockroachDB).

Why it matters: Both are drop-in PostgreSQL replacements for distributed deployments. CockroachDB uses Pebble — the same engine our pebble/ module wraps. Our PostgreSQL dialect should work with minimal modification. CockroachDB #73, YugabyteDB #122.
