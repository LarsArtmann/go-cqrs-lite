Cache-Line & Data Layout Analysis 2026-06-02 — Memory hierarchy, struct layout, pointer chasing, and server-CPU implications

Server CPU Baseline

This analysis targets general server hardware, not desktop/workstation CPUs. The library must perform well on AWS c6a, GCP n2, Azure D-series, and bare-metal EPYC/Xeon deployments.

Attribute Desktop (for reference) Typical Server (EPYC/Xeon) Impact on our code

L2 per core 1–2 MB 512 KB – 1 MB Fewer events fit — 500 KB ≈ 1,800 reordered events
L3 shared 40 MB 16–32 MB (shared 32–128 cores) Effective L3 per core: 0.25–1 MB — cannot rely on L3

AVX-512 Yes Mixed (Xeon 4th+ yes, EPYC no) Cannot rely on AVX-512

Key insight: On a 64-core EPYC sharing 32 MB L3, per-core L3 budget is ~500 KB. Under load, 32+ cores scanning event streams means L3 is constantly evicted — you live in L2 (512 KB) or hit RAM (~100 ns per miss). Every byte wasted in struct layout is a real throughput cost.

ImmutableEvent Layout — The Core Problem

Current layout (~280+ bytes, 4–5 cache lines minimum)

Offset  Field              Size   Hot-path access?
──────  ─────────────────  ────   ────────────────
0       id                 16     signing canonical
16      eventType          16     EVERY iteration (filter, fold, dispatch)
32      aggregateID        16     listing, signing, iteration
48      aggregateType      16     listing, signing, iteration
64      version            8      EVERY iteration (fold, validate, key)
72      schemaVersion      8      serialize, upcaster
80      encoding           16     decode path only
96      payload            24     decode, serialize (CLONED on every access!)
120     metadata           ~120   serialize, tombstone (CLONED on every access!)
240     occurredAt         24     timestamp filtering, sorting
264     clock              8      construction only
272     newCodec           8      construction only
280     deadline           24     rarely accessed
The two most-iterated fields (eventType at +16 and version at +64) are in different cache lines. When iterating 10,000 events to filter by type, you pull in the entire 280-byte struct per element — 4–5 cache lines — to read 16 bytes. On a server with 32 KB L1D, that's only ~6–8 events' hot data in L1 at once.

Proposed layout — hot fields first, grouped by access pattern

type ImmutableEvent struct {
    // Cache line 0 (0–63): accessed by EVERY iteration
    eventType     Type           // +0   — filter/fold/dispatch
    aggregateID   id.AggregateID // +16  — listing/signing
    version       Version        // +32  — fold/validate
    aggregateType AggregateType  // +40  — listing/signing
    occurredAt    time.Time      // +48  — timestamp filter (24 bytes, spills to line 1)

    // Cache line 1 (64–127): construction + query access
    id            id.EventID     // +72
    schemaVersion SchemaVersion  // +88
    encoding      codec.Encoding // +104

    // Cache line 2+ (128+): heavy data, rarely touched in iteration
    payload       []byte         // +120
    metadata      Metadata       // +144
    clock         Clock          // +264
    newCodec      codec.Codec    // +272
    deadline      time.Time      // +280
}

Filtering by Type + Version hits cache line 0 only. L1 holds ~16 events' hot fields (vs ~6–8 before). L2 (512 KB) holds ~2,000 events' hot fields — enough for most aggregate streams. Hardware prefetcher streams sequential cache lines efficiently.

Problem 1: []Event = Pointer Chasing

Single biggest cache-layout problem. []event.Event is a slice of interfaces — each element is 16 bytes: (type pointer, data pointer). Every iteration dereferences a pointer to a heap-allocated ImmutableEvent. Iterating 10,000 events = 10,000 random heap reads = 10,000 potential cache misses. On a server under load, those pointers are scattered across NUMA nodes.

Fix A: Contiguous []ImmutableEvent for internal paths

For MemoryStore and pebble deserialization, store events as a contiguous slice of value types. Convert to []Event only at API boundaries: 

// internal: cache-friendly layout
type eventBlock struct {
    events []ImmutableEvent  // contiguous in memory
}

// Fold/Filter operate on the block directly — no interface dispatch, no pointer chasing
func (b *eventBlock) FilterByType(t Type) []ImmutableEvent { ... }

10,000 × 280 bytes = 2.8 MB. Does not fit in L2 on a server (512 KB), but sequential access means the hardware prefetcher streams from RAM at ~10 GB/s effective throughput. Compare: pointer chasing into RAM at ~100 ns per miss × 10,000 = 1 ms in stalls alone, vs sequential scan at ~300 ns.

Impact is larger on servers than desktops: 64 cores all pointer-chasing means L3 is constantly evicted, TLB misses compound (each ImmutableEvent likely on a different 4 KB page), and NUMA cross-socket hops add ~90 ns per miss.

Fix B: SoA (Struct of Arrays) for hot filter fields

When you only need Type, Version, OccurredAt for filtering, don't walk the full struct: 

type eventIndex struct {
    types      []Type       // 16 bytes × N
    versions   []Version    // 8 bytes × N
    timestamps []int64      // 8 bytes × N  (UnixNano)
    offsets    []uint32     // 4 bytes × N  — index into full event storage
}

Filter 10,000 events by type: scan 160 KB of types[] — fits in L2, pure sequential access, hardware prefetcher-optimal. Then index into full events only for matches.

Problem 2: Payload() and Metadata() Clone on Every Access

event.go:161 — slices.Clone(e.payload) on every Payload() call. event.go:167 — metadata.Clone() on every Metadata() call. In SharedInsertEvents (storage/), this means 2 clone allocations per event per insert — for a path where the caller is the store itself (trusted).

Impact at server scale

A 64-core server running 10,000 events/sec per core = 640K events/sec. Each event ~280 bytes = 179 MB/s raw data. Add Payload() + Metadata() clones and you're at ~500 MB/s just for defensive copies. On DDR4 servers with ~50 GB/s shared BW across all cores, that's 1% of total system bandwidth on copies alone — before business logic.

Fix — internal uncloned access

// Public: safe copy (Event interface method)
func (e *ImmutableEvent) Payload() []byte { return slices.Clone(e.payload) }

// Package-private: for trusted callers (storage, serialization)
func (e *ImmutableEvent) payloadBytes() []byte { return e.payload }

Problem 3: time.Time — 24 Bytes Per Instance

time.Time = wall (8) + ext (8) + loc (*Location, 8). Three instances across event fields (occurredAt, deadline) and checkpoint paths. At 640K events/sec throughput, that's 46 MB/s of time.Time data flowing through caches.

Fix — store occurredAt as int64 (UnixNano) internally

type ImmutableEvent struct {
    occurredAtNano int64  // 8 bytes instead of 24
    // ...
}

func (e *ImmutableEvent) OccurredAt() time.Time {
    return time.Unix(0, e.occurredAtNano)
}

Saves 16 bytes per time.Time converted → 16 bytes per event (for occurredAt alone). Over 10,000 events = 160 KB less memory pressure. Comparison occurredAtNano > thresholdNano is a single int64 compare vs time.Time.Compare() which checks both wall and ext.

Problem 4: Pebble LoadToTimestamp — Full JSON Deserialization to Check One Field

pebble/iteration.go:127 — deserializes the entire JSON event, builds an ImmutableEvent, just to call OccurredAt(). Then discards the event if past threshold. At 5.4 ms for a full scan, most of the time is JSON unmarshal of events that are immediately thrown away.

Fix — extract timestamp without full JSON unmarshal

// Fast path: extract occurred_at from JSON without full unmarshal
// Scan for "occurred_at":<number> — ~50 ns vs ~500 ns full unmarshal
func extractTimestamp(data []byte) (int64, bool) {
    idx := bytes.Index(data, []byte(`"occurred_at":`))
    if idx == -1 { return 0, false }
    // parse the int64 that follows
    ...
}

Or store occurredAt in the Pebble key itself — then range scan handles it natively with no deserialization at all.

Problem 5: Metadata — 120 Bytes Copied Per Access

Metadata.Clone() copies 120 bytes of fixed fields + maps.Clone. Most hot paths that read Metadata() only check Custom[MetadataKeyTombstone] or serialize it.

Fix — fast-path for Custom map access

func (e *ImmutableEvent) HasCustom(key MetadataKey) (string, bool) {
    if e.metadata.Custom == nil { return "", false }
    v, ok := e.metadata.Custom[key]
    return v, ok
}

Problem 6: MemoryStore — False Sharing on Mutexes

type MemoryStore struct {
    dispatcher.Lifecycle     // contains mu sync.RWMutex (16 bytes)
    mu     sync.RWMutex      // another 16 bytes — likely in SAME cache line
    events map[string][]event.Event
}

Two sync.RWMutex values potentially sharing a cache line. Under contention (many goroutines reading), the atomic counter in RWMutex causes cache-line bouncing between cores. On a 64-core EPYC, this is a measurable scalability limiter.

Fix — pad to separate cache lines

type MemoryStore struct {
    lifecycle dispatcher.Lifecycle
    _         [48]byte        // pad to own cache line
    mu        sync.RWMutex
    _         [48]byte        // pad to own cache line
    events    map[string][]event.Event
}

Problem 7: MemoryStore — Map Rehash Spikes

MemoryStore.events is a map[string][]event.Event. Go maps rehash when they grow, causing a stop-the-world spike proportional to map size. Under sustained event ingestion on a busy server, this map grows continuously, triggering periodic rehashes that stall all goroutines. Amortized cost is fine on desktop; on a server serving live traffic, it causes latency spikes.

Fix — sorted append-only log + stream index

type MemoryStore struct {
    log   []event.Event          // append-only, sorted by insertion order
    index map[string][2]int      // aggregate key → (start, end) in log
}

ReadAll becomes return s.log (zero-copy). Load uses the index for a slice slice. No sorting needed if insertion order matches occurrence order.

Problem 8: Projection filterFromCheckpoint — O(n×m) Type Filter

projection/runner_filter.go:40 — slices.Contains(types, evt.Type()) per event. With 50 event types and 100K events, that's 5M string comparisons.

Fix — map[Type]struct{} for O(1) lookup

typeSet := make(map[event.Type]struct{}, len(types))
for _, t := range types { typeSet[t] = struct{}{} }

for _, evt := range all {
    if _, ok := typeSet[evt.Type()]; ok { ... }
}

Prioritized Improvement Plan (Server-First)

NUMA Considerations (Multi-Socket Servers)

  • Go's memory allocator is NUMA-unaware — events allocated on socket 0 may be consumed on socket 1 = ~130 ns cross-socket hop vs ~40 ns local
  • No code changes needed — this is an ops-level concern: pin Go goroutines to NUMA nodes via numactl or runtime.LockOSThread
  • The contiguous layout fixes (change 6) partially mitigate this: sequential access is prefetcher-friendly even across NUMA boundaries
