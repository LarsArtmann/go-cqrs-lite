Commands vs Facts

LiveStore and DataStar, interrogated on one question: where does the decision boundary live? The owner’s suspicion about LiveStore is verified — and it is the exact fault line the rest of the local-first industry converged away from. What each choice costs, and the shape that keeps LiveStore’s UX without surrendering the decider.

00Summary

The owner’s dislike of LiveStore was a hypothesis: “they don’t seem to have the concept of Commands.” Verified: they do not. A LiveStore client calls store.commit(events) and the events are the mutation — there is no intent-vs-state decision step, no rejection path that can consult authoritative current state, and the consequences surface where they are hardest to fix: merge-conflict handling is still unimplemented (open issue #253, reopened May 2026, blocked on an unbuilt “facts system”).

Meanwhile the rest of the local-first industry converged on the opposite pole: Replicache and Zero run client mutators speculatively and re-run them authoritatively on a server push endpoint; ElectricSQL ships read-path sync only and routes every write through your own API. In CQRS vocabulary they all reinvented the Command boundary. go-cqrs-lite was born with it.

System Who mints facts (events) Can the answer be “no”? Where decide() lives
LiveStore The client, directly (store.commit) Only payload-schema errors; state checks see pre-commit local state Nowhere (the gap)
Replicache / Zero The server, after re-running the queued intent Yes — server may compute a different outcome; rejects revert the optimistic client state Server push/mutate endpoint
ElectricSQL Your API (write-path sync explicitly out of scope) Yes — writes are plain API calls Your handlers
DataStar The server (there is no client write model at all) Yes — the docs mandate backend validation Your handlers — by construction
go-cqrs-lite The decider, always Yes — Rejection family is a first-class error family Server-side decider (L4 keeps it there)
The bottom line The fault line is who is allowed to say what happened. LiveStore answers “the client, optimistically” and is still paying for it in unimplemented conflict resolution. Everyone else answers “the server, after judging an intent” — which is the Command, rediscovered. This repo’s L4 offline tier, if ever opened, syncs queued Commands into server-side deciders — never client-minted events; DataStar needs nothing new because it never took the boundary away. The owner’s instinct was the correct architecture review.

01Command vs Fact, precisely

The distinction this whole report turns on, in this repo’s own vocabulary:

Command Event (Fact)
What it is Intent: a request that the world change Immutable truth: something that happened
Who may create it Anyone (a user, a browser, a cron) Only the decider, after deciding
Can it be refused? Yes — decide(state, cmd) may return a Rejection after consulting current state No — refusing a fact is a category error; the decision already happened
Timing Pre-decision Post-decision

This is exactly the DOMAIN_LANGUAGE “Record vs Event vs Command” row: a Command is a Record of intent (may be rejected); an Event is a Record of a fact (immutable truth). Collapse the two — let the client write facts — and every business rule that depends on current state (“email not already taken”, “balance sufficient”, “item not already deleted”) loses its enforcement point. That is the critique to test against LiveStore, not a strawman: maybe they enforce it elsewhere.

02LiveStore, verified

Primary sources: docs.livestore.dev (llms.txt index, main concepts, sync, contributing, eventschemas pages) and the GitHub repo, fetched 2026-11-22. Quotes verbatim; status: v0.5.0, self-described “beta”, Apache-2.0, developed full-time by Johannes Schickling (since 2021), incubated as the foundation of his local-first music app Overtone, sponsors include ElectricSQL, Netlify, Expo, Axial. No hosted backend; self-hosted sync only.

02.1 · The verdict on Commands: absent, confirmed

The word “command” appears in their docs exactly where you’d find it if the concept existed — and it doesn’t: CLI usage. The mutation primitive is: 

const store = useStore(app)
store.commit({ type: 'todoCreated', ...args })

The client authors the event. Sync then pushes event batches to the backend, which validates payloads and assigns a global sequence number — it judges shape and order, never business outcome. There is no artifact in the system whose job is “given current state and an intent, emit events or reject.”

02.2 · The ladder of “no” — what a LiveStore client can and cannot be told

Check that exists When it runs State it can see Can enforce business invariants?
Effect-Schema payload validation (types, required, defaults) on event tables At store.commit, client-side The event payload only No — shape, not meaning
Synchronous callback on store.commit Before local materialization Pre-commit state only — it cannot see the batch’s own effects or a concurrent remote writer’s state Partially, on stale data — a race window by construction
Materializers (event → SQL) After commit Post-state — but they must be deterministic; they cannot reject, roll back, or branch No — projection, not policy
Sync-backend validation On push, server-side Payload schema + seqNum ordering No — it is a serializer/orderer, not a decider

The strongest rung is the commit callback — and it is client-side, pre-state, and blind to concurrency. Everything a decider does is squeezed into the one place it cannot be done.

02.3 · The sync model (the part worth stealing)

  • Git-like: push batches of new events, pull batches of new events since a cursor; batch headers carry {seqNum, parentSeqNum, name, args}.
  • The server assigns the global total order; sync backends must process one push at a time; a client pushing into a moved head gets ServerAheadError → pull → rebase its pending events (a rebaseGeneration counter tracks exactly this).
  • Optimistic by default: every commit is applied locally immediately; pending events are distinguished from confirmed ones; clients can stream only backend-confirmed events.
  • Client-only events (never synced, last-write-wins) exist for UI state — a clean seam this repo would not need (browser state is not domain state).

02.4 · Where the missing boundary bites: conflicts, still unimplemented

Issue #253 (merge-conflict handling) is open, was reopened May 2026, and depends on issue #254 — an unbuilt “facts” system. The README markets “custom merge conflict resolution”, which in practice means: your app re-applies its own event in a callback during rebase. This is the tax of client-minted facts — two clients that both committed “the truth” produce a structural conflict the platform cannot resolve, because no component ever had the authority to say “no” before the facts existed. In a command-first system that collision is not a merge problem at all: the second intent simply loses at decide() and the client reverts its optimistic state — the exact semantics Zero ships today.

02.5 · Be fair: what LiveStore gets right

+
Optimistic UI with an honest ledger Pending vs confirmed events, rebase generations, and nanoid-based global IDs give the UX layer exactly the vocabulary an offline client needs.
+
Eventlog ≠ state, dual SQLite The eventlog is the source of truth; materialized state is disposable and rebuildable — the same ADR-0136 ladder this repo enforces (replayable → compensable → must-be-an-event).
+
Typed event tables Effect-Schema event definitions with defaults and validation are genuinely good developer UX — the same goal as our catalog schema registration, aimed at the same problem from the TS side.
+
Serious, funded, solo-driven Full-time since 2021, real app (Overtone) eating the dogfood, respected sponsors. This is not a toy — which is exactly why its architectural bet is worth understanding rather than dismissing.

Not fetched (UNVERIFIED): the cookbook pattern pages (state machines, undo/redo) and the @livestore/livestore API reference beyond the concepts pages; the “facts system” (#254) design does not exist in public form yet.

03The industry answer: everyone else kept the boundary

Verified 2026-11-22 against primary docs. Three engines, one converged model: read-path sync to the client, write-path judgment on the server.

Replicache — speculative client, authoritative server

  • “Mutators are arbitrary functions that run once on the client immediately (aka ‘optimistically’), and then run again later on the server (‘authoritatively’) during sync.”
  • The push endpoint receives mutator name + args — intents, not state: “executes the pushed mutations in order … canonicalizing the mutations’ effects in the server’s state.”
  • “It is important to understand that the push endpoint is not necessarily expected to compute the same result that the mutator on the client did. This is a feature. … In Replicache, the server is authoritative.”
  • Even failure is a server judgment: “If a mutation is invalid or cannot be handled, the server must still mark the mutation as processed.”

Zero (Rocicorp) — the same shape, named plainly

  • “A copy of each mutator exists on both the client and on your server … the server can add extra checks to enforce permissions, or send notifications or interact with other systems.”
  • You must implement the mutate endpoint; zero-cache calls it per mutation, running the server-side mutator in a transaction.
  • Rejection semantics: “The mutation is skipped and the next mutation runs as normal. The optimistic mutation on the client will be reverted.” Their own heading: “Server authority to the rescue!”

ElectricSQL — declined the write path entirely

  • “Electric does read-path sync … It does not do write-path sync. It doesn’t provide (or prescribe) a built-in solution for getting data back into Postgres.”
  • All four documented write patterns are server-mediated (REST calls, optimistic wrappers over REST, a change-log syncer); “If an offline write is rejected by the server, the local application needs to find some way to revert the local state.”
Read the convergence in CQRS terms Replicache’s “push endpoint” and Zero’s “mutate endpoint” are Command handlers. The “speculative client run” is optimistic UI. The “revert on rejection” is a Rejection-family error surfacing to the fold. The entire local-first industry re-derived Commands — and this repo already owns the concept, the error taxonomy (errorfamily.NewRejection), and the decider primitive. LiveStore is the one serious bet on the other pole.

04DataStar, deeper than the sibling report

The 2026-11-07 sibling report established the baseline (33,553 B raw / 13,365 B gzip client; the go-sse → go-datastar → cqrs-htmx/datastar → templ-components/wire stack the fleet already owns; the metaengine/datastaradapter proposal). This section covers what is new or unexamined: verified against data-star.dev and the GitHub org on 2026-11-22.

04.1 · Delta since the sibling report

  • Client v1.0.5 shipped 2026-11-09 (five weeks after the v1.0.4 the sibling verified); cadence is healthy. The official Go SDK remains v1.2.2 (2026-06-02) — the fleet’s own go-datastar v0.6.3 wrapper is not behind on anything that matters.
  • Nothing in the delta changes the sibling’s adapter design; its P0–P2 rollout stands as written.

04.2 · The protocol is exactly two events — and that is the whole contract

event: datastar-patch-elements
data: elements <tr id="user-42">...

event: datastar-patch-signals
data: signals {"projectionLagMs": 12}
  • patch-elements: HTML fragments with nine patch modes (outer/inner/replace/prepend/append/before/after/remove); morph is ID-based (the sibling’s “stable IDs” rule).
  • patch-signals: a JSON object deep-merged into the reactive store; null removes a key; onlyIfMissing seeds defaults.
  • No third event type exists. A read model served as signals is a one-line encoder from a Watcher[V]; served as HTML it takes the caller-supplied renderer the sibling proposed.

04.3 · The command half: fetch actions, and a docs mandate for the boundary

  • Writes are @post/@put/@patch/@delete (and @query, the QUERY method, since v1.0.4) — plain HTTP to your handlers, with Datastar-Request: true and the signals object as JSON body ({datastar: *}; @get puts them in the query string instead).
  • Their security docs, verbatim: “always implement backend validation” — DataStar itself tells you the browser is not the decision-maker. CSP: default build needs unsafe-eval for expressions; an opt-in CSP mode with data-nonce exists (v1.0.3+); expressions are a real XSS surface if user data is ever interpolated into them (sibling’s limits section covers the mitigation rules).
  • Pro tier boundaries (verified): $349/$399 solo lifetime, $1,299/$1,499 team ≤25 — gates ~a dozen convenience attributes (data-animate, data-persist, data-query-string…) and actions (@clipboard, @fit, @intl) plus devtools. Rocket (bundler) moved out of Pro in v1.0.4. None of the gates touch the protocol or the SSE contract — the sibling’s design already avoided all of them.

04.4 · Where DataStar sits on the fault line

DataStar has no client write model at all — no local store, no mutation queue, no sync. That absence is why it composes so cleanly with this repo: the CQRS boundary is not something DataStar respects or violates; it simply never touches it. Commands remain HTTP calls into handlers that dispatch to deciders; events reach the browser only as derived rendering (fragments or signals over SSE). Commands are first-class by construction — the exact property LiveStore lacks and Replicache/Zero rebuilt.

05The synthesis for this repo

Put every option on one axis — who mints facts — and the front-end strategy from the 11-21 report becomes a placement decision, not a new architecture:

who mints facts? ├── server only, no client model — DataStar (render target browser) ├── server only, typed thin client — contracts pipeline (11-21 report, L2/L3) ├── server, after judging queued intents — L4 offline tier (this report's shape) └── client, optimistically — LiveStore (the pole we decline)

05.1 · L4, redesigned: an offline command queue, not event sync

If the local-first gate ever opens (named consumer + offline requirement, per the 11-21 report), the verified industry shape is the design — and this repo already owns every server-side piece:

Replicache / Zero concept go-cqrs-lite equivalent (exists today)
Client mutation queue (name + args) PersistedCommand over command.CommandSink — the durable command journal is already a product surface; the client-side queue (IndexedDB) is the only new code
Exactly-once push processing idempotency / engine DedupStore — deterministic command IDs are already the documented pattern (id.DeriveCommandID, deriver.Idempotent())
Server push/mutate endpoint The command dispatcher itself — deciders run behind it, Rejections flow back as first-class errors
Speculative client run + revert on reject Optimistic local fold of the expected event, reverted on Rejection — requires fold purity on the client, the same constraint Zero imposes on its mutators
Pull (read-path sync) Journal tail (SeekableJournal.ReadFrom) or per-view Watcher replay — Last-Event-ID semantics already tested in sse_replay_test.go
The one rule that falls out of this research Clients may queue intents and fold projections; only deciders mint events. That single boundary keeps LiveStore’s UX (optimistic, offline, local reads) while avoiding precisely the debt they are still paying (#253): in a command-first system, a concurrent collision is a decide() rejection, not an unresolvable structural merge.

05.2 · LiveStore concept → this repo, translated

LiveStore go-cqrs-lite Note
store.commit(event) — No equivalent, deliberately: clients dispatch Commands instead
Event table (typed event schema) catalog.SchemaFromType[T] registration Same goal; ours also feeds AsyncAPI/EventCatalog/TS contracts
Materializer (event → SQL) Evolution / fold + metaengine engine Theirs runs in every client; ours server-side (L4 folds client-side for projections only)
Sync provider (push/pull) Command push + journal pull (L4, gated) Their push carries events; ours carries intents
Pending vs confirmed events Queued command vs decider-accepted The optimistic/revert ledger maps 1:1
Client-only events (LWW UI state) Out of scope Browser state is not domain state in this architecture
Conflict resolution (#253, unimplemented) decide() rejection at sync time The problem does not structurally exist here

05.3 · DataStar: nothing to redesign — only to wire

The sibling report’s adapter plan is unchanged and endorsed: metaengine/datastaradapter as a Tier-4 encoder beside projectionadapter, goldens adopted from the upstream conformance corpus, P0–P2 rollout. This report adds only the command-side observation: the same wire.Action spec that renders an HTMX or DataStar fetch action should point at command-dispatch handlers, so the “always implement backend validation” mandate is satisfied by the decider — not by hand-rolled handler checks.

07Risks in the synthesis

R1 · Medium

The L4 client queue is still new client-side code

IndexedDB durability, ordering, flush retry — none of it exists here

The server side is all existing pieces; the browser side (durable queue, per-stream ordering, revert-on-rejection UX) is genuinely new and is the real cost of L4 — the reason it stays gated.

R2 · Medium

Optimistic folding demands client-side fold purity

speculative apply → revert must be total

Zero imposes the same constraint on its mutators; for us it means the L4 client folds projections only, from expected-then-confirmed events, with version-keyed state so a revert is a key rollback, not a diff undo.

R3 · Low

Queued commands age badly across long offline windows

intent captured against ancient state

A command queued for days decides against fresh server state — correct, but the UX must expect late Rejections. Zero/ Replicache share this property; it is inherent to the model, not a defect. Document, don’t engineer around.

10Owner’s addendum (2026-11-22, later): the local-Commands question

After this report closed, the owner sharpened the requirement into a precise question — recorded verbatim, then reconciled against the findings above. Original sections are untouched; this addendum extends them.

The Question “How can we make the browser OWN its data smartly, be as local-first as possible (i.e. including Commands), but at the same time be able to smartly branch-rebase (like Git) with a server as soon as the client has a connection again! All that transparently. Like we kinda need to be able to have Commands & Events that only have happened on the client. And we need to be able to share the logic for these Commands & Events & Queries (as long as they do not [access] other protected server resources) with the client, efficiently!”

10.1 · Decomposed against this report’s findings

Part What it demands Where the report stands The delta
P1 · Browser owns its data Local read models + local history, client-side persistence L4 pull leg (journal tail / Watcher replay) feeds local folds; client store choice open (SQLite-WASM vs IndexedDB) Small — storage pick, not architecture
P2 · Local-first including Commands Intents decided on the client, offline — not merely queued §05.1 queues commands, decides server-side only NEW — client-side decider execution; deciders are pure functions, so this is legal — the constraint is porting them (10.3)
P3 · Git-like branch/rebase on reconnect, transparently Local work rebases onto server truth; user sees one coherent state LiveStore’s rebase UX is the reference (§02.3); Zero’s revert-on-reject is the semantics (§03) Rebase intents, not facts: re-decide queued commands against fresh state; rejections surface as UX, not merges
P4 · Commands & Events that only happened on the client Client-local speculative events “Only deciders mint events” (§05.1) Refines the rule: only deciders mint authoritative events; a client-side decider may mint speculative local ones (10.2)
P5 · Shared Command/Event/Query logic, minus protected resources Same logic both sides, efficiently Contracts (types/validators) generate (11-21 report); logic does not NEW — the client-safe decider seam (10.3)

10.2 · The shape: a local branch, rebased on intent

  • Local = a branch. Client holds: last-confirmed server facts (base) + a pending-command log + speculative events minted by the client-side decider running on that log. UI reads the local read-model; speculative vs confirmed is a flag on rows, not two code paths (LiveStore’s pending/confirmed vocabulary, applied to intents).
  • Reconnect = fetch + push + rebase. Push the queued commands (server re-decides; Rejections trigger revert of the optimistic state — Zero’s documented semantics). Pull authoritative facts. Rebase: rebuild the local branch by replaying server facts, then re-applying still-pending commands through the (possibly newer) decider — an interactive rebase where a rejection is the conflict, surfaced to the user as a first-class Rejection, never a structural merge.
  • Transparency follows from purity. Because Apply/Decide are pure and version-keyed, rebuilding the branch is replay — the exact machinery (journal, checkpoints, deterministic replay) this library ships server-side today.

10.3 · The client-safe decider seam (P5)

“As long as they do not access other protected server resources” is a decider-scoped property, and it is statically checkable:

Decider kind Reads Client-portable?
Stream-local decider Only its own stream’s events + the command YES — pure, self-contained; runs anywhere
Cross-stream decider Other streams’ state (users, quotas, PII) NO — protected; server-side forever
Effectful decider wrapper External systems, timers, side-channels NO — not a decider anymore; belongs behind the server boundary

Sharing mechanisms, honestly ranked: (a) dual implementation + contract tests (pragmatic today: shared scenario DSL already exists — scenario.Given/When/Then pins both sides to identical behavior); (b) TS codegen of fold/decide logic (does not exist; the 11-21 pipeline generates contracts only); (c) TinyGo/WASM (parked on verified fidelity gaps, 11-21 §03.E). Version skew: command payloads carry schemaVersion; decider LOGIC version must ride the same envelope so the server knows which spec a queued intent was decided under.

10.4 · Status and routing

This addendum is a design question, not a verdict — the evidence base is the in-flight landscape sweep at docs/competition/ (per-tool pages + index answering the six axes this question decomposes into). It refines D41(b): the ratifiable principle becomes “clients queue commands and may decide locally on a speculative branch; only server deciders mint authoritative events; deciders declare their resource dependencies, and stream-local ones are client-portable.”
