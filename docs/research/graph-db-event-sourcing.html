Command & Event Sourcing
in Graph Databases

Date: 2026-05-29 · Scope: Thought experiment — implementing go-cqrs-lite event stores on Neo4j and JanusGraph

Graph databases model relationships as first-class citizens. Event sourcing models facts as immutable, ordered records. At first glance, they have nothing in common. But peer deeper: every event has a causal relationship to previous events, every command targets an aggregate, and every saga is a connected chain of cause and effect. What if the relationships between events are more interesting than the events themselves?

Part 1

Why Graph Databases Make This Interesting

Traditional event stores treat events as flat rows in an append-only table. The only relationship is "this event comes after that event, in the same stream." Graph databases ask: what if events are nodes in a richly connected web of causation, correlation, and temporal ordering?

01

The Flat Store Blind Spot

Problem

In a traditional event store (Postgres, EventStoreDB, Pebble), events are stored as rows in an append-only sequence. The only structural relationship is (aggregate_id, version). Cross-aggregate questions require full table scans or additional projection tables:

QuestionFlat StoreGraph Store
Load events for aggregateIndex scan — O(n)Chain traversal — O(n)
What caused this event?Scan by correlation_idFollow [:CAUSED_BY] — O(1)
Full causal chain across aggregatesRecursive CTE (expensive)Variable-length traversal — O(k)
Events produced by this commandScan by command_id columnFollow [:PRODUCED] — O(1)
Saga step completionQuery saga_state tableTraverse saga subgraph — O(steps)
Impact of replaying event XUnknown without scanFollow all outgoing relationships — O(k)
Key insight: The moment you ask "what caused what?" or "what is related to this event?", a graph database's traversal model is fundamentally more efficient than scanning flat rows. This is the entire value proposition.

Part 4

Implementation Sketch: Neo4j (Cypher)

Pseudocode for the full write/read path. Maps to go-cqrs-lite's EventSink and EventSource interfaces.

01

Save — Append Events with Optimistic Concurrency

Write 
func (s *Neo4jEventStore) Save(
    ctx context.Context,
    ref event.AggregateRef,
    events []event.Event,
    expectedVersion event.Version,
) error {
    return s.driver.ExecuteWrite(ctx, func(tx neo4j.ManagedTransaction) {
        // 1. Find or create aggregate node
        result, _ := tx.Run(`
            MERGE (a:Aggregate {id: $aggID})
            ON CREATE SET a.type = $aggType,
                          a.version = 0,
                          a.created_at = datetime()
            RETURN a.version AS currentVersion
        `, map[string]any{
            "aggID":   ref.ID.String(),
            "aggType": ref.Type,
        })

        // 2. Optimistic concurrency check
        currentVersion := result.Collect()[0]["currentVersion"]
        if currentVersion != expectedVersion {
            return event.ErrConcurrencyConflict
        }

        // 3. Find last event in chain (for NEXT relationship)
        var lastEventNode string
        if currentVersion == 0 {
            lastEventNode = "a" // point to aggregate if first event
        } else {
            last, _ := tx.Run(`
                MATCH (a:Aggregate {id: $aggID})-[:HAS_EVENT]->(e:Event)
                WHERE NOT (e)-[:NEXT]->()
                RETURN elementId(e) AS lastId
            `, map[string]any{"aggID": ref.ID.String()})
            lastEventNode = last.Collect()[0]["lastId"]
        }

        // 4. Append events as linked chain
        for i, evt := range events {
            payload, _ := json.Marshal(evt.Payload())
            tx.Run(`
                MATCH (prev) WHERE elementId(prev) = $prevId
                CREATE (e:Event:`+evt.Type()+` {
                    event_id:     $eventID,
                    type:         $eventType,
                    seq:          $seq,
                    payload:      $payload,
                    schema_version: $schemaVersion,
                    occurred_at:  $occurredAt,
                    correlation_id: $correlationID,
                    causation_id: $causationID
                })
                CREATE (prev)-[:NEXT]->(e)
                WITH e
                MATCH (a:Aggregate {id: $aggID})
                CREATE (a)-[:HAS_EVENT]->(e)
                SET a.version = $seq
            `, map[string]any{
                "prevId":        lastEventNode,
                "eventID":       evt.ID().String(),
                "eventType":     evt.Type(),
                "seq":           int(evt.Version()),
                "payload":       string(payload),
                "schemaVersion": int(evt.SchemaVersion()),
                "occurredAt":    evt.OccurredAt(),
                "correlationID": evt.CorrelationID(),
                "causationID":   evt.CausationID(),
                "aggID":         ref.ID.String(),
            })
            // Update lastEventNode for next iteration
            lastEventNode = /* new event's element ID */
        }
    })
}
02

Load — Reconstruct Events by Traversal

Read 
func (s *Neo4jEventStore) Load(
    ctx context.Context,
    ref event.AggregateRef,
) ([]event.Event, error) {
    result, err := s.driver.ExecuteRead(ctx, func(tx neo4j.ManagedTransaction) {
        // Option A: Index-based (fastest for large streams)
        records, _ := tx.Run(`
            MATCH (a:Aggregate {id: $aggID})-[:HAS_EVENT]->(e:Event)
            RETURN e ORDER BY e.seq ASC
        `, map[string]any{"aggID": ref.ID.String()})
        return records.Collect()

        // Option B: Chain traversal (uses index-free adjacency)
        // records, _ := tx.Run(`
        //     MATCH (a:Aggregate {id: $aggID})-[:HAS_EVENT]->(e0:Event)
        //     MATCH path = (e0)-[:NEXT*0..]->(e:Event)
        //     RETURN e ORDER BY e.seq ASC
        // `, map[string]any{"aggID": ref.ID.String()})
    })

    var events []event.Event
    for _, record := range result {
        nodeProps := record["e"].(neo4j.Node).Props
        evt, _ := reconstructEvent(nodeProps)
        events = append(events, evt)
    }
    return events, nil
}

func reconstructEvent(props map[string]any) (event.Event, error) {
    return event.NewEvent(
        props["type"].(string),
        /* aggregate ID from HAS_EVENT relationship */,
        props["aggregate_type"].(string),
        event.Version(props["seq"].(int64)),
        json.RawMessage(props["payload"].(string)),
        event.WithSchemaVersion(int(props["schema_version"].(int64))),
        event.WithOccurredAt(props["occurred_at"].(time.Time)),
    )
}
03

Cross-Aggregate Queries — Where Graph Shines

Unique Power 
-- What caused this event? (Causal chain traversal)
MATCH (e:Event {event_id: 'evt-01JM3X...'})-[:CAUSED_BY*1..5]->(cause:Event)
RETURN cause

-- Full saga trace: command → events → downstream commands → events
MATCH path = (cmd:Command {id: 'cmd-42'})-[:PRODUCED|TRIGGERED_BY|CAUSED_BY*1..10]->(leaf)
RETURN path

-- What aggregates are affected by replaying this event?
MATCH (e:Event {event_id: 'evt-01JM3X...'})-[:CORRELATES_WITH*1..3]->(related:Event)<-[:HAS_EVENT]-(a:Aggregate)
RETURN DISTINCT a

-- Dead letter detection: commands that produced no events
MATCH (cmd:Command) WHERE NOT (cmd)-[:PRODUCED]->(:Event)
RETURN cmd

-- Anomaly: order placed but no payment within 24 hours
MATCH (o:Aggregate:Order)-[:HAS_EVENT]->(placed:Event:OrderPlaced)
WHERE NOT EXISTS {
    MATCH (o)-[:HAS_EVENT]->(paid:Event:PaymentTaken)
    WHERE paid.occurred_at < placed.occurred_at + duration({hours: 24})
}
RETURN o, placed

-- Global event journal with causal context
MATCH (e:Event)
OPTIONAL MATCH (e)-[:CAUSED_BY]->(cause:Event)
OPTIONAL MATCH (e)<-[:PRODUCED]-(cmd:Command)
RETURN e, cause.event_id AS caused_by, cmd.id AS source_command
ORDER BY e.occurred_at ASC
This is the killer feature. These queries are either impossible or require expensive recursive CTEs in a SQL event store. In a graph, they're single Cypher queries using variable-length path patterns. The database was BUILT for this.

Command Sourcing: The Missing Piece

Most event sourcing implementations store only the outcome (events). Command sourcing stores the intent (command) alongside the outcome. Graph databases make this natural because commands and events are both nodes with explicit causal relationships.

02

Saga as a First-Class Subgraph

Saga Pattern 
-- A saga is a connected subgraph. Trace the entire saga:

CREATE (saga:Saga:OrderFulfillment {
  id: "saga-001",
  status: "in_progress",
  started_at: datetime()
})

-- Step 1: OrderPlaced event triggers saga
CREATE (saga)-[:STEP {n:1, status:"completed"}]->(e1:Event:OrderPlaced)

-- Step 2: Saga triggers ReserveInventory command
CREATE (saga)-[:STEP {n:2, status:"completed"}]->(cmd1:Command:ReserveInventory)
CREATE (e1)-[:TRIGGERED]->(cmd1)
CREATE (cmd1)-[:PRODUCED]->(e2:Event:InventoryReserved)

-- Step 3: Saga triggers TakePayment command
CREATE (saga)-[:STEP {n:3, status:"pending"}]->(cmd2:Command:TakePayment)
CREATE (e2)-[:TRIGGERED]->(cmd2)

-- Query: What's the current state of this saga?
MATCH (saga:Saga {id: 'saga-001'})-[step:STEP]->(node)
RETURN step.n AS step_number, step.status AS status,
       labels(node) AS type, node
ORDER BY step.n
Sagas become queryable graphs. No separate saga state table. No saga orchestrator polling. The saga IS the subgraph. "Which step failed?" is a traversal. "What compensating actions do we need?" is a reverse traversal.
Part 6

The Secret Sauce: Why Graph Makes Event Sourcing Better

Not just "can a graph database store events?" — but "what does a graph database give you that a flat store cannot?"

01

Causal Discovery

Superpower

In a traditional event store, causation is implicit — stored as a causation_id column that you must manually join on. In a graph, causation is a first-class relationship. You traverse [:CAUSED_BY] edges. The database was designed for exactly this.

QuestionSQL Event StoreGraph Event Store
What caused event X?SELECT ... WHERE id = (SELECT causation_id...)MATCH (e)-[:CAUSED_BY]->(cause)
Full causal chain (5 levels)Recursive CTE, 5 self-joinsMATCH (e)-[:CAUSED_BY*1..5]->(cause)
All effects of event XScan entire tableMATCH (e)<-[:CAUSED_BY*]-(effect)
Causation becomes structure. Not metadata you filter on — topology you traverse. O(k) where k = chain length, not O(n) where n = total events.
02

Saga as First-Class Citizen

Superpower

In traditional CQRS, sagas are implemented as state machines in a separate table, with polling or message queues for step transitions. In a graph database, a saga IS a subgraph. Each step is a node. Transitions are edges. The saga state IS the graph topology.

  • Step status — query which [:STEP] edges have status:"completed"
  • Compensation — reverse traversal to find completed steps, apply inverse
  • Visualization — the saga subgraph IS the visualization
  • Debugging — "why did saga X fail?" = traverse the saga subgraph
03

Bitemporal Modeling

Superpower

Graph databases naturally model valid time (when something happened in the real world) and transaction time (when it was recorded). In Model B (Event-as-Edge), every transition carries both timestamps as edge properties. 

-- "What did we know about user-1 at time T?"
MATCH path = (s0:State:User {id:"user-1", version:0})
              -[:TRANSITION*]->(sN:State:User)
WHERE ALL(r IN relationships(path) WHERE
    r.recorded_at <= datetime($asOfTime))
RETURN last(nodes(path)) AS state_at_time
Time travel for free. No temporal tables, no system-versioning, no audit log sidecar. The graph topology IS the temporal record.
04

Event Mesh & Microservice Tracing

Superpower

In microservice architectures, events flow between services. A graph database can model the entire event mesh — which service produces which events, which consumes them, which sagas span services, and where dead letters accumulate. 

-- Cross-service event trace
(:Service:OrderService)
    -[:EMITS]->(:EventType:OrderPlaced)
    -[:CONSUMED_BY]->(:Service:InventoryService)
    -[:EMITS]->(:EventType:InventoryReserved)
    -[:CONSUMED_BY]->(:Service:PaymentService)
    -[:EMITS]->(:EventType:PaymentTaken)

-- Dead letter detection
MATCH (s:Service)-[:EMITS]->(e:EventType)
WHERE NOT (e)-[:CONSUMED_BY]->(:Service)
RETURN s.name AS orphan_producer, e.type AS unconsumed_event
System-level observability. The graph doesn't just store YOUR domain events — it maps the entire distributed system's event topology. Dependency mapping, dead letter detection, and impact analysis become traversal queries.
05

Pattern Detection & Anomaly Queries

Superpower 
-- Fraud detection: circular payment pattern
MATCH path = (a:Aggregate:Account)-[:HAS_EVENT]->(:Event:TransferSent)
              -[:CORRELATES_WITH]->(:Event:TransferReceived)
              <-[:HAS_EVENT]-(b:Aggregate:Account)
WHERE length(path) > 2

MATCH (a:Aggregate)-[:HAS_EVENT]->(last:Event)

AND last.occurred_at < datetime() - duration({days: 30})
RETURN a, last

MATCH (e:Event)
RETURN labels(e)[1] AS event_type, count(*) AS frequency

Part 7

Performance: The Honest Assessment

Graph databases have trade-offs. Event stores have specific requirements. Let's be honest about where graph databases excel and where they struggle.

Where Graph Excels

  • Cross-aggregate queries — O(k) traversal vs O(n) scan for causal chains, correlation, saga tracing
  • Point-in-time queries — Model B gives free temporal reads via chain traversal
  • Variable-depth queries — "find all events related to X within 5 hops" is a single Cypher pattern
  • Schema flexibility — New event types are new labels; new relationships are new edge types. No migration needed
  • Pattern detection — Anomaly detection, fraud patterns, dead letter detection as native queries
  • Visualization — The graph IS the visualization. No ETL to a separate tool

Where Graph Struggles

  • Sequential write throughput — Graph DBs optimize for reads, not append-only sequential writes. Event stores need the opposite
  • Large event payloads — Storing KB-sized JSON as node properties is an anti-pattern. Neo4j's property storage isn't optimized for blobs
  • Append-only semantics — Graph DBs allow mutation. You need constraints to enforce event immutability
  • Write scaling — Neo4j is single-writer (causal clustering adds read replicas, not write scaling). JanusGraph distributes but with eventual consistency
  • Journal throughput — Global event journal (ReadAll) requires scanning ALL event nodes. No dedicated append-only log optimization
  • Operational complexity — Running Neo4j/JanusGraph is significantly more complex than PostgreSQL or SQLite

Two graph databases with fundamentally different architectures. Same graph model, wildly different operational characteristics.

The Sacred Rule of Graph Event Sourcing
  Graph databases are NOT better event stores.
  They are better EVENT RELATIONSHIP engines.

  The question isn't "can a graph store events?"
  (Yes, trivially. Every database can.)

  The question is: "What questions become trivial when events live in a graph?"

    1. "What caused this?"              ← O(k) traversal, not O(n) scan
    2. "Trace the full saga"            ← Subgraph traversal, not JOIN hell
    3. "What did we know at time T?"    ← Chain walk, not temporal tables
    4. "What if I replay event X?"      ← Follow outgoing edges
    5. "Find anomalous patterns"        ← Cypher pattern matching
    6. "Map the event topology"         ← The graph IS the topology

  These questions are IMPOSSIBLE or EXPENSIVE in a flat event store.
  They are TRIVIAL in a graph.

  But these questions are READ-SIDE concerns.
  The WRITE SIDE (append events) is where flat stores win.

  Therefore: flat store for writes, graph for reads.
  Project from one to the other.
  Let each tool do what it does best.

  The thought experiment isn't "should I use a graph as my event store?"
  The thought experiment is "what would I gain if I projected my events
  into a graph?" — and the answer is: superpowers you didn't know you needed.
What This Teaches About Event Store Design
  Understanding WHY graph databases are almost-perfect event stores
  teaches you what an event store actually needs:

    1. Append-only immutability           ← Graph DBs: no native guarantee
    2. Ordered reads within a stream       ← Graph DBs: via chain or index
    3. Exact version addressing            ← Graph DBs: YES (unlike TigerBeetle)
    4. Arbitrary payload size              ← Graph DBs: stored as properties (limited)
    5. High write throughput               ← Graph DBs: weaker than flat stores
    6. Schema evolution (upcasting)        ← Graph DBs: no native support
    7. Cross-stream relationship queries   ← Graph DBs: THIS IS THE SUPERPOWER

  The gap between "can store events" and "is an event store" is items 1, 5, 6.
  The gap between "event store" and "event relationship engine" is item 7.

  The future of event sourcing isn't one or the other.
  It's a flat store for writes, projected into a graph for reads.
