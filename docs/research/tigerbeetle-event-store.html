as Event Store

Date: 2026-05-29 · Scope: Thought experiment — implementing go-cqrs-lite persistence on TigerBeetle

TigerBeetle is a financial accounting engine — Accounts, Transfers, Balances. It knows nothing about events, aggregates, or CQRS. But its data model is secretly an append-only ledger with idempotent writes, timestamp ordering, and two-phase commits. Which is... exactly what an event store is.

Part 1

Why This Is Delightfully Absurd (and Kinda Works)

TigerBeetle's core primitives map surprisingly well to event sourcing concepts. The trick is seeing a Transfer not as a money movement, but as an immutable fact recorded in time.

The Isomorphism
  Event Sourcing                  TigerBeetle
  ──────────────                  ───────────
  Aggregate Stream        ←→      Account (with History flag)
  Domain Event            ←→      Transfer (immutable, timestamped)
  Event Payload           ←→      UserData128 + UserData64 + UserData32 + Code + Ledger
  Optimistic Concurrency  ←→      Built-in idempotency + Linked flag chains
  Event Store (append)    ←→      CreateTransfers (idempotent by ID)
  Event Store (load)      ←→      GetAccountTransfers (timestamp-ordered)
  Event Store (reverse)   ←→      GetAccountTransfers with Reversed flag
  Global Journal          ←→      QueryTransfers (cross-account)
  Position-based replay   ←→      QueryTransfers with TimestampMin

The Core Mapping

01

Aggregate Stream → Account

Mapping 
tb.Account{
    ID:      aggregateRefToAccountID(ref),
    Ledger:  aggregateTypeToLedger(ref.Type),
    Code:    1,   // "event stream" account type
    Flags:   AccountFlags{History: true}.ToUint16(),
}
go-cqrs-lite TigerBeetle Notes
AggregateRef{Type, ID} Account.ID (Uint128) Hash aggregate type + ID into 128-bit account ID
Aggregate type Account.Ledger (uint32) Enum: 1=User, 2=Order, 3=Payment...
Event stream AccountFlags.History Keeps all transfers, not just running balances
Key insight: The History flag is TigerBeetle's "event stream mode." Without it, TB only keeps balances. With it, every Transfer is retained — exactly what an event store needs.

03

Load Operations

Mapping
go-cqrs-lite Method TigerBeetle API How
Load GetAccountTransfers All transfers for account, timestamp-ordered
LoadFromVersion GetAccountTransfers + TimestampMin Skip events before version's timestamp
LoadToVersion GetAccountTransfers + TimestampMax Approximate (timestamp ≠ exact version)
LoadToTimestamp GetAccountTransfers + TimestampMax Native TB timestamp filter
LoadBackwards GetAccountTransfers + Reversed flag TB has native reverse ordering!
ReadAll (Journal) QueryTransfers (no filter) Global cross-account transfer query
ReadFrom (Seekable) QueryTransfers + TimestampMin Timestamp-based pagination
Note: TigerBeetle returns max 8190 results per call. Large aggregates or journal replay requires pagination via TimestampMin from the last result's timestamp.
04

Concurrency Control

Mapping 
// Linked chain: all-or-nothing transfer batch
//
// Transfer 1 (Linked=true)  → event 1
// Transfer 2 (Linked=true)  → event 2
// Transfer 3 (Linked=false) → event 3 (commit point)
//
// If any transfer in the chain fails,
// ALL preceding linked transfers are rolled back.

for i, t := range transfers {
    if i < len(transfers)-1 {
        t.Flags |= TransferFlags{Linked: true}.ToUint16()
    }
}
CQRS Pattern TigerBeetle Mechanism
Optimistic concurrency Idempotent transfer by ID — duplicate ID = rejected
Atomic multi-event append Linked flag chains — all succeed or all roll back
Exactly-once processing Idempotency key = transfer ID (event ID)
Saga orchestration Pending + Post/Void two-phase transfers
Key insight: TigerBeetle's two-phase commit (Pending → Post/Void) is literally saga orchestration. A pending transfer reserves capacity; posting confirms it; voiding cancels it. This maps 1:1 to long-running distributed sagas.
Part 3

The Big Problem: Payload Size

TigerBeetle's Transfer gives you 28 bytes of user data. An event payload is typically 100+ bytes of JSON. This is the central challenge.

Available User Data in a Transfer (128 bytes total)
┌─────────────────────────────────────────────────────────────────────┐
│  Field           Size     Used For                                  │
├─────────────────────────────────────────────────────────────────────┤
│  UserData128     16 B     SHA-256 payload hash (truncated to 128b)  │
│  UserData64       8 B     Version (upper 32b) + TypeCode (lower 32b)│
│  UserData32       4 B     Payload size (bytes)                      │
│  Code             2 B     Event type ID                             │
│  Ledger           4 B     Aggregate type ID                         │
│  Timeout          4 B     — unused                                  │
│  ─────────────────────                                             │
│  Total usable   34 B     But the payload can be 500+ bytes          │
└─────────────────────────────────────────────────────────────────────┘

  The ratio is brutal: 34 bytes of metadata for 500+ bytes of payload.
  We need a sidecar.
Part 4

Three Options: Practical → Unhinged → Brilliant

A

Hash Index + External Blob Store

Practical 
Write path:
  Event → JSON marshal → SHA-256 hash
       → Transfer{UserData128: hash, ...}
       → BlobStore.Put(hash, payload)

Read path:
  GetAccountTransfers → [Transfer, ...]
  → bulk Get hashes from BlobStore
  → reconstruct Events

TigerBeetle becomes the ordered index + concurrency control + tombstone marker. The blob store (S3, Pebble, Postgres, anything) holds the actual JSON payloads. Load path: query TB for transfer list → bulk-fetch payloads by hash.

Legit architecture. TB handles what it's best at (ordering, concurrency, idempotency). Blob store handles what it's best at (large values). This is a real two-store architecture that makes sense in production.
B

Multi-Transfer Chunking

Unhinged 
Split payload across N transfers via Linked chains:

  Transfer 0: [header]  — metadata + chunk count
  Transfer 1: [chunk 0] — UserData128 + UserData64 = 24 bytes
  Transfer 2: [chunk 1] — 24 more bytes
  Transfer 3: [chunk 2] — 24 more bytes
  ...

  A 240-byte event  = 1 header + 10 chunks = 11 transfers
  A 500-byte event  = ~22 transfers

Reconstruct by querying all transfers, grouping by header ID, sorting by chunk index, concatenating UserData fields.

  • Pro: Pure TigerBeetle — no sidecar store needed
  • Con: 22× write amplification on a 500-byte event
  • Con: Burns through TB's transfer space at insane rates
  • Con: Reconstruction complexity on every load
Verdict: A war crime. But technically correct — the worst kind of correct.
C

Financial Events Only — The Right Answer

Brilliant

        ↕                                ↕
  Projections rebuild            Financial reports
  from event store               query TB directly

Don't shoehorn generic events into TB. Use TB for what it is: a financial event store. Only store events that are financial transactions. Bridge via middleware that writes to both stores.

  • OrderPlaced → writes domain event to event store AND transfer to TB
  • PaymentTaken → writes domain event to event store AND transfer to TB
  • EmailChanged → writes domain event to event store ONLY (no financial fact)
The production answer. Use TB as the financial ledger it was designed to be. Keep go-cqrs-lite's event store for domain events. Each tool does what it's best at.
Part 5

Implementation Sketch (Option A)

Pseudocode for the hash-index + blob-store approach. Maps directly to go-cqrs-lite's EventSink and EventSource interfaces.

01

Save — Append Events with Concurrency

Write 
func (s *TBEventStore) Save(
    ctx context.Context,
    ref event.AggregateRef,
    events []event.Event,
    expectedVersion event.Version,
) error {
    accountID := aggregateRefToAccountID(ref)

    // Ensure aggregate "account" exists (idempotent)
    s.client.CreateAccounts([]tb.Account{{
        ID:     accountID,
        Ledger: aggregateTypeToLedger(ref.Type),
        Code:   1,
        Flags:  tb.AccountFlags{History: true}.ToUint16(),
    }})

    transfers := make([]tb.Transfer, 0, len(events))
    for i, evt := range events {
        payload, _ := json.Marshal(evt.Payload())
        hash := sha256.Sum256(payload)

        s.blobs.Put(hash[:], payload) // sidecar write

        t := tb.Transfer{
            ID:              eventIDToUint128(evt.ID()),
            DebitAccountID:  accountID,
            CreditAccountID: s.systemAccount,
            Amount:          tb.Uint128{},       // zero
            UserData128:     tb.Uint128(hash),
            UserData64:      uint64(evt.Version())<<32 |
                             uint64(eventTypeToCode(evt.Type())),
            UserData32:      uint32(len(payload)),
            Ledger:          aggregateTypeToLedger(ref.Type),
            Code:            eventTypeToCode(evt.Type()),
            Timestamp:       uint64(evt.OccurredAt().UnixNano()),
        }
        // Linked chain: atomic all-or-nothing
        if i < len(events)-1 {
            t.Flags |= tb.TransferFlags{Linked: true}.ToUint16()
        }
        transfers = append(transfers, t)
    }

    results, err := s.client.CreateTransfers(transfers)
    return checkResults(results, err)
}
02

Load — Reconstruct Events from Transfers

Read 
func (s *TBEventStore) Load(
    ctx context.Context,
    ref event.AggregateRef,
) ([]event.Event, error) {
    accountID := aggregateRefToAccountID(ref)

    transfers, err := s.client.GetAccountTransfers(
        tb.AccountFilter{
            AccountID: accountID,
            Limit:     8190, // TB max per call
            Flags: tb.AccountFilterFlags{
                Debits:  true,
                Credits: true,
            }.ToUint32(),
        },
    )
    if err != nil { return nil, err }

    // Paginate for large aggregates
    for len(transfers) == 8190 {
        last := transfers[len(transfers)-1]
        page, err := s.client.GetAccountTransfers(
            tb.AccountFilter{
                AccountID:    accountID,
                TimestampMin: last.Timestamp + 1,
                Limit:        8190,
                Flags:        /* same */,
            },
        )
        if err != nil { return nil, err }
        transfers = append(transfers, page...)
    }

    // Bulk-fetch payloads from blob store
    hashes := extractHashes(transfers)
    payloads := s.blobs.BatchGet(hashes)

    return reconstructEvents(transfers, payloads), nil
}
03

Reconstruct — Transfer + Blob → Event

Glue 
func reconstructEvent(t tb.Transfer, payload []byte) event.Event {
    version := event.Version(t.UserData64 >> 32)
    typeCode := uint16(t.UserData64 & 0xFFFFFFFF)
    eventType := codeToEventType(typeCode)
    aggType := ledgerToAggregateType(t.Ledger)
    aggregateID := uint128ToID(t.DebitAccountID)

    evt, _ := event.NewEvent(
        eventType,
        aggregateID,
        aggType,
        version,
        json.RawMessage(payload),
        event.WithEventID(uint128ToEventID(t.ID)),
        event.WithOccurredAt(time.Unix(0, int64(t.Timestamp))),
    )
    return evt
}
Part 6

What TigerBeetle Gives Us For Free vs. What We Lose

Free Features

  • Append-only guarantee — transfers are immutable, no update/delete
  • Idempotent writes — same transfer ID always returns same result
  • Atomic multi-event append via Linked flag chains
  • Temporal ordering — Timestamp on every transfer, nanosecond precision
  • Native reverse iteration — AccountFilterFlags.Reversed for LoadBackwards
  • Global journal — QueryTransfers across all accounts
  • Two-phase commit — Pending + Post/Void for saga orchestration
  • Crash safety — arguably the most crash-safe DB in existence (formally verified via Io_uring + mission testing)
  • Zero-config clustering — built-in replication
  • Performance — millions of transfers per second on a single node

What We Lose

  • Single-store simplicity — need sidecar blob store for payloads
  • LoadToVersion precision — TB timestamps aren't version numbers, only approximate pagination
  • Rich queries — no WHERE event_type = 'X', must filter client-side
  • 8190 transfer limit per query — must paginate for large aggregates
  • Event schema evolution — no built-in upcasting, must handle in application layer
  • Snapshot support — TB has no concept of snapshots, need separate store
  • Metadata flexibility — only 28 bytes of user data per transfer
  • The respect of your peers — "You did WHAT on TigerBeetle?"

Part 7

The Verdict

Option A

Hash Index + Blob Store

Genuinely interesting for domains where financial correctness and event sourcing overlap — payments, accounting, trading. TigerBeetle becomes the source of truth for ordering and concurrency; the blob store holds payloads. You get TB's legendary safety guarantees for your event stream metadata.

Legit architecture for fintech event sourcing
Option B

Multi-Transfer Chunking

Pure TigerBeetle, no sidecar. But 22× write amplification on a typical JSON event, complex reconstruction logic, and you'd burn through TB's transfer space at terrifying rates. Technically correct — the worst kind of correct.

A war crime and I won't apologize for it
Option C

Financial Events Only

The production-ready answer. Use TigerBeetle as the financial ledger it was designed to be. Keep go-cqrs-lite's event store (Postgres, Pebble, SQLite) for domain events. Bridge them via middleware that writes financial events to both stores. Each tool does what it's best at.

The correct answer — use each tool for its purpose
The Sacred Rule of Abstraction
  If you have to squint at a database and say "well, technically..."
  to justify using it for something it wasn't designed for...

  ...that's exactly when the thought experiment becomes valuable.

  TigerBeetle isn't an event store.
  But understanding WHY it almost works teaches you everything
  about what an event store actually needs:

    1. Append-only immutability         ← TB has this
    2. Ordered reads within a stream     ← TB has this
    3. Idempotent writes                 ← TB has this
    4. Atomic multi-append               ← TB has this
    5. Arbitrary payload size            ← TB does NOT have this
    6. Schema evolution (upcasting)      ← TB does NOT have this
    7. Exact version addressing          ← TB does NOT have this

  The gap between "almost" and "actually" is where the design lives.
