01

Context

The core/event package defines two journal interfaces for cross-aggregate event replay: 

type Journal interface {
    ReadAll(ctx context.Context) ([]Event, error)
}

type SeekableJournal interface {
    Journal
    ReadFrom(ctx context.Context, afterEventID id.EventID, limit int) ([]Event, error)
}

Meanwhile, the core/command package already has the Sink/Source/Store split — mirroring the event side — but lacks the Journal equivalent. The question arose: should we introduce a generic Journal[T, ID] to serve both, or keep them as separate concrete interfaces?

02

Current State

Both event and command packages follow the same ISP split pattern:

Concern Events Commands
Write side EventSink CommandSink
Read side EventSource CommandSource
Combined Store Store
Cross-aggregate read Journal / SeekableJournal ❌ Missing
Position-based read SeekableJournal.ReadFrom ❌ Missing

The gap is real: there is no way to answer "what commands were dispatched across the system?" — which is essential for audit trails, compliance, and replay debugging.

03

The Gap: Missing CommandJournal

A CommandJournal would serve several use cases that currently have no home:

  • Audit trail — "Show me every command that touched aggregate X across all types"
  • Compliance — "Who issued what commands and when?"
  • Replay debugging — "Replay commands to reproduce a bug state"
  • Analytics — "Which command types are most frequent? Which fail?"
Agreed

CommandJournal is a legitimate concept. The question is only about how to model it — shared generic or independent concrete.

04

Option A — Generic Journal[T, ID]

Extract a generic base into a shared location (e.g. core/pkg/journal) and have both event and command journals inherit from it: 

// core/pkg/journal/journal.go
package journal

type Journal[T any] interface {
    ReadAll(ctx context.Context) ([]T, error)
}

type SeekableJournal[T any, ID comparable] interface {
    Journal[T]
    ReadFrom(ctx context.Context, after ID, limit int) ([]T, error)
}

// Usage:
var _ journal.SeekableJournal[Event, id.EventID] = (*SQLEventStore)(nil)
var _ journal.SeekableJournal[*PersistedCommand, id.CommandID] = (*SQLCommandStore)(nil)

Pros

  • DRY — one interface definition for the shared shape
  • Enforces structural consistency between event and command journals
  • Opens the door for generic utilities (e.g. replay logic that works on any journal)

Cons

  • The return types diverge — events return []Event (value), commands return []*PersistedCommand (pointer with serialized payload). Consumers handle them completely differently.
  • Only two implementations — if we had 5+ journal types, a generic pays off. With 2, it's abstraction overhead for symmetry.
  • No good home — putting Journal[T, ID] in core/pkg/journal/ creates a micro-dependency that exists purely for DRY. Neither event nor command package should depend on the other's abstraction.
  • They will diverge — Command journals may need ReadByStatus(), ReadByUser(). Event journals may need ReadByAggregateType(). A shared generic constrains both to the lowest common denominator.
  • Type parameters add noise — SeekableJournal[*PersistedCommand, id.CommandID] is harder to read than SeekableCommandJournal.
Risk

The generic base becomes a least common denominator that neither side is happy with. Each domain grows domain-specific methods, and the shared base becomes an empty ceremony.

05

Option B — Concrete CommandJournal

Mirror the event pattern with domain-specific interfaces in core/command/store.go: 

// core/command/store.go — new interfaces

// CommandJournal reads all commands across all aggregates,
// ordered by ReceivedAt. The command-audit-trail equivalent of event.Journal.
type CommandJournal interface {
    ReadAll(ctx context.Context) ([]*PersistedCommand, error)
}

// SeekableCommandJournal extends CommandJournal with position-based reading.
// Position is based on CommandID (ULID-based, time-sortable).
type SeekableCommandJournal interface {
    CommandJournal
    ReadFrom(ctx context.Context, afterCommandID id.CommandID, limit int) ([]*PersistedCommand, error)
}

Pros

  • Zero coupling — command and event packages evolve independently
  • Free to diverge — add ReadByStatus() to CommandJournal without breaking Event Journal's contract
  • Clear naming — SeekableCommandJournal is self-documenting; SeekableJournal[*PersistedCommand, id.CommandID] is not
  • Follows existing pattern — mirrors CommandSink/CommandSource which are already concrete
  • 10 lines of duplication — cheaper than the generic abstraction layer

Cons

  • Structural duplication — both journals have ReadAll + ReadFrom
  • No shared utility code (but no actual need for it yet)
Strength

The ISP split pattern is already proven in this codebase. CommandSink/CommandSource are concrete mirrors of EventSink/EventSource. CommandJournal should follow the same proven pattern.

07

Decision

Verdict — Concrete CommandJournal

The duplication is ~10 lines of interface definitions — far cheaper than the abstraction cost of a generic base. The two domains (events and commands) will diverge in their query needs, and a shared generic would become an LCD straightjacket. The existing Sink/Source precedent already proves the concrete-mirror pattern works well in this codebase.

The generic approach would only pay off if we had 5+ distinct journal types with identical semantics. With 2 (events and commands), the cost of the abstraction exceeds the cost of the duplication.

Key reasons

  1. Return types diverge — []Event vs []*PersistedCommand are fundamentally different shapes
  2. Query needs will diverge — commands need status/user filtering; events need aggregate-type filtering
  3. No good home for the generic — a core/pkg/journal package exists purely for DRY
  4. Proven pattern — CommandSink/CommandSource already mirror EventSink/EventSource concretely
  5. YAGNI — exactly 2 implementations; generic overhead is premature

09

Journal vs Outbox

Both Journal and Outbox deal with event streams, but they solve fundamentally different problems. They are complementary, not competing.

Journal Outbox
Purpose Complete ordered log — replay, audit, projections Reliable publishing queue
Lifecycle Permanent, append-only Temporary — entries deleted after ACK
Data scope All events/commands ever Only unpublished events
Consumer Projections, audit, debugging Background publisher → Bus
Interface ReadAll / ReadFrom Append / PollPending / Ack
Ordering By OccurredAt (global) By CreatedAt (FIFO queue)

The Outbox solves the dual-write problem: atomically persist events + stage them for Bus.Publish in the same transaction. Once published and ACKed, entries are deleted. 

// Outbox lifecycle (core/event/outbox.go):
// 1. Repository.Save calls Outbox.Append(events) inside the store tx
// 2. Background OutboxPublisher polls Outbox.PollPending
// 3. Publisher calls Bus.Publish for each entry
// 4. On success, publisher calls Outbox.Ack(entry.ID)

type Outbox interface {
    io.Closer
    Append(ctx context.Context, events []Event) error
    PollPending(ctx context.Context, limit int) ([]OutboxEntry, error)
    Ack(ctx context.Context, ids []OutboxID) error
}

A Journal is the opposite: it keeps everything forever for replay. You never ACK or delete from a Journal.

Does CommandJournal need an Outbox?

Yes — if commands are published. Commands can and should be published, just like events. A CommandBus (or CommandPublisher) is the natural mirror of event.Bus. When a command is both persisted and published, the same dual-write problem applies: you need atomic persistence + staging, which is exactly the Outbox pattern.

Events Commands (future)
Publish event.Bus.Publish CommandBus.Publish (not yet implemented)
Subscribe event.Bus.Subscribe CommandBus.Subscribe
Outbox event.Outbox (implemented) CommandOutbox (not yet implemented)
Journal event.Journal (implemented) CommandJournal (proposed)

Currently, commands only have a Dispatcher (dispatch to handler in-process). There is no CommandBus / CommandPublisher yet. But the design should account for it — commands flowing between services (microservice orchestration, saga coordination) need the same reliable publishing guarantees as events.

Gap Identified

The command side is missing three event-side concepts: CommandBus (publish/subscribe), CommandOutbox (reliable publishing), and CommandJournal (audit trail). The event side has all three: event.Bus, event.Outbox, event.Journal. This is an architectural gap worth addressing.

Insight

Journal is a source of truth (permanent, read-heavy). Outbox is a reliability mechanism (ephemeral, write-then-delete). They coexist naturally: events/commands are persisted to the Journal and staged in the Outbox atomically. The Outbox empties; the Journal grows.

10

PersistedCommand vs ImmutableEvent

A natural question when encountering PersistedCommand: why does the command side have a separate "persisted" type, while events have ImmutableEvent and no PersistedEvent?

Answer

Both sides actually have the same shape: an in-memory type that can be persisted but doesn't have to be. The naming difference is misleading — ImmutableEvent is just as "live" as BasicCommand until you call Save().

Both sides have in-memory forms that become persisted on Save

// Events — ImmutableEvent is an in-memory struct. Only persisted when you call sink.Save().
evt, _ := event.NewEvent("user.created", userID, "User", event.Version(1), UserCreated{Name: "Alice"})
// evt exists in memory. It's NOT persisted yet.
// You could throw it away, publish it to a bus, or save it:
_ = sink.Save(ctx, event.AggregateRef{Type: "User", ID: userID}, event.Version(1), evt)

// Commands — BasicCommand is an in-memory struct. Only persisted when you create a PersistedCommand.
cmd := command.New("create.user", aggregateID, command.WithCorrelationID(corrID))
// cmd exists in memory. It's NOT persisted yet.
// You could dispatch it and forget, or persist it:
persisted, _ := command.NewPersistedCommand(cmd.Type(), ref, payload)

The real difference isn't "born persisted" vs "two lifecycles" — both types live in memory until explicitly persisted. The actual distinction is:

ImmutableEvent BasicCommand → PersistedCommand
In-memory form ImmutableEvent (always has ID, timestamp, serialized payload) BasicCommand (no ID, no timestamp, typed payload)
Persisted form Same struct — ImmutableEvent goes straight to Sink.Save() Separate struct — NewPersistedCommand() wraps with ID, timestamp, []byte
Serialization At creation time (NewEvent marshals payload → bytes) At persistence time (NewPersistedCommand takes []byte)
ID allocation Always (id.EventID via ULID) Only on persist (id.CommandID)
Honest Assessment

The event side could have a PersistedEvent too — a separate struct that adds storage-specific fields. It doesn't because ImmutableEvent was designed to be storage-ready from the start (ID, timestamp, bytes payload). The command side didn't get that treatment: BasicCommand is lightweight (no ID, no timestamp, typed payload), so PersistedCommand bridges the gap. Both approaches work, but the asymmetry is a design choice, not a law of nature.

The command side — two forms, two lifecycles

BasicCommand (live) PersistedCommand (storage)
ID — id.CommandID
Timestamp — ReceivedAt
Payload typed struct (generic T) []byte (serialized)
Aggregate info AggregateID() AggregateRef{Type, ID}
Use case In-memory dispatch via Dispatcher Storage, audit, replay

Commands have two distinct lifecycles: they're dispatched in-memory (live) and optionally persisted to storage (audit). The split exists because not every dispatched command needs persistence — allocating an ID and timestamp for every fire-and-forget dispatch would be wasteful.

Revised comparison

Aspect Events Commands
Nature Facts — immutable by definition Intentions — may succeed or fail
In-memory form ImmutableEvent (heavy: ID + timestamp + bytes) BasicCommand (light: type + aggregateID only)
Storage-ready? Yes — same struct goes to Sink.Save() No — must convert to PersistedCommand
Serialization timing At creation (NewEvent) At persist (NewPersistedCommand)
Publishable? Yes — Bus.Publish Not yet — no CommandBus exists
Outbox? Yes — event.Outbox Not yet — no CommandOutbox exists

Open Questions

1. Could the command side follow the event pattern — make BasicCommand carry an ID and timestamp from creation, eliminating PersistedCommand? This would unify the shapes but allocate IDs for fire-and-forget dispatches. 2. Should the event side introduce a PersistedEvent too, for full symmetry? Probably not — ImmutableEvent already works as both forms. 3. When CommandBus is added, should PersistedCommand become the publishable type (like ImmutableEvent is for Bus.Publish), or should publishing use BasicCommand?
