Change Over Time, Without Another Service

How the fleet's contracts evolve today, where change management falls short, and where Apicurio Registry does and does not fit. Written for the owner deciding whether to adopt a registry or fix the pipeline.

00Summary

Two questions led here. The first was whether Apicurio Registry, an open-source schema and API registry, is worth using. The second was whether the fleet manages change over time well, and whether another service is the right fix. The answer to the second decides the first.

The fleet does not manage contract change over time well yet, and the cause is a missing record. The hub that federates all twelve catalogs rebuilds everything from scratch and keeps only the latest result. No previous state is kept, so nothing can say what changed between two builds, and nothing has a history to push into a registry.

Apicurio Registry stores versions; it does not create them. It would add a service to operate without closing the gap. The gap closes with a commit.

The bottom line Commit one deterministic snapshot of every source's contracts on each hub build, classify the diff with the library's own classifier, and render the history on the static hub. Git becomes the registry. Keep Apicurio out of the runtime and out of the gates.

01The question, precisely

Change management for contracts has four parts. Each answers a different question, and a system can have one without the others.

Part Question it answers What good looks like
Classify Is this change safe for everything that already exists? One policy, one classifier, used by every gate
Prevent Can a breaking change be stopped before it merges? A gate that runs on every source and cannot be skipped by accident
Detect Did something change since the last known state? A previous state to compare against, at fleet level
Record What changed, when, and was it deliberate? A history anyone can read without rebuilding old commits

Scope

  • In: the messages (commands, events, queries) of the twelve sources the hub federates, with their payload schemas, versions, producers, consumers and error surfaces, and how those are classified, gated, detected and recorded.
  • Out: which version of which service ran on which host when. inventory.json records hosts, ports and health paths, not versions. That is a separate ledger (section 08).
  • Out: whether old events stay readable. That is the data half, it is the strong half, and it is only summarised here.
  • Out: Apicurio Registry as a runtime schema registry. It was assessed and is not recommended (section 05).

Method

Evidence comes from the local checkouts of go-cqrs-lite, eventcatalog-hub and the source repositories as they stood on this machine on 2026-11-25, and from apicur.io pages fetched the same day. All twelve sources were checked locally: ten as separate checkouts, and mesh-billing and mesh-orders inside go-cqrs-lite's example/mesh-demo. Every count in this report was produced by a command; the commands are listed in section 09.

03What already exists

Much of the hard part is already built. The gaps in section 04 are about wiring and record-keeping, not about missing capability.

+
A policy-backed classifier catalog/compat walks two schema trees and classifies every difference against docs/SCHEMA-COMPATIBILITY.md. It names the upcast op a change owes, and only a breaking change without a version bump blocks (CompatCatalog, catalog/v4/compat/catalog.go:22). CUE subsumption was measured first and rejected at 22 of 24 fixtures, with two false "compatible" verdicts.
+
A snapshot format waiting for a consumer compat.Baseline is "a committed snapshot of the payload shapes at the last release" (catalog/v4/compat/baseline.go:24), keyed by message ID with kind, version and schema. CompareBaseline classifies a catalog against it.
+
Evolution on the data side Declared upcast chains wired through system.DomainConfig.Schema (ADR-0155), schema fingerprints with an advisory-to-hard drift ladder, and the cqrs-lint ladder rules E021 and E022.
+
Changelog and deprecation surface in the catalog Message.Changelog carries entries of version, date and summary (catalog/v4/types.go:147) and is exported as changelog.mdx; messages can be marked deprecated with a reason (DeprecationInfo).
+
A federation with gates The hub merges twelve sources, lints each source and the merged tree, audits collisions against a frozen baseline, and warns when its own data goes stale.
+
A base-vs-head gate recipe with a pinned agreement test check-architecture-changes.sh diffs two export trees (12 fixtures in 2 modes), and check-gate-agreement.sh states exactly where the two gates disagree instead of letting it be assumed.

04Where change management stands

Ordered by impact on the goal: knowing and governing change over time.

Blocking · High impact

Nothing records what changed over time

eventcatalog-hub · AGENTS.md:23 · git ls-files

The hub's content directories are generated and gitignored; its build and CI wipe and re-copy them on every run. The JSON it does commit is a deployment inventory (96 services with hosts, ports and health paths), project metadata, and a collision baseline. None of it records which messages, versions or schemas existed at a given time. The only history is each source repository's git, which answers "what did the fleet look like in October" only by rebuilding old commits.

The hub names the consequence itself. Its gate-agreement test documents that "the union has no time axis".

Fix: commit a deterministic contract snapshot per source on every build Section 06, step 1. Everything else in the recommendation depends on this snapshot existing.
Blocking · High impact

The hub cannot detect change between builds

eventcatalog-hub/scripts/check-gate-agreement.sh:14

With no previous state, the hub's union gate sees only the current merge. The agreement test pins the result: four breaking classes are asserted as invisible to the hub gate (schema changed, producer removed, consumer removed, error surface changed). They are visible only to the per-source recipe, which exists in two sources.

Fix: compare against the committed snapshot Section 06, step 5. The four classes become checkable at the hub for all twelve sources.
Important · Medium impact

Prevention exists for two sources and enforces in none that could be verified

.forgejo/workflows/architecture-gate.yml in bank-sync and cqrs-htmx · eventcatalog-hub/TODO_LIST.md:703 · cqrs-htmx/TODO_LIST.md:157

The base-vs-head workflow is committed and on the default branch of bank-sync (first commit 2026-10-28, last 2026-11-14) and of cqrs-htmx (2026-10-28). The hub's backlog still lists "mint the HUB_GATE_TOKEN secrets" as open under "blocked: upstream". cqrs-htmx's backlog records that its gate skips while SSH_PRIVATE_KEY is unset and that master has no branch protection, so every check is advisory. The other ten sources have no gate workflow.

The part of change management that stops a breaking change is the least deployed part, and it hangs on two secrets and one protection decision.

Fix: finish the two open items, then make the check cheap for the rest Mint the secrets and decide on branch protection once the classifier agrees with the policy (finding 4). Offer the hub's committed baseline as a token-free check for the remaining ten (section 06, step 6).
Important · Medium impact

Two classifiers disagree, and the precise one is idle

docs/SCHEMA-COMPATIBILITY.md:18 · catalog/v4/compat/catalog.go:17 · eventcatalog-hub/scripts/check-architecture-changes.sh:35 · FEATURES.md:1074

The library's policy says an additive change is safe without a version bump, and catalog/compat blocks only a breaking shape change whose message version did not move. The hub's recipe blocks any schema change under the same message version. The precise classifier has never run on a real catalog in CI: no compat-baseline.json is committed, so the gate "exercises fixtures and --self-test only". The coarse rule is the one wired into the two gate workflows. A policy-legal added field would fail that gate.

Demand for the precise version exists. CV's catalog self-review lists adopting a compat.CompatCatalog baseline as an open item that "needs owner scope call".

Fix: one definition of "breaking" Make the recipe's schema_changed defer to the classifier (section 06, step 3) and give the classifier a committed baseline (steps 1 and 2).
Important · Medium impact

The changelog surface exists and nothing was found feeding it

catalog/v4/types.go:147 · catalog/v4/eventcatalog/writer.go:138

The catalog can carry per-message changelog entries and exports them as changelog.mdx. Whether sources use this was not measured: only one source export was present on disk (webphone: 8 resources, no changelog file). A history that depends on someone remembering to write it stays sparse. Detected changes can generate the factual entries, and hand-written entries stay for intent.

Fix: generate fact entries from the snapshot diff Section 06, step 4.
Nice to have · Low impact

Stale notes found on the way

bank-sync/TODO_LIST.md:947 · docs/adr/0159:42 · two docs/planning files

bank-sync's backlog still opens with "Push the uncommitted catalog-governance set" although its gate workflow is on origin/master; the row covers several files and was not re-verified item by item. The old dependency budget DEP_BUDGET[catalog]=5 is still cited in ADR-0159 and in two planning documents. Those are dated records and were left alone. The living note in catalog/v4/AGENTS.md cited the same old cap and was corrected during this review (the gate defines 10, and the budget is full at 10).

05Why a registry does not close the gap

A registry answers a storage question: where do versions live so that clients can fetch them? The fleet's gap sits one step earlier. The hub rebuilds every tree from scratch and keeps only the result of the last run, so there is no previous version to store. Pushing each run to a registry would close the gap only because the push created the record. The same commit in git creates the same record with no service attached.

Once every state is committed, git already provides what the registry would provide: every version retained, any two comparable, each tied to a date and a commit message. What git lacks is the derived view, a timeline page and a classified diff, and that is a build step.

Decision matrix

Candidate use Verdict Why
Fleet-wide index of OpenAPI, AsyncAPI and per-message JSON Schemas Only on a trigger The real gap here is that nobody searches API documents across services or fetches old versions over an API. A committed snapshot plus a static timeline covers most of it without a server. Revisit when a trigger below appears.
Runtime schema registry (Kafka serializers, Confluent API) No No Kafka client in the fleet, Java-only serializers, Go types on CBOR, and ADR-0155 already rejected a registry on the data path.
Compatibility gate or second opinion No Apicurio rates its AsyncAPI compatibility "None". Its JSON Schema checker would have to clear the bar CUE failed at 22 of 24, and the fleet already owns a classifier that meets it.
Official Go SDK inside catalog No Six Kiota runtime modules for what would be four REST calls. The module's production dependency budget is already full. Plain net/http is enough if a client is ever needed, and it belongs beside the hub, not in the library.
Agent registry, MCP registry, prompt templates Later All experimental and off by default. The sibling prompt-registry is copy-paste documents, and the hub already serves llms.txt for agent consumers.

Triggers that would change the verdict

  • A service starts producing to Kafka with Confluent-compatible serializers. Apicurio implements that API and ships the Java serializers.
  • Clients written outside Go need to fetch schemas at runtime by identifier.
  • A second team needs a writable registry with its own review workflow, instead of git.
  • The fleet wants a searchable console for OpenAPI and AsyncAPI documents enough to justify running and upgrading a server for it.

06Recommendation: give the hub a journal

The library's own model applies to the fleet: a projection without a journal cannot answer questions about the past. The hub is that projection. The proposal adds the journal and changes nothing in the library's runtime.

12 sources → export + merge → snapshot, committed → classify, red on breaking → timeline page
1

Commit one deterministic snapshot per source on every hub build

Record, for each message, the id, kind, version, producers, consumers and a digest of its schema. Use canonical ordering so an unchanged rebuild produces an empty diff. Keep it in the hub repository, one file per source. The hub is the right place because it already merges all twelve trees, including the two exported by a Python script, so one implementation covers everything. compat.Baseline is an existing format for the Go sources; the exact file layout is an open decision (section 08).

2

Classify the diff on every build

Compare the new snapshot with the committed one. Red on breaking, info on additive. The library policy decides what "breaking" means, through catalog/compat.

3

Make the source recipe defer to the policy

schema_changed should block only when the classifier calls the change breaking. An added optional field stops failing the two gate workflows.

4

Render the history and feed the changelog

Add a timeline page to the static hub, generated from the git log of the snapshots: date, source, message, class, commit. Write each detected change into Message.Changelog as a fact entry, and leave intent to hand-written entries.

5

Close the four hub-blind classes

With a previous state in the repository, the hub can report schema, producer, consumer and error-surface changes for all twelve sources, and the four hub-side zeroes in the matrix of Appendix B can be flipped.

6

Offer PR-time prevention as a read

A source can compare its catalog against the hub's committed baseline before pushing, using CompareBaseline. No token, no second export, no clone of the hub.

The main risk is a red gate against never-recorded history, which is why the first rollout should warn.

07Do and do not

Recommend doing

Do Why
Commit a deterministic contract snapshot per source on every hub build Without a previous state, nothing can be detected, classified or recorded.
Classify diffs with catalog/compat, and let docs/SCHEMA-COMPATIBILITY.md be the only definition of "breaking" One policy, one classifier. It also gives the idle gate the real catalog it was built for.
Make the recipe's schema_changed defer to that classifier A gate that fails policy-legal changes gets re-baselined until it is noise.
Render a timeline from the committed history History nobody can read is not change management.

Finish the two open gate items (secrets, branch protection) after the classifier agrees with the policy Enforcing a gate that disagrees with the policy would enforce the wrong rule.
Keep Apicurio as a noted option and revisit on a trigger Section 05 lists the triggers. None is present today.

Recommend not doing

Do not Why Instead
Put a registry on the runtime path ADR-0155 already rejected the coupling. Keep upcast chains in-process.
Let Apicurio's compatibility rules replace or duplicate the gate AsyncAPI compatibility is "None"; JSON Schema fidelity is unmeasured here; CUE set the precedent at 22 of 24. Use catalog/compat.

08Limits and open decisions

Limits of this assessment

  • Hub-side detection happens after a source's default branch moved. Stopping a change before merge still needs a per-source check.
  • The classifier split is read from the two rule texts. The two tools were not run on the same fixture.
  • "Enforcing in none" rests on two open backlog rows and a branch-protection check dated 2026-10-27. The secrets themselves are server-side state and cannot be inspected from a checkout.
  • Changelog usage was measured on the one source export present on disk, not across all twelve.
  • The hub's published dist branch was not inspected. Any history kept there is unverified.
  • One search error was caught during this review. The first pass skipped hidden workflow directories and reported no gate workflow anywhere. The numbers here come from the corrected pass.

Open decisions for the owner

◆Appendix A · Apicurio spike checklist

Only relevant if a trigger in section 05 appears, or if the owner wants first-hand evidence before closing the question. 

docker run -it -p 8080:8080 apicurio/apicurio-registry:3.3.5   # in-memory, no persistence

curl -X POST localhost:8080/apis/registry/v3/groups/bank-sync/artifacts \
  -H "Content-Type: application/json" \
  --data @artifact.json        # artifactId, artifactType, firstVersion.content
  1. Does it accept the AsyncAPI 3.0 output this library generates? Its AsyncAPI validity check is syntax only.
  2. Does the console render it usefully?
  3. Does label search (/apis/registry/v3/search/artifacts?labels=) answer a question the hub cannot?
