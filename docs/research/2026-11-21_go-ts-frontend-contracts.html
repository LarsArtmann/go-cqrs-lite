One Declaration, Two Runtimes

00Summary

“Command & Event code written in Go that also works efficiently in the front-end” is two different problems wearing one sentence, and the research says they have opposite answers:

Problem What it means Verified answer
Contracts Types + runtime validation for command/event/query payloads Generate them — Go stays the single source of truth, the browser gets TypeScript that costs zero runtime bytes
Behavior Decide / fold logic running client-side Do not ship it — the smallest honest Go runtime in a browser is ~2 MB raw (~500 KB gzipped) with copy-semantics at the JS boundary

The pipeline this report proposes: Go payload structs → catalog JSON Schemas → generated TypeScript types + validators → a thin typed client → server-folded reads over the SSE machinery that already exists (metaengine.ServeSSE, replay, Last-Event-ID resume, backpressure — all shipped and tested today). The only new module code is one small exporter package inside catalog/v4; the rendering core already exists, test-pinned, inside the architecture export.

The bottom line Generate the contract, never the runtime. The catalog is already the contract hub — the same registration that feeds AsyncAPI, EventCatalog and the architecture reference will feed a TypeScript exporter. Drift is gated exactly like the API golden: regenerate, diff, fail CI on stale output. Local-first folding in the browser stays parked behind an evidence gate (a named fleet consumer), not built on speculation.

01The problem, precisely

“Efficiently” is doing all the work in the question, so it gets decomposed into five measurable properties. Any proposal that fails one of these is not efficient — it is merely possible.

Property Definition Failing smell
E1 · No drift One source of truth; the browser artifact is derived, never authored Hand-ported TS types that lag Go by three patches
E2 · Runtime bytes Types erase at compile time; validation costs ~kilobytes, not megabytes A Go runtime (WASM/GopherJS) inside the bundle
E3 · Wire fit Payload format matches the delivery path already shipped (SSE + JSON) Binary payloads base64-encoded over a text-only protocol
E4 · Version-skew safety Old front-end against new backend (rolling deploy) degrades loudly, not silently A schema change that bricks every open tab
E5 · DX One command regenerates; tsc and CI enforce the rest A four-step manual ritual nobody runs

Fleet context. Today’s front-ends in the first-party fleet are server-rendered: cqrs-htmx is templ + HTMX, and its only TypeScript lives in Playwright e2e specs. This proposal therefore targets the next front-end (a real SPA or local-first client), not the current one — and it stays additive on the v4 train: a new subpackage plus generated artifacts, no breaking surface, so the v5 free window is not needed and the v4 byte-freeze is not touched.

02What the repo already has

This is why the proposal is cheap: most of the pipeline exists, tested, behind a different door.

+
Schemas from Go types — catalog.SchemaFromType[T]() The single-source-of-truth mechanism (E1) already exists: register a payload struct once, get its JSON Schema.
+
AsyncAPI export embeds per-message schemas catalog/v4/asyncapi/builder.go:336-339 writes every message schema into Components.Schemas — a machine-readable interchange contract is already emitted, so any off-the-shelf generator can consume it as a fallback path.
+
A TypeScript renderer already exists, test-pinned typeScriptInterface() at catalog/v4/architecture/schema.go:74 renders TS interfaces from catalog schemas (pinned by TestTypeScriptInterface). Today it is unexported and embedded only in the HTML architecture reference — the proposal promotes it.
+
Declare-once composition root system.DomainConfig (system/v4/config_types.go:17) registers the full command/query/projection universe at boot, and the catalog-export cmd is a working copy-paste template for turning registrations into exported artifacts (EventCatalog MDX today).
+
Browser delivery leg is shipped and tested metaengine.ServeSSE (metaengine/v4/sse.go:111) serves a Watcher[V] over materialized read models with replay, Last-Event-ID resume, drop-old backpressure and heartbeats — the reconnect semantics the client will rely on are pinned in sse_replay_test.go.
+
A verified hypermedia alternative already scoped The sibling report Datastar, Client-Side (2026-11-07, this series) verified a 33,553 B raw / 13,365 B gzip client that consumes SSE directly — the zero-codegen path for HTML-shaped front-ends. This report is the other half: typed contracts for app-shaped front-ends.
+
The drift-gate pattern is institutionalized #check-generated-artifacts already regenerates docs-ui.css, error-taxonomy, engine-capabilities and the API golden with drift-restore. A TypeScript freshness leg slots into an existing gate, not a new invention.
+
Local-first reference model pre-researched The LiveStore deep dive (2026-05-01, archived) mapped client-side event sourcing end-to-end; §03.F updates it with current status — including the one property that matters here (pluggable sync backend).

03The landscape, verified

Every load-bearing claim below was checked against a primary source on 2026-11-21 (blog index, pkg.go.dev, npm, GitHub README, spec text). Claims that could not be confirmed are labeled UNVERIFIED inline and repeated in §10. Two legs of this research killed assumptions the author brought into the session — both are documented as negative results.

A · The official Go→TypeScript generator does not exist

The session opened with a lead: “the Go team ships tsgen under golang.org/x/tools.” That lead is false, verified four ways:

  • the complete Go blog index (fetched through “Go Turns 17”, 2026-11-10) contains no Go→TS generator announcement;
  • go.dev/blog/go-typescript returns HTTP 404 (raw-fetched);
  • pkg.go.dev/golang.org/x/tools/cmd/tsgen returns HTTP 404;
  • a Sourcegraph search of github.com/golang/tools finds no tsgen.

The near-miss that likely spawned the myth: github.com/microsoft/typescript-go — the TypeScript compiler being rewritten in Go (the reverse direction; “tsgo”). Implication: there is no official shortcut. Generation is either first-party (this proposal) or third-party (§03.B).

Both consume the same catalog registration; (a) is one moving part, (b) is a safety net if the experimental API moves.

D · Proto-first (buf / ConnectRPC): excellent, and the wrong default here

ConnectRPC’s TypeScript stack is real and current: the connect-es v1 packages were renamed to @connectrpc/connect v2 (v2.3.0 verified on npm, 2026-10), codegen runs through buf plugins, protobuf-es v2 is the official runtime, the wire protocol is curl-able JSON plus a binary option, and buf adds breaking-change lint — the same drift discipline this repo enforces by golden. Server streaming exists, but rides length-prefixed envelopes over HTTP POST, not SSE.

Why it is still the wrong default for this library: proto-first inverts the truth direction. Today a Go struct is the declaration and every artifact (AsyncAPI, EventCatalog, D2, architecture reference, the planned TS contracts) derives from it. Adopting .proto as the hub would make the Go structs generated, re-route the journal’s Go-typed event payloads through a second schema system, and import a toolchain the fleet does not run — to solve a problem the catalog hub already solves. Fit verdict: parked. If a fleet-wide RPC standard ever emerges (it has not), revisit as an additional export target, not a replacement hub.

E · Go in the browser (WASM): the numbers say no

Approach Verified floor Verdict for sharing domain code
Mainline Go (GOOS=js + wasm_exec.js) ~2 MB raw floor for trivial programs, 10–20 MB common, ~500 KB gzipped (Go issues/wiki, verified 2026-11-21) Fails E2 by three orders of magnitude
wasip2 / WasmGC targets Go issue #65333 still Backlog — not shipped Not available
TinyGo Hello world ~575 B; partial reflect, slow GC, recover() not reliable on wasm (docs note stale) Fails on fidelity: catalog schema reflection and rich payload types lean on exactly what TinyGo half-supports
GopherJS Not archived, but six minors behind: v1.21.0 (2026-06) compiles against a go1.21.13 stdlib (corrected 2026-11-21: an earlier draft said “not under active development” — phrasing absent from the verified source, and the June 2026 release contradicts it) Dead for a Go 1.27 library — every module declares go 1.27.2

Beyond size, the boundary is copy-semantics: syscall/js moves values by serialization (no shared structs), and a wasm instance blocks the main JS event loop on synchronous calls. Every command dispatch would pay two marshalling hops to reach code the server can run natively. Fit verdict: never the default. The one defensible future use — compiling a pure fold function for offline-first clients — stays parked with the local-first tier (§05 L4), behind a named consumer.

F · Local-first engines: one candidate is actually composable

Engine Contract definition Custom Go sync backend? Status (2026-11-21)
LiveStore TS-first (typed event tables, state schemas) Pluggable SyncBackend is documented API — the only one MIT; docs self-describe as pre-1.0 alpha
ElectricSQL PG schema + replication shapes Tied to their sync engine Active
PowerSync Sync rules (YAML/SQL) Their service/protocol Active
Zero (Rocicorp) TS schema + ZeroQL CGR protocol tied to their server Active
Triplit / Instant / Evolu TS-first schemas; Triple store; CRDT-SQLite Own protocols Active

Fit verdict: none of these become a dependency. LiveStore’s value is architectural confirmation: a serious local-first client separates eventlog from materialized state and exposes sync as a backend interface — which is exactly the shape a go-cqrs-lite journal-sync tier would take (§05 L4). The repo’s own deep dive (2026-05-01) already found the missing piece on their side — catch-up/replay — that this repo ships today via checkpoints + SSE replay.

G · Wire format: JSON over SSE is not a compromise, it is the correct default

  • The WHATWG HTML spec makes SSE data UTF-8 text by definition — binary over EventSource requires base64 (+33% bytes), so a CBOR wire would pay its savings back at the encoding boundary.
  • cbor-x’s own README claims “2–15× faster” parsing and “20–50% smaller” payloads — measured on Node/V8 server-side; browser-specific speedups are UNVERIFIED.
  • WebSocket does carry binary frames natively — but the repo’s delivery leg (replay, Last-Event-ID, heartbeats, backpressure) is SSE-shaped and tested.

Fit verdict: JSON over SSE (what ServeSSE already emits) is the default; a CBOR/WS path is a measured-need upgrade, not a starting position.

05The proposal: five layers

One pipeline, five layers — each independently shippable, each gated, and only L1 touches this repository’s module code.

Go structs + system.New ├── L0 declaration (exists) ├── L1 catalog → contracts.ts + schemas.json (NEW, small) ├── L2 thin typed client (generated, ~KB) ├── L3 server-folded reads over ServeSSE (exists) └── L4 local-first tier (PARKED, evidence gate)

L0 · Declare once — Go stays the truth

Nothing new: payload structs registered in the catalog, exactly as AsyncAPI/EventCatalog consumers do today. The catalog-export copy-paste cmd pattern generalizes: one registration feed now has one more consumer. 

// L0 — today's shape, unchanged
reg := catalog.NewRegistry()
reg.RegisterEvent(catalog.EventConfig{
    Name:   "todo.created",
    Schema: catalog.SchemaFromType[TodoCreated](), // Go struct → JSON Schema
})
reg.RegisterCommand(catalog.CommandConfig{
    Name:   "todo.create",
    Schema: catalog.SchemaFromType[CreateTodo](),
})

L1 · Emit contracts — catalog/v4/typescript (the only new package)

Promote the existing, test-pinned renderer (architecture/schema.go:74) into an exported package beside asyncapi/d2/eventcatalog: 

// L1 — new package, ~2 files + tests
package typescript

func Export(cat *catalog.Catalog, opts ...Option) *Result
// Result.Files: "contracts.ts"  — one interface per message
//              "schemas.json" — the JSON Schemas verbatim
// Result envelope carries catalog version + generation stamp
  • Types are first-party — deterministic naming (exportName is already behavior-pinned), no Node toolchain needed to build this repo.
  • Validators ride schemas.json — the app imports them via z.fromJSONSchema() at build time (experimental, §08 R1) or through the OpenAPI→hey-api zod path as the supported fallback.
  • Artifacts are committed in the consuming app; a new leg in #check-generated-artifacts regenerates and fails on drift — same ritual as the API golden.

L2 · Thin typed client — generated into the app, ~KB, zero deps

// generated contracts.ts (excerpt) — types cost 0 runtime bytes
export interface CreateTodo { title: string; dueAt?: string }
export const CreateTodo = z.fromJSONSchema(schemas["todo.create"])

// app code — the whole client is fetch + EventSource
const res = await cqrs.dispatch("todo.create", { title }, { parse: CreateTodo })
for await (const batch of cqrs.subscribe("todos/active")) { render(batch) }

The client template (dispatch via JSON POST; subscribe via EventSource with Last-Event-ID handled by the browser natively, replay/backpressure by the server) starts life inside the first consuming app — cqrs-htmx’s admin demo or an example/ — and is promoted to a shared template only when a second fleet consumer exists. Same evidence gate the queue task tables used.

L3 · Server-folded reads — the browser never folds

This is a decision, not an omission: the metaengine already exists to fold events into query-optimized projections, and §03.E shows what shipping folds to the browser would cost. The front-end subscribes to query results (Watchers over materialized state), not to raw event replay. The north-star vision already promises this: developers declare, the system projects and routes.

L4 · Local-first tier — parked with a written gate

A journal-sync tier (LiveStore’s shape: client eventlog + rebuildable state + sync backend interface, with go-cqrs-lite journal + checkpoints as the backend) is architecturally compatible — and explicitly not built now. Gate: a named fleet consumer with an offline requirement, at which point the TinyGo-fold question (§03.E) gets re-evaluated with real constraints, not speculation.

What “efficient” cashes out to E1: one truth (the catalog). E2: zero-byte types + ~KB validators. E3: JSON over the SSE leg that ships today. E4: schemas carry schemaVersion, the envelope names its type, unknown versions fail loudly in the validator. E5: one generate command, two CI gates (tsc in the app, freshness in this repo).

08Risks

R1 · Medium

z.fromJSONSchema() is experimental

zod v4 · keyword coverage still expanding (4.6, 2026-09)

The import direction this pipeline wants (JSON Schema → validator) carries an experimental label; keyword coverage gaps could silently loosen validation for exotic schemas.

Mitigation Pin the zod version in the app; CI asserts the generated schema set only uses covered keywords (our schemas are flat-struct-shaped); fallback path is OpenAPI → hey-api zod plugin, which is supported.
R2 · Medium

Schema fidelity gaps at the Go→JSON boundary

unions, time.Time, branded IDs, pointer-vs-optional

Go sums (interfaces) do not map to closed TS unions; time.Time serializes as RFC 3339 string (a string to TS unless annotated); branded IDs are strings on the wire — losing the brand in the browser re-opens the exact bug class branding exists to close.

Mitigation P0 golden tests cover the known-hard shapes; generated TS uses template-literal brands for branded-ID fields where the schema carries the marker; a lint pass (cqrs-lint candidate) flags event payload fields that fall in the gap classes.
R3 · Low

Freshness gate bypass

#check-generated-artifacts leg

A developer edits Go structs, forgets regeneration, and CI catches it — if the app importing the contracts is in the same gate run. Cross-repo (cqrs-htmx) consumption needs the gate to live where the artifact is committed.

Mitigation The generation stamp (L1 result envelope) lets the consuming repo’s CI diff its committed artifact against a fresh regeneration without importing Go — stamp mismatch fails the app build.
R4 · Low

Version-skew during rolling deploys

old tab, new backend

A browser tab holds contracts from deploy N against a backend at N+1. Validators reject unknown fields or new required fields appear — either can break an open session.

Mitigation Envelope carries type name + schemaVersion; validators are tolerance-configured (unknown fields strip, missing-new-optional defaults); hard failures surface a typed “contracts-stale” signal the app can act on (reload prompt) instead of a silent undefined.
