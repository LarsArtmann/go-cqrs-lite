01

The Problem

core/event/ contains 28 files, ~2,500 lines, and 8 distinct concerns — from the Event type itself to snapshot strategies, outbox publishers, and projection checkpoints. It's the only package in the repo that violates the "one concept, one package" rule.

The core/ prefix is the only nested module group in a repo of 17+ flat top-level modules. It forces command/ and query/ — which share zero dependencies — to share a go.mod with 15+ dependencies they don't need.

"core" is meaningless. Every module thinks it's core. It's the util of package naming.

What was wrong with v1 of this proposal: It created a store/ module for Sink/Source interfaces. But this is a CQRS library — store interfaces are domain-specific. EventSink belongs in event/. SnapshotStore belongs in snapshot/. A generic store/ module would be the same anti-pattern as core/ — a drawer for things not properly named.

02

Principles

  1. 01 Honest names. Every module named after what it is, not where it sits in a hierarchy.
  2. 02 Sink/Source is a domain pattern, not a shared module. Every domain owns its own read/write split: EventSink/EventSource in event/, SnapshotSink/SnapshotSource in snapshot/, CommandSink/CommandSource in command/. No generic store/.
  3. 03 Peer-level modules. The repo already uses flat top-level modules. core/ is the outlier.
  4. 04 Minimal go.mod. A module's dependencies should be only what it needs.
  5. 05 Interface–implementation separation. Core modules define interfaces. Implementations live in their own modules.
  6. 06 git mv preserves history. Move files once. No copy-then-delete dance.

06

schema/

Upcasting is currently buried in core/event/ — but it's neither an event concern nor a store concern. It's schema evolution. Naming the module upcaster/ would describe the mechanism. schema/ describes the domain.

Future growth. A schema/ module naturally accommodates compatibility checks, version registration, auto-documentation hooks (via catalog/), and migration policies — none of which fit under "upcaster."

File Exports Origin
upcaster.go Upcaster, NewUpcaster from event/upcaster.go
registry.go Registry from event/upcaster_registry.go
versioned_source.go VersionedSource, NewVersionedSource from event/versioned_store.go
version.go SchemaVersion, ParseSchemaVersion extracted from event/types.go
errors.go ErrMissingUpcaster, ErrIncompatibleSchema new
07

snapshot/

Snapshots are currently 3 files (~115 lines) in core/event/. They're a distinct concern — aggregate state caching, not event storage. A snapshot store has different read/write patterns (save whole state, load latest), different implementations (in-memory, SQL, Redis), and different consumers (decider, projection) than the event store.

Giving snapshots their own module follows the same principle: store interfaces live in their domain. SnapshotStore belongs in snapshot/, not lumped into event/.

File Exports Origin
snapshot.go Snapshot, SnapshotSink, SnapshotSource, SnapshotStore from event/snapshot.go
strategy.go SnapshotStrategy, EveryNEvents, MustEveryNEvents from event/snapshot_strategy.go
helper.go ShouldSnapshot from event/snapshot_helper.go
08

The memory/ Problem

memory/ currently provides in-memory implementations of 5 unrelated interfaces in a single package:

File Implements Interface defined in
store.go + store_load.go MemoryStore event/ (Store, Journal, SeekableJournal, BackwardsSource, StreamLoader)
bus.go MemoryBus bus/ (Publisher, Subscriber, Bus)
snapshot.go MemorySnapshotStore snapshot/ (SnapshotStore)
checkpoint.go MemoryCheckpointStore event/ (CheckpointStore)
outbox.go MemoryOutboxStore outbox/ (Outbox)

After the split, memory/ would need to depend on event/, bus/, snapshot/, outbox/ — importing from 4+ modules to provide test doubles.

Options

Option Structure Trade-off
A. Keep memory/ as-is One module, many deps Simple to find. But pulls 4+ modules for consumers who only need MemoryStore.
B. Split into domain sub-packages event/memory/, bus/memory/, snapshot/memory/ Consumers import only what they need. But 5 more sub-modules.
C. Keep memory/ as re-export facade Sub-packages do the work, memory/ re-exports Both convenient and clean. More files to maintain.

Recommendation: Option B. Each module owns its own test implementations. It follows the same principle as the rest of this proposal: things live in their domain. A consumer who only needs MemoryStore imports event/memory/ — not a grab-bag.

Dependency Graph

After the split — clean DAG, no cycles, no false coupling.

Key difference from v1: No store/ module. event/ owns its own storage interfaces. snapshot/ owns its own. command/ and query/ have zero dependency on event/.

Migration Plan

Each phase is a single commit. git mv preserves history. Tests pass after every phase.

  1. Create target directories + go.mod files
    Create event/, bus/, schema/, snapshot/, command/, query/, decider/, id/, dispatcher/, outbox/. Add minimal go.mod to each. Update go.work.
  2. git mv core/event/ → event/ (event stays as package)
    Move the entire core/event/ directory to event/. Fix all import paths. Run tests. This is the biggest single move.
  3. git mv event/{bus,snapshot,upcaster,checkpoint,projection,outbox} files → new modules
    Extract bus.go → bus/, snapshot*.go → snapshot/, upcaster*.go + versioned_store.go → schema/, outbox*.go + publish_helper.go → outbox/, projection.go + checkpoint.go + replay.go → projection/. Fix imports. Run tests.
  4. git mv core/{command,query,decider} → top-level
    Move core/command/ → command/, core/query/ → query/, core/decider/ → decider/. Fix imports. Run tests.
  5. git mv core/pkg/{id,dispatcher} → top-level
    Move core/pkg/id/ → id/, core/pkg/dispatcher/ → dispatcher/. Fix imports. Run tests.
  6. Split memory/ into domain sub-packages
    memory/store.go → event/memory/, memory/bus.go → bus/memory/, memory/snapshot.go → snapshot/memory/, etc. Keep memory/ as optional facade or remove.
  7. Delete core/
    Remove the core/ directory. Remove from go.work. Full test suite green. Done.
