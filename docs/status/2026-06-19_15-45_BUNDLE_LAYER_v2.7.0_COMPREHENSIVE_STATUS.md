## e) WHAT WE SHOULD IMPROVE

### Architecture

1. **SQL-backed kv.Store adapter** — SQLite and Postgres presets use `kv.MemStore` for read models. This means read models are lost on restart. A SQL-backed kv.Store would make them persistent. The `kv.Store` interface (Get/Set/Has/Delete/Iterator/Batch/Closer) maps cleanly to SQL tables.

2. **Event bus for persistent presets** — SQLite, Pebble, and Postgres presets all use `memory.NewMemoryBus()`. For Postgres, LISTEN/NOTIFY would enable real distributed pub/sub. For SQLite, a WAL-based notification mechanism is possible.

3. **Read model Scan performance** — The current `readModelAdapter.List/Count` scans ALL keys and filters in memory. For large datasets, secondary indexes or a SQL-backed read model would be needed.

4. **Bundle validation is minimal** — `validate()` only checks "at least one field set." It doesn't check for coherent combinations (e.g., EventSink set but no EventSource).

## g) Top #1 Question I Cannot Figure Out Myself

**Should read models for SQL-backed presets (SQLite, Postgres) use a SQL-backed `kv.Store` adapter, or should we accept that read models are ephemeral and rebuilt by projections on restart?**

Arguments for SQL-backed KV:
- Read models survive restarts without projection replay
- Simpler deployment (no "warm-up" period)
- Consistent with events/commands/snapshots being persistent

Arguments against:
- `kv.Store` interface has `Iterator` (prefix scan) which maps poorly to SQL (needs indexed LIKE query)
- Adds complexity to presets that already work
- Projection replay is fast and idempotent — rebuilding read models is the "correct" ES pattern
- SQL is not a natural fit for key-value access patterns (no range scans without custom indexes)

The `kv.Store` interface was designed for LSM-tree backends (Pebble), not SQL. Forcing it onto SQL would mean either a JSON blob table with poor query performance, or admitting that read models need a fundamentally different storage abstraction than events.

**My recommendation:** Keep `kv.MemStore` for SQL presets (document it clearly), and let consumers who need persistent read models use the Pebble preset (which already has a proper KV backend). If SQL-backed read models are needed later, consider a separate `readmodel.SQLStore[T,K]` that doesn't go through `kv.Store` at all.
