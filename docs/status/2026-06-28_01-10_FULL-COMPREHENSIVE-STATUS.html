signing module fails per-module build & test (GOWORK=off)

signing/internal/testutil/testutil.go:8 · signing/go.mod

signing/internal/testutil/testutil.go imports github.com/larsartmann/go-cqrs-lite/event/v3/eventtest (line 8). But signing/go.mod only requires event/v3 — eventtest is a separate module with its own go.mod, and it is missing from signing's dependency list.

Verified: cd signing && GOWORK=off go test ./... → FAIL ... [setup failed]. The workspace hides this because go.work resolves everything transitively.

Fix (trivial): cd signing && GOWORK=off go get github.com/larsartmann/go-cqrs-lite/event/v3/eventtest then tidy. This violates the project's stated principle #10 (multi-module isolation) and the CI claim of "GOWORK=off per-module".

eWhat We Should Improve

Make per-module isolation CI-enforced for ALL modules

The signing bug proves "GOWORK=off per-module" is either not run for every module or its failure is not gating. Isolation is principle #10 — it should be a hard gate, not an aspiration. Audit the CI matrix.

Add a "no placeholder doc.go" lint guard

A trivial grep for // Package \w+ provides \.\.\. failing CI would have caught all 15 stubs instantly. Documentation quality is part of the "would a consumer trust this?" gate.

Treat doc accuracy as testable

The doc.go review found 4 examples that wouldn't compile (pebble) or referenced renamed APIs (grpc.Dial). A go test-extracted "doc examples compile" check (àla testable examples) would harden every code block in doc comments.

Audit all modules for the same missing-subpackage-dep class of bug

If signing is missing eventtest, other modules may be missing idtest/querytest/eventtest. Run GOWORK=off go build ./... for every module and capture which fail.

Coverage honesty for stack/postgres

0% local coverage misleads. Either run postgres tests in CI with a live DSN, or label the module's coverage as "skipped locally" in FEATURES.md so the number isn't read as "untested".

Reconcile & date tracking docs on every release

TODO_LIST, FEATURES, ROADMAP "Updated" dates drifted by 3+ days. Tie a doc-freshness check to the release process.

gThe One Question I Cannot Answer Myself

Top question (blocking trust in the module-isolation guarantee):

The signing module provably fails GOWORK=off go build and go test because of a missing event/v3/eventtest dependency — yet CI is reportedly green and described as "GOWORK=off per-module". How, exactly, did this slip through?

There are only three possibilities, and I cannot determine which without reading the full CI matrix:

  1. CI does not actually run GOWORK=off for signing — maybe only a subset of modules get the per-module treatment, and signing fell outside it.
  2. CI runs it but the failure is not gating — e.g. continue-on-error, a swallowed exit code, or the per-module step is best-effort.
  3. The dependency was removed/changed very recently and no CI run has executed against this state since.

Resolving this is more important than the one-line go get fix, because if isolation isn't enforced for signing, it likely isn't enforced for other modules either — and "every module builds in isolation" is a load-bearing promise of this library. Answering this decides whether item #4 in the Top 25 is "fix a CI gap" or "fix a CI lie".

Why I can't self-resolve: I inspected signing/go.mod and reproduced the failure locally, but I have not read .github/workflows/ci.yml's per-module loop to see whether signing is in its iteration list and whether its exit status gates the workflow. That file is the single source of truth, and reading it is the one external step needed.
