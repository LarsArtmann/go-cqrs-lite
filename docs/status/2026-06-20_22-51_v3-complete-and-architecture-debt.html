05e) What We Should Improve

High

119 workspace replace directives — replace tangle

*/go.mod files across the monorepo

36 modules each carry replace ... => ../sibling directives to point at local paths during development. This is standard Go workspace hygiene, but 119 lines of replace directives is a maintenance tax: every new module means editing N go.mod files. A go.work file already handles this for local dev; the per-module replaces exist so each module is independently importable with GOWORK=off. Consider whether that independence is worth the tangle, or whether a thin release tool could sync versions automatically.

High

AGENTS.md test command references non-existent module paths

AGENTS.md — the "Test" row

The documented test command lists top-level ./memory/..., ./pebble/..., ./readmodel/... paths that no longer exist (they moved to ./storage/memory/..., ./storage/pebble/..., and readmodel was deleted). A copy-paste of that command fails. The correct paths come from go.work's use-set. This cost me ~10 min this session and will cost every new contributor.

07g) The One Question I Cannot Answer Myself

The question Is independent module importability (each module works with GOWORK=off go build) worth the cost of maintaining 119 hand-synced replace directives across 36 go.mod files?

I can verify the current state, I can count the directives, I can run the build both ways — but I cannot decide the tradeoff for you. Here is the tension:

Status quo (independent)
Alternative (consolidated)
Each module has its own go.mod + replaces pointing at siblings. A consumer can go get github.com/.../event/v2 and it resolves to a published version. Every module is independently versionable and importable. Cost: 119 replace lines, manual sync, easy to forget one (this session found 4 broken modules missing watermill/storage/memory replaces).
Collapse to fewer, larger modules (e.g. one go.mod per layer). Fewer replaces, less drift, simpler releases. Cost: consumers import more than they need, versioning is coarser, and the "minimal dependencies" principle (AGENTS.md #3) weakens.

This is a genuine product-direction call about who the library is for: minimal-footprint importers (favor independence) vs. operational simplicity (favor consolidation). The codebase is healthy either way; I just need your steer before recommending a path.
