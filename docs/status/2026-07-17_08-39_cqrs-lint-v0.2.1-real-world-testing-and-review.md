## d) TOTALLY FUCKED UP

Nothing was broken this session. All changes were verified before
committing. No regressions detected.

**However, one thing was already fucked up before this session and I
should have caught it during testing:**

The D002 rule (JSON tag casing consistency) reports at the **file level**
(line 1:1) rather than at the **struct/field level**. This means:

```
INFO /path/to/file.go:1:1 File mixes camelCase and snake_case JSON tags
```

This is imprecise — the user has to manually find which struct has the
mixed tags. For files with multiple structs, this is unhelpful noise.
D002 is the **most fired rule across all consumers** (33x on KeyCountdown,
20x on DiscordSync, 7x on Kernovia). Every one of these findings points
to line 1:1, which is a file-level heuristic, not a precise location.

I should have caught this during the real-world testing and flagged it
as a UX problem. Instead I just reported the counts.

## e) WHAT WE SHOULD IMPROVE

### Correctness

1. **D002 should report at the struct level, not file level** — Currently
   fires at `file.go:1:1`. Should point to the specific struct with mixed
   JSON tags. This is the highest-impact improvement for finding quality.

2. **E007 rule fires too aggressively** — 30x on KeyCountdown, 7x on
   crush-daily. I didn't look at what E007 checks, but 30 findings on
   one project suggests the heuristic is too broad.

3. **Existing suppression comments may be stale** — bank-sync has 3
   suppression comments for rules that don't fire at those locations.
   The linter should warn when a suppression comment references a rule
   that never fires at that line (stale suppression detection).

### UX

4. **D002 snippet shows the package declaration, not the offending struct** —
   The snippet for D002 shows `package cqrs` (line 1 of the file) instead
   of the struct with mixed tags. This makes the finding nearly useless
   without manually opening the file.

5. **No `--since-commit` or diff-aware mode** — Running on the full
   project every time is slow for large codebases. A diff-aware mode
   would make CI integration practical.

6. **No way to export a baseline and compare** — After fixing findings,
   there's no way to verify they don't regress without a baseline file.

### Testing

7. **No real-world test of auto-fix** — The `--fix` and `--dry-run`
   modes are completely untested on real code.

8. **No real-world test of config file** — `.cqrs-lint.json` loading and
   rule overrides are untested on real projects.

### Architecture

9. **The finding pipeline is a series of free functions** — `collectFindings`
   → `filterSuppressed` → `filterBySeverity` → `filterByConfidence`. Adding
   a new filter means remembering to wire it into `run()`. A `FindingPipeline`
   struct with named stages would be more maintainable.

10. **Health score weighting constants are magic numbers** — Critical=10,
    Error=5, Warning=2, Info=1. These are in `health.go` but not tunable
    via config (only the Info cap is tunable).

## g) Questions I Cannot Figure Out Myself

### 1. Should D002 be restructured to report per-struct, or is file-level acceptable with a better snippet?

D002 currently fires at `file.go:1:1` with the message "File mixes
camelCase and snake_case JSON tags." This is the most-fired rule across
all consumers (33x on KeyCountdown, 20x on DiscordSync). Two options:

- **Per-struct reporting** — fire at the struct declaration line,
  pointing to the specific struct with mixed tags. More precise, more
  useful, but significantly more complex to implement (need to track
  per-struct JSON tag state during AST traversal).
- **Keep file-level, improve snippet** — still fires at line 1, but
  the snippet shows the first struct with mixed tags instead of
  `package cqrs`. Less precise but much easier to implement.

I cannot decide this because it depends on how much precision consumers
need vs. how much implementation complexity you want to take on.

### 2. Should we warn about stale suppression comments (where the suppressed rule never fires)?

bank-sync has 3 `//cqrs-lint:ignore(...)` comments where the referenced
rules don't actually fire at those locations. This could mean:

- The rule was fixed/changed and the suppression is now stale
- The rule was never firing there (false suppression from the start)
- The user pre-emptively suppressed a rule they expected to fire

Should the linter detect and warn about stale suppressions? This would
be a new feature, but it could help consumers clean up their code. The
risk is false warnings if the rule fires conditionally (e.g., only with
certain feature profiles enabled).

### 3. Is the current exit-code behavior correct for CI?

Currently: exit 1 only when Error+ severity findings are present.
Warnings and Info don't trigger exit 1. This means a project with 50
warnings but 0 errors will pass CI. Some linters (like golangci-lint)
allow configuring the exit-code threshold.

Should cqrs-lint add a `--fail-on warning` option, or is the current
"only Error+ triggers exit 1" the right default? This depends on your
CI philosophy and whether you want to enforce zero warnings.
