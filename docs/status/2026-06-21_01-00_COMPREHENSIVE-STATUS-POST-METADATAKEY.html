DTotally Fucked Up

Failing Test

CBOR canonical encoding is not a fixed point (NaN map keys)

codec/codec_fuzz_test.go:336 · FuzzCBORCodec_CanonicalFidelity · seed 5f72aef8648194a5

The fuzz test FuzzCBORCodec_CanonicalFidelity fails on a stored seed that contains a CBOR map with a NaN half-float key (\xf9\x7f). Canonical re-encoding reorders two NaN keys differently, so encode(decode(x)) != encode(decode(encode(decode(x)))). This is a known issue — flagged as priority #7 in the brutal self-review (2026-06-20). It passes in isolation (cd codec && go test -run FuzzCBOR) but fails in the full workspace run, suggesting a shared-state / initialization-order component.

Impact Canonical CBOR is used by signing (hash stability) and pebble storage. In practice, no consumer puts NaN floats in map keys, but the canonical-form contract is violated. The fuzz seed is committed to codec/testdata/fuzz/, so this will fail CI until fixed.
Fix The canonical encoder must produce a deterministic order even for keys that compare equal (NaN). Either reject NaN keys at encode time, or use byte-level tiebreaking after canonical sort.

EWhat We Should Improve

TransactionID ghost type

id/transaction_id.go exists but is unwired — no field on event.Metadata, no Option, no propagation. A type that does nothing is worse than no type. Either wire it or delete it. (TODO_LIST marks it open.)

Version.Add underflow

event.Version.Add(n int) can underflow if n is negative. Domain invariant: versions are never negative. Should be Add(n uint64) or guarded. No property test exists for Add/Sub invariants.

PgxListener race

storage.PostgresBus PgxListener l.conn is not guarded against concurrent Close() + receiveLoop. Known race; needs sync.Mutex or atomic.Pointer + a -race test against real Postgres.

storage/ coverage 79.3%

Lowest coverage among core modules. The SQL store happy paths are tested; error branches (duplicate-key, tx failures, scan corruption) are lighter. Brings down the aggregate.

CBOR fuzz flakiness

The canonical-fuzz failure is order-dependent (passes isolated, fails in full suite). The encoder mode initialization may not be goroutine-safe, or a prior test mutates shared state. Worth investigating independent of the NaN fix.

Rapid underuse

pgregory.net/rapid is a dependency but barely used. Perfect for Version arithmetic, Metadata round-trips, ULID ordering, CBOR canonical encoding. Should be the default for pure-function properties.

GTop Question I Cannot Answer

Is it time to cut the v3.0.0 release, or hold for real consumers?

All 10 v3 breaking changes are shipped and tested. The only remaining [v3] item is the eventOptions deep-copy — a minor internal cleanup with zero consumer API impact. The library is, by every objective measure, feature-complete for v3.

What I cannot figure out: whether to (a) tag v3.0.0 now and let real consumers surface the rough edges, or (b) hold and do another polish pass (tasks #3–#10 above) first. The brutal self-review's position was "STOP, do not start Tier 3/4, wait for a consumer" — but that was about new features, not about shipping the release. There is zero internal consumer signal (this is a library; examples are demos, not deployments).

Cutting v3 commits the breaking changes publicly — once tagged, the aliases are gone forever and any silent consumer breaks. Holding costs nothing except momentum. I lean toward shipping (the breakage is well-documented in V3_MIGRATION.md, and the half-applied ADR limbo was worse than a clean break), but this is a one-way door that only you can open.
