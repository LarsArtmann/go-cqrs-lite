## e) WHAT WE SHOULD IMPROVE

### Critical reflections on this session's work:

1. **The `ExplainableScan` dual-path is a code smell** — `TypedReader.Explain` checks TWO interfaces: first the exported `ExplainableScan`, then the unexported `explainScan` method. The sqliteEngine should migrate to implement `ExplainableScan` directly, eliminating the unexported method and the dual-path branching. This would be a clean follow-up.

2. **`CalibrationCosts` doesn't cover all engine profile fields** — The struct has `NsPerOp`, `NsPerRead`, `NsPerWrite`, and `ReadCosts`. But `EngineProfile` also has `Replication`, `ReplicationLag`, `NetworkRTT` — none of which are calibratable. This is probably fine (those are topology, not performance) but should be documented as a deliberate boundary.

3. **The adttest layout harness seeds ALL 3 scenario collections in one `Seed` function** — Each scenario calls `MapSet` on "layout_filter", "layout_sort", AND "layout_filter_sort" regardless of which scenario is running. This wastes writes. The seed function should be per-scenario.

4. **Benchmark naming inconsistency** — The new benchmarks use `BenchmarkDuckDB_Layout*` but existing ones use `BenchmarkCalibration_DuckDB_*`. The naming convention is mixed.

5. **No benchmark for `ExplainScanQuery` itself** — Explain is a debugging tool so this is low priority, but we have zero perf coverage of the explain path.

6. **The `CalibrateEngine` doc comment is very long** — It includes a code example for manually setting `ReadCosts` which is great, but it's unusual for a doc comment. Consider extracting to an example test.

7. **`layout_bench_test.go` uses `populateDuckDBEngine`** which writes via `MapSet` one at a time — this is DuckDB's worst case (single-row autocommit). The benchmark measures read performance, so this is OK for seeding, but the seeding itself takes a long time relative to the measured operation. A batch-seed helper would speed up benchmark startup.

8. **The auto-commit daemon shipped unrelated work during this session** — Commits `433c2078` (StreamTemporalReader), `e951d089` (pebble stream log), `37e929bf` (SCREAM diagnostics), `6028f9dc` (StreamLogBackend), and `066b4e7b` (documentation) all landed while this session was running. ## g) Questions (things I genuinely cannot determine myself)

### Q1: Should sqliteEngine migrate to the exported `ExplainableScan` interface?
The current `TypedReader.Explain` has a dual-path: it checks `ExplainableScan` first (for DuckDB), then falls back to an unexported `explainScan(ctx, col, cfg scanConfig)` method (for SQLite). Migrating sqliteEngine to `ExplainableScan` would eliminate the branching but requires translating `scanConfig` → `ExplainOptions`. The `scanConfig` struct has `orGroups`, `sortCols`, `ranges`, and `inSpecs` that `ExplainOptions` doesn't have. Should I:
- **A)** Expand `ExplainOptions` to cover all `scanConfig` fields and migrate SQLite?
- **B)** Keep the dual-path (it works, just slightly ugly)?
- **C)** Make `explainScan` the single internal method and have `ExplainableScan.ExplainScanQuery` call it?

I chose B for this session because expanding `ExplainOptions` changes the public API more than the task required. But this is a design decision you may want to weigh in on.

During this session, the daemon shipped: `StreamTemporalReader`, `StreamLogBackend`, `SCREAM diagnostics`, `SnapshotBackend consolidation`, and documentation updates. Some of these (like the `SnapshotBackend` move from system → metaengine) overlap conceptually with the calibration export work. The git history interleaves daemon commits with this session's edits. Should I:
- **A)** Leave it — the daemon's work is independent and was committed correctly?
- **B)** Audit the daemon commits for conflicts with this session's intent?

### Q3: Should the `CalibrationCosts.ReadCosts` override be additive or replacement?
Currently `ApplyCalibration` does per-field overrides: each `ReadCosts` field is applied only if `> 0`, preserving engine defaults for unset fields. This means you can calibrate `NsPerPointLookup` without affecting `NsPerAggregate`. Is this the right semantic? The alternative is "replace the entire `ReadCosts` struct" which is simpler but less flexible. I chose per-field because it matches the existing `NsPerOp`/`NsPerRead`/`NsPerWrite` pattern, but I want to confirm this was the right call.
