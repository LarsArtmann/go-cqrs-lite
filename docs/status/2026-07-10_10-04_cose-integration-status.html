01What the First Report Got Wrong

False claim: "dead encodeToBuffer function at codec/cose.go:306"

The first report claimed encodeToBuffer was dead code still in the codebase. Verification: grep -rn 'encodeToBuffer' codec/ returns nothing. It was removed during the original refactoring before the commit. The report documented a problem that didn't exist — because the report's author didn't verify the claim against the actual code.

Fixed: duplicated normalizeCOSEAlgorithm

The first report correctly identified that normalizeCOSEAlgorithm was copy-pasted into both signing/cose.go and encryption/cose.go. This has now been fixed. The function is exported as codec.NormalizeCOSEAlgorithm in codec/cose.go. Both signing and encryption call it via the codec import. The duplicated copies, their unused errors (ErrCOSEAlgorithmOverflow, ErrCOSEInvalidAlgorithm), and the math import were removed from both modules.

Net change +48 lines (shared function + errors in codec/), -88 lines (duplicated code + errors + imports in signing/ and encryption/).

Trimmed: 50-task roadmap was 60% fantasy

The original 50-task list included ECDSA P-384, WalnutDSA, post-quantum algorithms (ML-DSA-44/65/87), CWT claims, verifiable data structure proofs, and 6 forms of key agreement. These are not tasks for a Go CQRS library — they're an IETF working group backlog. The revised report has 20 tasks, all of which are actionable by one developer in one sitting.

Answered: 2 "unanswerable" design questions

The first report posed two design questions it claimed it couldn't answer. Both are answerable from the library's existing design principles. See section 06.

05What Could Be Better

No RFC 9052 test vectors

RFC 9052 Appendix C contains canonical test vectors. Our tests verify round-trips but never compare against the RFC's published bytes. We could be producing valid but non-standard CBOR.

Canonical payload is not portable

SignCOSE1 places the library's custom canonical signing bytes (length-prefixed event fields + SHA-256 payload hash) in the COSE payload field. The COSE message is structurally valid RFC 9052 but the payload is only meaningful to go-cqrs-lite. This is a deliberate tradeoff (see Design Decisions) but limits interop.

No content type header

RFC 9052 defines content type (label 3) for identifying payload format. Our messages don't set it. Consumers need out-of-band knowledge to interpret the payload.

No CBOR tags

RFC 9052 defines CBOR tags 18 (COSE_Sign1) and 16 (COSE_Encrypt0). Our messages are untagged arrays. Tagged messages are self-identifying.

go.mod replace directive maintenance burden

signing/go.mod and encryption/go.mod now carry 11 replace directives each. Any time event/ gains a new dependency, both must be updated manually for GOWORK=off (CI per-module tests). This is a workspace- level problem, not COSE-specific, but COSE triggered the latest instance.

06Design Decisions (Self-Answered)

The first report posed two questions it claimed it couldn't answer. Both are answerable from the library's stated design principles.

D1: Canonical payload vs raw event bytes in COSE_Sign1

Decision: canonical payload is correct for v1. The library's Signer interface defines signing over canonicalPayload(evt) — covering event ID, type, aggregate, version, schema version, occurredAt, and payload hash. COSE_Sign1 wraps this same byte string. This ensures identical security coverage to the existing non-COSE signing path.

A future SignCOSE1Raw variant could sign just the event payload bytes for systems that only need payload integrity (not event metadata). But that would be a different trust boundary, not a replacement. The current design is the right default.

D2: Additive middleware vs replacement of existing signing

Decision: additive, not replacement. The library's principle #1 is "Library, not framework." COSE is an opt-in interoperability escape hatch. The existing metadata-based signing (SignMiddleware) remains the default because it's simpler and already works. COSE middleware (SignCOSE1Middleware) will attach the COSE bytes in custom metadata alongside the existing signature, giving consumers both formats when they need cross-system interop.

Replacing the existing signing path entirely would be a v4 breaking change that serves no one — consumers who don't need COSE interop would pay the CBOR overhead for no benefit.
