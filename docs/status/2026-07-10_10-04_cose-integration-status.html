05What Could Be Better

No RFC 9052 test vectors

RFC 9052 Appendix C contains canonical test vectors for COSE_Sign1 and COSE_Encrypt0. Our tests verify round-trips but never compare against the RFC's published vectors. We could be producing valid but non-standard CBOR.

Canonical payload vs raw payload design tension

SignCOSE1 places the library's custom canonical signing bytes (length-prefixed event fields + SHA-256 payload hash) in the COSE payload field. This means the COSE message is not portable to a system that doesn't understand the go-cqrs-lite canonical format. An alternative design would sign the raw event payload bytes and put event metadata in the COSE protected header.

No content type header in COSE messages

RFC 9052 defines a content type header parameter (label 3). Our COSE_Sign1 and COSE_Encrypt0 messages don't set it. Consumers receiving the COSE bytes have no way to know the payload format without out-of-band knowledge.

No CBOR tag usage

RFC 9052 defines CBOR tags 18 (COSE_Sign1) and 16 (COSE_Encrypt0). Our MarshalCOSESign1/MarshalCOSEEncrypt0 produce untagged arrays. Tagged messages are self-identifying; untagged ones require context to interpret. Adding a WithTag() option would improve interoperability.

Signing module's go.mod replace block is fragile

signing/go.mod now has 11 replace directives. Any time event/ gains a new dependency, signing/go.mod must be manually updated. This is not sustainable. The workspace go.work handles this at build time, but GOWORK=off (used in CI per-module tests) requires every go.mod to be self-contained.

07Top 2 Questions

Q1: Should COSE_Sign1 wrap the canonical payload or the raw event bytes?

Current design: SignCOSE1 places the library's custom canonical signing bytes (length-prefixed event fields + SHA-256 payload hash) in the COSE payload field. This authenticates the full event (ID, type, aggregate, version, payload hash, timestamp) but the COSE message is only meaningful to systems that understand the go-cqrs-lite canonical format.

Alternative: Sign the raw event payload bytes directly and carry event metadata (type, aggregate ID, version) in the COSE protected header. This would make the COSE message truly portable — any RFC 9052 implementation could verify it — but it would change what fields are authenticated and break compatibility with the existing canonicalPayload approach used by the non-COSE signers.

Why I can't resolve this: It depends on the intended consumer. If COSE is primarily for external interop, the raw payload approach is correct. If it's for go-cqrs-lite ecosystems that need event-level integrity, the canonical approach is correct. Both have valid use cases.

Q2: Should COSE middleware attach COSE bytes in event metadata, or replace the existing signing/encryption middleware entirely?

Option A (additive): New SignCOSE1Middleware attaches the COSE_Sign1 CBOR bytes as a base64 string in event custom metadata (event.cose_sign1). The existing SignMiddleware and EncryptMiddleware remain the default. Consumers who want COSE use both.

Option B (replacement): The COSE middleware replaces the existing signing path entirely. The event's payload is the COSE message itself, not the original JSON/CBOR. This is cleaner but breaks every existing consumer and changes the event store's byte layout.

Why I can't resolve this: Option A is safe but means two parallel signing systems. Option B is architecturally cleaner but is a v4 breaking change. The decision depends on whether COSE is an "escape hatch for interop" or "the future of event security in this library."
