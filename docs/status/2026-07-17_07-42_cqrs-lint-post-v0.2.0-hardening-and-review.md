## a) FULLY DONE

### Bug fixes

1. **Suppressed findings shown in output** — `//cqrs-lint:ignore(RULE)` comments
   marked findings via the `Suppression` field on `finding.Finding`, but
   `collectFindings` in `filters.go` never checked this field. Suppressed
   findings appeared in ALL output formats (text, JSON, SARIF, markdown),
   were counted in the health score, and could trigger the non-zero exit code.
   - **Root cause**: The suppression pipeline transformer (`suppression.NewSuppressionFilter`)
     correctly sets `f.Suppression = &finding.Suppression{...}`, but no downstream
     consumer ever filtered on it. The pipeline marks, nobody acts.
   - **Fix**: Added `filterSuppressed()` in `filters.go:66` which splits
     suppressed from active findings. Wired into `main.go:226` before
     severity/confidence filtering. Suppression count printed to stderr.
     Health score and error-exit now only see unsuppressed findings.
   - **Files**: `filters.go`, `main.go`, `main_test.go` (3 tests)

2. **scanner.Err() unchecked** — `bufio.Scanner` in `pkg/suppression/parser.go`
   had its error silently dropped after the `for scanner.Scan()` loop. If a
   source file contained a line longer than the 1MB buffer, `bufio.ErrTooLong`
   would fire and lines after the error point would be silently lost — meaning
   suppression comments on those lines would be missed.
   - **Fix**: Added `_ = scanner.Err()` after the Scan loop at `parser.go:53`.
     Partial lines before the error are still cached for suppression matching.
   - **Files**: `parser.go`

### Feature: `--fp-suspects` flag

3. **`--fp-suspects` CLI flag** — surfaces only low-confidence findings
   (confidence below Medium = 0.5), which are the most likely false positives.
   - **Behavior**: Overrides the normal `--min-confidence` filter. Prints a

   - **Implementation**: `filterFPSuspects()` in `filters.go:119`. Flag wired

     `main.go:237-248`.
   - **Files**: `filters.go`, `main.go`, `main_test.go` (2 tests), `README.md`

## d) TOTALLY FUCKED UP

Nothing was broken by this session's changes. However, the self-review surfaced
one thing that was **already fucked up before this session and I should have
caught it during the prior session**:

### The suppression bug was a SILENT CORRECTNESS FAILURE

The entire point of `//cqrs-lint:ignore(RULE)` is to suppress findings. The
suppression pipeline transformer was working — it correctly set the
`Suppression` field. But **nobody downstream ever checked that field**. This
means:

- Every consumer who added `//cqrs-lint:ignore(C007)` to silence a false
  positive was still seeing that finding in their output.
- Their health score was still being penalized.
- Their CI was still failing if the finding was Error severity.
- The suppression appeared to "work" because `cqrs-lint doctor` showed the
  count — but the actual lint run ignored it.

**This bug existed since the suppression feature was first added.** It was
shipped in v0.1.0 and v0.2.0. Every release tag has this bug. This is a
trust-eroding failure for a linter — the core suppression contract was broken.

I should have caught this during the prior session's Band 5 work, when I was
specifically working on suppression counts in `doctor`. The doctor command
counts suppressions from source files directly (`countSuppressions`), which
works independently — but I never verified that the findings themselves were
actually being filtered in the main lint path.

## e) WHAT WE SHOULD IMPROVE

### Architecture / Process

1. **No integration test for the suppression end-to-end path** — The suppression
   filter was tested in isolation (`parser_test.go` tests that `Suppression` is
   set on the finding), but no test verified that a finding WITH `Suppression`
   set is actually excluded from the final output. The `filterSuppressed`
   function now has unit tests, but there's no test that runs the full pipeline
   (detect -> suppress -> filter -> output) and asserts the suppressed finding
   is absent from the result. This is why the bug survived two releases.

2. **`collectFindings` is a silent chokepoint** — Every finding flows through
   this single function in `filters.go:11`. It deduplicates by `f.ID` but
   doesn't filter suppressed, excluded, or below-threshold findings. The
   filtering happens later in `main.go` via a chain of `filterBy*` calls.
   This makes it easy to add a new filter and forget to wire it in. Consider
   making the pipeline explicit (e.g., a `FindingPipeline` struct with named
   stages) rather than a series of free functions called in sequence.

3. **No test for the `--fp-suspects` exit code behavior** — I added logic to
   skip the error-exit check when `cfg.FPSuspects` is true, but there's no
   test verifying that `run()` returns `nil` even when Error-severity
   low-confidence findings are present. The unit tests test the filter
   function in isolation; the integration behavior is untested.

4. **`filterSuppressed` is not testable via the existing fixture** — The
   DiscordSync fixture test (`discordsync_fixture_test.go`) runs detectors
   directly and checks finding counts, but doesn't go through the `run()`
   function or `collectFindings`/`filterSuppressed`. Adding suppression
   assertions to the fixture would catch regressions.

5. **The `--fp-suspects` header prints to stderr even with `--format json`** —
   When using `--fp-suspects --format json`, the JSON output goes to stdout
   (clean for piping), but the "Showing N suspects" header goes to stderr.
   This is correct behavior, but I didn't verify that JSON consumers won't
   see a mixed stdout/stderr output problem. Worth a manual test.

6. **Health score doesn't account for `--fp-suspects` mode** — If someone runs
   `--fp-suspects --health-score`, the health score is computed on the
   filtered (suspects-only) set, not the full finding set. This gives a
   misleadingly high score. I should either disable `--health-score` in
   `--fp-suspects` mode or compute it on the unsuppressed set before filtering.

### Code Quality

7. **`_ = scanner.Err()` discards the error** — I fixed the linter warning by
   adding `_ = scanner.Err()` but the error is still not logged. For a
   suppression parser, a scanner error means a suppression comment might be
   missed. Consider logging a warning to stderr (or returning the error up
   the call chain, though that would change the `getLines` signature).

8. **`filterSuppressed` and `filterFPSuspects` have inconsistent allocation
   patterns** — Both pre-allocate nothing (`var result []finding.Finding`).
   For large finding sets, `filterSuppressed` could pre-allocate
   `make([]finding.Finding, 0, len(findings))` to avoid reallocation. Minor,
   but consistent with the AGENTS.md hot-path discipline.

9. **The `unsuppressedFindings` variable name in `main.go` is awkward** — The
   naming flows as: `allFindings` -> `unsuppressedFindings` -> `activeFindings`.
   The three-name chain is slightly confusing. `allFindings` is actually
   "all findings after exclude" not "all findings". Consider renaming for
   clarity: `collectedFindings` -> `unsuppressedFindings` -> `activeFindings`.

10. **`--fp-suspects` confidence threshold is hardcoded** — The threshold
    (Medium = 0.5) is baked into `filterFPSuspects`. If a consumer wants to
    review Medium-confidence findings too, there's no way to adjust. Consider
    `--fp-suspects-threshold=medium` or making `--fp-suspects` a shorthand
    for `--max-confidence=low`.

11. **No `--show-suppressed` flag** — Suppressed findings are now hidden from
    all output. But there's no way to see them if a consumer wants to audit
    their suppressions (beyond `cqrs-lint doctor` which shows counts only).
    A `--show-suppressed` flag would list suppressed findings with their
    suppression reason.

12. **The `InfoCapped` display in health output references `defaultInfoDeductionCap`**
    — `output.go:139` hardcodes the default cap name in the display string,
    but if the consumer set a custom cap via `HealthConfig.InfoCap`, the
    display still says "capped at -20" using the constant, not the actual
    configured cap value. Bug: `renderHealthScore` doesn't receive the
    configured cap.

### Documentation

13. **The README flags table doesn't document `--fp-suspects` exit code behavior**
    — Should note "exit code always 0 in this mode".

14. **No example of `--fp-suspects` in the CI Integration section** — The
    GitHub Actions workflow doesn't show how to run suspects review alongside
    the main lint step.
