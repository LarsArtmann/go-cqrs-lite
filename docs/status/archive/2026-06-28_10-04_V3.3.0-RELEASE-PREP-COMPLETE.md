ambiguous import but is workspace-global. If a module legitimately needs a newer
monolithic genproto version, it can't upgrade independently. Real fix is
`cockroachdb/errors` dropping the monolithic genproto dep (cockroachdb/errors#79).

## g) Top #1 Question I Cannot Figure Out Myself 🤔

**Should `stack/` accumulate more dependencies, or should it be split into
thinner composition modules?**

`stack/` is at 13 production deps (budget bumped from 12→13 for `projection/v4`).
Every new feature that the Bundle needs to wire (relational projections, graph
projections, dead-letter stores, future scheduler/deriver) pushes the count
higher. At some point `stack/` becomes a god-module that re-exports everything.

**Option A: Keep growing `stack/`.** The Bundle is the composition root — it's
supposed to know about everything. A high dep count is expected for a preset
layer. Accept the creep and bump the budget.

**Option B: Split into thinner composition modules.** e.g., `stack/relational/`
for RelationalProjection wiring, `stack/graph/` for GraphProjection wiring.
Each sub-preset has its own dep budget. But this fragments the one-call
`bundle.RunProjections` story.

I lean toward **Option A** — the Bundle IS the integration point, and a high dep
count there is honest. But I can't tell if this is a slippery slope toward
`stack/` becoming a dumping ground, or if it's the correct architectural shape for
a preset layer. The answer depends on how many more features will be wired into
the Bundle, which depends on consumer demand I can't predict.
