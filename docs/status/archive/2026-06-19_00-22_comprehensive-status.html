01Fully Done

Gap #1: Projection replay/live split

Runner.RunReplay(ctx) (synchronous catch-up) + Runner.RunLive(ctx) (background tail) shipped. 3-state atomic lifecycle (idle→ready→live) with CompareAndSwap guards makes invalid transitions unrepresentable. ErrReplayRequired returned if RunLive called before RunReplay. Run() preserved as convenience wrapper. 6 tests covering read-your-writes, double-call guards, Close safety, concurrent corruption. ExampleRunner godoc shows the pattern.

Gap #2: Exported marker types

All 8 phantom marker types exported (AggregateMarker, UserMarker, CorrelationMarker, RequestMarker, CausationMarker, ClientMarker, CommandMarker, EventMarker). External-package test (id_test) proves downstream usability. ADR-0024 records the decision and rationale.

Documentation closed out

SKILL.md updated with RunReplay+RunLive example (was stale runner.Run). CHANGELOG Unreleased section lists all 8 markers. FEATURES.md updated. Feedback doc marked RESOLVED with commit refs. ADR-0024 + index entry. projection/README.md read-your-writes section. projection/doc.go package docs.

05What We Should Improve

1. Close projection replay→live dedup gap

event.DistinctByEventID() exists but isn't wired into the Runner. An event processed at the replay/live boundary could be handled twice. This is the highest-value incomplete work for consumer correctness.

2. Fix or suppress gopls false-positive diagnostics

17 phantom "pgregory.net/rapid not in go.mod" errors. Either: (a) add a workspace-level gopls hint file, (b) file a gopls issue for multi-module workspace support, or (c) add inline //nolint suppressions. Option (a) is cleanest.

3. Real-world consumer validation

The library has zero known external consumers besides cqrs-htmx (which just gave us feedback). The quality gate is "would a consumer trust this?" — we need real adoption signal. The catalog exporters, storage backends, and reactive APIs are all unvalidated in production.

4. Documentation site

SKILL.md is excellent for AI consumers. But human developers coming from pkg.go.dev get godoc only. A Hugo/MkDocs site with composition recipes would lower the barrier.

5. Schema registry (ADR-0017) — from Proposed to Accepted

The infrastructure (catalog/schema/) exists. The gap is the validation middleware. This would make event contracts enforceable, not just documented.

6. Benchmark regression CI

benchmark-baseline.txt exists and CI should fail if >2× slower. Verify this is actually enforced in ci.yml — the baseline may be stale.

07Top Question I Cannot Answer

Should this library pursue real-world adoption, or remain a reference implementation?

The library is architecturally sound: 30 modules, 1328 exports, 24 ADRs, clean layer graph, zero lint issues. But it has exactly one external consumer (cqrs-htmx) that just gave us feedback. The Top 25 list above assumes adoption is the goal (real-world validation, docs site, broker adapters, gRPC transport). But if this is a reference implementation / learning project, then the high-value work is different: deepen the ADRs, add more examples, write blog posts, and stop adding features.

Why I can't figure this out The codebase is too good to be a throwaway, too clean to be production-hardened, and too feature-rich to be a toy. The signal from cqrs-htmx feedback suggests real adoption intent, but one consumer is not a trend. This determines whether tasks #7, #14-17, #20 are worth doing at all.
