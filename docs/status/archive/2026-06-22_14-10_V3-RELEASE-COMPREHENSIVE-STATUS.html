The headline

v3.0.0 is tagged and healthy. All 38 modules build and vet clean. All 35 testable modules pass — zero failures. Core CQRS/ES coverage is 80–98%. Zero TODO/FIXME in production code. Zero panics in production paths. The v3 breaking changes (11 total) are all shipped. Consumer-facing docs (README, FEATURES, ROADMAP, CHANGELOG, AGENTS) were updated this session to reflect the released reality.

The catch

The v3 module-path migration (/v2 → /v3) was committed without running go mod tidy across all modules. 25 of 38 modules have go.mod drift — stale indirect deps (samber/lo, samber/ro from the deleted ghost bus) linger in 9 go.mod files. This causes 2 modules (command, query) to fail lint because golangci-lint can't load the module. Additionally, 6 internal artifacts still reference the pre-release state ("Ready to tag"), deleted modules (readmodel, projection), or stale module paths.

05What We Should Improve

1. go mod tidy sweep — highest bang-for-buck

25 modules have drift, 2 fail lint because of it. A single go mod tidy sweep across all modules fixes both issues simultaneously. This should be the first commit after this report.

2. api-stability checker: config + golden file regeneration

Fix the 4 stale module names, add the correct v3 paths (including storage/memory, storage/pebble, storage/turso), regenerate the golden file. Then investigate whether the 1,605 count is real or inflated/deflated by the stale config. This is the gate that protects the public API — it needs to be trustworthy.

3. Internal docs sweep — eliminate all pre-release language

V3_MIGRATION.md, PRESETS.md, turso-indexing-guidance.md all need updates. A grep for "Ready to tag", "v3-ready", deleted module names, and stale paths across docs/ (excluding status/archive/planning) would catch everything in one pass.

4. Add direct tests for stack.Materialize

The stack module has zero test files. Materialize[V,K] is the tombstone-aware projection builder — a critical path. It's tested transitively through presets, but direct tests for the tombstone handler path would close the coverage gap and document the expected behavior.

5. CHANGELOG accuracy audit

The "1806 → 1852 exports" claim is wrong. After fixing the api-stability checker and regenerating the golden file, update the CHANGELOG with the real before/after numbers. A release note with a wrong API surface count undermines trust.

6. Split catalog test helper (402 lines → ≤350)

catalog/internal/cattest/builders.go is 402 lines — the only file over the 350-line gate. It's a test helper (the CI gate may exempt it), but splitting it would make the codebase fully compliant. Low effort, high consistency.

7. Document the GOEXPERIMENT requirement more visibly

The experimental build tags (goexperiment.arenas, goexperiment.jsonv2) are documented in AGENTS.md but not in README. A consumer who clones the repo and runs go build without the tags gets silently different (slower) code. A note in the Getting Started or Contributing section would help.

8. Consider a single-command tidy/format/test CI guard

The project has nix run .#test and nix run .#lint, but go.mod drift slipped through. Adding a go mod tidy -diff check to CI (or to nix run .#lint) would prevent this class of issue from recurring.

07The #1 Question I Cannot Figure Out

Unresolved

Did the v3 migration accidentally remove 247 legitimate exports, or is the CHANGELOG number just stale?

CHANGELOG.md:64 vs docs/api_surface.txt

The CHANGELOG [3.0.0] section claims "API surface — 1806 → 1852 exports". The actual golden file has 1,605 exports. That's a 247-export gap.

Two hypotheses:

  1. The CHANGELOG number is stale. It was written during the v2.7.0 → v3 timeframe and references the pre-migration export count. After the v3 breaking changes (deleting projection, readmodel, ghost bus, renaming APIs), the count dropped to 1,605. The CHANGELOG was never updated. This is the most likely explanation.
  2. The api-stability checker is undercounting. Its config references "projection" (deleted), "memory" (moved), "pebble" (moved), "turso" (moved). If those stale entries cause the checker to skip real modules that do exist (e.g., storage/memory, storage/pebble, storage/turso), then the 1,605 count is too low and the real surface is higher.

I cannot resolve this without comparing the pre-v3 export list to the post-v3 list. The pre-v3 golden file no longer exists (it was overwritten). The only way to answer this is:

How to resolve
  1. Fix the api-stability checker config (stale module names → correct v3 paths).
  2. Regenerate the golden file with the correct config.
  3. If the count changes significantly, the old 1,605 was wrong (hypothesis 2).
  4. If the count stays ~1,605, the CHANGELOG 1,852 was stale (hypothesis 1).
  5. Update the CHANGELOG with the verified number.

Why this matters: The api-stability checker is the CI gate that protects the public API surface. If it's silently skipping modules because of stale config, breaking API changes could ship undetected. This is the single most important thing to verify before any further release activity.
