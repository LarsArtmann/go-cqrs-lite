07g) Top #1 Question I Cannot Figure Out Myself

Needs your call

Should this skill be globally available, or stay project-local?

availability model · ~/.config/crush/skills/ vs project .agents/skills/

The restructure put the skill at go-cqrs-lite/.agents/skills/go-cqrs-lite/, so Crush discovers it only when working inside the go-cqrs-lite repo. But the skill's whole purpose is to help consumers (like cqrs-htmx, or any app importing go-cqrs-lite/*/v3) — and those consumers live in other working directories where this skill would never trigger.

I can't decide this for you because it's a tradeoff between two valid models:

Option A — Global (symlink to ~/.config/crush/skills/go-cqrs-lite): the skill triggers everywhere. Best for the "single source of truth for AI consumers" mission. Cost: a machine-local symlink not tracked by git, so it must be re-created per machine (or scripted in the devShell).
Option B — Project-local only (current state): the skill triggers only inside go-cqrs-lite. Consumer projects would each need their own copy/symlink. Cleaner git story, but defeats the purpose for the majority of users who consume the lib, not contribute to it.

My recommendation: Option A (global), wired via the flake.nix devShell so the symlink is reproducible across machines. But this is your environment/library boundary to call — should I implement Option A, or do you want consumers to opt in per-project?
