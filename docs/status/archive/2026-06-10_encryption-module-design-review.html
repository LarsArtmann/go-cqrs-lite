1. What We Built

A new encryption/ module providing AES-256-GCM event payload encryption as a sibling to signing/. Whole-payload encryption with middleware for automatic encrypt-on-publish / decrypt-on-handle.

27 tests pass. 14 BDD specs (Ginkgo) + 11 unit tests + 2 runnable examples. Round-trip benchmarks: ~1.1µs for 1KB payload encrypt+decrypt. Stdlib-only crypto. Zero new external dependencies.

Quick Usage

enc, _ := encryption.NewAES256GCM(key)
bus.UsePublish(encryption.EncryptMiddleware(enc))  // auto-encrypt on publish
bus.Use(encryption.DecryptMiddleware(enc))          // auto-decrypt on handle

4. Architecture Improvements

4.1 Shared Metadata Helpers in event/

Both signing and encryption need to attach/extract opaque byte blobs in event metadata. This is a generic operation that should live in event/ as unexported helpers (both modules already depend on event): 

// event/metadata_blob.go (internal)

func attachBlob(evt Event, key MetadataKey, blob []byte) (*ImmutableEvent, error)
func extractBlob(evt Event, key MetadataKey) ([]byte, error)
func hasBlob(evt Event, key MetadataKey) bool

4.2 Type Model: Opaque []byte Values

Both Signature and Ciphertext are []byte with identical methods: IsZero, Bytes, String, MarshalJSON, UnmarshalJSON. This pattern could be extracted to a shared internal type, but the Go type system makes this tricky — you can't embed a base type and get different methods on the embedding type. Recommendation: keep them separate but share the implementation via a helper function.

4.3 Ciphertext.Nonce() / Data() — AES-GCM Specific

These accessors assume 12-byte nonce prefix, which is AES-GCM specific. XChaCha20-Poly1305 uses 24-byte nonces. Consider moving these to an AES-GCM-specific helper rather than the generic Ciphertext type.

4.4 Established Libraries

Library Use Case Verdict
golang.org/x/crypto/chacha20poly1305 XChaCha20-Poly1305 (24-byte nonce) Add as alternative implementation — quasi-stdlib, zero risk
filippo.io/age Age encryption format Too heavy — we need raw AEAD, not file encryption
google/tink/go Google's crypto library Way too heavy for this module
tidwall/gjson JSON path queries for field-level encryption Already in workspace via catalog/ — natural fit for encryption/fieldlevel/

4.5 Field-Level Encryption Design

Approach A (recommended): JSON path encryption as a sub-package. Uses Encrypter/Decrypter interfaces from parent. Preserves non-sensitive fields for projection, indexing, catalog. Already have tidwall/gjson dependency in workspace. 
enc, _ := encryption.NewAES256GCM(key)
fieldEnc := fieldlevel.New(enc, fieldlevel.Paths("$.ssn", "$.email"))
bus.UsePublish(fieldlevel.EncryptMiddleware(fieldEnc))
bus.Use(fieldlevel.DecryptMiddleware(fieldEnc))

// Before: {"name":"Alice","ssn":"123-45-6789"}
// After:  {"name":"Alice","ssn":"enc:v1.AAAA..."}

6. Open Question

Should shared helpers live in event/ as public API or unexported internals?

Public event.CloneEvent(evt, key, value): Generic event manipulation primitive. Future modules might need it. Consumers might want custom metadata blobs.

Unexported in event/: Both signing and encryption already depend on event. No public API surface addition. Consumers use signing/encryption middleware, not raw helpers. Safer for a library.

My recommendation: Unexported in event/. This preserves the "library, not framework" principle while eliminating duplication. Public API surface is a one-way door — once exported, we can't remove it.
