05e) What We Should Improve

Stop generating status reports and start generating consumers. The single highest-leverage improvement is to find one real project that imports this library. Every other improvement is downstream of that.

1. Find a consumer, or declare the project scope-closed

Either (a) build a small real app that imports the library end-to-end, or (b) explicitly declare the library feature-complete and stop adding capabilities. The current trajectory — adding Hot-State cache TODOs, transport adapters, secondary indexes — without consumers is making the API surface harder to adopt, not easier. 1,605 exports is a lot to evaluate.

2. Archive old status reports

Move docs/status/*.md older than 7 days into docs/status/archive/. Keep only the latest HTML dashboard + the latest markdown. Reduces 363 files to ~10 active. The archive/ directory already exists — use it.

3. Fix FEATURES.md in one pass

Three known inaccuracies (projection deleted, memory moved, streaming reads done) plus missing stack modules. One focused edit. Run the docs-freshness-check skill.

4. Polish the stack layer

17 of 62 lint issues and the worst coverage live in stack/. The stack presets are the consumer-facing entry point — they should be the most polished, not the least. Fix stack/sqlite/preset.go (11 issues alone) and add constructor-error tests.

5. Tag v3.0.0

All breaking changes are additive. Tagging costs nothing and gives consumers a stable major to pin against. Until v3 is tagged, the entire v2-with-v3-teed-up state is a tax on every consumer evaluation.

6. Add real consumer-facing examples beyond toy apps

The 4 examples are demos, not reference applications. A consumer evaluating this library has no model for: HTTP API with auth, production deployment, observability stack, schema migration in production. The example/user/ Dockerfile is the closest, but it's still single-aggregate.

7. Reduce API surface where possible

1,605 exports is a lot. The docs/brainstorming/2026-06-21_07-21_API-SURFACE-REDUCTION-IDEAS.md brainstorm exists — act on the high-impact items. Specifically: collapse duplicate convenience constructors, hide internal helpers behind internal/.
