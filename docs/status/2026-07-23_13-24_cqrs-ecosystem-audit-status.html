eWhat We Should Improve

1. Verify before declaring

Run go build ./... and go test ./... before stating that a project has build or runtime risks. If we cannot build, say so explicitly.

2. Always confirm the artifact home before writing

For cross-project reports, ask which repository or directory should own the snapshot before producing 1000-line files. If /home/lars/projects is meta-only, the report should probably live in go-cqrs-lite or cqrs-htmx.

3. Re-verify agent findings manually for top N items

Sub-agents are great for breadth, but every high-impact or high-risk finding should be anchored to a specific file and line by the primary worker before publication.

4. Read project AGENTS.md before diagnosing projects

Each consumer project's AGENTS.md is the single source of truth for that project. Skipping it is like ignoring the codebase's README.

5. Produce deltas, not only fresh audits

When prior reports exist, the new report should state what changed, what is still true, and what is now resolved. This prevents parallel histories and ghost documentation.

6. Investigate tool warnings

A "parseErrors=1" warning should never be left unexplained. It is usually a sign of a real problem.

7. Mark uncertainty explicitly

Reports should label findings as Verified, Inferred, or Speculative. This protects readers from acting on unverified claims.

8. Integrate reports into living docs

After a snapshot report, update TODO_LIST.md, FEATURES.md, or ROADMAP.md in the owning project so the findings have a maintenance path.

9. Provide executable next steps, not just recommendations

Every recommendation should come with a command, a script, or a concrete edit. "Use app.Command" is less useful than a copy-paste handler replacement.

10. Build a repeatable audit pipeline

The dependency-graph tool should be run on CI or in a scheduled job so version drift and adoption gaps are detected automatically, not only when a human remembers to ask.
