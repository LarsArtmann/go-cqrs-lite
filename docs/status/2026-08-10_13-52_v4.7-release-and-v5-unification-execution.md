### Process improvements

1. **Read test helper contracts before refactoring**: The double-close panics would not have happened if I'd read how `adttest.RunMatrix` manages engine lifecycle (it closes engines itself).

2. **Batch grep before batch sed**: When changing a type signature across files, `grep -r 'OldType' **/*_test.go` FIRST, then fix ALL matches, not just the first 3 the compiler reports.

3. **Test one lint removal at a time**: Removing 5 linters at once produced 680 violations in a wall of noise. Remove ONE, see the count, decide, repeat.

## g) Questions I CANNOT Figure Out Myself

### 1. Should `record.CommonMetadata` use branded types (`id.CorrelationID`) or plain strings?

Currently `CommonMetadata` uses plain `string` for `CorrelationID`, `CausationID`, `ActorID`, `RequestID`. The `metadata.Tracing` struct uses branded types (`id.CorrelationID = cbid.ID[CorrelationMarker, ulid.ULID]`). This is the core design decision blocking full type consolidation:

- **Option A (branded types)**: `CommonMetadata` adopts branded types. Pro: type safety. Con: `record/` gains a dependency on `id/` (currently zero-dep Tier 0).
- **Option B (plain strings)**: All consumers switch from branded to plain strings. Pro: `record/` stays zero-dep. Con: loses compile-time type safety.
- **Option C (generic over ID type)**: `CommonMetadata` stays string, consumers bridge. Pro: flexible. Con: bridge boilerplate forever.

**What do you want?** This determines whether record/ stays Tier 0 zero-dep.

The current state is: registry moved, engines self-register, deprecation markers set, but NO breaking deletions have happened. `stack.Bundle`, `storage.RelationalProjection`, `graph.GraphProjection` all still exist. If we cut v5 now, consumers see new infrastructure but no breaking changes. If we wait for M26, the full vision is delivered but it's a much larger release.

**What do you want?** Ship incremental v5.0 with infrastructure + follow with v5.1 for fold inference, or wait for the full vision?

### 3. Should the `system/sqlite_driver.go` factory move to `sqliteengine/register.go` now?

Currently `sqliteengine/register.go` exists but `system/sqlite_driver.go` also exists with the full `createSQLiteEngine` function.
