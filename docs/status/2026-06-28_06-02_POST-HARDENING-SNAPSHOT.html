gThe One Question I Cannot Answer Myself

Top question (blocking CI trust on the postgres path):

Should stack/postgres tests get a real Postgres service container in CI (option A: accurate coverage but heavier CI), or should the module's coverage number be explicitly suppressed/labelled as "skipped without DSN" in all reporting (option B: honest but still 0%)?

This is a real tradeoff with no obviously correct answer:

  • Option A (Postgres in CI): gives accurate coverage numbers and catches Postgres-specific bugs, but adds CI runtime and infrastructure complexity. Every PR pays the cost.
  • Option B (suppress/label): keeps CI fast, but stack/postgres shows 0% in every coverage report forever. Contributors misread it as "untested" even though it has tests that simply skip locally.

I cannot self-resolve this because it's a project-level resource decision (CI budget, maintainer preference for "fast CI vs thorough CI"), not a technical one. The code supports both paths — the question is which philosophy this project wants to encode. Your call.

Why now: the isolation and doc-stub gates are in place, coverage on kv/codec/graph improved, and the Drainer shipped. The remaining coverage gaps are either stdlib-blocked (jsonv2) or need this CI decision (postgres). This is the next bottleneck for reaching "85%+ everywhere" honestly.
