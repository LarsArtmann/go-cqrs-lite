g)The 1 Question I Cannot Figure Out Myself

Needs Human Decision

Should the god-package splits (storage/, event/) happen in v3.x or v4.0?

storage/ has 38 Go files and event/ has 30. Both are god-packages by any reasonable definition. Splitting them into sub-packages (e.g., storage/relational/, storage/view/, storage/migrations/) would improve navigability and reduce merge conflicts.

The tension: Splitting changes import paths. Every consumer that imports storage.SQLEventStore would need to update to storage/relational.EventStore (or whatever the new path is). This is a breaking change for all consumers.

Option A: Split in v3.x with type aliases. Keep the old types as aliases in the root package. Consumers do not break, but the aliases are confusing. Go type alias system supports this, but it creates a parallel declaration surface.

Option B: Split in v4.0. Clean break. No aliases, no confusion. But v4 is months away, and the packages keep growing in the meantime.

Option C: Do not split - they are fine as-is. The 350-line file limit keeps individual files small. Maybe 38 files in one package is acceptable for a library where the package IS the storage abstraction.

I cannot determine which is correct because it depends on the project versioning philosophy: is v3.x a semver-major that allows breaking changes, or a semver-minor that promises stability? The 48-module architecture suggests stability is paramount. But the growing god-packages suggest structural change is needed.
