Hot-state cache designed but unimplemented

TODO_LIST.md:44 · docs/design/hot-state-cache.md

A full design doc exists for a decider hot-state cache keyed by (aggID, version) to eliminate snapshot+delta replay on sustained-hot aggregates. NATS / Redis / Kafka transport adapters

ADR-0025 originally called for these, but they were superseded by the Watermill command bridge — brokers plug into watermill.NewCommandBus via publisher/subscriber adapters rather than getting bespoke modules. ROADMAP marks these as done-by-supersession. No standalone transport/nats module exists, which is the intended end state unless a consumer asks otherwise.

Read-pressure snapshot strategy

EveryNEvents snapshots based on writes; a ReadPressureStrategy that snapshots based on load frequency is designed but unbuilt. Deferred because the hot-state cache (also unbuilt) would subsume most of its benefit. Listed in TODO_LIST as "consider after the State cache lands."

Distributed projection runner (multi-node)

Single-machine distributed checkpointing exists, but true multi-node leader-election coordination is a ROADMAP "raw idea" with no code and no deadline. The doc is explicit: "single-machine is sufficient for now."

Deriver module (stateless saga: events → commands)

A ROADMAP raw idea. The saga pattern currently emerges from bus.SubscribeAll + command dispatch (see example/todo/), but no dedicated deriver/ module formalises it.

Graph DB drivers beyond the in-memory reference

graph.GraphProjection ships with an in-memory traversal engine. A Neo4j/Memgraph driver (graph/neo4j/) is listed as a consumer-pulled sibling module — no code until a consumer asks.

EWhat We Should Improve

1. Doc freshness is a manual process — and it's losing

Three of the "Totally Fucked Up" items are doc-vs-code drift discovered in a single session. The project has a docs-freshness-check skill and a doc-check tool, but nothing enforces it in CI on every commit. A green build does not mean green docs. The single highest-leverage improvement is a CI gate that fails when FEATURES.md / TODO_LIST.md / ROADMAP.md contradict the source.

2. The "zero lint findings" claim should never be asserted without re-running lint

The 10:04 report asserted zero findings as a headline victory, but a commit between the report's write and HEAD reintroduced one. Status reports that make absolute claims ("zero", "all", "none") should embed the exact command + commit hash that produced the claim, and the claim should be re-verified at report-write time, not carried forward from session memory.

3. The one isolation-unclean module (transport/grpc) has no workaround tracked

transport/grpc is blocked on an upstream cockroachdb/errors issue. That's legitimate. But the project has a CI isolation gate that presumably either (a) exempts this module silently or (b) would fail. Either way, the exception should be loud: a CI-annotated allowlist entry with the upstream issue link, so the gate doesn't silently rot.

4. api-stability should be a first-class flake app

cmd/api-stability builds, runs, and had its golden file regenerated this release — but it isn't wired as nix run .#api-stability. Every other quality gate (build, test, lint, check-layers) is a flake app. This one isn't, breaking the convention and making the API-stability check easy to forget during releases.

5. Postgres is the only preset with no local coverage signal

Without POSTGRES_TEST_DSN, stack/postgres tests skip and show 0% coverage. Consider a CI job that runs Postgres in a service container (the standard GitHub Actions postgres service) so the Postgres happy-path is exercised on every PR, not just when a maintainer remembers to set a DSN.

6. The unbuilt performance features need a profile, not more design

Hot-state cache and read-pressure snapshots both have design docs and both are unbuilt. The hot-state doc itself says "profile before building." The improvement: run a benchmark on a realistic hot-aggregate workload (the stack/bench module exists for exactly this). If snapshot + page cache is already fast enough, close the items. If not, the data justifies the build. Either way, stop holding open design docs that may already be moot.
