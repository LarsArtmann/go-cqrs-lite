TinyBase

A 7–17 kB reactive data store for JavaScript with mergeable stores, pluggable CRDT persistence, and reactive derived tables (metrics, indexes, relationships, queries). On the Question’s read side it is the closest thing to what go-cqrs-lite’s metaengine already is; on the write side it has no opinion at all — by design.

00The question this page answers

The owner’s lens (brief, 2026-11-22) “How can we make the browser OWN its data smartly, be as local-first as possible (i.e. including Commands), but at the same time be able to smartly branch-rebase (like Git) with a server as soon as the client has a connection again! All that transparently. We need Commands & Events that only happened on the client. And we need to share the logic for Commands & Events & Queries (as long as they do not access protected server resources) with the client, efficiently.”

TinyBase’s answer: the browser owns a fully reactive, persistable, syncable copy of the data; writes are local cell/value mutations that reconcile later through CRDT metadata; and queries/metrics/indexes/relationships are derived and recompute incrementally on the client. It solves the Queries half of the owner’s sharing demand almost exactly the way this repo’s metaengine vision describes — and it has nothing whatsoever to say about Commands.

01Six axes, scored with evidence

Axis Verdict Evidence (primary sources, dates below)
1 · Client data ownership FULL “TinyBase works anywhere that JavaScript does, but it’s especially great for local-first apps: where data is stored locally on the user’s device and that can be run offline” (tinybase.org, 2026-11-23). Persistence to IndexedDB/OPFS/SQLite/PGLite, including “twelve SQLite-based persistence options, four for PostgreSQL, and one for SQL Server” (persistence guide, 2026-11-23); OPFS “Since v6.7” (architectural-options guide).
2 · Local commands CLIENT-MINTS-FACTS Mutations are setCell/setValue on an in-memory Store — the client writes state directly; there is no intent, validation, or decision step anywhere in the API surface (tinybase.org, 2026-11-23). The library is explicit about staying out of that business: “TinyBase deliberately avoids having an opinion on simultaneous or conflicting updates, deferring that to the underlying CRDT framework” (CRDT persistence guide, 2026-11-23).
3 · Reconnect rebase CRDT — delegated, cell-granular Synchronization rides on MergeableStores: the Store “records additional metadata as the data is changed so that potential conflicts can be reconciled”, over “WebSockets, the browser’s BroadcastChannel API, or other custom media” (synchronization guide, 2026-11-23). First-party CRDT sync delegates to Yjs/Automerge persisters; conflicts resolve “at a Cell or Value level” with a client-ID tiebreak (“Yjs typically runs a tie-break based on the client ID of the document, where the higher one wins”) — i.e. LWW inside a CRDT envelope (CRDT guide, 2026-11-23). Landscape: conflict handling “Automatic via CRDT”, resolution “Client” with “Server can also resolve conflicts” (2026-11-22).
4 · Client-local Commands & Events State-level only — no journal A client can compute anything locally (queries, metrics run in-memory), but persistence and sync carry state, not an append-only event log: the store is “an in-memory data store” saved as tables/JSON (architectural-options guide, 2026-11-23). Client-local Commands & Events in the CQRS sense would be app code on top; the substrate neither records causality nor replays history. (Rebuild-from-log semantics: UNVERIFIED — no journal feature found in fetched docs.)
5 · Logic sharing + protected resources One TS runtime everywhere; no auth notion The same store/synchronizer code runs in browser, workers, Node, Bun, React Native (home + architectural options, 2026-11-23) — query/fold logic shares naturally because everything is TypeScript. Protected resources: none in the fetched docs; no auth, roles, or server-side enforcement surface appears in the product. Servers in the picture are yours (WebSocket synchronizers, PostgreSQL persisters).
6 · Maturity / license Mature · MIT Landscape: Mature, MIT, ~1 ms local refresh, 5–10 MB per store (2026-11-22). Site: “just 7.3kB - 16.7kB and with no dependencies - yet 100% tested, fully documented, and of course, open source!” Repo github.com/tinyplex/tinybase: 5,219 stars, MIT, pushed 2026-11-18 (GitHub API, 2026-11-23).

02TinyBase vs go-cqrs-lite

Dimension TinyBase go-cqrs-lite
Write boundary None — “deliberately avoids having an opinion” Everything — Decide is the only path to an event; Rejection is first-class

Offline Persist offline, sync on reconnect — first-class guidance L4 parked: queue Commands, decide on server after reconnect (research 2026-11-22)

Fit verdict: PATTERN-TO-ADOPT Not a dependency (no Go surface, no write model) but the best map of what the client half of the owner’s Question looks like when it is done well: reactive derived queries over locally-owned data, merge metadata recorded at mutation time, and a tiny pluggable perimeter (persister/synchronizer) instead of a monolithic engine.

03What to steal

+
MergeableStore: record merge metadata at write time Conflict metadata is captured when the change happens, not computed at sync time — the L4 journal should stamp each client event with its causal context the same way, so rebase is bookkeeping, not archaeology.
+
Metrics/Indexes/Relationships as reactive fold declarations Derived tables that recompute incrementally when source rows change are precisely Evolutions/fold declarations from ADR-0151 — proof the developer-facing surface can be declarative and still reactive in a browser.
+
The persister/synchronizer seam One tiny interface, many backends (twelve SQLite variants, Postgres, Yjs, Automerge, PartyKit, Supabase…). The go-cqrs-lite client tier should expose exactly one such seam for storage and one for sync — not a hardcoded engine.
+
Honest scope statement “Deliberately avoids having an opinion on… conflicting updates” is the exact inverse of this repo’s thesis; saying so plainly on both sides is what makes the eventual combination (TinyBase-shaped reads, decider-shaped writes) clean rather than muddled.
