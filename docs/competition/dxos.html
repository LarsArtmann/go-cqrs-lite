A maximalist open-source stack for collaborative local-first apps — graph database, key-based identity, P2P networking, optional cloud peer — where the client is everything and no server has authority.

03Analysis vs the owner's question

DXOS is the maximalist answer to the owner's lens: it takes “local-first including the write path” all the way to client-authoritative everything — data, identity, networking — with an optional cloud peer (EDGE) that by doctrine holds no authority. If the owner ever wonders what the far end of the local-first dial looks like as a shipped framework, this is it: ECHO spaces on-device, Automerge merges on rejoin, key-pair identity, invitations as first-class UX.

The cost structure is equally instructive. Because every peer is an equal, a conflict can never be a Rejection — “without loss or conflict” is the homepage's promise, which forecloses exactly the rebase-and-reject semantics §10 of the research grounding calls for (rejections surfaced as UX, never structural merges). The one validation gate, Effect Schema “validated on write”, is structural typing — it can check an Order payload's shape on the client, but it cannot decide whether this Order may ship given server-side state. That decision needs an authority DXOS deliberately does not have.

License correction + maturity caveats The localfirst.fm landscape self-report lists DXOS as MIT; that is stale. Live verification (2026-11-23) shows the repo LICENSE is FSL-1.1-Apache-2.0 (source-available, competing-use restricted, converting to Apache-2.0 two years after each change) and npm agrees. For an app that may be fine; for a library embedding scenario it is a real constraint. Add the docs' own warning that the SDK “features follow what Composer needs” and a 0.x version, and DXOS reads as a strong product bet, not a stable substrate.

Still, two patterns travel well: typed objects with validation happening at the write boundary on the client is the shape of go-cqrs-lite's client-side command guard (cheap local reject before queuing), and the SAGE framing — agents operating on shared data through typed operations — is the same seam the owner needs for sharing query folds with non-browser consumers.

04Fit verdict

COMPETITOR

DXOS is a full-stack competitor that proves the ceiling of client-authoritative local-first — and pays for it with merge-only conflict handling (no Rejections), a TypeScript-only SDK with no Go seam, an FSL license that the landscape misreports as MIT, and an API that tracks one product's needs. Adopt its client-side write-validation and typed-agent seam; run the domain on go-cqrs-lite.
