Convex

An open-source reactive backend where queries, mutations and actions are TypeScript functions that run inside the backend; the browser holds subscriptions and optimistic patches, never the write path.

Maturity: Production-Ready (localfirst.fm landscape self-report) License: backend FSL-1.1-Apache-2.0 (LICENSE.md, accessed 2026-11-23) · client Apache-2.0 (GitHub) Initial release: not reported by the landscape; backend repo created 2024-03-08 (GitHub API) Bundle size: ~120KiB (landscape self-report) LOCAL COMMANDS: SERVER-ONLY-WRITES REBASE: NONE (client) · server OCC re-run Back to the landscape index

00Summary

Convex answers the owner's question with a counter-thesis: do not make the browser own writes at all. The browser owns a subscription to server-folded query results, plus optimistic patches to those results that are rolled back when the real answer arrives. Every mutation is a named, validated, transactional function that executes on the backend under optimistic concurrency control, with deterministic re-runs instead of merges.

Structurally this is the closest thing in this shard to go-cqrs-lite's own server thesis: Commands (mutations) are intents with arguments that are dispatched to exactly one handler, run transactionally, may fail, and cannot touch external systems; effects are quarantined in a different function type (actions); reads are server-folded results streamed to the client. What Convex does not have is the other half of the owner's question: no local write path, no client-minted facts, no logic on the client, and no first-party Go client.

The bottom line Convex is the strongest server-authoritative rival to the browser-owns-its-data premise, and the best-documented argument that a deterministic decide function makes rebase automatic: “determinism is what guarantees there is never a "merge conflict"”. For a Go CQRS library it is a thesis competitor and a pattern source, not a building block.

01Six axes against the owner's question

Colours rate each axis against the owner's question (blue: serves it, yellow: partly, red: does not). They are not a product-quality score; on product quality Convex is strong, and that is exactly why its answer to this question deserves a careful read.

# Axis Verdict What that means, with evidence
1 Client data ownership THIN The client holds query results for active subscriptions and optimistic patches to them (E8). No local database is part of the product; the documentation index (accessed 2026-11-23) has no offline, local-storage or persistence page, and the request manager keeps pending work in memory (E10). Closing the tab ends the session's state.
2 Local Commands SERVER-ONLY-WRITES Mutations run on the backend (E1). The client does keep a single, ordered queue of mutations (E4) and re-issues unsent ones on reconnect, but the queue lives in memory and nothing is decided offline (E10).
3 Reconnect rebase NONE (client) Nothing is persisted, so there is nothing to rebase: reconnect means re-subscribing and re-sending. The rebase that does exist is server-side and automatic: an OCC conflict re-runs a deterministic transaction until it commits (E7).
4 Client-local Commands & Events NO There are no Command or Event records on the client and no event journal on the wire: the server syncs query results, per the landscape self-report. Optimistic state is a cache by construction: “temporary, local changes to your query results” (E8).
5 Logic sharing & protected resources TS, SERVER-SIDE TypeScript end to end, so client and server share types, but the logic runs only on the backend (E1). The function-type table is a declarative protected-resource seam: mutations are deterministic and cannot call third parties; actions can call anything but cannot run transactionally (E3, E2).
6 Maturity & license PRODUCTION-READY Production-Ready per the landscape self-report; SOC 2 and HIPAA are claimed on the homepage (E14). Backend is fair-source FSL-1.1-Apache-2.0, converting to Apache-2.0 two years after each release (E12); the JS client, CLI and dashboard are Apache-2.0 and the backend is self-hostable.

E1 · Where the code runs

E2 · Three function types, three capability sets

https://docs.convex.dev/functions/overview.md · accessed 2026-11-23

“Queries read data from your Convex database and are automatically cached and subscribable (realtime, reactive). Mutations write data to the database and run as a transaction. Actions can call OpenAI, Stripe, Twilio, or any other service or API you need to make your app work.”

E3 · Mutations must be deterministic; effects live in actions

https://docs.convex.dev/functions/mutation-functions.md · cache 2026-11-22

“For this to work, similarly to queries, mutations must be deterministic, and cannot call third party APIs. To call third party APIs, use actions.”

E4 · Client-side ordering of mutations

https://docs.convex.dev/functions/mutation-functions.md · cache 2026-11-22

“When mutations are called from the React or Rust clients, they are executed one at a time in a single, ordered queue. You don't have to worry about mutations editing the database in a different order than they were triggered.”

E5 · OCC treats a transaction as a proposal against read versions

https://docs.convex.dev/database/advanced/occ.md · cache 2026-11-22

“It does this by treating the transaction as a declarative proposal to write records on the basis of any read record versions (the "read set"). At the end of the transaction, the writes all commit if every version in the read set is still the latest version of that record.”

E6 · Convex's own Git analogy

https://docs.convex.dev/database/advanced/occ.md · cache 2026-11-22

“This is akin to being unable to push your Git repository because you're not at HEAD. We all know in that circumstance, we need to pull, and rebase or merge, etc.”

E7 · Determinism makes the rebase conflict-free

https://docs.convex.dev/database/advanced/occ.md · cache 2026-11-22

“An OCC conflict means we cannot push because our HEAD is out of date, so we need to rebase our changes and try again. And determinism is what guarantees there is never a "merge conflict", so (unlike with Git) this rebase operation will always eventually succeed without developer intervention.”

E8 · Optimistic UI is a cache of query results, not a ledger

https://docs.convex.dev/client/react/optimistic-updates.md · cache 2026-11-22

“Optimistic updates are temporary, local changes to your query results which are used to make your app more responsive. … Optimistic updates are run when a mutation is initiated, rerun if the local query results change, and rolled back when a mutation completes.”

E9 · Wrong optimistic state self-corrects

https://docs.convex.dev/client/react/optimistic-updates.md · cache 2026-11-22

“That's okay! The Convex client will handle rolling back this update after the mutation completes and the queries are updated. If there are small mistakes in optimistic updates, the UI will always eventually render the correct values.”

03Analysis against the owner's question and the go-cqrs-lite thesis

The owner's addendum decomposes the question into P1 to P5 plus storage. Convex's answer to each is a clean "no", and the interesting part is how well-argued each "no" is.

Part Convex's answer What it means for go-cqrs-lite
P1 · Browser owns its data No. The browser holds subscriptions to server-folded results and optimistic patches, both disposable (E8, E9). The opposite pole of the design space, executed well. Any go-cqrs-lite offline tier must beat this on capability while matching its honesty about what is provisional.
P2 · Local-first including Commands No. Mutations execute on the backend; the client orders them and re-sends the unsent ones on reconnect (E4, E10). This is the exact shape of the 11-22 report's section 05.1 with one refinement: the reconnect protocol treats idempotent and non-idempotent requests differently (E10). A command queue should do the same: deterministic, deduplicable commands can be re-sent freely; effectful work must be cancelled and reported, never silently retried.
P3 · Git-like rebase on reconnect No client-side rebase. The server re-runs deterministic transactions on OCC conflicts and calls that a rebase: “we need to rebase our changes and try again” (E6, E7). This is the cleanest published statement of the owner's own “transparency follows from purity” argument. The difference: Convex's re-run cannot fail a business rule (a deterministic transaction eventually commits), while an offline intent re-decided against fresh state can be rejected. Rebase-on-reconnect needs the Rejection path that server-side OCC does not.
P4 · Commands & Events that only happened on the client No such records exist client-side. Confirms that the client-only branch is unclaimed territory among the mature tools: nobody in this shard persistently separates speculative from confirmed work except by hand-rolled status fields.
P5 · Shared logic, minus protected resources Shared types, not logic; all logic server-side, TypeScript only. The mutation/action split encodes the protected-resource boundary in the function type (E3). Two lessons. First, same-language sharing did not tempt Convex to move decide logic to the client, which is evidence the authority boundary is about correctness, not convenience. Second, the split is exactly the client-safe decider seam of the addendum: stream-local, deterministic deciders are portable; effectful wrappers are not, and Convex enforces that with a table rather than by convention.
Reads and export Reads are reactive query functions (E2); a paginated, cursor-checkpointed data export exists behind the Pro plan (E13). The read model is the same shape as go-cqrs-lite's server-folded results over SSE. The export's rule to “persist these changes atomically with pagination.nextCursor” is the checkpoint discipline a client-side journal replay needs.

What to adopt

  • Idempotency classes decide reconnect semantics. Re-send mutations, cancel actions: the client source makes the distinction explicit (E10). For go-cqrs-lite: commands with deterministic IDs (the documented id.DeriveCommandID pattern) are safe to re-send and dedupable at the engine; effectful derivers are not, and a reconnect must surface them rather than silently retry.
  • The function-type table as a static capability map. Query, mutation and action declare database access, transactionality, caching and external calls. A decider catalog can carry the same declaration, which is what makes “client-portable” checkable rather than asserted.
  • Optimistic state as a cache with a self-correcting contract. “If there are small mistakes in optimistic updates, the UI will always eventually render the correct values” (E9) is the right promise to make about speculative folds: they are display sugar, never a source of truth.
  • Rejections with reasons already flow. The HTTP API returns an error body with errorMessage and errorData for application errors (functions API page, accessed 2026-11-23), the same idea as a first-class Rejection payload.

Where it bites (for this question)

  • The browser cannot own anything durable. A long offline session with queued intents is simply not a Convex use case; the ordered mutation queue is for connectivity blips, and it is in-memory.
  • No Go. “Convex doesn't have first-party clients for languages such as Go, Java, or C++”, and the OpenAPI escape hatch is non-reactive and in beta (E11). Sharing Go decider logic with a Convex backend is not possible; sharing with the client is not attempted.
  • No event journal. Mutations write documents inside a transaction; there is no replicated log of facts to fold from, which is what an event-sourced client branch would consume.
  • Fair-source backend. Self-hosting is supported and the code becomes Apache-2.0 two years after each release (E12), but competing hosted services are excluded during that window.

How the two would relate

browser (TS) → query subscriptions → mutation calls → Convex backend: TS functions → OCC re-run, no client branch

There is no composition with go-cqrs-lite worth recommending: the two disagree about where the write path lives, and Convex's stack is TypeScript from schema to client. The value of the page is the pattern evidence, and one irony from the ecosystem: PowerSync's philosophy page now lists Convex as a supported source database, read through “Convex document deltas”. The sync-engine world has decided that Convex is a backend to sync from, which is the same slot go-cqrs-lite would occupy.

04Fit verdict

COMPETITOR LOCAL COMMANDS: SERVER-ONLY-WRITES REBASE: NONE (client)

Convex is the most credible rival answer to the owner's question: it keeps the Command boundary, adds transactional, deterministic decide functions with automatic conflict-free re-runs, and delivers local-first-grade UX by streaming server-folded results, all while telling you the browser should not own writes. For a Go shop it is not usable as a component (TypeScript functions, no first-party Go client, non-reactive HTTP escape hatch), so the relationship is competitive on thesis rather than on dependencies. Its mutation/action capability split and idempotency-aware reconnect protocol are worth adopting wholesale.
