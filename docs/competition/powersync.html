PowerSync

A sync engine that keeps a client-side SQLite database (including in the browser) in sync with a backend database you already have, and routes every write through a write endpoint that you implement.

Maturity: Production-Ready (localfirst.fm landscape self-report) License: Service Apache-2.0 (LICENSE on main, accessed 2026-11-23) · SDKs Apache-2.0 (landscape self-report) Initial release: 2023-11-30 (landscape self-report) Bundle size: @powersync/web 2.7.0 — 49.5KB min / 15.5KB gzipped JS plus ~2.3MB SQLite WebAssembly (bundlephobia and npm, accessed 2026-11-23) LOCAL COMMANDS: COMMANDS-QUEUED REBASE: LWW Back to the landscape index

00Summary

PowerSync is the tool in this shard closest to the owner's storage thesis: a real SQLite file in the browser (WebAssembly, Origin Private File System, web worker), partial replication by subscription, and a durable, ordered queue of local writes. It is also the clearest picture of that thesis without Commands: the queue carries row-level PUT, PATCH and DELETE operations, and all business logic is deferred to a server endpoint the developer writes. Nothing is decided on the client and nothing is rebased. The client waits with its queued writes, the server decides, and the synced result overwrites the local copy.

That makes it a shell around go-cqrs-lite rather than a rival to it. The write endpoint is the one place PowerSync insists that you supply validation, authorization and domain rules, which is exactly where a command dispatcher with deciders belongs. The cost of that composition is the subject of the analysis below.

The bottom line PowerSync proves the browser can own its data with SQLite on OPFS, and hands the write logic to the server. It complements go-cqrs-lite because it needs a backend that owns business rules, it competes with a hand-built offline client, and its queue carries state changes rather than Commands.

01Six axes against the owner's question

Colours rate each axis against the owner's question (blue: serves it, yellow: partly, red: does not). They are not a product-quality score. Evidence references link to the quotes in section 02.

# Axis Verdict What that means, with evidence
1 Client data ownership STRONG The app reads and writes a local SQLite database, online or offline (E1, E2). In the browser the file lives in OPFS behind a web worker, with IndexedDB as the legacy default (E9). Tables are SQLite views over synced JSON, and access is scoped by Sync Streams, so the browser owns a partial replica plus local-only tables.
2 Local Commands COMMANDS-QUEUED The client applies SQL changes locally and records them in an ordered upload queue, drained by a developer-supplied uploadData() function (E3). The queue stores only PUT, PATCH and DELETE; custom operations are still described as a possible future feature (E8). Intents are therefore queued as state changes, not executed as Commands.
3 Reconnect rebase LWW Server-authoritative reconciliation: the backend decides how queued mutations apply, and the simplest backend yields per-field last-write-wins (E5). The client never resolves conflicts and never rebases: it stays on its last checkpoint while the queue is non-empty (E7) and is then overwritten by the synced copy (E6).
4 Client-local Commands & Events NO There is no Command record and no Event record on the client. The only client-local write record is the CRUD queue (ps_crud); the inbound ps_oplog is the sync service's operation history, not domain events (E13). Everything local is provisional until the server echoes it back.
5 Logic sharing & protected resources SERVER ONLY No logic is shared with the client. Write logic lives entirely in your backend (E4), and PowerSync explicitly refuses to authenticate or authorize writes (E11). What is shared is declarative: the client-side schema and SQL-like Sync Stream queries.
6 Maturity & license PRODUCTION-READY Production-Ready per the landscape self-report. Service: Apache-2.0 (LICENSE file on main, accessed 2026-11-23; GitHub's license detection agrees). SDKs: Apache-2.0. The landscape's "FSL" label for the Service conflicts with the primary source (see UNVERIFIED in section 05).

03Analysis against the owner's question and the go-cqrs-lite thesis

The owner's question decomposes into five parts in the 2026-11-22 addendum (P1 to P5) plus a storage decision. Here is what PowerSync does for each, and what follows for a command-first library.

Part PowerSync's answer What it means for go-cqrs-lite
P1 · Browser owns its data Yes, concretely: a SQLite file on OPFS in a web worker, a partial replica scoped by Sync Streams, local-only tables, and a queue written in the same transaction as the change (E3, E18). This validates the storage direction. Three caveats come from its own docs: the recommended OPFS VFS cannot ATTACH a second database (E9), so "dual SQLite" means two files or two connections; shared-worker sync is off by default on Android, iOS and Safari (E10), so one writer across tabs is not free on mobile Safari; and OPFS access can fail in private browsing, where the fallback is in-memory and unsent writes are lost.
P2 · Local-first including Commands No. What runs on the client is SQL against the replica; the decision runs later, in the write endpoint (E4). A go-cqrs-lite composition would be "queue intents, decide on the server", which is the 11-22 report's section 05.1, not the addendum's P2 (decide on the client). To go further, a client-side decider would have to run outside PowerSync, writing to the same SQLite file.
P3 · Git-like rebase on reconnect Deliberately absent. The client never resolves conflicts (E7); it waits, drains, and is overwritten by the synced copy (E6). This is "revert to server truth", the semantics the 11-22 report attributes to Zero. It is not a rebase: a queued change cannot be re-expressed against new state, which is why a value such as a stock count is lossy (E15). A command-first design re-decides the intent instead.
P4 · Commands & Events that only happened on the client No such concept. The nearest primitives are an insert-only table excluded from Sync Streams (rows go up, never come down) and the per-field change log of Strategy 6 (E14). Both are a command journal rebuilt by hand in userland. go-cqrs-lite models this natively with command.PersistedCommand and command.CommandSink; the row ID that makes an insert-only row idempotent is the same idea as a deterministic command ID.
P5 · Shared logic, minus protected resources Nothing is shared. The write endpoint is yours, in any language (E4); PowerSync does not authenticate or authorize writes (E11), and scopes reads by authenticated JWT parameters inside Sync Streams (landscape self-report). This is the boundary the addendum draws, pushed all the way to the server: every decider is treated as protected. It is the safe default, and the reason the two tools compose.
Storage One SQLite file holding data tables, the inbound operation log and the outbound queue (E13). A useful precedent for the "DB1 journal + DB2 projections" plan: PowerSync keeps both logs and the materialized data in one file and rebuilds views from the log.

What to adopt

  • The write-failure taxonomy. Retryable errors keep the entry and retry; rejected writes are acknowledged with a 2xx plus a reason so the queue keeps moving; only unfixable failures stay at the front and block (E12). go-cqrs-lite's error families map onto it directly: Transient means throw and retry, Rejection means acknowledge with the reason, and a Conflict or an Infrastructure error is the blocking case.
  • Rejections as data. To show a user why a write was refused, PowerSync suggests returning the reason or writing it to a table that syncs back, plus a dead-letter table on the backend. A Rejection that is recorded rather than thrown away is the same move.
  • Freeze-then-overwrite as the simple case. Holding the checkpoint while the queue is non-empty (E7) removes client-side conflict handling altogether. It is worth keeping for commands whose decider is not client-portable, upgrading only the stream-local ones to a rebase.
  • Warn before losing the queue. PowerSync's docs suggest watching the queue table to tell the user when uploads are pending. Any local command journal needs the same affordance.

Where it bites

  • The unit on the wire is a row, not an intent. A PATCH says which columns changed, not what the user did. PowerSync's own inventory recipe has to reinterpret a value as a delta (E15), and its change-log recipe re-adds a per-change status table (E14). Commands carry that meaning natively.
  • The docs lean towards accepting over rejecting. One recommendation is to relax backend constraints because "Accepting slightly inconsistent data can be better than discarding the user's change." That is a defensible UX stance, but the opposite of a Rejection-first command model, and it should be a deliberate choice per stream rather than a habit.
  • A blocked write stalls everything behind it. The queue is strictly ordered, so one undecidable write freezes later unrelated writes from the same device until the app resolves it. An intent queue can do better by reordering commands that touch different streams.
  • No Go SDK. The client SDK list in the documentation index (accessed 2026-11-23) covers JavaScript, React Native, Capacitor, Tauri, Node, Dart/Flutter, Kotlin, Swift, .NET and Rust. A Go backend is fine as the write endpoint; a Go client is not on the menu.

How the two would compose

browser app → local SQLite on OPFS → upload queue → uploadData() → write endpoint: dispatcher, deciders → source database → PowerSync Service → Sync Streams → local SQLite

The read leg needs a supported source database. The philosophy page lists Postgres, MongoDB, MySQL, SQL Server, Azure DocumentDB and Convex, read through logical replication, change streams, the binlog, change data capture or document deltas. The no-conflict-policy quote (E17) comes from the same page. The write leg is where go-cqrs-lite's command.Dispatcher would sit, with one translation problem in between: rows arrive, and commands must be derived from them. The clean alternative is to queue real commands in an insert-only table and dispatch those rows.

04Fit verdict

COMPLEMENT LOCAL COMMANDS: COMMANDS-QUEUED REBASE: LWW

PowerSync is built to sit in front of a backend that owns the business rules, which is precisely the slot go-cqrs-lite's deciders occupy, and it supplies the read-path sync and durable upload queue that the planned offline client lacks. It competes with a hand-rolled offline client rather than with the Go library, and it needs one of its supported source databases behind it. Its queue carries row-level state changes rather than Commands, so a command-first design would have to queue intents in a synced table or re-derive them at the write endpoint.
