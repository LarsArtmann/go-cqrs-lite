03Analysis vs the owner's question

Basic reframes “the browser owns its data” as “the user owns the data, in Basic's cloud”. The PDS is the primary store; the device is a first-write cache. That is a coherent answer to a different question — data portability and app interop — and it is the inverse of the owner's device-primary stance. Notably, the local-first sync page spends most of its words qualifying what offline cannot do (“Not every feature works offline, and working with someone else’s shared data may still need a connection”).

As a write model it is the anti-thesis of go-cqrs-lite in three specific ways. First, CRUD-with-reconciliation has no intent record: after a conflict you get a reconciled item, not a Rejection you can show the user — the docs literally outsource this: “the app may need to help resolve them”, with no machinery to do so. Second, there is no event log, so no replay, no audit, no derived projections — the reconciled present overwrites the past. Third, server-side logic is closed: the thing the owner most wants to share (Decide/Apply/query folds) has no seam here; the server is a product, not a library.

What is genuinely worth stealing Two ideas: (1) schema-travels-with-the-data — go-cqrs-lite's catalog (payload structs, event types) could ride along with exported streams, letting a second client version understand the data without the server; (2) the permission model — user-approved, per-scope app access to a personal store is a cleaner expression of “protected server resources” than role checks scattered through handlers.

Beta status, a small docs footprint, and an unverified “schema lenses” roadmap claim round out the picture: interesting product direction, immature platform, wrong architecture for the owner's Commands-and-facts requirement.

04Fit verdict

COMPETITOR

Basic competes for the same slot — the local-first backend under an app — while inverting the owner's premise: the user's cloud store is primary, writes are client-minted CRUD reconciled on the server, and neither Commands nor Events exist. Its permissioning and schema-portability ideas are adoptable; its write model is not.
