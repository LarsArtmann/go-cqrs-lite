RxDB

A local-first, reactive NoSQL database for JavaScript that runs in the browser, Node and mobile, and replicates documents with any backend through three handlers (pull, push, stream), resolving conflicts on the client.

Maturity: Production-Ready (localfirst.fm landscape self-report) License: Apache-2.0 core (package.json and LICENSE.txt, accessed 2026-11-23) · commercial premium plugins Current version: 17.6.0 (package.json on master; GitHub release 17.6.0 published 2026-10-05) Bundle size: ~40kB, storage-dependent (landscape self-report) LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: GIT-LIKE-REBASE (default merge: master wins) Back to the landscape index

00Summary

RxDB is the incumbent answer to the browser half of the owner's question: a real local database with observable queries, pluggable storage, and a replication protocol designed so that “the backend can be "dumb"”. The wire unit is a document state with a revision; the protocol is explicitly described as git-like, with a fork (client), a master (server), an assumed base, and a client-side conflict handler that by default drops the fork state and keeps the master.

That protocol is the reason this page exists: it is the closest shipping implementation of “branch, then merge with the server on reconnect”, and it is built for states, not intents. RxDB's own downsides essay then recommends, as its fifth conflict strategy, storing “all the events that lead to the current state” — which the reader will recognise as the whole go-cqrs-lite thesis, published by the tool that ships without it.

The bottom line RxDB occupies exactly the browser slot the planned offline client targets, and its protocol pushes document state through a deliberately dumb backend. It is the incumbent to beat or to reuse; either way, its git-like fork/master shape and its honest downsides page are required reading.

01Six axes against the owner's question

Colours rate each axis against the owner's question (blue: serves it, yellow: partly, red: does not). They are not a product-quality score.

# Axis Verdict What that means, with evidence
1 Client data ownership STRONG, WITH CAVEATS A local database is the gateway for all persistent changes; queries are observable; storage is pluggable (E1). The caveat is durability: browser storage “cannot be trusted to stay there forever” (E13), and the recommended OPFS, SQLite, worker and shared-worker storages are commercial premium plugins (E19).
2 Local Commands CLIENT-MINTS-FACTS The client writes document states directly; there is no command abstraction and no multi-document transaction — “a single write operation to a document is the only atomic thing you can do” (E2). Client-side gates exist (revisions that throw a 409 on stale writes, and middleware hooks that can stop an operation, E17), but nothing is re-decided anywhere.
3 Reconnect rebase GIT-LIKE-REBASE The protocol is explicitly “like git”: the client is a fork that pushes with an assumed master state; the backend returns the real master state on mismatch; the client's conflict handler produces a new state and pushes again (E4). Reconnect replays via a RESYNC event and checkpoint iteration (E8). The default merge is “drop the fork state and use the master state” (E7).
4 Client-local Commands & Events DOCUMENTS ONLY No Commands and no Events exist as records. Local (non-replicated) documents exist for metadata and could hold a queue, but that is do-it-yourself. Conflicts are the price of the state model, and RxDB's own remedy is to switch units: store events and fold (E14).
5 Logic sharing & protected resources PROTOCOL ONLY The shareable artefact is the protocol contract: three endpoints plus a conflict handler with isEqual and resolve, small enough to implement in any backend (E5). Schemas are JSON Schema, so validators can be shared. Business rules and authorization are explicitly the backend's job per the landscape self-report.
6 Maturity & license PRODUCTION-READY Production-Ready per the landscape self-report; 23,440 stars and a release cadence up to 17.6.0 (GitHub, accessed 2026-11-23). Core is Apache-2.0; OPFS, SQLite, filesystem, worker, shared-worker, sharding and encryption plugins are commercial (E22, E19).

03Analysis against the owner's question and the go-cqrs-lite thesis

RxDB matters to this review for two reasons: it already ships the fork-and-merge shape the owner wants, and it is the most senior witness that state replication keeps rediscovering event sourcing.

Part RxDB's answer What it means for go-cqrs-lite
P1 · Browser owns its data Yes: a local reactive database is the source of truth for the UI, with multi-tab coordination (one tab replicates, E18). Persistence is best-effort: eviction and quota are real (E13). The planned dual-SQLite client should copy two things: the single-replicator-per-origin rule, and the honesty that local data needs a rebuild path. The premium paywall around OPFS and shared-worker storage is also market evidence that the owner's storage plan is the hard, valuable part.
P2 · Local-first including Commands Writes happen locally and replicate as document states; there are no transactions and no decide step (E2). A command-first client cannot use RxDB's write path as-is: the interesting logic would have to run in app code before insert, which RxDB never sees. Middleware hooks (E17) can gate writes locally, but that logic is not shared with the server.
P3 · Git-like rebase on reconnect Structurally yes, semantically no. The fork/master protocol with an assumed base is the right shape (E4), and reconnect is a checkpoint replay (E8). But the merge function receives two states; it can only guess intent field by field, and by default it keeps the master and discards the client's work (E7). This is the exact gap the addendum's design closes: rebase the intents (re-decide queued commands against fresh state) instead of merging states, and a conflict becomes a Rejection the user can act on, rather than a heuristic field merge or a silent loss.
P4 · Commands & Events that only happened on the client Not modelled. The nearest primitive is local (non-replicated) documents. A workable composition exists (below), but the speculative-versus-confirmed distinction has to be built by hand on top, just as PowerSync users rebuild status tables.
P5 · Shared logic, minus protected resources The protocol and the schema are the shared contracts; all behaviour logic is client-side JavaScript, and the backend is expected to be storage, not rules (E5). The three-handler contract is genuinely small enough to implement once in Go and reuse. The CRDT plugin makes the complementary choice: it shares an operation format simple enough that “the backend can also do document writes and still be compliant” (E12) — the same idea as sharing a fold/decide contract rather than code.
Version skew Client code versions drift by weeks (E16). Confirms the addendum's requirement that a decider logic version ride with the data: with intents, the server can know which spec a queued command was decided under.

The composition that would actually work

RxDB: read-model collections → pull-only replication → Go backend: SSE pullStream
RxDB: command collection → push-only replication → Go backend: dispatcher, deciders

RxDB supports one-directional replication as a first-class configuration (E6), and its docs bless server-sent events as a stream transport (E9). That suggests a clean split: read models flow one way, from go-cqrs-lite's server-folded query results into pull-only RxDB collections, while Commands flow the other way as rows of a push-only collection, dispatched by the Go backend. Nothing is merged, so the master-wins default never fires; conflicts become decider Rejections instead. The open cost is the adapter: pullStream$ wants document batches plus checkpoints, and go-cqrs-lite streams query results, so the shapes must be reconciled (UNVERIFIED until prototyped).

What to adopt

  • The fork/master protocol shape. Push carries the assumed base and the new state; the backend answers only with real states on mismatch; the client resolves and repushes. For a command-first system, swap the merge function for a re-decide: the same loop, with meaning preserved.
  • RESYNC on reconnect. A single signal meaning “anything unknown changed, replay from your checkpoint” (E8) is exactly the reconnect entry point an intent-rebase needs.
  • Conditional, re-interpretable operations. The CRDT plugin's selector pattern re-evaluates an operation against current state at apply time (E11) — the same property that makes a pure fold safe to replay.
  • The downsides essay as a checklist. Eviction, stale assumptions, migration skew and “realtime is a lie” (E13, E15, E16) are the four risks any offline tier will be judged against.

Where it bites (for this question)

  • State is the unit, so meaning is lost. The conflict handler sees two document states and must guess; the CRDT plugin explicitly stops where judgement is required (E10).
  • The default merge discards the client's work. “Always drop the fork state and use the master state” (E7) is the right default for a state-sync world and the wrong one for a user's queued intent.
  • Its own docs recommend event sourcing instead. The fifth conflict strategy is to store “all the events that lead to the current state” (E14) — evidence from inside the ecosystem that the state model is the ceiling.
  • The strongest storage options are paid. OPFS, SQLite, worker and shared-worker storages sit in the premium tiers (E19), so the free comparison point for a dual-SQLite design is Dexie or IndexedDB.

04Fit verdict

COMPETITOR LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: GIT-LIKE-REBASE

RxDB competes for the browser slot the owner's dual-SQLite plan targets, and its write path embodies the state-replication thesis: documents with revisions pushed through a deliberately dumb backend, conflicts merged as states, and the offline client's work dropped by default. It can host a command-first design only by sidelining its own conflict machinery (pull-only read models plus a push-only command collection), which is viable but leaves most of its value unused. As a pattern source, its git-like protocol and its candid downsides essay are the two most useful documents in this shard.
