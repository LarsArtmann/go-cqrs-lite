03Analysis vs the owner's question

Yjs is not an app framework or a backend — it is the field's de-facto CRDT substrate, and it must be read as such. On the six axes it is nearly a pure neutral: it gives the browser total ownership of collaborative state in ~20 kB, it never phones home, and it has the deepest language-port bench in the landscape — including ygo, which matters to a Go-first library more than any other single fact on this page.

For the owner's question the core trade-off is stated on its own docs page: shared types “automatically merge without merge conflicts”. That is a commitment that structurally excludes go-cqrs-lite's central move — a queued command re-decided against fresh server state can come back as a Rejection, and a Yjs update cannot be rejected by anyone, only merged. Updates are opaque ops with no schema, no validation, and no business rules: an illegal state merges as happily as a legal one. So Yjs answers “how do browsers share state” and is silent on “who may decide what state means” — the exact silence the go-cqrs-lite thesis fills with server-authoritative Commands and pure Deciders.

The seam worth copying Yjs's provider split — data model, connection provider, persistence provider as independent modules — is the cleanest client-runtime factoring in the landscape. The go-cqrs-lite worker client can mirror it exactly: shared-types state → read-model rows; y-indexeddb → SQLite-WASM on OPFS; y-websocket → the SSE command/query channel.

Concretely for the repo: Yjs (with ygo or Yrs via FFI) is the right tool if the owner ever needs a genuinely collaborative surface — multiplayer canvas, shared text buffer, presence — alongside the domain model. Domain streams (Orders, Users) should stay on the intent-rebase track: dual-track architecture, with the CRDT doc linked to its owning stream by ID in metadata.

04Fit verdict

COMPLEMENT

Yjs does not compete for the write model at all — it is the mature, tiny, Go-portable substrate one would put next to a CQRS domain for freeform collaborative surfaces. Its provider-separation architecture is directly reusable for the go-cqrs-lite client worker; its merge-always semantics are correctly kept away from Commands and Events.
