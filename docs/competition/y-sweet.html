03Analysis vs the owner's question

Y-Sweet matters to this review less as a product and more as the cleanest published blueprint of the “thin server” posture: a generic Rust sync relay over object storage, an application backend that owns authentication, and clients that do all the write logic in Yjs. Ground truth is a byte blob on S3 — the server never inspects, validates, or decides anything about document content.

That posture is exactly one deletion away from go-cqrs-lite: remove the Decider and you have Y-Sweet. The consequence for the owner's question is instructive — because no server-side decision exists, there is nothing to rebase onto: a reconnecting client exchanges missed updates and converges. The branch-rebase-with-server that the owner wants is impossible in this architecture by construction, not by omission. Rejections, protected-resource commands, and server-folded read models all need a server that understands intent.

Two adoptable seams First, token delegation: the Go server authenticating a user and minting a short-lived, stream-scoped token before the browser opens its SSE/command channel is the same pattern, and it maps cleanly onto “as long as they do not access protected server resources” — scope the token, then let shared logic run anywhere it is valid. Second, the metadata/data split (“ground-truth document data only lives on S3, but document metadata exists in your existing DB”) mirrors the thesis's snapshot-plus-journal split.

As a dependency it is hard to recommend today: the creating team was acquired by Modal (announced July 10, 2025), the repo's last push was 2025-12-04, and both npm packages have been quiet since September 2025 (all as of 2026-11-23). The project's current hosting and roadmap under Modal are UNVERIFIED. Study the architecture; do not build on the binary.

04Fit verdict

PATTERN-TO-ADOPT

Y-Sweet is a reference architecture, not a rival: it shows the ceiling of server-thin local-first (CRDT persistence with no decisions) and supplies a directly reusable token-delegation seam for go-cqrs-lite's client/server boundary. Its post-acquisition dormancy makes adopting the running software unwise; adopting the pattern is cheap.
