CouchDB

The Apache document database that started the offline-first category: HTTP replication between peers, a per-document revision tree with deterministic conflict winners, and validation functions that also gate replicated writes. In the browser it is used through PouchDB.

Maturity: Production-Ready (localfirst.fm landscape self-report) License: Apache-2.0 (LICENSE on main, accessed 2026-11-23) Current release: 3.5.3, 2026-10-12 (project homepage) Initial release: 2010-07-13 (landscape self-report) Bundle size: not applicable server-side; browser peer PouchDB is 46KB gzipped (its own homepage) LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: GIT-LIKE-REBASE (fork + deterministic winner, no built-in merge) Back to the landscape index

00Summary

CouchDB is where this whole design space was invented, and it is the only system reviewed here whose own documentation compares itself to Git in detail — and then explains why the comparison breaks: a conflict is a “fork”, there is “no merge” in the data model, and the revision history is “incidental”. Clients mint document revisions offline; replication is unidirectional, checkpointed HTTP; conflicts persist as sibling revisions until an application merges them.

Two features matter disproportionately for this review. First, validate_doc_update is a pure function over the proposed document, the current document, the user and the security object, and it is enforced for replicated updates too — the receiving peer re-validates offline-originated writes against its current state. Second, the replication protocol defines per-document, non-fatal rejection with explicitly non-retryable status classes. Both are exactly the mechanics an intent-rebase needs on the server side.

The bottom line CouchDB is not a candidate component for a Go CQRS library, but it is the reference implementation for “browser mints facts, server re-validates on arrival, rejection never blocks the queue”. Read it for the validation gate and the rejection protocol; read its conflict window as the cost of merging states without intents.

01Six axes against the owner's question

Colours rate each axis against the owner's question (blue: serves it, yellow: partly, red: does not). They are not a product-quality score.

# Axis Verdict What that means, with evidence
1 Client data ownership VIA POUCHDB The server does not run in the browser; the project itself delegates that to PouchDB, which keeps a full replica in IndexedDB and syncs when connected (E2). Replication can be full or filtered, and the protocol is plain HTTP.
2 Local Commands CLIENT-MINTS-FACTS The client writes document revisions directly; there is no intent layer. The receiving side may refuse: validation functions run for replicated updates (E12), and the protocol explicitly lets the target reject a document with forbidden (E16).
3 Reconnect rebase GIT-LIKE-REBASE Topology is git-like: a branching revision tree where each database deterministically picks a winner (E5), and the docs themselves say a conflict is a fork (E6). But there is “no merge in the data model” (E7); resolution is application code, and the history is “incidental” (E8).
4 Client-local Commands & Events REVISIONS ONLY Revisions are the facts and they all replicate; the protocol's only local-only documents are _local checkpoint records. No speculative-versus-confirmed distinction exists.
5 Logic sharing & protected resources LOGIC AS DATA Design documents replicate, so map/reduce, filters, update handlers and validation functions ship with the data and run wherever a query server exists (E14). The sharing is JavaScript strings, not typed code, and the browser peer's validation “does not behave… like the Apache CouchDB validate_doc_update() API” (E15).
6 Maturity & license PRODUCTION-READY Production-Ready per the landscape self-report; 3.5.3 released 2026-10-12; Apache-2.0 throughout (E22). Sixteen-plus years of production use; show and list functions are deprecated and slated for removal in 4.0.

02Evidence

"accessed 2026-11-23" means the page was fetched live for this review; "cache 2026-11-22" means the quote comes from the scraped copy taken the day before. Ellipses mark omitted words.

E1 · The original peer-based claim

https://docs.couchdb.org/en/stable/intro/overview.html · cache 2026-11-22

“CouchDB is a peer-based distributed database system. It allows users and servers to access and update the same shared data while disconnected. Those changes can then be replicated bi-directionally later.”

E2 · Browsers are delegated to PouchDB

https://couchdb.apache.org/ · cache 2026-11-22

“CouchDB is built for servers (from a Raspberry Pi to big cloud installations), while PouchDB is built for mobile & web-browsers. They can seamlessly replicate data with each other.”

E3 · The storage discipline is append-only

https://docs.couchdb.org/en/stable/intro/overview.html · cache 2026-11-22

“On-disk, CouchDB never overwrites committed data or associated structures, ensuring the database file is always in a consistent state.”

E4 · A revision is explicitly not a VCS revision

https://docs.couchdb.org/en/stable/replication/protocol.html · cache 2026-11-22

“Revision: A MVCC token value of following pattern: N-sig where N is ALWAYS a positive integer and sig is the Document signature (custom). Don't mix it up with the revision in version control systems!”

E5 · A deterministic winner, chosen everywhere alike

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“By default, CouchDB picks one arbitrary revision as the “winner”, using a deterministic algorithm so that the same choice will be made on all peers.”

E6 · Its own docs call a conflict a fork

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“CouchDB “conflicts” do not correspond to Git “conflicts.” A Couch conflict is a divergent revision history, what Git calls a “fork.””

From the embedded essay “What is the CouchDB replication protocol? Is it like Git?”, credited to Jason Smith, StackOverflow, 2011-01-29.

E7 · And there is no merge in the data model

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“In the data model, there is no merge. The client simply marks one time line as deleted and continues to work with the only extant time line. In the application, it feels like a merge.”

E8 · The history is incidental

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“These behaviors are different because, in Git, the time line itself is important; but in CouchDB, the data is important and the time line is incidental—it's just there to support replication.”

E9 · On a single node, the 409 path is a mini-rebase

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“When working on a single node, CouchDB will avoid creating conflicting revisions by returning a 409 Conflict error. … apply the same changes as were applied to the earlier revision, and submit a new PUT”

The recommended recovery is literally: fetch the current revision, re-apply your edit to it, and PUT again.

E10 · The unresolved-conflict window

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“Whilst this keeps the main application simple, the problem with this approach is that there will be a window between a conflict being introduced and it being resolved. From a user's viewpoint, this may appear that the document they just saved successfully may suddenly lose their changes, only to be resurrected some time later.”

E11 · Server-side validation functions exist

https://docs.couchdb.org/en/stable/ddocs/ddocs.html · accessed 2026-11-23

“A design document may contain a function named validate_doc_update which can be used to prevent invalid or unauthorized document update requests from being stored.”

E12 · Validation also gates replicated writes

https://docs.couchdb.org/en/stable/intro/overview.html · cache 2026-11-22

“The update validations are enforced for both live usage and replicated updates, ensuring security and data validation in a shared, distributed system.”

E13 · Update handlers are server-side logic you can call

https://docs.couchdb.org/en/stable/ddocs/ddocs.html · accessed 2026-11-23

“Update handlers are functions that clients can request to invoke server-side logic that will create or update a document.”

Their result is a pair of document-or-nothing and a response: “If the first element is null no document will be committed to the database.” They are request-driven; nothing suggests they run during replication.

E14 · Logic ships as data

https://docs.couchdb.org/en/stable/intro/overview.html · cache 2026-11-22

“Both documents and designs can replicate, allowing full database applications (including application design, logic and data) to be replicated to laptops for offline use, or replicated to servers in remote offices where slow or unreliable connections make sharing data difficult.”

E15 · The browser peer does not run the same validation

https://pouchdb.apache.org/api.html · cache 2026-11-22

“Note: this is a very, very simple validation example. It does not behave, for example, like the Apache CouchDB validate_doc_update() API.”

From the PouchDB plugin example that intercepts bulkDocs().

E16 · The protocol lets the receiver refuse, per document

https://docs.couchdb.org/en/stable/replication/protocol.html · cache 2026-11-22

“Document updating failure isn't fatal as Target MAY reject the update for its own reasons. It's RECOMMENDED to use error type forbidden for rejections, but other error types can also be used (like invalid field name etc.). The Replicator SHOULD NOT retry uploading rejected documents unless there are good reasons for doing so…”

E17 · One rejection does not block the batch

https://docs.couchdb.org/en/stable/replication/protocol.html · cache 2026-11-22

“Note that while a update may fail for one Document in the response, Target can still return a 201 Created response. Same will be true if all updates fail for all uploaded Documents.”

E18 · Non-retryable status classes are named in the protocol

https://docs.couchdb.org/en/stable/replication/protocol.html · cache 2026-11-22

“Replicator SHOULD NOT retry requests in case of a 401 Unauthorized, 403 Forbidden, 409 Conflict or 412 Precondition Failed since repeating the request couldn't solve the issue with user credentials or uploaded data.”

E19 · Its own advice: carry the change description with the state

https://docs.couchdb.org/en/stable/replication/conflicts.html · accessed 2026-11-23

“So if you want to work with diffs, the recommended way is to store those diffs within the new revision itself. That is: when you replace v1 with v2a, include an extra field or attachment in v2a which says which fields were changed from v1 to v2a.”

E20 · The browser peer retries with backoff

https://pouchdb.com/api.html · cache 2026-11-22

“options.retry: If true will attempt to retry replications in the case of failure (due to being offline), using a backoff algorithm that retries at longer and longer intervals until a connection is re-established, with a maximum delay of 10 minutes.”

E21 · The leading JS consumer bypasses the protocol

https://rxdb.info/replication-couchdb.html.md · accessed 2026-11-23

“This plugin does NOT use the official CouchDB replication protocol because the CouchDB protocol was optimized for server-to-server replication and is not suitable for fast client side applications, mostly because it has to run many HTTP-requests (at least one per document) and also it has to store the whole revision tree of the documents at the client.”

03Analysis against the owner's question and the go-cqrs-lite thesis

CouchDB is the ancestor that already ran the experiment the owner is designing for, and its documentation records where the git analogy held and where it failed.

Part CouchDB's answer What it means for go-cqrs-lite
P1 · Browser owns its data Through PouchDB: a full or filtered replica in IndexedDB, replicating over HTTP with retry and backoff (E20). The oldest proof that the browser can own a replica. The 2026 caveat is ecosystem decay: RxDB dropped its PouchDB storage and bypasses the replication protocol for client performance (E21).
P2 · Local-first including Commands No commands: the client mints revisions. The only “decide” is on the receiving side, as a validation function that may forbid (E11). Validation-on-arrival is the server half of the addendum's design, sixteen years old and still the best statement of it: an offline write is not trusted until the receiving node has checked it against current state.
P3 · Git-like rebase on reconnect Half git: a fork per conflict, a deterministic winner, app-side merges, and a sweeper window where saved work can “suddenly lose their changes” (E10). On a single node the 409 recovery is a genuine rebase of an edit (E9). The contrast to draw: rebase the intent, not the state. When the unit is an edit of a document, recovery means refetch-and-reapply, and anything not re-applied is lost. When the unit is a command, recovery means re-decide, and the outcome is a new fact or a first-class Rejection.
P4 · Commands & Events that only happened on the client Not modelled; every revision replicates. CouchDB's own advice gestures at the fix: store the change description inside the new revision (E19). That is causation metadata — the link between a fact and the intent that produced it — embedded in the state, which is how merges become intent-aware.
P5 · Shared logic, minus protected resources Logic replicates as design documents (E14), but the browser peer does not faithfully run the server's validation (E15). The historical answer to “share the logic” was: make it data. The lesson is that shared behaviour needs more than shipping code: it needs the same execution guarantees, or a contract both sides implement.
Rejection semantics Per-document, non-fatal (E17), with named non-retryable classes (E18). A ready-made mapping for the error families: 403/409/412 correspond to Rejection and Conflict (do not retry); everything else is Transient (retry with backoff). And unlike PowerSync's blocking FIFO, one rejection never stalls the rest of the batch.

What to adopt

  • Validation on the receiving end. A pure check over (proposed state, current state, user, security) that runs for live and replicated writes (E12) is precisely the gate an intent-rebase passes through on arrival. go-cqrs-lite gets a stronger version for free, because a decider returns an outcome, not just a verdict.
  • Non-blocking, classified rejection. Rejections are per document, do not fail the batch (E17), and the protocol names the statuses that must not be retried (E18). Copy this taxonomy into the offline command queue contract.
  • Causation carried with the fact. “Store those diffs within the new revision itself” (E19) is the storage-side expression of linking every event to the command that caused it.
  • Append-only discipline under conflicts. Committed data is never overwritten on disk (E3); conflicts coexist instead of destroying each other. An event journal already behaves this way, which is why a command-first rebase never needs a sweeper window.

Where it bites (for this question)

  • The winner can silently hide user work. Deterministic winning plus delayed resolution means “the document they just saved successfully may suddenly lose their changes” (E10).
  • No merge, and history is incidental. The revision is explicitly “not” a version-control revision (E4), compaction discards old bodies, and diffs must be re-embedded by hand (E19).
  • The protocol is heavy for browsers. At least one HTTP request per document and a full revision tree at the client, per RxDB's reasons for bypassing it (E21); browsers also cap parallel long-polls per domain, which that page works around with HTTP/2 proxies or subdomains.
  • Validation cannot compute an alternative. validate_doc_update accepts or forbids; it cannot produce a different outcome. Update handlers can, but they are request-driven, not replication-driven (E13).

Where the git analogy holds and breaks

branch per conflict → deterministic winner → app-specific merge → sweeper closes the window
queued command → re-decide on fresh state → event or Rejection → no window to sweep

The browser-side peer has its own page in this review series (PouchDB), which covers the IndexedDB replica, the changes feed and the retry behaviour in detail.

04Fit verdict

PATTERN-TO-ADOPT LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: GIT-LIKE-REBASE

CouchDB will not be a dependency of go-cqrs-lite: it is an Erlang server database whose browser story now runs through an aging PouchDB and whose replication protocol the JS ecosystem bypasses for performance. It earns PATTERN-TO-ADOPT because it is the only reviewed system that already implements the receiving-side gate this design needs — validation enforced on replicated updates, with per-document non-fatal rejection and named non-retryable classes — and because its documented failure mode (deterministic winners plus a resolution window that can hide a user's work) is the clearest argument for rebasing intents instead of merging states.
