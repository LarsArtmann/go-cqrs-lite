PouchDB

The 2012-vintage browser database that pioneered offline-first: full local ownership, MVCC revision trees that branch on conflict exactly like Git, and — via its CouchDB counterpart — the oldest server-side write-validation seam in this landscape.

LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: GIT-LIKE (revision trees, manual merge) FIT: COMPLEMENT ← all entries

00The question this page answers

The owner’s lens (brief, 2026-11-22) “How can we make the browser OWN its data smartly, be as local-first as possible (i.e. including Commands), but at the same time be able to smartly branch-rebase (like Git) with a server as soon as the client has a connection again! All that transparently. We need Commands & Events that only happened on the client. And we need to share the logic for Commands & Events & Queries (as long as they do not access protected server resources) with the client, efficiently.”

PouchDB’s answer is 14 years old and still the most literally Git-shaped thing in the landscape: the browser owns the data outright, writes are local document puts against a revision tree, conflicts fork the tree into accessible branches, and every replica deterministically picks the same winner. What it never had is Commands — the client writes state, and the only “no” lives in a CouchDB design document on the server.

01Six axes, scored with evidence

Axis Verdict Evidence (primary sources, dates below)
1 · Client data ownership FULL “It enables applications to store data locally while offline, then synchronize it with CouchDB and compatible servers when the application is back online” (pouchdb.com, 2026-11-23). Persistence adapters: IndexedDB, LevelDB, SQLite, LocalStorage (landscape, 2026-11-22). Local reads never wait on the network.
2 · Local commands CLIENT-MINTS-FACTS The mutation primitive is a document write with MVCC: “To update an existing document, you must include both an _id parameter and a _rev parameter” (pouchdb.apache.org/api.html, 2026-11-23). The client authors state directly; there is no intent object, no decide step, and landscape lists optimistic updates: yes (2026-11-22).
3 · Reconnect rebase GIT-LIKE (branch + deterministic winner, manual merge) Conflicts branch the revision tree: “conflicting leaf revisions will be attached in _conflicts array” (api.html, 2026-11-23). CouchDB’s model, which PouchDB implements: conflicts are “a common state, not an exceptional one”, replicas keep all branches, “each database instance deterministically deciding which document is the ‘winner’” (docs.couchdb.org overview, 2026-11-23). Rebase/merge is application code — the part Git automates, PouchDB deliberately leaves to you. Revision history is bounded: revs_limit defaults to 1000 (api.html).
4 · Client-local Commands & Events Buildable — and the landscape says apps do Landscape data model entry: “Document & Event Sourcing” (2026-11-22) — the only entry in the whole dataset with Event Sourcing in its data model. A local append-only store of domain events with a changes feed is a documented PouchDB pattern class; specific guides not fetched — UNVERIFIED beyond the dataset label. Command execution client-side is trivially possible (it is a JS database), but every invariant check is app code.
5 · Logic sharing + protected resources Same JS in browser and server; server-side validation seam PouchDB runs in browser, Node, React Native (home page, 2026-11-23) — one JavaScript module can hold shared command/event/query logic. The protected-resource notion exists server-side in CouchDB: a design document “may contain a function named validate_doc_update which can be used to prevent invalid or unauthorized document update requests from being stored”, throwing forbidden / unauthorized (docs.couchdb.org/ddocs, 2026-11-23). That is a pure validation/rejection gate — it cannot mint events, so it is half a decider.
6 · Maturity / license Production-ready · Apache-2.0 Landscape: Production-Ready, Apache-2.0, conflict handling “Flexible/Custom”, resolution “Client and/or Server”, authority “Default centralized, decentralized possible” (2026-11-22). Repo moved to github.com/apache/pouchdb: 17,632 stars, Apache-2.0, last push 2026-11-05 (GitHub API, 2026-11-23). Browser cost: “just a script tag and 46KB (gzipped)” (pouchdb.com).

02PouchDB vs go-cqrs-lite

Dimension PouchDB go-cqrs-lite
Who mints facts The client (document puts); server may only reject via validate_doc_update The decider — decider.Decider[State] folds events, Decide emits or rejects (errorfamily Rejection family)
Conflict unit Per-document revision tree; deterministic winning rev; losers stay queryable until resolved Per-stream Version with optimistic concurrency; conflict = rejected append, never a silent fork
Offline queue Replication is document-level; intent queueing is app code L4 concept: queue Commands, sync into server deciders on reconnect — never client-minted events (research 2026-11-22)
Event log Optional pattern (“Document & Event Sourcing” in landscape data) Native: append-only streams + global event.Journal / SeekableJournal.ReadFrom for catch-up
Protected resources validate_doc_update + per-db security objects/roles (CouchDB server) Commands touching protected resources simply never share their decider — the shareable set is the pure fold/decide subset
Ecosystem Apache project, 17.6k stars, 14 years of production use Proprietary fleet-first library, v4/v5 dual-support
Fit verdict: COMPLEMENT PouchDB is not a competing write model — it is a candidate substrate. A go-cqrs-lite client tier could store its queued-Command outbox and local projection cache in PouchDB and inherit battle-tested replication to a CouchDB-shaped server endpoint, while the decider discipline stays ours. The revision tree is also the best existing mental model for “speculative local branch”.

03What to steal

+
Conflicts as a common state, not an error Losing revisions remain addressable (_conflicts, open_revs) instead of being overwritten — the right substrate semantics for a client that committed speculative events offline: nothing is lost, the branch is just not the winner.
+
Deterministic winner without a coordinator Every replica independently computes the same winning revision from the tree — the property an offline client needs to show consistent state before the server has even seen its branch.
+
validate_doc_update as the minimal server gate One function, (newDoc, oldDoc, userCtx) → throw-or-accept, applied to every write. The L4 push endpoint can be exactly this shape — but backed by a real decider that emits events, which CouchDB’s validator cannot do.
+
Bounded revision history revs_limit (default 1000) prunes ancestry while keeping recent merge ability — a concrete answer to “how long must a client-local branch stay rebaseable?”
