00Identity & metadata

Zero has two parts: zero-cache, a cloud service holding a read-only SQLite replica of your Postgres, and zero-client, a TypeScript client store kept up to date by query-driven partial replication (ZQL over logical replication, incrementally maintained). Writes go through application-defined mutators that execute once on the client for instant UI and again inside your own mutate endpoint in a Postgres transaction; the server’s outcome replaces the optimistic one. This is the exact “Command boundary, rediscovered” the repo’s 2026-11-22 research report identified, and it is now generally available.

02Evidence

“Zero makes web apps feel instant by syncing the data your UI needs into a local, normalized client datastore. Reads and writes hit that local store first, then sync continuously with your server in the background.” … “Server Authority: All reads and writes flow through your code on your server, giving you complete control over permissions and business logic.”

zero.rocicorp.dev home + introduction · https://zero.rocicorp.dev/ · cache 2026-11-22

“When a mutator is invoked, it initially runs on the client, against the client-side datastore. Any changes are immediately applied to open queries and the user sees the changes. In the background, Zero sends a mutation (a record of the mutator having run with certain arguments) to your server's push endpoint. Your push endpoint runs the push protocol, executing the server-side mutator in a transaction against your database and recording the fact that the mutation ran.” … “Any pending mutations which have been applied to the server have their local effects rolled back.”

zero.rocicorp.dev/docs/mutators, Life of a Mutation · https://zero.rocicorp.dev/docs/mutators · cache 2026-11-22

“Zero does not support offline writes. When the client is in the disconnected, error, or needs-auth states, reads from synced data continue to work, but writes are rejected.” … “Supporting offline writes in collaborative applications is inherently difficult, and no sync engine or CRDT algorithm can automatically solve it for you. Despite what their marketing says.” … “It is of course possible to create applications that support offline writes well (Git exists!). But it requires significant tradeoffs.”

zero.rocicorp.dev/docs/connection, Offline + Why Zero Doesn't Support Offline Writes · https://zero.rocicorp.dev/docs/connection · live 2026-11-23

“A copy of each mutator exists on both the client and on your server … Often the implementations will be the same, and you can just share their code … But the implementations don't have to be the same, or even compute the same result. For example, the server can add extra checks to enforce permissions, or send notifications or interact with other systems.” Branching is explicit: if (tx.location === 'client'), and server registries can override shared ones via defineMutators(baseMutators, {}) — the docs headline this “Server authority to the rescue!”

zero.rocicorp.dev/docs/mutators, Architecture + Server-Specific Code · https://zero.rocicorp.dev/docs/mutators · cache 2026-11-22

Protected inputs: “Mutator parameters are supplied by the client application and passed to the server automatically by Zero. This makes them unsuitable for credentials, since the user could modify them. For this reason, Zero mutators also support the concept of a context object” — ctx.userID “User cannot control … so this enforces authorship”. Queries mirror mutators: defineQuery runs client-side, while zero-cache asks your server to resolve name+args into ZQL “where you also enforce permissions via context”. Impure mutators are allowed: “Impure mutators can be useful, e.g., to consult some external system on the server for authorization or validation.”

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

The repo’s 2026-11-22 report already ratified the Zero/Replicache shape as the L4 offline design (“clients queue commands and deciders mint events”). This dossier re-verified the core quotes live and adds three deltas: the API has been formalized (defineMutators/defineQueries registries with dotted names, .client/.server result promises, JSON return values, tx.retryOn), the project is GA, and the no-offline-writes position is now argued in writing rather than implied.

Question partZero’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Deliberately no: a disposable query cache in front of an authoritative server; the client store is not a source of truth. Confirms the two-tier read plan (server folds, client caches) but refuses ownership. go-cqrs-lite’s DB1 journal must be owned, not cached — Zero shows you cannot get that from replication alone.
P2 · local-first including Commands Commands run locally for one optimistic frame, then the server re-runs them authoritatively. Not offline. The dispatch contract matches this library’s command.Dispatcher model almost exactly: name + validated args, exactly one handler, server-authoritative. Zero is the existence proof that this shape is productizable — minus offline.
P3 · git-like branch/rebase None: reconciliation replaces optimistic effects with authoritative rows; rejected mutations simply vanish from the queue. Zero demonstrates the cheap alternative to rebase: never carry speculative work across a divergence. The owner wants the stronger property; keep Zero’s “skip and revert” as the fallback semantics when a replayed command cannot be decided.
P4 · client-only Commands & Events Explicitly out of scope, with a written argument: constraints, business rules and schema changes “can pass while offline, but break when the user reconnects”; only restricted offline writes (create-only, single-device) would be safe. This is the strongest counter-argument to the owner’s P4 in the whole landscape — quote it in the design doc. The answer stays what the addendum sketched: restrict client-local deciding to stream-local deciders whose whole input set is on the device, and surface late rejections as first-class UX.
P5 · shared logic minus protected resources Best-in-class: one codebase deployed twice, tx.location branching, server-only overrides, verified ctx, impure server mutators for external authorization. Direct template for the client-safe decider seam: stream-local deciders ship to the client unchanged; cross-stream/effectful ones live only in the server registry; ctx is the analogue of record.CommonMetadata actor claims, and tx.location of the initial/replay phase flag.

Against the thesis: Zero has re-derived Commands (the mutate endpoint is a command handler; the optimistic run is optimistic UI; revert-on-reject is a rejection surfacing) but keeps rows, not events, as the sync substrate, and pushes events out of the model entirely. For Go: zero-cache will happily call a mutate endpoint you write in Go, but the wire protocol is undocumented — implementing it means reading the TypeScript reference today.

04Fit verdict

PATTERN-TO-ADOPT

The canonical, now-GA statement of “same command code on client and server, server decides”: adopt the registry/override/context discipline wholesale for the client-safe decider seam, and adopt revert-on-reject as the terminal semantics of a replayed command. Not a complement — TypeScript-only clients, Postgres-bound, and it rejects exactly the offline branch the owner wants — which is why its written argument against offline writes belongs in the design doc as the position to answer.
