NextGraph

A decentralized, E2EE, P2P local-first ecosystem built on CRDTs and the Semantic Web (RDF). The only entry in this shard with a mechanism that enforces invariants on client-minted commits — a quorum-signed “synchronous transaction” — which is why it earns a longer look than its alpha status would suggest.

LOCAL COMMANDS: CLIENT-MINTS-FACTS REBASE: CRDT (DAG semilattice) FIT: ORTHOGONAL (pattern donor) ← all entries

00The question this page answers

The owner’s lens (brief, 2026-11-22) “How can we make the browser OWN its data smartly, be as local-first as possible (i.e. including Commands), but at the same time be able to smartly branch-rebase (like Git) with a server as soon as the client has a connection again! All that transparently. We need Commands & Events that only happened on the client. And we need to share the logic for Commands & Events & Queries (as long as they do not access protected server resources) with the client, efficiently.”

NextGraph’s answer: the browser fully owns its data (per-user encrypted repositories replicated P2P), writes are CRDT commits minted by the client, and merge is automatic by DAG causal history. Where it is unique: a document-level mechanism that can enforce rules on those commits via a signing quorum — the closest thing in this shard to a decide() that survives decentralization.

01Six axes, scored with evidence

Axis Verdict Evidence (primary sources, dates below)
1 · Client data ownership FULL — user-held repos “Local-first Data Repositories”; data lives on the user’s devices, synced P2P via relay servers (landscape, 2026-11-22). Site: “Total ownership of data”, “documents can be linked together, signed, shared securely” (nextgraph.org, 2026-11-22).
2 · Local commands CLIENT-MINTS-FACTS “Each commit represents a transaction, that is executed atomically when received by a replica. Those transaction are called asynchronous.” The client authors commits; there is no intent-vs-fact boundary (docs/framework/transactions, 2026-11-23). Synchronous Transactions (below) add quorum finality — the exception, not the write model.
3 · Reconnect rebase CRDT (DAG semilattice) “Repositories that contain branches that themselves organize commits in the form of a DAG”; when several concurrent commits form the HEAD, “the DAG is a Semilattice” until merged (docs/architecture, 2026-11-23). Forks are first-class; landscape: conflict handling “Automatic via CRDT” (2026-11-22).
4 · Client-local Commands & Events PARTIAL Asynchronous commits execute client-side with no invariant checks: “A commit can have rules that need to be enforced. But those rules can only be checked based on the causal past that was present at the replica at the moment when the commit was created” (docs/local-first, 2026-11-23). The Synchronous Transaction is the only enforcement path and it needs a signing quorum — “once this commit has been accepted by a certain threshold of Signers, it is guaranteed that no other concurrent transaction has happened or will ever happen” (docs/framework/transactions, 2026-11-23). Truly offline decide() is therefore not what NextGraph offers.
5 · Logic sharing + protected resources SDKs TS/JS/Rust/Python; crypto-capability ACLs Landscape lists TypeScript/JavaScript/Rust/Python SDKs and “Schema validation on write” (2026-11-22). Permissions: “all permissions are handled in NextGraph with cryptographic capabilities”; grant links (Nuri) carry read caps, editors additionally need the BranchWriteCapSecret; “removing permissions is a synchronous operation that requires a SyncSignature (signed by the quorum)” (docs/framework/permissions, 2026-11-23). No shared command/event/query logic layer.
6 · Maturity / license Alpha · permissive Landscape: Alpha, MIT, initial release 2024-09-02 (2026-11-22). Site: “available in alpha release (with limited features)” and “double permissive licensing: Apache License, Version 2.0 or MIT” (nextgraph.org, 2026-11-22) — the landscape’s MIT-only entry understates the dual grant. NLnet / EC-funded (verified on site). Not on GitHub (repo API 404; source lives at git.nextgraph.org per landscape + site).

02NextGraph vs go-cqrs-lite

Dimension NextGraph go-cqrs-lite
Who mints facts The client (CRDT commits); quorum only for Sync transactions The decider, always — decider.TypedDecider[State, Cmd] runs Decide against current state; Rejection is a first-class error family
Offline write path Async commits: yes, unchecked. Sync transactions: need signer threshold reachable Parked L4 tier would queue Commands client-side and sync them into server-side deciders on reconnect — never client-minted events (research report 2026-11-22)

Fit verdict: ORTHOGONAL A different universe (RDF, P2P, end-user ecosystem) — no component composes into a Go CQRS library. But its synchronous-transaction design is the only mechanism in this shard that enforces invariants over client-minted facts without a single-authoritative server, which makes it a pattern donor, not a dependency.

03What to steal

+
Quorum-signed synchronous transactions “We temporarily prevent any fork in the DAG while the transaction is being signed… the commit is final.” For go-cqrs-lite’s L4: a client-minted event branch could require server (or multi-node) countersignature before it is folded into the journal — a signing gate instead of a rebase gate, using the existing signing module’s mental model.
+
Honest causal-past rule checking Their docs concede rule checks are only valid against the causal past visible when the commit was created — exactly why a local speculative decide() is stale-blind (same finding as LiveStore’s commit callbacks, research 2026-11-22). Worth quoting in the L4 design doc.
+
Capability links (Nuri) as the share format A URL that embeds read capability + broker locator + optional write secret. The client-tier equivalent of a signed stream subscription: no server session needed to start reading.
+
Transparent permission revocation Revocation is a synchronous, quorum-signed operation while grants can happen offline — a clean split the L4 tier will need (grant = client-local; revoke = authoritative).
