00Identity & metadata

Electric has narrowed to what it is uniquely good at: Postgres Sync streams subsets of a Postgres database (“shapes”: table + where + columns) into any client store — from an in-memory variable to PGlite, TanStack DB or SQLite — over an HTTP API designed for CDNs, with SSE live mode and offset-based resume. Writes are explicitly out of scope and routed through your existing backend, which is why Electric composes with a Go command side instead of competing with it. Since 2026-08-11 the team is part of Databricks (joining Neon, building Lakebase); the hosted Electric Cloud is winding down, the open-source components continue.

02Evidence

“Postgres Sync is a sync engine that syncs subsets of your data out of your Postgres database, into local apps and services. You can sync data into anything you like. From web, mobile and desktop apps and client stores like TanStack DB to databases like PGlite.” … “The same shape log is delivered to every subscriber — web tabs, mobile devices, server workers, agents — in real time, with the same ordering and guarantees.”

electric.ax/sync/postgres-sync · https://electric.ax/sync/postgres-sync.md · cache 2026-11-22

“Electric does read-path sync … It does not do write-path sync. It doesn't provide (or prescribe) a built-in solution for getting data back into Postgres from local apps and services.” The writes guide then documents four patterns — online writes, optimistic state, shared persistent optimistic state, through-the-database sync — all with writes going “using your existing API”, and warns: “If an offline write is rejected by the server, the local application needs to find some way to revert the local state.”

electric.ax/docs/sync/guides/writes · https://electric.ax/docs/sync/guides/writes.md · cache 2026-11-22

Shapes — “a Shape is a SQL query against your Postgres. Postgres Sync carves out the matching rows and keeps them live for every client that subscribes” — defined by table, optional where clause, optional columns; single-table with subquery filtering; the TypeScript client stores “the last offset and handle you'd seen” so that after going offline “you'd pass in the last offset … so it knows at what point in the shape to catch you up from”.

electric.ax/docs/sync/guides/shapes + TypeScript client docs · https://electric.ax/docs/sync/guides/shapes.md · cache 2026-11-22 (shapes), live 2026-11-23 (TS client)

HTTP API control flow: after an initial offset=-1 sync the client receives { "headers": { "control": "up-to-date" } }; the other control message is must-refetch, which tells the client to throw away local shape data and re-sync. Live mode adds SSE: live=true&live_sse=true with “Keep-alive comments: Sent as : keep-alive every 21 seconds”; offset=now skips history.

electric.ax/docs/sync/api/http · https://electric.ax/docs/sync/api/http.md · live 2026-11-23

Durable Streams + fork: “Every position in a stream is identified by an offset … Opaque … Lexicographically sortable”; reads return Stream-Next-Offset to resume; “For exactly-once write semantics, a producer can identify itself using three headers” (Producer-Id, Producer-Epoch, Producer-Seq) with stale producers fenced out by 403. Fork (2026-04-15): “a single API call that branches a stream at any point … Forks don't copy data. They use copy-on-write (COW)” via Stream-Forked-From + Stream-Fork-Offset.

electric.ax/docs/streams + blog “Fork — branching for Durable Streams” · https://electric.ax/blog/2026/04/15/fork-branching-for-durable-streams · live 2026-11-23

Any language, including Go: the docs ship a guide for “writing an Electric client for any language that speaks HTTP and JSON” (the streams page shows a Go SSE reader in six lines). Writes: “Bring your own writes … Write through your API (Plain API). POST or PUT to your existing endpoints. The Postgres txid flows back through the read path”; TanStack DB adds “optimistic mutations that tie into the sync machinery” — “UI updates instantly. The collection awaits the txid on the stream and reconciles.”

electric.ax docs index + postgres-sync + tanstack-db · https://electric.ax/sync/tanstack-db.md · cache 2026-11-22

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

Electric is the only entry in this shard that keeps the CQRS boundary by construction — it never took the write path, so there is nothing to re-derive. For this repo it is interesting twice: as a production reference for the SSE read leg, and as the declared non-goal that go-cqrs-lite’s L4 tier would have to fill.

Question partElectric’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Owned, resumable copies of queried shapes in any local store; the offset+handle pair is the durability contract. Same shape as metaengine.ServeSSE + Watcher replay with Last-Event-ID: compare Electric’s opaque offsets, up-to-date/must-refetch control messages and 21-second keep-alives against this repo’s heartbeat/replay behaviour — a ready conformance checklist.
P2 · local-first including Commands Declined, in writing: writes go through “your existing API”, optimistic state is a documented pattern you build. Validates the thesis: the industry’s read-path specialist chose to keep Commands in application backends — exactly where go-cqrs-lite’s dispatcher and deciders live. A Go backend + Electric read fan-out is a coherent stack.
P3 · git-like branch/rebase No offline rebase; instead the Durable Streams protocol makes the log first-class: opaque sortable offsets, exact resume, idempotent producers with epoch fencing, and copy-on-write fork at any offset. The fork primitive is the closest thing to “branch like Git” shipped anywhere in this landscape — but it branches server-held logs online. For the offline branch, the producer-id/epoch/seq dedupe headers are a directly comparable design to deterministic command IDs (id.DeriveCommandID) plus engine dedup.
P4 · client-only Commands & Events Not offered. The most complete published recipe for bolting optimistic writes onto a read-synced store is pattern 4: PGlite shadow tables + INSTEAD OF triggers + a local change log drained to the server. Pattern 4 is a working sketch of the owner’s DB1/DB2 split minus events: local writes land in a shadow table, a change log drains them to the API, and reads merge synced + local. Swap “change log” for “pending command journal + speculative events” and it is the L4 client store.
P5 · shared logic minus protected resources No logic is shared because none runs client-side; interop is the protocol. Authorization is compositional: your proxy owns identity and injects per-user where clauses; the sync service stays dumb and cacheable. The “dumb pipe behind an authorizing proxy” posture is what lets a Go server own the boundary while any client consumes read models — the same reason go-cqrs-lite serves reads as folded JSON rather than sharing query engines. Public-by-default is the failure mode to avoid.

Against the thesis: Electric is the read half of this library’s architecture, built for Postgres rather than for an event journal — its shape logs carry row changes, not domain facts, so projections served this way are state-sync, not event-sourced reads. Organizationally it is mid-pivot (Databricks/Neon/Lakebase, cloud winding down), which matters for a complement chosen as infrastructure.

04Fit verdict

COMPLEMENT

Electric wants exactly the division go-cqrs-lite enforces: it syncs read models and refuses the write path, speaks plain HTTP/SSE to any language (Go included), and is Apache-2.0 and self-hostable. Pair it with a Go command side whose deciders write to Postgres, and it covers partial replication, CDN-scale fan-out and offline reads that metaengine.ServeSSE would otherwise have to grow — while its Durable Streams protocol (opaque offsets, idempotent producers with fencing, copy-on-write fork) doubles as the reference spec for this repo’s SSE and journaling contracts. Budget for the pivot: the cloud is winding down, so the complement is the self-hosted Elixir service.
