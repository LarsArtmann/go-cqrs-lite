00Identity & metadata

Triplit runs one embedded database on both sides of the wire: every client keeps a local cache plus an outbox of unconfirmed writes, answers queries locally, and syncs attribute-level deltas over WebSockets with a server that enforces role-based permission filters. Entities decompose into per-attribute Lamport-timestamped registers, so concurrent edits to different attributes never collide and same-attribute edits resolve last-writer-wins.

02Evidence

“Apps that use Triplit work offline by default. No extra configuration is needed. All Triplit clients save data to a local cache and mutate that cache optimistically without waiting for the server to respond. Mutations that are made offline queue in an "outbox" and are sent to the server when the client comes back online.” … “Triplit's CRDT-based sync protocol ensures that data is eventually consistent across all clients, even those that have been offline for an extended period.”

Triplit docs, Offline mode (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/offline-mode.mdx · live 2026-11-23

Client/server model: “each client has its own database that is fully queryable just like the remote database”; on the client “Triplit keeps your data in two storage areas: an outbox and a cache” with merged results by default, and queries “can be configured to only return data from the cache (to display only confirmed data) or only … from the outbox (to denote unconfirmed data)”.

Triplit docs, Client (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/client/index.mdx · live 2026-11-23

“Access control checks run exclusively on the server, and are not enforced on the client. Invalid writes will only be rejected when they have been sent to the server.” Permissions are per role and operation, “defined as query filters” over JWT claims ($token.sub, custom roles); updates check the old state and postUpdate may compare against $prev; attribute-level access control “is not yet supported”.

Triplit docs, Authorization and access control (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/schemas/permissions.mdx · live 2026-11-23

“Every entity inserted into Triplit is broken down at the attribute level, and each attribute is assigned a unique timestamp … When two users do update the same attribute at the same time, we use these timestamps to decide which value will be kept. In the literature this type of data structure is called a CRDT or more specifically a Last Writer Wins Register that uses Lamport timestamps.”

Triplit docs, FAQ (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/faq.mdx · live 2026-11-23

Sync failure handling: onEntitySyncError fires “when a write for that entity fails to sync with the server” (corruption, failed schema check, or “insufficient write permissions”) and “You may choose to undo the write by calling clearPendingChangesForEntity or retry the write by mutating the entity again”; onFailureToSyncWrites covers the whole buffer. Transactions roll back fully if any mutation fails on the client; server failures “will need to be handled” via these listeners.

Triplit docs, Event listeners + transact (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/client/event-listeners.mdx · live 2026-11-23

Any-language server access: “You can use the HTTP API … if your application wants to forgo the local cache and optimistic updates” — REST routes /fetch, /insert, /update, /delete, /bulk-insert, authenticated with JWTs (service or anonymous token); the FAQ: “How do I connect to Triplit from a server? … anywhere that supports HTTP.”

Triplit docs, HTTP API + FAQ (repo packages/docs, main branch) · https://github.com/aspen-cloud/triplit/blob/main/packages/docs/src/pages/http-api.mdx · live 2026-11-23

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

Triplit once marketed itself as exactly the owner’s P1–P4 stack (“full-stack database”, offline out-of-the-box, optimistic everything). Its architecture is honest about the cost: ownership means an outbox you must be able to un-send, and conflict handling means per-attribute LWW plus manual recovery handlers.

Question partTriplit’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Local database (pluggable storage; IndexedDB for durability) plus a persisted outbox; queries can select cache-only (confirmed) or outbox-only (unconfirmed) views. The cache/outbox split with a per-row confirmed/unconfirmed query flag is precisely the “speculative is a flag on rows, not two code paths” rule from the owner’s addendum — the single most portable idea on this page.
P2 · local-first including Commands State-shaped mutations only; the server’s contribution is schema + permission filters at apply time. Transactions are atomic client-side, advisory server-side. Another confirmation that optimistic state-mutation without intents ends in LWW; the client-side rollback of a failed transaction is the local half of what a client-side decider would own.
P3 · git-like branch/rebase Lamport-timestamped LWW registers per attribute; no history, nothing to rebase. Nothing to adopt; note their data-type discipline though — sets over arrays because arrays “lose many nice properties under collaboration” is the same argument that pushes event payloads toward addable facts.
P4 · client-only Commands & Events Durable offline writes with automatic resync; failures exposed per entity with undo-or-retry callbacks; no event log anywhere. The per-entity sync-error handler (onEntitySyncError with clearPendingChangesForEntity) is a good UX primitive for late rejections of replayed commands — finer-grained than a global “sync failed” badge.
P5 · shared logic minus protected resources Same engine + query language on client and server is genuine logic sharing; rules-as-filters are server-only; any-language servers go through the HTTP API with a service token. Rules-as-query-filters is a weaker cousin of the client-safe decider seam (filters cannot branch or compensate). The “one engine, two deployments” claim is only possible because the logic is data-shaped — the exact reason a Go decider cannot ride along.

Against the thesis: Triplit is state-replication with server-side filters — no Commands, no Events, no fold. And the ecosystem facts dominate any architectural lesson: AGPL-3.0 makes incorporation into a permissively-licensed Go stack a legal question rather than an engineering one, and the project has been untouched for over a year (main frozen 2025-09-11, npm frozen 2025-07-31, cloud closed, founder at Supabase, which promises further open-sourcing of the codebase).

04Fit verdict

ORTHOGONAL

Dormant, AGPL-3.0, and architecturally a sibling of InstantDB (client-minted state, attribute LWW, server-side filters) with a nicer offline outbox. Harvest exactly two small patterns — the cache/outbox split with per-view confirmed/unconfirmed flags, and per-entity sync-error handlers with explicit undo-or-retry — and treat its stalling as evidence that the “full-stack syncing database” category is brutal to sustain independently.
