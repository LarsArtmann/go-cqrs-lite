00Identity & metadata

LiveStore models app state as an append-only eventlog that is materialized into a local SQLite database by user-defined materializers, wrapped in a signals-based reactivity system, and synced between clients through a pluggable sync backend that enforces one global total order of events. Writes are store.commit(event) calls that take effect locally first and are pushed upstream later — pending events are rebased onto the server head on reconnect, exactly like a git rebase. It is TypeScript-only, self-hosted, and developed full-time by Johannes Schickling since 2021 (facts re-used from the repo’s own 2026-11-22-verified research report).

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

The owner’s addendum (research report of 2026-11-22, section 10) decomposes the question into P1 browser owns its data, P2 local Commands, P3 git-like rebase on reconnect, P4 Commands & Events that only happened on the client, P5 shared logic minus protected server resources. LiveStore is the reference system for P1 and P3 and the anti-reference for P2.

Question partLiveStore’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Eventlog is the source of truth on the device; SQLite state is a disposable projection. Leader thread owns dbEventLog + dbState; sessions hold in-memory mirrors. This is the owner’s dual-SQLite topology (journal DB + projections DB in a worker) almost verbatim — adopt the leader/session split and the “state is rebuildable” stance.
P2 · local-first including Commands Not available: the client commits events directly. The shipped validation ladder is payload schema, a pre-state commit callback, deterministic materializers, and backend ordering — none can consult authoritative state. Confirms the 2026-11-22 finding: no Command concept exists in the shipping API. Do not copy the write model; keep command.PersistedCommand queueing with server-side deciders.
P3 · git-like branch/rebase Push/pull with rebasing of pending events onto the arbitrated head; rollback to the divergence point, replay, renumber — with a rebaseGeneration counter. The UX to steal — but rebase intents, not facts: re-decide queued commands against fresh server state so a collision is a errorfamily.NewRejection, never a structural merge.
P4 · client-only Commands & Events clientOnly events are a clean local-only seam (UI state). RFC 0002 proposes a journaled, replayable command executed on the client with ctx.phase initial/replay and a confirmation promise that ends in confirmed or conflict. RFC 0002’s shape is nearly identical to the owner’s speculative-branch design; its Alternatives D (server-side command execution) and E (client-authoritative facts) bracket exactly the choice go-cqrs-lite already made. Watch this RFC — the outlier is converging.
P5 · shared logic minus protected resources One TypeScript schema (event tables + materializers) runs in every client; no notion of a protected decider. Auth is an app-level syncPayload; “sensitive/trusted” writes go through a server-side client. LiveStore shares data logic, not decision logic. go-cqrs-lite’s equivalent seam is the stream-local vs cross-stream decider split (pure decider.TypedDecider portable; anything reading other streams server-only).

Against the thesis: LiveStore is event-sourcing with the Command boundary deleted — the exact pole the 2026-11-22 report declined, and the project is now paying for it in public: merge-conflict handling and compaction are unimplemented and blocked on an unbuilt facts system (#253/#254). What makes this page more than a confirmation is the delta since that report: the repo now carries a merged-but-unaccepted RFC that re-introduces Commands on the client, while keeping the wire format events-only. The published package does not contain the RFC’s API (no defineCommand / store.execute in the 0.5.0 tarball, checked 2026-11-23) — so nothing shipped has changed, but the design direction has.

UNVERIFIED (2) Bundle size (“~500kb gzipped” + WASM) is a landscape self-report, not re-measured here; and whether any in-repo branch already implements the RFC 0002 API was not checked — only main’s intent documents and the published npm tarball were inspected.

04Fit verdict

PATTERN-TO-ADOPT

Adopt the sync and storage anatomy — pull-before-push rebase of a pending log, pending-vs-confirmed event states, the leader/session worker split over a durable eventlog plus disposable SQLite state, and the clientOnly seam — and treat RFC 0002 as free validation of the speculative-branch design, including its honest pricing of offline replay (cascading rejections, audit-trail rewrite). Do not adopt the write model: client-minted facts remove the one boundary go-cqrs-lite exists to keep, and LiveStore’s own tracker shows the bill.
