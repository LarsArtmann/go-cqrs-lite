Ditto

A proprietary edge-native database with built-in peer-to-peer mesh sync: every device holds a CRDT copy of the documents it subscribes to, writes execute locally with real transactions, and the server is just a trusted peer.

Maturity: Production-Ready (localfirst.fm landscape self-report) License: “Ditto Binary License”, all rights reserved (SDK LICENSE.md, accessed 2026-11-23); no public source repo found (GitHub API 404) Initial release: 2019-04-30 (landscape self-report) · current SDK 5.2.0 (npm, accessed 2026-11-23) Bundle size: not reported; the web SDK downloads a WebAssembly binary at startup LOCAL COMMANDS: COMMANDS-EXECUTED-LOCALLY REBASE: CRDT Back to the landscape index

00Summary

Ditto is the only tool in this shard where Commands really do execute on the client: DQL read-write transactions run at serializable isolation against the local store, can inspect state before writing, and can roll back. It is also the tool whose browser story is weakest for this question, because the JavaScript SDK keeps all data in RAM and persists nothing: closing the tab discards the database.

The interesting part for go-cqrs-lite is Ditto's honest answer to the rejection problem. Instead of a server that may say no, Ditto removes “no” from the system: every write is accepted, conflicts are merged by CRDT type rules, and business rules are re-derived at read time from a log of facts. That is event sourcing's storage discipline with the decide step deleted, and Ditto's own best-practice guide documents exactly that idiom.

The bottom line Ditto executes commands locally and merges like Git never could, but it cannot keep browser data, cannot say no, and shares no logic across platforms. Adopt its audit-log-plus-derivation idiom and its commit-ID watermark; answer its argument against write-time rejection.

01Six axes against the owner's question

Colours rate each axis against the owner's question (blue: serves it, yellow: partly, red: does not), not product quality. Ditto's axis-2 verdict is about the write path only; its browser storage verdict is the worst in this shard.

# Axis Verdict What that means, with evidence
1 Client data ownership SESSION ONLY On native platforms the device owns a full local store (E2). In the browser it owns nothing durable: “all local Ditto data is released” when the tab closes, with no writes to local or session storage (E3). Unsynced offline work in a browser tab is lost at tab close.
2 Local Commands COMMANDS-EXECUTED-LOCALLY Writes are executed by the local store, including multi-statement transactions at serializable isolation with an explicit commit-or-rollback result (E8), and the device keeps working with no connection at all (E1). The catch: the transaction sees only what has synced in via subscriptions, and no peer or server ever re-decides its outcome.
3 Reconnect rebase CRDT There is no rebase because there is no conflict in the structural sense: concurrent writes coexist (add-wins maps) or are ordered (last-write-wins registers) by deterministic type rules (E7). Causal consistency is guaranteed within a database ID.
4 Client-local Commands & Events FACTS ONLY Everything committed locally is a replicated fact; nothing stays client-only except rolled-back transactions and data outside your subscriptions. The audit-log pattern stores client-side facts (state transitions in an add-wins map) and derives current state from them (E11), which is the closest thing here to “events that happened on the client”.
5 Logic sharing & protected resources NONE Derivation functions are application code you write per platform; the only shared artefacts are data shapes. The protected-resource notion exists for data: signed permissions expressed as queries, enforced by every peer (E15) but only on the immutable document id (E14).
6 Maturity & license PRODUCTION-READY Production-Ready per the landscape self-report, with a large SDK family (Swift, Kotlin, Flutter, React Native, JavaScript, Java, C#, C++, Rust, Python preview, Go preview). The SDK ships under the proprietary “Ditto Binary License” (E18).

03Analysis against the owner's question and the go-cqrs-lite thesis

Ditto is the strongest “yes” to P2 and the weakest “yes” to P1, which is an instructive combination.

Part Ditto's answer What it means for go-cqrs-lite
P1 · Browser owns its data On the device, fully; in the browser, only for the session (E3). The engine itself is a WebAssembly binary fetched from a CDN (E4). For a browser-first design this is disqualifying on its own: a pending-command journal that vanishes at tab close is not a journal. PowerSync's OPFS-backed SQLite is the contrast case in this shard.
P2 · Local-first including Commands Yes, and this is Ditto's unique strength: local serializable transactions with read-then-check-then-write and rollback (E8). The closest existing model for a client-side decider's mechanics. But the decide runs against whatever the subscription has delivered, and its verdict is not authoritative: a peer with different local data can commit a different verdict, and the two outcomes merge by CRDT rules rather than by re-deciding.
P3 · Git-like rebase on reconnect Replaced by commutative merge. Concurrent work never conflicts structurally; instead business invariants are computed at read time (E9). Rebase answers “what should my intent now produce, given the new state?”. CRDTs answer “how do these two histories coexist?”. The owner wants the first question answered; Ditto argues the second question is the wrong one to ask — worth reading, and worth having a counter-argument to.
P4 · Commands & Events that only happened on the client Everything committed is a fact that will replicate; there is no speculative state. The confirmation side exists though: per-device commit IDs compared against a per-peer watermark (E17). That watermark is exactly the “speculative vs confirmed” flag of the addendum's design: a monotonic local commit id plus a per-peer ack high-water mark tells the UI which local writes the server has taken. Adopt the shape, not the CRDT.
P5 · Shared logic, minus protected resources No shared logic; per-platform derivation code. The docs themselves demonstrate the skew risk: peers with different strict-mode settings sync fine but derive differently (E16). Ditto in production forces the problem the addendum solves with a versioned logic envelope: identical data plus different interpretation logic equals silent disagreement. If logic cannot be shared, it must at least be versioned alongside the data.
The rejection question A write-time resolver “makes business logic decisions, and you only get one shot to get the merge right” (E10). The go-cqrs-lite answer: a decide step is not a one-shot merge. It is re-runnable on fresh state, and a rejected intent stays on record as a Rejection with its command, instead of being discarded. Ditto's audit log and this are the same two halves: facts preserved, interpretation explicit.

What to adopt

  • The audit-log idiom. “The audit log stores the facts. Your derivation function interprets them” (E11) is event sourcing stated for a serverless world: transitions as timestamp-keyed map entries, add-wins so nothing is lost, and a per-domain derivation policy (latest, most-advanced, earliest, custom). It is a good client-side projection vocabulary for speculative branches.
  • Derivation strategies as a named list. Latest timestamp, most advanced state, earliest occurrence, custom business logic — a compact catalogue of fold policies for the same fact log, which is what a client-side fold needs to declare per view.
  • Commit-ID watermark. A per-device monotonic commit id plus a per-peer synced_up_to_local_commit_id (E17) gives a precise, cheap answer to “which of my local writes has the server confirmed?” without per-row acks.
  • Versioned behaviour settings. The strict-mode warning (E16) is a live example of why a decider logic version must ride with the data, which the addendum already specifies for command payloads.

Where it bites (for this question)

  • No durable browser storage. RAM only, released at tab close (E3), so the browser-owns-its-data premise fails outright in the web SDK.
  • No rejection path anywhere. “Accept every write” means a domain rule like “balance must stay positive” can only be enforced as a read-time derivation, never as a refusal. Money-moving intents are exactly the case the owner's Rejection family exists for.
  • State writes lose intent. A diff against the local copy “can't tell which fields the user intended to edit” (E12), and a full-document save can silently undo a peer's edit (E13).
  • Permissions cannot express business rules. They key on the immutable _id only (E14), so they scope who may write what, not whether a write is valid.

Two shapes of the same problem

intent (command) → decide on fresh state → event or Rejection → projection
local write (state) → CRDT merge → audit log of facts → read-time derivation → derived state

Both rows end in a projection; they differ in where the decision happens and what survives being wrong. Ditto keeps every fact and reinterprets; go-cqrs-lite keeps every intent and re-decides. The owner's branch-and-rebase design is the second row with the offline window added.

04Fit verdict

PATTERN-TO-ADOPT LOCAL COMMANDS: COMMANDS-EXECUTED-LOCALLY REBASE: CRDT

As a product Ditto does not serve this question: its browser SDK persists nothing, its mesh-first architecture has no server to rebase against, and it is proprietary with no public source repository. As a pattern source it is the best page in this shard: it demonstrates that “accept every write, derive at read time” is event sourcing minus the decide step, supplies the audit-log and derivation-strategy vocabulary, and states the strongest published objection to write-time rejection, which a command-first design should be able to answer.
