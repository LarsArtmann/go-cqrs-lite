00Identity & metadata

Jazz 2 (Garden Computing) turns what was a peer-to-peer CoValue/CRDT toolkit into a backend-embedded relational database: createJazz runs inside your own server (Vercel, Cloudflare Durable Objects, or a plain Node box with SQLite), browsers sync through your origin’s /jazz route, and every read and write is filtered by typed permission policies that compile to SQL. Clients start “thin” (server-side queries, no local store) and can upgrade to a local-first client that runs the same Rust engine as a Wasm build inside a SharedWorker with a local replica in IndexedDB. Note the landscape self-report below still describes pre-2.0 “Classic Jazz”.

02Evidence

“Jazz is a relational database with tables, blobs, durable streams, collaborative rich text and more, all protected by declarative permissions. It runs in your existing cloud as part of your backend.” … “Clients start thin. Switch one to local-first for offline use and instant reads: it runs the same Rust engine on the device, with the same queries.”

jazz.tools home · https://jazz.tools/ · cache 2026-11-22

“A local-first client keeps a local replica of the data each user can read in the browser”; in persistent mode “the worker owns the SQLite database (stored in IndexedDB) and the server connection; each tab communicates with that runtime through a message port. There is no tab-leader election.” Browsers treat default storage as “best-effort — under disk pressure … the browser can clear it without warning”, so apps are told to request navigator.storage.persist().

jazz.tools, How Sync Works + Local-First Client + Advanced Internals · https://jazz.tools/docs/recipes/local-first/how-sync-works.md · cache 2026-11-22

“[Writes] are applied locally immediately so the UI updates without waiting on a round-trip. Jazz queues the corresponding row-version updates for upstream sync. When the client reconnects, queued writes are sent and active query subscriptions are replayed automatically.” … “Offline, only local can resolve. A global wait stays pending until the device reconnects and Core accepts or rejects the queued write, however long the outage lasts.”

jazz.tools, How Sync Works + Writing Data · https://jazz.tools/docs/recipes/local-first/how-sync-works.md · cache 2026-11-22

“Jazz sends every transaction upstream as one unit, and the authority decides that unit as a whole.” The authority “checks permissions and other rules before accepting them”; a rejected write “has already been undone locally” when awaited — PersistedWriteRejectedError carries the server’s code, reason and transactionId.

jazz.tools, Transactions + Writing Data · https://jazz.tools/docs/writing/transactions.md · cache 2026-11-22

“When two clients change the same column, the edit the server accepts last wins, whatever the clients’ clocks say, and the overwritten value stays in the row’s history. A run of offline edits is applied when it syncs, so it overwrites edits others made to the same columns while the device was offline. Every write also records the version of the row it was made over, which merge strategies (such as text merging) use to combine concurrent edits instead of picking one.”

jazz.tools, Advanced Internals (Merge strategies) · https://jazz.tools/docs/reference/internals.md · live 2026-11-23

“A serializable transaction uses a stable view of the data. Before accepting it, the authority checks whether another write made a conflicting change. If so, it rejects the whole transaction and Jazz removes its local changes.” … “For an app without a sync server, the authority runs locally instead.” … “The authority checks only the reads the writing client reports … it is not a security boundary: a client that under-reports its reads can commit anyway.”

jazz.tools, Transactions · https://jazz.tools/docs/writing/transactions.md · cache 2026-11-22

History: “Every table has a read-only history table … It contains all accepted versions of each row … Pending writes do not appear until the server accepts them.”

Clients that fail a policy check have their writes rejected and their reads filtered.” … “Only backends read jazz.permissions.json … Client bundles never include it, and nothing imports schema.ts at runtime.”

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

Jazz 2 matters to this review for two things nobody else in the shard ships together: an explicit two-kind transaction model that separates “optimistic merge” from “authority-validated invariant”, and durability tiers that make pending-vs-confirmed a first-class API rather than an implementation detail.

Question partJazz’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Opt-in replica, per account, in IndexedDB behind one SharedWorker; thin default keeps nothing; storage eviction is the app’s problem. Validates the owner’s “no IndexedDB” instinct in part: Jazz keeps SQLite inside IndexedDB via Wasm rather than using IndexedDB as a database. The single-worker, no-leader-election topology is a simpler variant of the owner’s dedicated-worker plan.
P2 · local-first including Commands No commands: a transaction of row writes commits locally, Core validates after. The serializable variant is the closest legal analogue of a decided command — but validation is read-set checking, not re-execution, and it cannot settle offline. Two error classes map directly: a rejected write behaves like errorfamily.NewRejection with server-supplied code/reason, and “serialization_conflict … treat both as read again and retry” is the retry semantics a rebase loop needs. Keep the decider as logic; Jazz shows the data-only ceiling of the same UX.
P3 · git-like branch/rebase No history rebase: column-LWW by acceptance order plus merge columns, with every overwritten version retained in row history. Branches exist but are domain-level (head-over-base views, frozen snapshots), merges are userland. Contrast, not pattern: Jazz buys always-merges semantics and pays with lost same-column updates. The owner’s rebase-intents model keeps the stronger guarantee by re-deciding; Jazz’s frozen-base snapshots are still worth copying for “branch captured at a point” UX.
P4 · client-only Commands & Events Durable offline writes with local/global wait tiers; a local authority exists when no server is configured; pending uploads counted and observable; history shows only accepted versions. This is the pending/confirmed ledger with a public API. Adopt the tier vocabulary for the client store: DB1 journal write = local; decider acceptance = global; a row flag derived from the tier, exactly like Jazz’s getPendingUploadRows.
P5 · shared logic minus protected resources One TypeScript schema generates every client binding; the permissions artifact is backend-only by construction; trusted machines get a separate credential class; advice APIs (canInsert…) return “allowed / denied / unknown” and are explicitly “advice, not permission enforcement”. The permissions-file split is the cleanest published version of “share the catalog, withhold the protected part” — the direct analogue of go-cqrs-lite emitting TS contracts from catalog.SchemaFromType while cross-stream deciders stay server-side. Jazz’s “advice” tier is the right shape for client-side pre-validation.

Against the thesis: Jazz has no Command concept — Core orders and authorizes row versions and validates read-sets; it never runs your logic. go-cqrs-lite’s deciders are shared logic; Jazz’s policies are shared data filters compiled to SQL. For a Go shop the practical blocker is stated plainly: the main backend must be TypeScript, and the Go client (whose bindings are generated from the same schema) is experimental.

04Fit verdict

PATTERN-TO-ADOPT

Not a complement — it demands a TypeScript main backend and its Go client is experimental — but the richest pattern mine in this shard: the mergeable-vs- serializable transaction split (optimistic merge vs authority-validated invariant), the local/global durability tiers that make speculative state a row flag, and the schema-generates-client-bindings-while-permissions-stay- server-side split that answers the owner’s P5 almost exactly. Its column-LWW reconnect model is the part to decline.
