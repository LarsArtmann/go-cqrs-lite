00Identity & metadata

Instant gives the frontend a real-time database: relational InstaQL queries resolve against a local triple store, InstaML transactions (db.transact(db.tx.todos[id()] .update({}))) apply optimistically through a pending queue, and a Clojure sync server tails Postgres’ WAL to invalidate and push query novelty. Everything data-shaped is triples, which is why conflicts mostly do not exist and, where they do, last-write-wins per attribute decides.

03Analysis vs the owner’s question and go-cqrs-lite’s thesis

InstantDB is what “a database in the browser” looks like when the only shared artifacts are data shapes: excellent optimistic UX, honest undo, and a ceiling made of LWW plus permission filters. Nothing in the system can consult state at decision time except a CEL predicate evaluated at apply time.

Question partInstant’s answerRead-across to go-cqrs-lite
P1 · browser owns its data Owned cache of subscribed queries (IndexedDB) plus a pending outbox — scoped to what queries asked for, capped (10 subscriptions cached by default). Confirms the query-driven pull leg (journal tail / Watcher replay feeding local folds) but shows why a real ledger beats a cache: a cache answers “what did I see”, not “what happened”.
P2 · local-first including Commands No commands. The closest thing to a business rule is a CEL rule like size(data.ref('owner.ownedTodos.id')) <= 2 — a state read, but read-only and evaluated only when the transaction reaches the server. Useful negative result: filters-on-apply cannot express “intent refused because the world changed”. That is precisely what decider.TypedDecider + errorfamily.NewRejection exist to do, and why the offline client must queue intents, not effects.
P3 · git-like branch/rebase None. Attribute-LWW; triple layout hides most conflicts; the rest silently resolve by arrival order. No rebase machinery to borrow — the pending-queue undo is the only transferable piece (revert optimistic state when the server says no).
P4 · client-only Commands & Events Optimistic transactions exist client-side and survive reloads; there are no client-minted events because there are no events at all. Reinforces the thesis’s ledger rule: without an event log, “what only happened on the client” is unrepresentable, and history/audit reduces to backups.
P5 · shared logic minus protected resources Same TS schema and same transaction vocabulary on client and server; protected logic lives behind an admin token over a documented HTTP API in any language; rules never run client-side. The admin-HTTP-API shape is worth copying for any TS-owned store a Go backend must touch; it is also the exact boundary go-cqrs-lite avoids needing, because Go is already the source of truth.

Against the thesis: Instant is the anti-thesis end-to-end — client-mints state deltas, no Command, no Event, server folds nothing, reads are pushed rows. Its one durable engineering lesson for this repo is the immutable-store-plus-pending-queue merge that makes undo trivial. Strategically it is also a reminder that hosted local-first backends can evaporate: the cloud dies 2027-08-31 and the self-hosted path is a JVM service.

04Fit verdict

ORTHOGONAL

Neither competitor nor complement: it is sunsetting, it has no command or event model to adopt, and its one transferable pattern — optimistic pending queue with revert-on-rejection — is better documented in Zero and Jazz, which keep an explicit authority. Keep it in the review as the canonical statement of the Firebase-shaped ceiling (“just a database in the browser”) and as a deprecation-risk data point.
