Liveblocks Storage

Liveblocks’ own structured sync engine (LiveObject / LiveList / LiveMap): client-minted ops, attribute-level last-write-wins resolved on the server — and, per the landscape dataset, “fix-ops” broadcast to every client when the server settles a conflict. That correction-broadcast loop is the most directly relevant reconciliation pattern in this shard for the owner’s “transparent rebase” demand.

00The question this page answers

The owner’s lens (brief, 2026-11-22) “How can we make the browser OWN its data smartly, be as local-first as possible (i.e. including Commands), but at the same time be able to smartly branch-rebase (like Git) with a server as soon as the client has a connection again! All that transparently. We need Commands & Events that only happened on the client. And we need to share the logic for Commands & Events & Queries (as long as they do not access protected server resources) with the client, efficiently.”

Liveblocks Storage’ answer: the client writes structured live objects optimistically, the server is the resolution point (attribute-level LWW plus fractional indexing for list order), and the protocol closes the loop by sending clients the resolved result. Transparent? Yes. Git-like? No — divergence is settled by overwrite rules, not by re-running intent. Commands and Events do not exist; ops on three collection types do.

Dimension Liveblocks Storage go-cqrs-lite
Conflict unit Attribute / map entry / list position Stream + Version; a rejected append is a decision, not an overwrite
Resolution authority Liveblocks servers, LWW rules, results pushed as fix-ops The decider on your servers; client speculation is reverted by re-running the Command authoritatively (the Zero-style loop verified in research 2026-11-22)

Fit verdict: PATTERN-TO-ADOPT As a product it is orthogonal hosted infrastructure; as a pattern it is the clearest illustration in the shard of transparent server-corrected reconciliation: clients speculate, the authority resolves, and the protocol itself tells every client what was fixed. That loop — not the LWW rule inside it — is the adoptable part for the L4 tier.

03What to steal

+
fix-ops: corrections as protocol messages When the server resolves a conflict it does not just bump a version — it sends every client the compensating ops. The L4 rebase should do the same: emit explicit compensation/correction events (the ADR-0136 replayable→compensable ladder from research 2026-11-22) rather than silently swapping state under the UI.
+
Granularity-typed containers LWW at attribute level, fractional indexing only where order matters — conflict granularity is a property of the container type, declared up front. go-cqrs-lite’s equivalent decision (per-stream Version vs per-field merge) deserves the same explicit, typed surface.
+
Reconnect catch-up as an engine guarantee “Catches clients up when they reconnect” is the client-side twin of what metaengine.ServeSSE already guarantees server-side (replay, Last-Event-ID resume) — the two halves of one protocol.
+
Snapshot version-history for users Browsable, restorable room snapshots are what event sourcing gives for free via replay — a reminder to surface the journal’s power as a product feature, not just an implementation detail.
