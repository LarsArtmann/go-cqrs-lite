# Testing Conventions & Environment

> Extracted from AGENTS.md (2026-09-08 indexed-split). Edit HERE; AGENTS.md carries only the index.

## Testing

- Table-driven tests preferred; BDD via Ginkgo v2 + Gomega for event/decider/query; fluent Given/When/Then via `scenario/`
- `t.Parallel()` for independent tests; core packages >80% coverage (most >90%)
- Golden tests use `go-snaps` (`snaps.MatchSnapshot`) — powered by `eventtest.AssertGolden`. Update: `UPDATE_SNAPS=true go test ./...`. Clean obsolete: `UPDATE_SNAPS=clean go test ./...`. Each module using golden tests has a `snaps_clean_test.go` with `TestMain` calling `snaps.Clean(m)`. **Cross-binary deletion trap (catalog hit 2026-09-23):** go-snaps `Clean` deletes every `.snap` in the dir that its OWN binary did not touch — so when multiple PACKAGES share one golden dir (catalog's `testdata/golden/` is shared by asyncapi, d2, eventcatalog, openapi), even module-wide `go test ./...` runs one binary per package and they clean each other nondeterministically. Regen scoped, then `git ls-files -d -- testdata/golden | xargs -r git restore --` the cross-deletions (details: catalog/AGENTS.md).
- Modules without event dependency (otel, codec) use `go-snaps` directly via local `matchGolden(t, name, got)` helpers
- **Postgres integration tests** use `testcontainers-go` (postgres:16-alpine). Each test gets its own fresh database. `POSTGRES_TEST_DSN`/`DATABASE_URL` env var overrides.
- **Cross-binary test resources on shared servers must be namespaced by default** — per-test DB names like `test_1` collide when PARALLEL PACKAGE BINARIES allocate on one shared Postgres (storage vs storage/relational vs benchkit were collision partners; each `go test` package binary is a separate process, so a per-package counter alone does not protect you — think "who else creates databases on this server", not "one package at a time"). The fix lives in `testutil/pgtestcontainer` (`test_<pid>_<n>` via `os.Getpid` + atomic counter); any NEW helper allocating databases/schemas/tables on a shared server must PID-qualify (or otherwise namespace) from day one (lesson from the 2026-08-28 phase-0 session).
- **Nix-based integration tests (no Docker)**: ephemeral PG/Redis/NATS/Dgraph via nixpkgs services. See Quick Reference for commands.
- **Relaunching the userspace MariaDB** (datadir at `/tmp/mariadb-cqrs`, port 33061 — /tmp is VOLATILE, expect it wiped across reboots/cleanups): if the datadir is gone, re-init first: `nix build nixpkgs#mariadb -o /tmp/mariadb-cqrs-bin && mkdir -p /tmp/mariadb-cqrs/{data,tmpdir} && /tmp/mariadb-cqrs-bin/bin/mariadb-install-db --datadir=/tmp/mariadb-cqrs/data --skip-test-db`, then start `/tmp/mariadb-cqrs-bin/bin/mariadbd --datadir=/tmp/mariadb-cqrs/data --socket=/tmp/mariadb-cqrs/mysql.sock --port=33061 --bind-address=127.0.0.1 --tmpdir=/tmp/mariadb-cqrs/tmpdir --silent-startup`. On a FRESH userspace init, `-u root` via socket is DENIED (unix_socket auth maps DB-root↔OS-root): connect as the INVOKING OS user (no `-u` flag) to run `CREATE DATABASE cqrs_test; CREATE USER 'cqrs'@'%' IDENTIFIED BY 'cqrs'; GRANT ALL ON cqrs_test.* TO 'cqrs'@'%';`, then `MYSQL_TEST_DSN="cqrs:cqrs@tcp(127.0.0.1:33061)/cqrs_test"`. Probe with the server's own client (`mariadb -e "SELECT 1"`), not /dev/tcp. Two tool-shell traps (2026-09-01): `$!` in mvdan/sh returns a job id like `g1`, NOT a numeric PID — capture the server PID via `pgrep -f mariadbd` and kill with `/run/current-system/sw/bin/kill`, or the process leaks.
- **MariaDB claiming store WORKS since 2026-09-06 (SKIP LOCKED verified live)** — `NewClaimingMySQLStore` is real: live probe on MariaDB 11.4.12 proved `FOR UPDATE SKIP LOCKED` (a tx holding row locks does not block a concurrent SKIP LOCKED claim of other rows; MariaDB gained it in 10.6). The claim is TWO statements in one tx (SELECT ... FOR UPDATE SKIP LOCKED, then UPDATE by IDs — MariaDB lacks UPDATE..FROM..RETURNING). Old guidance ("MariaDB has no SKIP LOCKED", `ErrClaimingUnsupported` for MySQL) is DEAD — do not restore it. Integration pin: `scheduling/sqlstore/mysql_claiming_integration_test.go` (build tag `integration`); run against :33061 with `MYSQL_TEST_DSN="cqrs:cqrs@tcp(127.0.0.1:33061)/cqrs_test?parseTime=true"`.
- **Race-aware test thresholds**: `-race` inflates allocations/CPU 5-10x. Use `testutil.RaceEnabled` (or `enginetest.RaceEnabled` for metaengine modules) to pick relaxed bounds. Four lean-budget modules (`benchkit`, `transport/grpc`, `idempotency/kvstore`, `idempotency/sqlstore`) keep local copies because adding testutil/enginetest would exceed dep budget. Always run affected test 3x with `-count=3 -race` after touching a threshold. Ginkgo suites (decider, event, query) reject `-count>1` outright — run `-count=1 -race` three separate times there.
- **Timing-assertion flake cure is structural, not margins** — when a test asserts "X visible immediately" against a TTL clock, descheduling under full-gate load legitimately expires X before the check; margin bumps (10→50→100ms all flaked in `idempotency/sqlstore`) never fix the class. Split the assertion onto a long-TTL key (vis-key pattern in `property_test.go`) so it is timing-proof by construction.
- **Soak test env vars**: `SOAK_SKIP_10M=1` skips 10M-event soak (~5s/25s-race). `SOAK_SKIP_DUCKDB=1` skips DuckDB AutoCRUD soak (~80s/100s-race). `SOAK_SKIP_BOLT=1` skips bbolt AutoCRUD soak (509-1145s under load; exported by the full `nix run .#verify` app, whose 8m per-package timeout it exceeds). `SOAK_SKIP_DGRAPH=1` skips the Dgraph AutoCRUD soak (~115s over the RAFT write path). The 50K-event `TestSoak_MemoryBounded` always runs as smoke. **The 52s-vs-15min `#integration-dgraph` discrepancy explained (2026-08-30)**: the dgraphengine package includes its AutoCRUD soak, so an unfiltered run pays ~2min of soak over the network on top of the matrix tests; a `-run`-filtered invocation (the Usage line in the app header) skips it. `SOAK_SKIP_DGRAPH=1` now gives the unfiltered run the same escape hatch.
- **`-shuffle=on` verdict (2026-08-30): ADOPT for the live-engine suites** — the very first shuffled MariaDB run caught a real order dependence (the planned-ops matrix leaked state across runs on the persistent `cqrs_test` DB; fixed with an adttest `Factory.PreClean` hook). Verified green over 2 shuffle seeds each on mysqlengine, plus sqliteengine and duckdbengine targeted suites. **Rolled into the app invocations 2026-09-11**: `ephemeral-pg.sh`, `ephemeral-dgraph.sh`, `ephemeral-redis.sh`, `vm-mysql.sh`, `vm-mysql-nspawn.sh` now pass `-shuffle=on` on their default go-test lines (the dgraph eval found two real contention gaps first — see below). `scripts/test-integration.sh` (the auto-detecting composite runner) deliberately does NOT yet pass it — give it its own eval before adding.
- **QEMU slirp cannot carry 16-way concurrent connection bursts (2026-09-19)** — `adttest`'s `ConcurrentCASExactlyOneWinner` defaults to 16 racers; under `#integration-mysql-vm` every round died with `invalid connection` (the slirp NIC resets the burst before mysqld sees it — an infra limit, never a store-semantics failure). Cure: `ADTTEST_CAS_RACERS` (>= 2) caps the racer count; the `vm-mysql.sh`/`vm-mysql-nspawn.sh` mysqlengine + queue/mysql legs export `ADTTEST_CAS_RACERS=10` (same pattern as `MYSQL_TEST_CONCURRENCY` for the idempotency leg). The nspawn leg (no slirp) runs the full 16.
- **A crashed nixos-test-driver ORPHANS its QEMU, which keeps holding the hostfwd port (33070) and poisons every subsequent leg run (2026-09-19)** — the driver dies on a QMP `ConnectionResetError` but the QEMU survives. Before AND after every `#integration-mysql-vm` run: `ss -tlnp | grep 33070` + `ps aux | grep qemu`; kill orphans with `/run/current-system/sw/bin/kill <pid>` (bare `kill` is not a supported builtin in the tool shell). Beyond the 16-way burst limit above, slirp under host load ≥ ~50 also resets SINGLE fresh dials (~once per run window) — any suite opening parallel connections without retry is one RST from red, and hardening each suite is whack-a-mole. The vehicle-level cure for LOCAL runs is the userspace MariaDB pattern (the `/tmp/mariadb-cqrs` recipe above): a second ephemeral instance at `/tmp/eph-mysql` on 127.0.0.1:13306 ran the full 6-suite mysql leg (stack/mysql, idempotency/sqlstore, metaengine/mysqlengine, scheduling/sqlstore, queue/mysql, claiming) green in <10s total on 2026-09-19; the QEMU/nspawn legs remain the CI-parity vehicles. Related shell hygiene: the tool shell caps at 50 background jobs and silently REFUSES new shells (even foreground) at the cap — `job_kill` finished job IDs before long legs, and note the DB server's shell ID (an accidental kill takes the server down with it).
- **Concurrent-session file ownership (multi-agent sessions)**: at session start, `git status` + `git log --oneline -5` to see what the parallel session owns; NEVER edit a file with foreign uncommitted changes (FEATURES.md/TODO_LIST.md near-collisions happened twice on 2026-08-30). Files a session has touched in its commits stay theirs for the workstream (e.g. calibration/WS-M); surface interest through the shared TODO_LIST instead of editing in place. If both sessions must touch shared ledgers (TODO_LIST/CHANGELOG), re-read the section immediately before each edit — the mod-time check on the edit tools catches mid-flight collisions. Never run linter `--fix` (or any repo-wide mutator: `nix fmt`, `go work sync`) at module/repo scope while foreign dirty files exist — scope fixes to files you own (a `golangci-lint run --fix ./...` reformatted a parallel session's in-flight work on 2026-09-06).
- Coverage drift checked by `nix run .#check-coverage` (`scripts/check-coverage.sh`).
- **"Time-sortable ID" claims must be pinned, not assumed** — `task.NewID()` minted a crypto-random same-ms suffix while its doc promised creation-time ordering that the queue claim tie-break (`ORDER BY created_at ASC, id ASC`) RELIES on; three enqueues in one millisecond (the normal case) made the claim pick a random task (~20% of `TestConformance/Reads/status_counts` runs claimed the wrong one → `running -> cancelled`). The "only under load" attribution in the 2026-09-16 filing was wrong — it was a coin flip misread as load-sensitivity because single runs passed. Fix (2026-09-19): monotonic per-ms sequence in NewID; pins in `queue/task/task_test.go`. Lesson: when a test flake is attributed to load, re-run it 30-100× standalone BEFORE accepting the attribution — a 20% coin flip survives "green standalone" eyeballing.
- **A workspace-only regression is invisible to `GOWORK=off` per-module tests (2026-09-19, ADR-0143 incident)** — `EngineResetter.ResetEngine` deleted journal rows; `system`'s replay test failed in EVERY full `#verify` (workspace mode = local engine trees) while passing 30/30 "standalone" — because `cd system && GOWORK=off go test` resolves engine deps to their PUBLISHED tags, which predate `ResetEngine`. The failure was mis-attributed to load-sensitivity for days (deadline bumps as "mitigation"). Lesson: when a test fails in verify but passes module-isolated, FIRST re-run it module-isolated IN WORKSPACE MODE (`go test ./system/ -run TestX` from repo root, no GOWORK=off) — if it fails there, it is a deterministic local-tree regression, not a flake. After touching a cross-module contract (interfaces engines implement, adapters), run the consumer module both ways.
- **Two `*sql.DB` pools over one SQLite file race the WAL conversion (2026-09-19)** — `journal_mode=WAL` conversion needs a momentary exclusive lock; when a test opens a second pool over a file another pool is still converting (or holding reads), the PRAGMA fails with `database is locked` (SQLITE_BUSY) as an intermittent flake. Every pool over the same file must carry the pragmas in its DSN — the `tx_isolation_test.go` shape `?_pragma=journal_mode(WAL)&_pragma=busy_timeout(10000)` — so the conversion is idempotent by the time the second pool opens AND both sides have a busy timeout (`sqliteengine.NewFromDSN` runs the same PRAGMAs but only on ITS pool, dsl.go). Prefer ONE pool per file (`sqliteengine.NewSQLiteEngine(db)` over the caller's `*sql.DB`) whenever the test does not specifically need reader/writer connection concurrency.
- **Reset tests on shared/persistent DBs need run-unique collections and keys (2026-09-19)** — engine `Reset()` empties derived collections, but the claimkit fact journal is append-only BY CONTRACT (ADR-0142 §5: rows survive resets, positions stay monotonic), so a rerun or `-count>1` against the same database sees the previous run's journal rows and any non-reset leftovers. Derive names per run — the adttest `claimConformanceCollection(base)` UnixNano-suffix pattern — for every collection/key a reset-observing test reads back (`ClaimFactsList`, counts, existence probes). Fixed names are only safe on fresh `t.TempDir()` or `:memory:` databases.
- **Poll the FINAL derived condition, not an upstream one (2026-09-19)** — `integration`'s graph-projection test polled until 2 user nodes appeared, then immediately asserted the follow EDGE; `user.followed` projects after the `user.created` events, so under the race detector at full-gate load the edge legitimately lagged the users (`expected at least 1 edge from alice, got 0` — the only failure of the first post-lint-clear `#verify`). When a wait-loop gates on condition A and the assertion checks condition B derived LATER in the same stream, give B its own deadline-bounded poll; an immediate assertion converts projection lag into a test failure.
- **`select` between a ready result and a ready `ctx.Done()` is a coin flip (2026-09-20, `system.GracefulClose`)** — Go's select picks UNIFORMLY at random between ready cases, so a PRE-cancelled/pre-expired context racing an instantaneous `Close()` loses ~50% of runs under parallel test load — a textbook nondeterministic flake that looks load-sensitive. The deterministic shape: when the result arrives, RE-CHECK `ctx.Err()` inside the result case and let a non-nil error win (`system/system.go:322`); the context can only be "more right" than a success that raced it. Testing lesson: any `select { case <-ctx.Done(): ... case r := <-done: ... }` with a potentially pre-done context needs the same re-check or a seeded clock, and a 50/50 flake will pass 30 standalone runs often enough to be misfiled as "green".
- **A quiet loadavg is necessary but NOT sufficient for benchmark verdicts (2026-09-21, T18b re-pin)** — five gate runs at load ≤5 still produced 4 noise-gate rejections (chronic `write_p99_ns` CoV volatility — now demoted from the headline set) and one decision-grade `MIN/matview` flag that was pure bimodal sampling (median-of-5 lands on either mode; samples 7.9–15µs on a quiet machine; now in the `KNOWN_UNSTABLE` table, expiry 2026-10-21). After a load-gated run, read the noise-gate verdict and the `UNSTABLE-KNOWN` lines before believing any single comparison — `calibration-gate.sh` certifies the machine, `benchmark-regression.sh`'s noise gate certifies the run, and NEITHER certifies a bimodal sampler. Also: ad-hoc scripts that invoke `go` must `export GOTOOLCHAIN=auto` — the ambient shell carries `GOTOOLCHAIN=local`, and go.work's `>= 1.27.1` then kills the run instantly (`wall=0s`, exit 1) exactly when the machine is quiet enough to matter.
- **Verification ladder (which gate to run when; release-tooling tail 2026-09-25)** — climb, don't jump: (1) module meta-tests (`cd <module> && GOWORK=off go test -count=1 .`) for the code you touched; (2) touched-module lint (`nix run .#lint-module -- <module>`) when the change could trip analyzers; (3) `nix run .#verify-fast` for cross-module compile + doc surface when APIs or docs moved; (4) composed `nix run .#verify` (via `preflight-composed.sh` + `can-run-composed-gate --wait-loop`) before release claims — it is the only gate that proves the guard chain end-to-end. Skipping rungs saves minutes and costs re-runs: the S03 arc burned attempts 7-9 on failures rung 3 would have caught in ~40 s.
- **Gate-script self-test inventory + earning rule (W0 tail (a), audited 2026-09-25)** — scripts WITH `--self-test` (wired into `#check-release-scripts`/nightly/verify where CI-consuming): calibration-gate, can-run-composed-gate, check-buildcache-capacity, check-canonical-facts, check-doc-annotations, check-error-taxonomy, check-go-version, check-golangci-hash, check-md-go, check-readme-deprecated, check-readme-links, check-turso-version, nightly-bench, preflight-composed, quiet-window-run, restore-depguard, wait-for-quiet (+ fixture suites test-tag-release/test-batch-release/test-check-retracts-shipped/test-pin-sweep/test-calibration-drift/test-benchmark-regression). Scripts WITHOUT one (check-arch, check-changelog-symbols, check-coverage, check-depguard, check-doc-links, check-doc-stubs, check-eventcatalog, check-file-size, check-formatters, check-heap-parallel, check-linter-names, check-modsums, check-module-isolation, check-private-deps, check-replace-directives, check-rule-count, check-staged-go, check-tag-existence, check-templ-paths, check-version-drift, check-workspace-sync, verify-parallel) are straight-line derivation gates: their entire logic is "compare repo truth vs expectation", a failure is self-evident, and a fixture copy would only re-test grep. EARNING RULE: a gate script earns a self-test when it has fault-injection hooks, a REPAIR path (silent-skip reads as green otherwise), fixture goldens, or CI-consumed branching — add the self-test in the same change that adds such logic.
