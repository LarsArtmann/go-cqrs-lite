### Tooling & Build

- **DSN secret-redaction heuristic (engines, 2026-09-08 audit)** — `tursoengine.redactDSN` redacts by CONTAINMENT, not exact spelling: any query param whose lowercased name contains `token` or `key`, on local AND remote DSNs (exact-spelling matching leaked `auth_token`/`AUTH_TOKEN`). `pgengine`/`mysqlengine` never echo the DSN (plain `%w` wraps of driver errors) — keep it that way; any new DSN-echoing error path must go through redaction. Strict-vs-lenient typo'd-param rejection is a pending owner ruling (TODO_LIST blocked item).
- **Repo is PUBLIC (2026-08-30) with an INTENTIONALLY PROPRIETARY license — do not "fix" either** — user decision: public visibility, no OSS license grant ("Keep unlicensed"). Consequence: pkg.go.dev shows "License: UNKNOWN" and hides documentation — that is EXPECTED, not a bug to fix. GOPRIVATE/VCS-auth gotchas below are largely obsolete for this repo and all sibling modules (all public). Secret-scan baseline: gitleaks full-history (5998 commits) + working tree clean as of 2026-08-30; the two hits were false positives (`maypok86/otter/v2` module path in an archived status doc; the intentional `sk-1234...` fixture in `cmd/cqrs-lint/pkg/rules/security/new_rules_test.go` — keep that fixture, it feeds the secret-detector test).
- **Always `nix fmt` BEFORE placing `//nolint` directives** — golines (max-len: 120) reformats long lines and moves nolint comments to wrong positions. Keep nolint comments under ~40 chars.
- **Scoped formatting**: `nix fmt` runs treefmt on the whole repo. For a single module, use `gofumpt -w <path>` + `goimports -w <path>` directly.
- **gosec G115** (integer overflow): extract a helper that isolates the `uint64()`/`uint32()` call on a short single line.
- **When adding new dependencies**, add them to `.golangci.yml` depguard allow list at the same time. Depguard was RESTORED 2026-08-30 after a 2-space→4-space reformat silently disabled it (collateral captured in commit `38afb6d2e`). golangci-lint v2 wants `linters.settings.depguard.rules` as an OBJECT (`rules:` → `main-allow-list:` → `allow:`); a YAML list of rules produces mapstructure errors (`rules[0][allow] expected a map`) that look like schema nonsense. `scripts/check-depguard.sh`'s awk is indentation-tolerant since the same day — it survives future reformats instead of hard-coding item columns.
- **`.golangci.yml` config reformats silently mutate linter semantics — now guarded AND self-healing** — SECOND incident 2026-09-05: a config reformat re-added `gci` to `formatters.enable`, making 366 treefmt-clean files fail `nix run .#verify` lint repo-wide (import grouping is owned by treefmt per the formatter gotcha above). Defense is mechanical now: `scripts/check-formatters.sh` pins `formatters.enable` to (goimports, gofumpt, golines) and runs inside `nix run .#check-lint-config`; since 2026-09-06 it SELF-HEALS — it strips a re-added `gci` in place and re-verifies (the auto-commit daemon re-added it a third time that day; the repair loop beats manual fixes, but the daemon is the root cause — see TODO_LIST daemon Q2). If you ever WANT gci back, you must change both the config AND the pin script — a one-line decision, made loudly.
- **SQL store helpers live in `storage/sql/`** — `RunInTx`, `IsDuplicateKeyError`, `CommitTx`, `ScanSlice`, `MarshalMetadata`. Don't duplicate transaction/duplicate-key logic in domain-specific store files.
- **golangci exclusion `paths` patterns are NOT cwd-relative — probe before removing** — the `#lint` app runs golangci from inside each module dir, yet repo-root-prefixed patterns (`event/`, `metaengine/sqliteengine/`) still suppress findings there (empirically verified 2026-09-06: deleting `event/` from `linters.exclusions.paths` surfaced ~120 findings in a plain per-module run). Suffix patterns (`\.pb\.go$`) match everywhere regardless. Probe method for staleness audits: back up `.golangci.yml`, delete the candidate pattern, re-lint the affected module exactly as the gate does (per-module), compare counts — 0 findings = redundant or dead (removable); suppressed findings = load-bearing (keep); then restore. Verdicts 2026-09-06: `event/eventtest/` DEAD (no such directory; removed from both lists), `event/` (~120 findings), `event/v4/eventtest/` (7), `metaengine/sqliteengine/` (6, incl. 2 gofumpt) load-bearing, `storage/view/` suppresses nothing today (kept as a drift guard). Related generator trap: `templ generate` bakes the invocation cwd into `_templ.go` FileName metadata — always run it from `catalog/docserver/`, never the repo root, or `nix run .#check-templ` reports permanent drift.
- **`scanCommand` and `scanQuery` must unmarshal metadata** — both scan a `metadataJSON []byte` column. Use `json.Unmarshal` into `command.Metadata` / `query.Metadata` (standalone structs, NOT aliases for `event.Metadata`), then pass via `WithCommandMetadata` / `WithQueryMetadata`. Forgetting this causes silent metadata loss on SQL load.
- **NEVER commit code that doesn't compile** — Commit `b3931503` shipped `slices.Contains()` with zero arguments. If you bypass the pre-commit hook, run `go build ./...` manually.
- **cqrs-lint fixture probes have prerequisites** — the linter skips non-consumer projects: a synthetic probe needs its own `go.mod`, an actual go-cqrs-lite import, and a SINGLE `--path` flag (multiple `--path` flags silently last-win — a 2026-09-06 benchmark measured 17 files instead of 196 this way). A probe that prints nothing may have been SKIPPED, not passed; assert the analyzed-file count.
- **In-repo examples are SELF-LINT-SKIPPED by cqrs-lint (V007/F030 never fire on them)** — `IsCQRSModulePath` matches by PATH PREFIX, so `github.com/larsartmann/go-cqrs-lite/example/...` counts as "the library itself" and consumer-coaching rules silently skip. Scanning `example/*` in place ALWAYS reports clean, violation or not (probe-proven 2026-09-11: an injected `event.TombstoneMark{}` violation passed the strict scan). To scan an example as a consumer, scan a throwaway COPY with the module line rewritten to a consumer path (see `TestExamples_AreV5Clean` in `cmd/cqrs-upgrade/examples_test.go`). Consequence: any manual "strict scan of the examples was green" run done in-place was a false green.
- **`go build -o` into a throwaway dir when a script builds main packages** — a bare `go build ./...` writes main-package binaries INTO the module directory, silently dirtying the tree after a successful release cut (found in BOTH release scripts 2026-09-11). `-o` refuses "no main packages to build" on library-only modules, so a fallback to the plain build is mandatory, not cosmetic — order: try `-o "$tmp"`, fall back to plain build, and the fallback still compiles (broken library code still aborts).
- **Re-View before editing files other processes write (daemon, annotate scripts)** — the auto-commit daemon and the docs-health annotation assets rewrite files between your reads; a stale-read edit is rejected by an mtime guard ("file modified since last read"). Treat the rejection as a refresh signal, not an error: re-View the target region, then retry with freshly copied text (hit twice on 2026-09-11 applying post-script banners). Corollary: never reconstruct long `old_string`s from memory — always copy from a fresh View.
- **`go/printer`'s `ExprString` elides variadic call args** — generating source text from AST expressions via `ExprString` produced non-compiling `evt.Type(...)` (2026-09-06, C003 fix generation). Derive call-argument text explicitly instead of trusting `ExprString`.
- **Verification gate: `nix run .#verify`** — build + vet + test + race + lint + doc-check + doc-assertions. Run before tagging releases.
- **"Stale GREEN" anti-pattern** — every session that changes code, go.mod, or docs must run `nix run .#verify` (or at minimum `nix run .#verify-fast`) before claiming GREEN. A stale GREEN claim is worse than no claim.
- **Exit codes after pipes lie** — `cmd | tail -N; echo "EXIT=$?"` prints tail's exit code, not cmd's (and `PIPESTATUS[0]` can come back empty in this shell). A golangci run with 11 issues printed `EXIT=0` this way. Always capture gates as `cmd > /tmp/x.log 2>&1; echo $?` and grep the full log — never trust a `| tail` view or a post-pipe `$?`.
- **Never run integration suites concurrently with `#verify`** — benchkit's timing tests (Duration=10ms abort bound) and the per-package `-timeout=5m` are load-sensitive; a concurrent Dgraph soak produced 3 benchkit + 1 duckdb false failures (~25 min wasted). Run the full gate exclusively, nothing else heavy running.
- **Per-task gate discipline (from session-4's three wasted verify cycles)** — a task commit ends with the gates its diff can affect: api golden (`cmd/api-stability … --update`) + per-module lint + `check-duplication` for code; `doc-check` for skill docs; `check-changelog-symbols.sh` for CHANGELOG edits. Never batch them into one mega-verify at session end and never bill a task green on gates you have not run for THAT task's diff.
- **Background jobs: write to a file, poll, auto-kill** — `cmd > /path/on-disk.log 2>&1` then poll the file on a timer; NEVER launch with `| tail` (fully buffered → invisible → an 8-hour wedge), and wrap live-server suites in `timeout -k 15 <bound>` because dgraph alpha ignores SIGTERM during drain. Log files go on disk (`/home/lars/projects/.gotmp/`), not /tmp tmpfs.
- **LSP phantom `/mnt/buildcache` diagnostics are ambient-env bleed** — the tool shell exports `GOLANGCI_LINT_CACHE=/mnt/buildcache/golangci-lint` (broken mount), which golangci-lint-langserver inherits despite `~/.config/crush/crush.json` setting a valid `GOLANGCI_LINT_CACHE` in its `env` block. The diagnostics are noise; `go build -tags "goexperiment.jsonv2"` + CLI golangci (with the disk-cache env chain) are authoritative.
- **Orphaned QEMU poisons every later `#integration-mysql-vm` run** — a crashed nixos-test-driver leaves `qemu-system-x86_64` alive holding `/run/user/1000/vm-state-machine` (qmp socket); the next run's `machine.start()` dies with a QMP `ConnectionResetError` and tests talk to a semi-dead orphaned VM where MySQL connections reset after ~16s (even untouched stack/mysql tests fail this way). Fix: `pkill -f qemu-system-x86_64` + `rm -rf /run/user/1000/vm-state-machine /run/user/1000/shared-xchg`, then re-run. For MySQL-flavored SQL verification without the VM, use the userspace MariaDB on :33061 (see Testing section) — `idempotency/sqlstore` integration tests are proven green there.
- **Storage-engine data-visibility quirks**: pebble `Close()` does NOT flush memtables — a write-count assertion after close/reopen under-reports unless `Flush()` is called first; bbolt mmap-remaps the file in 32KB-ish pages so `FileSize()` is quantized (never assert exact on-disk size), AND bbolt suites/benches need `TMPDIR=/tmp` (tmpfs) on btrfs/ZFS machines — the mmap+fsync workload times out at 10min on CoW filesystems (2026-09-04); MySQL-VM integration: probe liveness with the server's own client (`mysqladmin ping` via the forwarded port 33070), NOT /dev/tcp; the VM needs `GOWORK=off` + `-tags "goexperiment.jsonv2"` from the module dir (workspace mode picks up the VM-unfriendly default path); all VM tests share ONE database — never assume per-test isolation.
- **turso-go GROUPED materialized views return SILENTLY WRONG SUMs once a group is updated by a second transaction (upstream, 2026-09-07, repro verified)** — a grouped `SUM(json_extract(...))` view matches its base table exactly within ONE transaction; from the SECOND transaction on, groups spanning multiple transactions lose part of their delta (at 2k rows: 3 of 316 groups each miss ~half their sum; constant 430.50 delta at ≥1.3k rows), collapsing at ~27k rows (view reports 496,034 vs true 1,308,429 while reads succeed — verified on v0.7.2 through v0.8.0-pre.10, re-verified on pre.10 2026-09-11 with the identical 430.50 delta at 2k rows). SCALAR SUM views stayed exact in every test. Consequence for OUR feature: `MaterializedViewSpec` with `GroupBy` is UNSAFE beyond a single transaction's rows on tursogo ≤ v0.8.0-pre.10 — operators must not trust grouped views at scale until upstream fixes; scalar views are the safe shape. Single-sourced citation: the verified range lives ONLY in `metaengine.TursoGoIVMVerifiedThrough` (`metaengine/materialized_view_versions.go`) — the Doctor WARN renders it and `nix run .#check-turso-version` fails on any live doc/test citation naming a different version (run it after every live re-verification). One-command release check: `metaengine/tursoengine/ivm_repro_test.go` behind `-tags ivmrepro` (asserts defects A/B/C PRESENT — a failure there is the flip signal). Full flip procedure: `docs/turso-go-ivm-fix-flip-runbook.md`. Full characterization + repro: `docs/research/2026-09-07_turso-go-ivm-commit-failure-issue-draft.md`.
- **turso-go v0.7.2 COMMIT failure on IVM writes (upstream, 2026-09-07, repro verified)** — `turso: error: Transaction error: cannot commit - no transaction is active` fires **deterministically at ~27,000 cumulative view-maintained rows per process**: every write transaction through a materialized view after that total aborts at COMMIT, from fresh database files too (verified 24/24 rounds at exactly chunk 27000: 50k rows × 1 grouped view × 316 groups). Below the wall behavior is probabilistic — large single transactions (≥~5k statements) through many views (≥~6) fail earlier, prior scan activity in the process shrinks the budget, grouped views fail before scalar ones. Data committed before an abort is intact (clean rollback); plain (view-less) engines never fail at any size. Chunking to ≤1k statements/tx is necessary but NOT sufficient past the wall — bulk loads must keep TOTAL view-maintained writes per process under ~27k (rotate process/file). Ready-to-file upstream draft with self-contained repro: `docs/research/2026-09-07_turso-go-ivm-commit-failure-issue-draft.md`; bench guards in `seedInTxE` (`metaengine/tursoengine/matview_bench_test.go`). Through tursoengine the wall onset sits at ~24k-25k (not 27k — scan activity and the engine's per-row SQL shift it; treat the position as workload-sensitive). POST-ABORT READS THROUGH THE SAME ENGINE LIE: after a failed COMMIT the zombie transaction stays open on the single pooled connection (the PR #8257 mechanism), so a MapGet there can see the aborted chunk's rows AND further same-engine writes are rejected — a connection-state artifact, NOT persistence and NOT durable file poisoning; judge rollback only after closing and reopening the file fresh, which accepts writes again (`TestIVMReproDefectC_CommitAbortsAtRowWall` pins all three behaviors).
- **Turso terminology + the embedded-only driver (2026-09-07)** — "Turso Database" is the Rust SQLite rewrite (MIT, beta dropped at 0.7); libSQL is the legacy C fork. The `turso.tech/database/tursogo` `database/sql` driver (name `turso`) opens EMBEDDED Turso Database engines only — it has NO remote Hrana/`libsql://` client, so tursoengine's remote-DSN handling is a planner-level prior, not a wire client. Turso Cloud BYOK keys cannot be presented by a pure-remote Go connection at all; the sync engine's struct config (`TursoSyncDatabaseConfig.RemoteEncryptionKey`, base64) is the only encrypted-cloud path and is operator-managed today. Embedded encryption (experimental upstream, `tursoengine.WithEncryption`): HEX keys locally vs BASE64 keys on Cloud — mixing formats fails cryptically; DSN params `encryption_cipher`/`encryption_hexkey` require `experimental=encryption`; wrong keys fail explicitly (`Decryption failed for page=N`, the AEAD tag). `redactDSN` contract: any query param whose name contains `key` plus `authToken`/`token` is redacted on BOTH local and remote DSNs (local DSNs used to bypass redaction entirely — that is where encryption keys ride).
- **Host toolchain may be older than go.work requires** — `go: go.work requires go >= 1.26.6 (running go 1.26.5)` means prefix the command with `GOTOOLCHAIN=auto` (the newer toolchain is already cached). The same error in gopls/golangci LSP diagnostics is noise; `go build -tags "goexperiment.jsonv2"` is authoritative.
- **gopls `stdversion` warnings on `encoding/json/v2` symbols are LSP noise** (2026-09-10, triaged via real builds) — `json.Marshal requires go1.27 or later (file is go1.26)` fires on every `encoding/json/v2` import (e.g. `system/adapter_*.go`) because stdversion checks the module's `go` directive, not the `goexperiment.jsonv2` build tag that makes v2 available under go1.26. `GOWORK=off go build` + `go vet` with the tag are green; do not "fix" these by downgrading imports. Same class for the two `go mod tidy` diagnostics: `go mod tidy` itself is authoritative — if it keeps a flagged indirect require (e.g. `integration`'s genproto), the module graph needs it.
- **Committed go.work must stay CI-loadable — NO `../` sibling use-entries** (2026-09-03/04) — CI has no sibling checkouts, so every plain `go` command in every job fails at workspace load. The no-externals invariant is GATED by the go-work-sync CI job + `scripts/check-workspace-sync.sh`; co-dev siblings belong in a LOCAL UNTRACKED go.work. After any dependency-graph change: `go work sync` + full-repo `go mod tidy` sweep as ONE scripted wave, then re-run the sync check.
- **Workspace-mode alloc assertions see sibling working trees** — alloc-count tests (`TestAllocs_NewEvent_*`) resolve `../go-codec` through `go.work`, so untagged sibling perf work shifts counts and workspace gates go RED while `GOWORK=off` is GREEN. The F46 resolution (2026-09-06): go-codec's envelope fast path is TAGGED (v0.2.0), its tree is clean, and the alloc pins are upper-bound budgets (`allocs > 3`), not exact equality — keep that style for any pin touching dependency code; diagnose by running the failing test both ways before suspecting your diff.
- **/tmp tmpfs fills up (48G, shared) — link jobs die with "no space left on device"** — set `GOTMPDIR=/mnt/buildcache/tmp` (plus `TMPDIR` for the linker) on workspace-wide `go test ./...` runs. Never delete /tmp/bigtest (unknown ownership); `trash-empty` reclaims ~6.6G when needed.

- **`ephemeral-*.sh` script env passthrough strips inner quotes** — `TEST_ARGS="-run 'X|Y' -v"` reaches `${TEST_ARGS}` UNQUOTED, so the single quotes become part of the pattern and match nothing ("no tests to run"). - **NEVER use `git checkout <commit> -- .`** — destructively overwrites the working tree. Use `git worktree add /tmp/work <commit>` instead.
- **Tool-shell false negatives on live servers** — `/dev/tcp/127.0.0.1/<port>` redirections silently fail in the tool shell (mvdan/sh has no /dev/tcp), reporting a healthy server as DOWN; probe with the server's own client instead (`mysqladmin ping` for MariaDB/MySQL). `kill` is not a builtin there — use `/run/current-system/sw/bin/kill <pid>`. A mysqld whose datadir was trashed keeps serving from unlinked inodes with all its old state; before diagnosing "corruption" or "mystery stale data", check `pgrep -a mysqld` + process start time vs datadir mtime, kill, and restart on a fresh datadir.
- **Generated markdown must be formatter-excluded at BOTH layers — RULES.md's re-padder was dprint, not treefmt** (2026-09-08, root cause corrected): the earlier note blamed treefmt, but treefmt has NO markdown formatter — the table re-padding came from `dprint.json`'s markdown plugin (the daemon/BuildFlow reformat layer). `**/RULES.md` is now excluded there next to `**/CHANGELOG.md`, and `TestRULESMD_Fresh` is stable with the generator's minimal-table output. Lesson generalized: when a freshness test fights a formatter, identify the ACTUAL mutating layer (treefmt programs ≠ dprint ≠ BuildFlow) before choosing the fix; and where a comment or doc must co-name rule IDs or enum members with code, add a completeness meta-test so the drift fails CI instead of rotting silently (S-family split-brain pattern).
