## Recommendation

**Add BDD tests for `catalog/`** — it's the largest module without BDD coverage and has the most complex consumer-facing API (Registry → Builder → Catalog → Exporters). The user-facing scenarios are:

1. "As a developer documenting my system, I register services with commands and events, then export to AsyncAPI"
2. "As a developer generating API docs, I build a catalog with schemas and export to OpenAPI"
3. "As a developer visualizing my architecture, I export to D2"

**Other modules (id, dispatcher, codec, schema, snapshot, otel, watermill, pebble, turso, storage)** have adequate table-driven and property-based test coverage. BDD would add marginal value for leaf and adapter modules.

## Existing BDD Quality

All BDD tests follow the **user-focused pattern**:

- `Describe("As a developer...")` — user persona
- `Context("when I...")` — user action
- `It("should...")` — expected outcome

This is excellent. The signing BDD tests are the gold standard:

```go
When("I sign an event and verify it with the same key", func() {
    It("should confirm the event has not been tampered with so I can trust its integrity", ...)
})
```
