Data Model Deep-Dive

metaengine: From God-Struct to Sealed Union

A first-principles review of the cost-based storage planner's data model inside go-cqrs-lite/metaengine. The fold-return-type-is-the-ADT inference is genuinely elegant — but its internal representation is a minefield of any, nil-guarded handlers, and split-brain twin types.

Scope: 71 source files Reviewed: 2026-08-01 Design lang: Go 1.26 Module: metaengine/v4

01Current State

metaengine is a reflection-driven inference library: it derives projections, indexes, and engine assignments from two primitives — Events (mutations) and Queries (read intent). The core domain concepts are: Event, Query, Fold (event→projection mapping), ADT (inferred data structure), Engine (storage backend + cost profile), Store (runtime), Plan (optimizer output), Layout (physical storage), Cursor (pagination), Cost (estimate).

Genuine strengths
Honesty note. metaengine is a library whose entire purpose is to infer types at runtime from user-supplied generic declarations. Some any is inherent to the design — you cannot statically know the consumer's event types. This review distinguishes inherent erasure (defensible) from fixable erasure (the Fold god-struct, split-brain twins, god-object Store).

◆What Already Works

Credit where it is due. Five modeling decisions are genuinely superb and must be preserved by any redesign.

+
Fold-return-type-IS-the-ADT inference The developer never declares "I need a Map." The handler's Go signature (func(e) (K, V) → Map, func(e) Delta → Counter) IS the declaration. This is inspired API design — the type system does the talking.
+
ISP-respecting per-ADT backend interfaces Engines implement only what they support: MapBackend, SetBackend, CounterBackend, GraphBackend, etc. The apply path type-asserts the right interface and returns a clean "unsupported" error. No fat StorageEngine with stubbed methods.
+
Enum families ARE distinct named types ADT, ReadPattern, FoldKind, Complexity, StorageLayout, FilterOp are each type X string — not bare string. Cross-concept confusion (passing a ReadPattern where an ADT is expected) is a compile error. This is correct; the gap is validation/exhaustiveness, not branding.
+
Composable rule pipeline for planning PlanRule interface + RulePipeline apply rules sequentially after engine assignment. Rules enrich the PlanResult (diagnostics, layouts) without overriding selection. Extensible by composition, not inheritance — textbook correct.
+
Cost model is honest about its limits The cost.go file opens with an explicit "HONESTY NOTE: rough first-order model, not a calibrated query optimizer." Constants cite their calibration benchmark and date. This intellectual honesty is rare and valuable.

02Problem Catalog

Brutal honesty, graded by severity and mapped to the 12 canonical data-model anti-patterns (P1–P12). Every claim is verified against source.

Critical P2 + P5

C1 · The Fold god-struct: 11 mutually-exclusive any handlers

fold.go · fold_classify.go · store.go (applyFold dispatch)

Fold is a single struct with 11 any-typed handler fields (insertHandler, updateHandler, keyExtractor, countHandler, edgeHandler, setHandler, multiInsertHandler, appendHandler, vectorHandler, searchHandler, spatialHandler) plus 2 reflect.Type metadata fields, gated by a Kind FoldKind string discriminator.

At any moment, only one handler is set; the other ten are nil. The invariant "only the handler matching Kind is non-nil" is enforced solely by constructor discipline in onFold(). Nothing in the type system prevents Fold{Kind: FoldInsert, countHandler: someFn} — a struct that would nil-panic on the first applyFold.

Worse: every callXxx() helper in fold_classify.go does reflect.ValueOf(f.xxxHandler) with no nil guard. If the invariant ever breaks, you get a nil reflect.Value panic deep in the apply path — the most hostile possible failure mode for an event-sourcing library. 

// THE PROBLEM: one struct, 11 nil slots, 1 live slot, string-gated dispatch
type Fold struct {
    EventType   string
    EventSample any
    Kind        FoldKind   // ← the ONLY thing telling you which field is live

    keyType   reflect.Type
    valueType reflect.Type

    insertHandler      any // func(e E) (K, V)     ← live when Kind == FoldInsert
    updateHandler      any // func(e E, prev V) V  ← live when Kind == FoldUpdate
    keyExtractor       any // nil for 10 of 12 kinds
    countHandler       any
    edgeHandler        any
    setHandler         any
    multiInsertHandler any
    appendHandler      any
    vectorHandler      any
    searchHandler      any
    spatialHandler     any // 10 of these 11 are ALWAYS nil
}
Fix: sealed interface union. Each fold kind becomes a distinct concrete type implementing a sealed Fold interface. The handler lives inside the concrete type, typed. A type switch in apply replaces the string switch. See the Redesigned Model (section 06).
Critical P4

C2 · The engine layer is universally any — type erasure at the boundary

engine.go · store.go · execute.go · typed_reader.go

Generics are captured beautifully at the Query[Q, R] declaration boundary — then immediately erased to any the moment data enters the Store/Engine layer. Every backend interface shuttles any: 

type MapBackend interface {
    MapSet(ctx context.Context, collection string, key any, value any) error
    MapGet(ctx context.Context, collection string, key any) (any, bool, error)
    MapDelete(ctx context.Context, collection string, key any) error
}
type ScanResult struct { Items []any; HasMore bool }
func (s *Store) Execute(input any) (any, error)

The codebase itself names the consequence: the "double-decode tax" — any → reify → R requires 3 JSON operations where 1 would suffice (hence the RawValueReader optimization bolted on top). And reifyReflect reconstitutes map[string]any back to typed structs via reflection at every read.

Nothing prevents MapSet(col, UserID("u1"), OrderID("o9")) — passing an OrderID where a FindUserResult value belongs. The type system offers zero protection here.

Nuance. Some erasure is inherent: you cannot statically know the consumer's event/result types, so the engine layer storing any is defensible. But the call site (Store boundary) can validate key types against the declared keyType reflect.Type before dispatch — it just doesn't.
High P1

H1 · String enums lack validation and exhaustiveness

types.go · fold.go · engine.go · cost.go · layout_type.go

Six enum families (ADT, ReadPattern, FoldKind, Complexity, StorageLayout, FilterOp) are correctly distinct named types — so this is NOT bare-stringly-typed (that would be critical). The gaps are softer but real:

  • No Valid() method. ADT("banana") compiles and silently falls through every switch to a default that returns a generic ComplexityON.
  • No exhaustiveness. Add ADTHyperloglog and no switch breaks at compile time. Every switch adt silently mishandles the new variant.
  • No central registry. layoutComplexity, classifyADT, complexityRank, scaleThresholds each independently enumerate ADT/Complexity variants — adding a variant means hunting 4+ files.
High P6 + split-brain

H2 · queryRuntime: a type-erased twin of QueryDecl[Q,R]

store.go · query.go · planner.go

Two structs represent the same domain concept ("a declared query"): QueryDecl[Q,R] (generic, public, 8 fields) and queryRuntime (unexported, type-erased, 11 fields). planQuery() hand-copies nearly every field from one to the other via a struct literal with no constructor.

This is a classic split brain: two sources of truth with hand-maintained mapping. Add a field to QueryDecl and you must remember to add it to queryRuntime AND copy it in planQuery() — or it silently defaults to zero. The queryMeta interface (9 methods) exists solely to bridge them, exposing QueryDecl's full internals to the planner (an ISP violation: each decision site uses 2–3 of the 9 methods).

High P6

H3 · Store god-object — 17 fields mixing 9 concerns

store.go

The Store struct is a god object fusing nine orthogonal concerns into one type:

Field(s) Concern
engines, queries, byInputType, plan Query registry + planning
poisoned Error quarantine (fold-panic poisoning)
appliedEvent Idempotency dedup
hooks Observability
eventLog, queryDecls Audit / consistency verification
coalescer Read coalescing cache
writeCount, readCount, startTime Workload metering
watcherMu, watchers Reactive subscriptions
replays SSE replay journals

Each is a separable collaborator. The god-object makes the Store hard to test in isolation and means every method carries the weight of all 9 concerns.

Medium P4

M1 · Domain value structs use any for their payload

types.go · spatial.go · vector_search.go

Edge{From any, To any}, MultiEntry{Key any, Value any}, Append{Value any}. Edge{From: "u1", To: 42} compiles cleanly even though From/To should be the same NodeID type. The type system cannot enforce graph-edge consistency.

Medium P3

M2 · Delta is a raw map[string]int64 alias — nil-unsafe, no constructor

types.go

type Delta map[string]int64. The zero value is a nil map — useless but compiles. Nothing prevents malformed keys (Delta{"": 0}). A struct wrapper with a constructor and an Add(key, n) method would make the nil state unrepresentable.

Medium P7

M3 · CostEstimate / WorkloadStats: raw numbers, units only in field names

cost.go · materialize.go

EstimatedLatencyMs float64, NsPerOp float64, WriteRatePerSec float64, Volume int64. Units live in the field name, not the type. A branded type Nanoseconds float64 or a type Latency time.Duration would prevent cost.NsPerOp being silently added to cost.EstimatedLatencyMs.

Medium P11

M4 · ScanResult / RawScanResult: parallel structs, missing generic

engine.go

ScanResult{Items []any; HasMore bool} and RawScanResult{Items [][]byte; HasMore bool} differ only in element type. A ScanResult[T any] generic eliminates the duplication and the HasMore field-sync drift risk.

Medium P2

M5 · Cursor.Value any — opaque cursor, no kind discrimination

types.go · cursor.go

A point-lookup cursor and a sorted-scan cursor carry different value shapes but share one type. Cursor.Value is any, serialized to JSON opaquely. A cursor that knows whether it is a keyset boundary vs. a single-key marker would make pagination bugs representable as type errors.

Medium P8

M6 · No versioning/provenance on PlanResult

plan_types.go · serializable.go

The plan is recomputed on every Plan() call. There is no Version, no ComputedAt, no way to detect that a running store's plan has drifted from a freshly recomputed plan without a full re-plan + manual diff. SerializablePlan is hand-maintained as a parallel JSON shape — another drift surface.

Low P12

L1 · Errors are sentinel strings, not structured types

errors.go

~30 sentinel errors.New values + fmt.Errorf("%w", sentinel) wrapping. Consumers use errors.Is. This is idiomatic Go and acceptable, but rich context (which query, which fold, which key) is lost in string interpolation rather than a structured ApplyError{Query, EventType, Fold, Cause}.

Low P11

L2 · Watcher[V], SSEReplay[V] are well-generic, but watcherEntry leaks any

dx.go

The public Watcher[V] and SSEReplay[V] are correctly generic. But the internal watcherEntry.ch chan any and the watcherNotification{seq, value any} wrapper re-erase to any and rely on unwrapWatcherValue[V] type-assertions. Functional, but a missed opportunity for a typed notification channel.

03Reflection: Root Causes

Stepping back. Are these 13 symptoms separate issues, or a few systemic ones?

Root cause A: "one struct to rule them all" reflex

The Fold god-struct (C1), the Store god-object (H3), and the ScanResult duplication (M4) all share one root: the impulse to model a polymorphic concept as a single struct with optional fields rather than as an interface union with concrete variants. Go gives us sealed unions for exactly this; they were not used.

Root cause B: generic boundary, erased interior

C2, M1, M2, M5 all stem from capturing generics at the public boundary (Query[Q,R], Watcher[V]) then erasing to any one layer deeper. The inference design is inherently reflective — but the erasure happens earlier and more broadly than necessary. Key-type validation (C2) and typed notification channels (L2) are fixable without abandoning inference.

Root cause C: twin types for the generic↔erased bridge

H2 (queryRuntime) and M6 (SerializablePlan) are the same disease: when a generic type must cross into an erased context, the codebase duplicates the type rather than embedding or projecting. The hand-maintained field copy in planQuery() and the hand-maintained JSON projection in Serialize() are both drift surfaces.

The three core entities

Everything revolves around Event, Query, and Fold. The ADT is derived from Fold (do not model it as a first-class input). Engine and Store are infrastructure. The redesign focuses all energy on making Fold a sealed union and Query a single source of truth.

The invariants that must ALWAYS hold

  • A Fold is exactly one kind; its handler matches its kind — currently unenforceable, fixable.
  • A Query's fold value types match its declared result type R — currently a runtime WARN in schemaRule, could be a compile-time invariant.
  • An event applied to a query updates exactly that query's projection — holds, well-modeled.
  • A poisoned collection refuses reads until reset — holds, but poison state is an untyped sync.Map of any.

04The Vision

What a superb metaengine data model looks like — six properties, each making an invalid state unrepresentable.

1. Fold is a sealed union

Each fold kind is a distinct concrete type. The handler lives inside it, typed. No nil handler slots, no string discriminator, no reflect-without-nil-guard. A type switch dispatches apply.

2. One query, one representation

QueryDecl[Q,R] is the single source of truth. The erased runtime view is a projection (interface or embedded view), not a hand-copied twin. No drift.

3. Store is a composition of collaborators

Poison tracker, idempotency tracker, watcher registry, workload meter, audit log are injected collaborators — each testable alone, each nil-safe to disable.

4. Enums are validated and centrally registered

Each enum family has Valid(), a parse(), and a registry that switch-sites consult. Adding a variant touches one file, not four.

5. Units are branded, not field-name-encoded

Nanoseconds, RatePerSecond, ItemCount branded types prevent unit-mismatch arithmetic in the cost model.

6. Inference preserved, erasure minimized

The fold-return-type-IS-the-ADT elegance is untouched. Erasure happens only where truly inherent (engine storage of consumer values), never one layer early.

05Redesigned Go Data Model

The centerpiece: Fold becomes a sealed interface union. This single change dissolves C1 and cascades cleaner code through applyFold, classifyADT, and deriveKeys.

5.1 · Fold as a sealed union

// Fold is a closed union: only this package can add variants (sealed method).
// Each concrete type carries EXACTLY the handler it needs — no nil slots.
type Fold interface {
    fold()              // sealed tag
    EventType() string
    EventSample() any
}

// A typed invoker captures E,K,V at construction; the stored call site is
// a single erased closure so the union stays storable in []Fold.
type insertFold[K, V any] struct {
    eventType   string
    sample      any
    keyType     reflect.Type
    invoke      func(event any) (key any, val any)
}
func (insertFold[K, V]) fold()              {}
func (f insertFold[K, V]) EventType() string { return f.eventType }
func (f insertFold[K, V]) EventSample() any  { return f.sample }

// On() constructs the right variant; the generic K,V are captured here
// and erased ONCE into a typed invoke closure (no per-call reflection).
func On[E, K, V any](sample E, handler func(e E) (K, V)) Fold {
    return insertFold[K, V]{
        eventType: EventTypeName(sample),
        sample:    sample,
        keyType:   reflect.TypeFor[K](),
        invoke: func(event any) (any, any) {
            k, v := handler(event.(E))
            return k, v
        },
    }
}

// updateFold, removeFold, countFold, edgeFold, setFold, multiInsertFold,
// appendFold, vectorFold, searchFold, spatialFold, skipFold: one concrete
// type each, each carrying exactly its own handler. No nil slots anywhere.
What this buys. The 11 nil any fields collapse to 0. The Kind FoldKind string discriminator disappears (the concrete type IS the discriminator). applyFold becomes a type switch with one typed case per variant — no reflect.ValueOf(nil) panic possible. Adding a new fold kind is adding one concrete type; the compiler tells you every switch that needs a new case.

5.2 · apply dispatch becomes a clean type switch

// Was: a 12-arm switch on fold.Kind (string), each arm calling a
// reflect.ValueOf(f.xxxHandler) with no nil guard.
// Now: a type switch on a sealed union, each arm fully typed.
func (s *Store) applyFold(ctx context.Context, q queryRuntime, f Fold, payload any) error {
    switch fold := f.(type) {
    case insertFold[any, any]:        // matched by interface, not generic args
        key, val := fold.invoke(payload)
        return s.mapSet(ctx, q, key, val)
    case updateFold:
        return s.applyUpdate(ctx, q, fold, payload)
    case removeFold:
        return s.mapDelete(ctx, q, fold.keyOf(payload))
    case countFold:
        return s.counterInc(ctx, q, fold.deltaOf(payload))
    // ... one case per variant. The compiler warns on a missed variant.
    case skipFold:
        return nil
    default:
        return fmt.Errorf("%w: %T", errUnknownFoldKind, f)
    }
}

5.3 · Single-source-of-truth Query with an erased projection

// QueryDecl stays the public generic type. It ALSO satisfies the planner
// interface directly — no twin queryRuntime, no 9-method queryMeta.
type QueryDecl[Q, R any] struct {
    Name        string
    Folds       []Fold
    ADT         ADT
    ReadPattern ReadPattern
    Config      QueryConfig
    // engine + complexity are assigned AT PLAN TIME and stored back here:
    engine      Engine
    complexity  Complexity
    foldByEvent map[string]int
}

// The planner takes []any and type-asserts to *QueryDecl — but the
// ERASED view it needs is just the methods it actually calls:
type plannerQuery interface {
    QueryName() string
    QueryADT() ADT
    QueryReadPattern() ReadPattern
    QueryConfig() QueryConfig
} // 4 methods, not 9 — ISP-respecting.

07Validation Layer

How the redesigned model makes invalid states unrepresentable — four concrete guarantees.

Guarantee 1: A Fold can never have a nil handler

The handler is a required field of each concrete fold type, set by the constructor On(). There is no Fold{} zero value that compiles into the pipeline — the zero value of insertFold has a nil invoke, but it can only be created by bypassing On() (unexported fields). The apply path's type switch never sees a half-built fold.

Guarantee 2: Kind/handler consistency is structural, not conventional

In the old model, Kind == FoldInsert ↔ insertHandler != nil was an undocumented convention. In the new model, "this is an insert fold" and "this has an insert handler" are the same fact — encoded by being the concrete type insertFold. You cannot express the inconsistent state.

Guarantee 3: Enum values are checkable at boundaries

adt.Valid() lets Plan() reject ADT("banana") at the boundary with a clear error, rather than letting it fall through to a generic O(N) default. The registry makes "did I handle every ADT?" a grep over one slice.

Guarantee 4: Units cannot be silently mixed

Nanoseconds + RatePerSecond is a compile error. The cost model's arithmetic (ops * nsPerOp / 1e6) becomes ops * float64(nsPerOp) with an explicit, reviewable conversion — not an implicit same-type addition of two conceptually-different floats.

08Decision Log

Why each design choice, with the rejected alternative.

Decision Rationale Rejected alternative
Sealed interface union for Fold (not a struct with a kind enum) Kills the 11 nil slots + the string discriminator. Type switch gives per-variant typing. Compiler flags missing cases. Tagged struct with kind int + one handler any. Rejected: still one optional field, still needs a runtime assertion, just moves the problem.
Pre-bound invoke closure (not per-call reflection) Captures E,K,V once at On() time. Zero reflect.ValueOf on the hot path. Preserves the inference elegance (handler signature still determines the ADT). Keep reflect calls, add nil guards. Rejected: treats the symptom (panic) not the cause (erasure + reflection on every event).
Keep engine layer as any (do not genericize backends) Consumer types are unknowable to a library. MapBackend must store arbitrary values. This erasure is inherent. Generic MapBackend[K,V]. Rejected: engines serve many collections with different K,V; a generic backend per collection is an explosion of type params with no static benefit.
Single QueryDecl[Q,R] with assigned fields (not a twin runtime) One source of truth. The planner reads via a narrow 4-method interface. No field-copy drift. Keep queryRuntime, add a constructor. Rejected: constructor reduces panic risk but the split brain and 9-method interface remain.
Store holds injected collaborators (not 17 inline fields) Each concern (poison, dedup, meter, subs) is testable alone and nil-safe to disable. Store methods shrink. Embed all trackers as anonymous fields. Rejected: promotes 17 fields into Store's namespace anyway; doesn't solve testability.
Branded unit types (Nanoseconds, not float64) Compile-time unit safety in the cost model. Cheap (type alias, zero overhead). time.Duration everywhere. Rejected: Duration is int64-nanoseconds; the cost model needs sub-nanosecond float precision for NsPerOp.
Enums stay string-backed with Valid() (not iota int) Strings serialize directly (SerializablePlan, diagnostics output). iota would need a String() + a separate wire format. The distinct named types already prevent cross-enum confusion. Migrate to iota for exhaustiveness. Rejected: loses zero-effort JSON serialization; the real gap (validation/registry) is fixable on string backing.

09Anti-Patterns to Avoid

Traps when adopting this redesign.

Do NOT genericize the engine backends

It is tempting to write MapBackend[K, V any] to "fix" C2. Resist it. An engine serves collections with different K,V types; a generic backend forces either type-erasure at storage (back to any) or a separate engine instance per collection (absurd). The erasure at the engine layer is inherent — fix the boundary (key validation in Store), not the engine.

Do NOT make Fold an open interface

The sealed fold() method is what keeps the union closed. If consumers could implement Fold themselves, the apply type switch would need a real default arm and exhaustiveness is lost. Keep fold() unexported — only On()/OnTyped() construct folds.

Do NOT remove reflection entirely

The fold-return-type-IS-the-ADT inference depends on reflection (classifySingleReturn inspects the handler's return type). Reflection for inference at declaration time is fine and fast (runs once). Reflection on the hot apply path (per event) is what the redesign eliminates. Don't conflate the two.

Do NOT brand every string

Collection names, event-type strings, and SQL column names are consumer-defined identifiers, not domain concepts. Branding them (type CollectionName string) adds ceremony with no safety — the consumer passes arbitrary strings either way. Brand where the type system adds real protection (units, IDs, enums), not where it just adds friction.

10Migration Roadmap

Incremental, each step independently shippable and testable. Pareto-ranked: C1 first (highest impact, kills a panic class).

1

Introduce the Fold interface + concrete types (C1)

Add type Fold interface { fold(); EventType() string; EventSample() any } and the concrete insertFold, updateFold, etc. Have On() return the new concrete types. Keep the old Fold struct temporarily as an internal adapter that satisfies the new interface. Update applyFold to a type switch. This is the single highest-value change — it eliminates the nil-panic class and the 11 reflect calls on the hot path.

2

Collapse queryRuntime into QueryDecl (H2)

Add assigned fields (engine, complexity, foldByEvent) to QueryDecl[Q,R]. Replace queryRuntime with *QueryDecl (type-erased via the new plannerQuery interface). Delete the field-copy in planQuery(). Delete the 9-method queryMeta.

3

Extract Store collaborators (H3)

Pull poisonTracker, idempotencyTracker, workloadMeter, subscriberHub out of Store into injected structs. Each gets its own test file. Store's field count drops from 17 to ~9. Do this one collaborator at a time to keep diffs reviewable.

4

Add enum validation + registries (H1)

Add Valid() to each enum family. Add a package-level registry slice per family. Add a TestEnumExhaustiveness test that asserts every switch in the package handles every registered value (grep-driven, like the project's existing guard tests). Call Valid() at Plan() entry.

5

Generic ScanResult[T] + branded units (M3, M4)

Parameterize ScanResult; alias ScanResult[any]/ScanResult[[]byte] at call sites. Introduce Nanoseconds, RatePerSecond, ItemCount branded types in the cost model. Low-risk, mechanical, but run the calibration benchmarks after to confirm no perf regression.

6

Boundary key-type validation (C2, the fixable half)

In Execute/ExecuteTyped, validate the extracted key's reflect.Type against query.keyType before dispatch. Returns a clear ErrKeyTypeMismatch instead of a silent wrong-collection read. Does not touch the engine layer (which stays any).

11Conclusion

metaengine's idea is superb: derive the storage plan from the relationship between events and queries, letting the fold return type be the declaration. Its execution of that idea carries one critical debt — the Fold god-struct — that a sealed interface union dissolves cleanly, plus a tractable set of high/medium issues around twin types, a god-object Store, and unvalidated enums.
