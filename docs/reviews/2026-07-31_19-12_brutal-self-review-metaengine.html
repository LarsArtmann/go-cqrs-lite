The Metaengine: 19,350 Lines of Ambition vs One Counter in Production

An honest audit of the cost-based storage planner module. It is labelled "THE STRATEGIC FUTURE" but its only real consumer uses it to count tasks by status. The core planner is solid; everything around it is ghost systems, split brains, and vision debt.

The one-sentence truth

The metaengine has a genuinely good cost-based planner core (per-query engine selection, ADT inference from fold signatures, degradation diagnostics, SQL pushdown, layout planning) buried under three ghost systems, four split brains, four missing vision features, and exactly one real consumer that uses it for a single counter. The integration work this session added stack.WithMetaEngine() — a lifecycle hook — but did not make metaengine serve a single real read model. It attached a side-store.

♦What Actually Works (preserve this)

+
Cost-based per-query engine assignment planner.go:153-220 genuinely scores every engine per query pattern and pins the cheapest. Pass 2+ engines and different queries land on different engines. This is the real innovation.
+
ADT inference from fold return types The planner infers Map vs SortedMap vs Counter from the Go function signature. Clever and correct — reduces declaration boilerplate.
+
Degradation diagnostics planDiagnostics() emits real DEGRADED/WARN levels when a pattern is served suboptimally. Matches the design vision exactly.
+
SQL pushdown + layout planning FilterOnField/SortOnField → SQLite json_extract() WHERE/ORDER BY pushdown, plus layout plans generating indexed DDL. ADR-0063/0073 delivered. Real 10x wins on filter+sort.
+
Cross-engine parity testing adttest.RunMatrix verifies memory↔sqlite↔pebble behavioral parity for all 7 ADTs. Plus fuzz tests, benchmarks, and the nextKey regression guard. Test discipline here is strong.
+
Zero-dependency core boundary The core planner is stdlib + database/sql only. Pebble and projection-bridge are separate modules. This is correct dependency hygiene.

01Ghost Systems (built, never consumed)

Three systems exist in the metaengine that duplicate richer, already-shipped modules. Each one reinvents a weaker version of something that already works.

Ghost #1

metaengine.GraphBackend reinvents the graph/ module (weaker)

metaengine/engine.go:213-215 · metaengine/memory_backends.go:60-105 · graph/graph.go:1-131

The metaengine ships its own GraphBackend doing BFS traversal in Go — basic adjacency lists. ADR-0061 honestly calls it "Basic." But the repo already has a full graph projection tier (graph/): GraphDriver, GraphSink, GraphProjection, transactional snapshot semantics, schema validation, openCypher MERGE portability, MemoryDriver + Neo4j/Memgraph driver abstraction, a real Read API (Query/Traverse/Neighbors/ShortestPath).

The metaengine's BFS-in-Go is strictly weaker. There is no ADR reconciling them. The design vision even proposes projection.Graph[Friendship] as if metaengine should own graph — yet graph/ already does, more richly. This is the clearest ghost.

Decision required: Either (a) delete GraphBackend and have the planner assign Graph ADTs to the graph/ module's driver, or (b) write an ADR documenting why a second graph system exists. Currently it is an undocumented duplication.
Ghost #2

FluentBuilder (dx.go) is dead code with a broken doc example

metaengine/dx.go:21,95-115

FluentBuilder (New(name).Fold(...).Filter(...).Build[Q,R]()) is a syntactic sugar layer over query.go's Query[Q,R]() constructor. It is never used by any consumer — grep finds matches only in dx.go itself and docs. Worse, its doc comment example (dx.go:21) shows a chained method call that would not compile (Build is a free function, not a method).

The fix: Delete FluentBuilder entirely. Query[Q,R]() with On()/FilterOnField()/SortOnField() is the real API and it is already documented in the README. Two declaration APIs for the same thing is a split brain.
Ghost #3

Two SSE implementations with overlapping logic, no reconciling ADR

metaengine/sse.go:17-21 · transport/http/sse.go:27-32

metaengine.ServeSSE and transport/http.SSEBroker both implement SSE with replay, dedup, heartbeat, and Last-Event-ID reconnection — independently. Their doc comments cross-reference each other and claim "intentionally separate — see ADR discussion on SSE consolidation." No such ADR exists. Grep of docs/adr/ finds nothing on SSE consolidation. This is a dangling promise asserted as a decision.

The fix: Write the missing ADR, or consolidate. Two implementations of the same protocol with shared concerns (replay, dedup, backpressure) is a maintenance liability.

02Split Brains

Split Brain #1

Two query layers coexist with no migration path

kv/view_store.go:18 · storage/view/store.go:102 · metaengine/store.go:26

The OLD query layer (kv.ViewStore, storage.SQLViewStore, storage.ViewMapper, stack.Materialize) and the NEW layer (metaengine.Store) are parallel, not layered. ADR-0061 deliberately makes metaengine not wrap SQLViewStore. The vision doc says the developer will write "No storage.ViewMapper… No kv.ViewStore" — i.e., the intent is replacement. But nothing migrates existing consumers.

The flagship example (taskmanager) registers both stacks to the same projectionhost, processing the same events twice. handleListTasks still does the O(N) load+filter that metaengine's filtered-scan is designed to eliminate. The migration hasn't started.

Split Brain #2: The "separate project" contradiction

The canonical design doc (meta-engine-project-definition.md) opens with: "The meta-engine is a new project. It is not a module within go-cqrs-lite. It is a standalone research-grade system." It lists 7 reasons why it must be separate (complexity, dependencies, audience, research nature, versioning, reusability, the "lite" in the brand).

It is a module in go-cqrs-lite. This session's integration work (stack.WithMetaEngine) doubled down on the contradiction by deepening the coupling rather than addressing it. Every "improvement" to the integration is a step further from the stated architectural boundary.

Split Brain #3

Two declaration APIs for the same thing

metaengine/query.go:139 · metaengine/dx.go:95

Query[Q,R](name, On(...), FilterOn(...)) and FluentBuilder.Build[Q,R]() build the same thing via different ergonomics. The README documents Query[]; the FluentBuilder is undocumented and unused. Two ways to do one thing.

Split Brain #4

TTL: declared hint, no engine honors it

metaengine/dx.go:370

WithTTL(d) now stores c.TTL = d.Nanoseconds() with a doc comment "actual expiration requires engine support (SQLite: background sweeper, Memory: lazy eviction)." No engine implements either. The value is stored and ignored. This is a documented dead hint, not a feature. Either wire it into one engine or remove it.

Scope creep trap (self-review Q8)

The 19,350-line module has accumulated features far ahead of proving its core value. Watchers, SSE, PrefetchCache, TieredStore, engine hot-swap, Export/Import, cost calibration, DOT graph visualization — all shipped before a single real read model is served by metaengine in the flagship example. We built ergonomics for a system nobody uses yet. The Pareto principle says: prove the core (cost-based multi-engine planning in ONE real app) before adding the 10th nice-to-have.

04Where Documentation Lies

Lie #1

SSE comments reference an ADR that does not exist

metaengine/sse.go:17-21 · transport/http/sse.go:27-32

Both files say "see ADR discussion on SSE consolidation." There is no such ADR. A reader trusting this comment would search docs/adr/ and find nothing. This is a fabricated reference.

Lie #2

FluentBuilder doc example does not compile

metaengine/dx.go:21

The comment shows .Build[FindUser, UserView]() as a chained method, but Build is func Build[Q,R](b *FluentBuilder) — a free function taking the builder as an argument. The documented usage is invalid Go.

Lie #3

TTL documented as needing "engine support" that will never come

metaengine/dx.go:368-374

The comment names SQLite "background sweeper" and Memory "lazy eviction" as the implementation paths. Neither exists, neither is planned in any ADR or TODO. This reads like a feature with a roadmap; it is a stored int64 that nothing reads.

Lie #4

README omits dx.go, Watcher, ServeSSE entirely

metaengine/README.md (241 lines)

The README documents Query[]/Plan()/ExecuteTyped (correct), but Watcher, ServeSSE, SSEReplay, FluentBuilder, and the 7 optional backend interfaces (MapBackend, RawValueReader, etc.) are invisible. Shipped features with zero discoverability.

05Testing Gaps

What is tested well

Cross-engine parity (adttest.RunMatrix), pebble engine (fuzz + benchmarks + regression guards), pushdown paths, layout planning, cursor pagination, concurrency. The test discipline in the engine/planner layer is genuinely strong. This is worth preserving.

Gap #1

No test that stack.WithMetaEngine serves a real query through a preset

integration/metaengine_test.go

The integration test manually constructs the store + adapter. It never calls sqlite.New + WithMetaEngine + bundle.MetaEngine() end-to-end. The WithMetaEngine → bundle.MetaEngine() → projectionadapter path is only exercised in the taskmanager example, not in a test module. The integration work this session claimed to close this gap but didn't.

Gap #2

No multi-engine distribution test

metaengine/planner_test.go

No test proves that passing 2+ engines to Plan() actually splits different query collections across different engines. The per-query selection logic exists (planner.go:165-202) but there is no assertion test showing "query A on engine X, query B on engine Y." The headline feature is untested at the integration level.

Gap #3

No real-app benchmark (metaengine serving a real read model)

benchkit/phases_metaengine.go

The benchkit phase benchmarks a private synthetic counter store, not the consumer's actual metaengine. It measures "planner overhead ceiling," which is defensible, but it does not measure what a consumer experiences. There is no benchmark of metaengine serving a filtered scan on a real projection.

06The 11 Brutal Questions

1. What did you forget?

The design doc says this should be a separate project. The integration work deepened the coupling instead of addressing the contradiction. We forgot to question whether stack.WithMetaEngine is even the right direction.

2. What is stupid that we do anyway?

Registering two parallel projection stacks (old kv.ViewStore + metaengine) to the same host in the taskmanager, processing every event twice, while only one of them serves real reads.

3. What could you have done better?

Instead of stack.WithMetaEngine, migrate one real read model in the taskmanager from kv.ViewStore to metaengine. Prove the value with a working filtered-scan query, then wire the lifecycle hook.

4. What could you still improve?

Auto-denormalization (missing), Declare[] API (medium gap), generated typed reads (large gap), operator config (missing), plugin registry (missing). Pick the one that unlocks the most real consumers.

5. Did you lie to you?

Yes. The SSE "ADR discussion on SSE consolidation" does not exist. The FluentBuilder example does not compile. TTL is documented as needing "engine support" that no engine provides and none will.

6. How can we be less stupid?

Decide the query-layer question in an ADR: is metaengine replacing or coexisting with kv.ViewStore? Then act on it. Undecided architecture is the root of all the split brains.

7. Ghost systems?

Three: GraphBackend (reinvents graph/), FluentBuilder (dead, broken example), and the second SSE impl (overlaps transport/http.SSEBroker). See Ghost Systems.

8. Scope creep trap?

Yes. 19,350 lines of features (watchers, SSE, prefetch, tiering, hot-swap, export, calibration, DOT graphs) shipped before one real read model is served. Ergonomics for a system with no users.

9. Did we remove something useful?

No. The risk is the opposite: we keep adding without consolidating. The previously-broken items (transactions, tiering, watcher wiring) were fixed in later sessions — that was good.

10. Split brains?

Four: two query layers (no migration path), "separate project" vs module, two declaration APIs, TTL hint vs no engine. See Split Brains.

11. How are we doing on tests?

Engine/planner layer: excellent (parity, fuzz, benchmarks, regression guards). Integration layer: weak (no preset end-to-end test, no multi-engine distribution test, benchkit benchmarks the wrong store).

07Improvement Plan (Pareto-sorted)

Sorted by impact ÷ effort. Each step is small and self-contained.

Tier 1 — Strategic decisions (unblock everything)

1

Write ADR: query-layer migration path

Decide whether metaengine replaces or coexists with kv.ViewStore/storage.SQLViewStore. This single decision unblocks the taskmanager migration, the graph reconciliation, and the "separate project" question. Without it, every improvement is ambiguous.

2

Write the missing SSE consolidation ADR (or remove the comment)

The dangling "see ADR discussion" reference is a lie. Either write the ADR documenting why two SSE impls exist, or delete the comment and consolidate. Low effort, high trust payoff.

Tier 2 — Eliminate ghost systems

3

Delete FluentBuilder (dx.go) — dead code, broken example

Zero consumers. Query[Q,R]() is the documented API. Removing it eliminates split brain #3 and fixes lie #2 in one edit. Low effort, zero risk.

4

Reconcile GraphBackend vs graph/ module

Either delete GraphBackend and delegate Graph ADT planning to the graph/ driver, or write an ADR. The current state (undocumented weaker duplicate) is the worst option.

5

Migrate ONE real read model in taskmanager to metaengine

Move handleListTasks from mat.List() + Go-side filter to a metaengine filtered-scan query. Remove the parallel projection registration. This proves the value and removes the stupidity of processing every event twice.

Tier 3 — Close integration gaps

6

Add multi-engine distribution test

Test that Plan([engineA, engineB], ...) assigns different query collections to different engines. Assert "query A → engineA, query B → engineB." The headline feature needs a headline test.

7

Add preset end-to-end integration test

sqlite.New(dsn, sqlite.WithStack(stack.WithMetaEngine(store))) → bundle.MetaEngine() → projectionadapter → real query. Close the gap the session claimed to close but didn't.

Tier 4 — Vision alignment (decide or remove)

8

Either wire TTL into one engine or remove it

A stored int64 that nothing reads is a lie. Wire a Memory lazy-eviction or delete the option. Do not ship documented dead hints.

9

Update vision docs to reflect reality (or vice versa)

The design docs describe Declare[], store.Users.ByStatus(), operator YAML, plugin registry, auto-denormalization — none of which exist. Either build them or mark the vision docs as "aspirational, not current API" so readers aren't misled.

10

Document dx.go features (Watcher, ServeSSE) in README or remove them

Shipped features with zero README presence are invisible. If they are real, document them. If they are exploratory, move to a branch.
