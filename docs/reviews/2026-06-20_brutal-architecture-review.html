Your "Lightweight" CQRS Library Is Eating Itself

40 KLOC of Go pretending to be a library while morphing into a framework, a docs empire, a benchmark suite, a static-site generator, and a WASM demo. The code is competent. The architecture has lost the plot.

The Short Version

  • The one-paragraph verdict

  • 1 CI gate that silently never fires

00The Verdict

You can absolutely program. You can't absolutely stop.

The Go on display here is genuinely good: interface segregation done right (EventSink/EventSource/Journal/SeekableJournal), typed handlers, branded IDs via id.Of[T], real OpenTelemetry, decent error taxonomy, property-based tests, golden tests, integration tests against a real Postgres container. The unit of code quality is high.

The problem is everything around the code. The repo is a case study in compulsive scope expansion: every interesting thought becomes a module, every proposal becomes 5 versions of a markdown file, every CI gate is added with a || true escape hatch so it can never fail, every architectural rule is documented and then quietly broken. You're not building a library any more — you're building a monument to the idea of a library, and the monument is heavier than the library it commemorates.

The real bug is not in any .go file. It's the absence of a discipline that says "no". Every shiny object gets added. Nothing gets removed. Every release grows the public API surface (1351 → 1784 → 1852 exports in three releases) without removing anything, and the docs grow 3× faster than the code. This is how libraries die — not from bugs, but from becoming unmaintainable through their own ambition.

142,759 lines of markdown for 40,297 lines of production Go. That's a 3.5× documentation-to-code ratio. For comparison, the Go standard library ships roughly 1× doc-to-code. The Linux kernel is well under 0.5×. You are writing about the library more than you are writing the library.

02Did We Lie? Yes. Three Times.

Rule #5 in your own AGENTS.md says "Challenge instructions and tool output — both can be wrong, contradictory, or nonsensical." So let's apply that to AGENTS.md itself.

Lie #1

"30 modules (24 library + 1 integration + 3 examples + 2 cmd)"

AGENTS.md · Monorepo Structure section

Lie #2

"No any types (except dialect.go for database/sql interop)"

AGENTS.md · Design Principle #9

Actual count of any usages outside dialect.go (excluding generic [T any] syntax which is forced by Go): 165 runtime any positions. Examples that violate the literal rule:

Some of these are legitimate (codec interfaces, generic dispatcher boundaries). But the rule as written is false. You don't get to claim a strict-typing principle and then ship 165 exceptions to it. Deeper issue query.Handler returning any is the single biggest type-safety hole in the library. Every Dispatch caller has to type-assert the result and silently lose compile-time guarantees. This is what query.TypedHandler[Q, R] was supposed to fix — and it exists, but the untyped Handler is still the primary registration path documented in AGENTS.md.

04Split Brains

Split Brain #1

memory/v2 published as v2.6.0 but pinned as v2.5.0 in 11 consumer modules

command/, decider/, event/, integration/, listing/, middleware/, projection/, query/, schema/, stack/bench/, watermill/

Commit 6bcd5543 ("chore(deps): bump monorepo internal module versions to v2.6.0") bumped every sibling module except memory in those 11 consumers. 05CI Theater: Gates That Look Like Gates But Aren't

Theater #1 · Critical

file-size-gate is structurally incapable of failing

.github/workflows/ci.yml · file-size-gate job
failed=false
find . -name "*.go" ... | while read -r f; do
  if [ "$lines" -gt 350 ]; then
    echo "::warning::$f has $lines lines (max 350)"
    failed=true   # ← runs in a SUBSHELL because of the pipe
  fi
done
if [ "$failed" = true ]; then exit 1; fi
# ↑ $failed is always false here. Gate ALWAYS passes.

find … | while read runs the while loop in a subshell. The failed=true set inside never propagates back to the parent shell. I reproduced this exactly with sh -c '…' on this repo: 7 violations found inside the loop, $failed=false after the loop, exit 0. This gate has never fired in the history of the project. Every PR that added a 400-line file passed CI.

Fix Use process substitution so the loop runs in the parent shell: while read -r f; do …; done < <(find …). Or just write the loop in Go.
Theater #2 · Critical

gosec runs with -no-fail

.github/workflows/ci.yml · gosec job
gosec -fmt sarif -out gosec.sarif -no-fail ./event/... ./command/... ...

-no-fail means gosec returns exit 0 even if it finds critical vulnerabilities. The SARIF is uploaded to GitHub for display, but the job itself can never fail the build. So a SQL injection or hardcoded secret would surface as a nice yellow badge in the GitHub UI and ship anyway.

Theater #3

nix run .#vulncheck and nix run .#secrets-scan have || true

flake.nix · apps.vulncheck, apps.secrets-scan
${goPkg}/bin/go vet -vettool=$(which govulncheck) 2>/dev/null || true
(cd "$mod" && GOWORK=off ${goPkg}/bin/go list -json ./... \
  | ${pkgs.govulncheck}/bin/govulncheck -mode=source 2>/dev/null || true)
${pkgs.gitleaks}/bin/gitleaks detect --source . --no-banner --no-git 2>/dev/null || true

Both apps end with || true and are not wired into CI as jobs at all. So even if you run them locally, they print a green checkmark regardless of findings. This is performative security — you have the tools installed, you have the apps defined, but you have carefully arranged that they cannot inconvenience you.

Theater #4

Benchmark regression check uses ::warning:: not ::error::

.github/workflows/ci.yml · benchmark job

A benchmark that regresses >2× vs baseline produces a GitHub annotation, not a failure. Performance regressions ship. Combined with the fact that benchmark-baseline.txt is committed to the repo and updated by hand, the gate is both toothless and easy to gaslight (just commit a new baseline).

A "lightweight CQRS library" should be CQRS primitives. You have built:

The YAGNI question

How many consumers does each peripheral module actually have?

You don't know, because none of this is published to a package registry that reports download counts and you don't have a single real consumer in this repo (which is correct for a library). But ask honestly: how many people are importing turso/indexing/advisor? How many need the catalog docserver? How many want the AsyncAPI exporter specifically? You built all of these on speculation.

The cost Every peripheral module is a public API surface you have to maintain forever at v2 semver. The catalog module alone exports ~150 symbols. Every breaking change to event/ cascades into a coordinated release of 39 modules. You are paying maintenance interest on capabilities that have never been validated by a single user.

08Type Model: Where It Hurts

Type Hole #1

query.Handler returns any — by design

query/dispatcher.go:27
// The return type is `any` because a single dispatcher handles heterogeneous query types
type Handler = func(context.Context, Query) (any, error)

func (d *Dispatcher) Dispatch(ctx context.Context, query Query) (any, error)

// And the typed escape hatch:
func DispatchTyped[R any](ctx context.Context, d *Dispatcher, q Query) (R, error) {
    // internally does an unsafe type assertion on the any
}

The honest comment ("The return type is any because…") is good — at least the lie is documented. But the result is that every consumer either uses DispatchTyped (and pays a runtime type assertion plus an allocation) or re-implements the assertion themselves. This is exactly the failure mode your "Strong types — make impossible states unrepresentable" principle warns against.

The root cause is that Dispatcher is a single registry for heterogeneous query types, which forces the return type to be the LUB of all of them — any. That's a real design tension, not a typo. The honest fix is to admit that the untyped Dispatcher is a convenience layer and make TypedHandler[Q, R] the documented primary path, with the any-returning form deprecated or hidden. Right now both are equally first-class, and the docs lean on the unsafe one.

Type Hole #2

schema.Validator stores map[event.Type]func(any) error

schema/validator.go:35–36, 65, 95

The validator type-erases the payload to any, validates it, and the caller has to round-trip it back. RegisterType[T]() papers over this at registration time (ADR-0017), but the stored map still type-erases. There is no way to recover the original T from the validator, so consumers can't get a typed payload out — they have to re-decode.

Type Win

The branded ID work is genuinely good

id/

type Of[T any] = cbid.ID[T, ulid.ULID] with phantom markers (UserMarker, CorrelationMarker, etc.) is the correct pattern. The tradeoff — depending on your own external go-branded-id library — is debatable (the how-to-golang skill recommends go-composable-business-types instead, and yours has zero external consumers that aren't you), but the type-level design is solid.

10What Did We Forget?

Forgotten #1: A real consumer

This repo has 39 modules and 3 example apps, none of which exercise the library the way a real user would. example/todo is the closest, but it's grown into a parallel codebase (its own cmd/api/main.go with a 172-line run(), its own projections, its own Dockerfile) that's testing the example, not the library. There is no "minimum realistic consumer" that catches API papercuts before they ship.

Forgotten #2: A deprecation policy

1,852 exported symbols. CHANGELOG.md is 517 lines and every entry is "Added" or "Changed". Zero "Deprecated" / "Removed" entries. The library has never removed anything. The public API only grows. At some point you'll want to clean up the any-returning query.Handler, or the unwired prometheus/ module, or the redundant StreamLoader leftovers — and there is no policy, no deprecation cycle, no tooling for doing it safely.

Forgotten #3: A release discipline

740 commits in June 2026 alone (3 weeks, ~50 commits/day, 1 tag every ~25 commits). The bump commit 6bcd5543 (which missed memory in 11 modules) shows the cost: version coordination across 39 modules is hand-edit go.mod files. There is no release script, no go work sync wrapper that catches version drift, no automated check that all sibling-module versions agree. check-replace-directives.sh validates paths but not versions.

Forgotten #4: Multi-tenant / auth / security story

The library has signing, encryption, OTel — but no guidance on multi-tenant key derivation boundaries, no example that wires signing + encryption + multi-tenant context together. The HKDF example in AGENTS.md is one line. For a library that ships crypto modules, the security story for actual deployment is thin.

♦Honest Strengths (Don't Lose These)

A brutal review that doesn't acknowledge what works is just whining. These are genuinely good and should be preserved:

+
Real Postgres in CI Not a mock — an actual postgres:16-alpine container with -tags=integration tests for LISTEN/NOTIFY round-trip. This is rare and valuable.
+
Property-based tests with pgregory.net/rapid Not just table-driven happy paths. The channel-name validation in stack/postgres has 3 properties × 100 inputs. Real invariant testing.
+
Interface segregation on stores EventSink / EventSource / Journal / SeekableJournal / BackwardsSource — consumers depend on the narrowest interface they need. This is textbook ISP done correctly.
+
Zero lint violations across 34 modules Reproduced: nix run .#lint returns "0 issues" for every module. Not "0 warnings we care about" — actually zero. Real discipline.
+
Defensive cloning on all public accessors Payload(), Metadata(), EventTypes(), MultiSignature.Get() all clone on read. The contract is documented. This is correct concurrent-Go hygiene that most libraries skip.
+
Hot-path zero-allocation discipline is real Lazy map init, pre-computed middleware chains, cached SQL templates, batch inserts with SQLite 999-param chunking, projection event-type caching. Not aspirational — measured and benchmarked.
+
Per-module dependency budgets enforced in CI scripts/check-module-layers.sh actually fails the build when a module exceeds its DEP_BUDGET. This is more than most Go projects have.
+
Singleflight load coalescing in decider.Repository Concurrent Load calls for the same aggregate coalesce into one store query, and the safety argument (immutable *ImmutableEvent) is correct and documented.
+
Build / vet / test / race / lint / coverage / per-module / layer / replace / docker / postgres-integration — CI is broad 10 distinct CI jobs. The bones of CI are excellent. The problems are in individual gates (see §05), not in coverage of concerns.
+
Branded IDs with phantom types type UserID = id.Of[id.UserMarker] makes UserID and OrderID compile-time distinct even though both are ULIDs. Impossible states made unrepresentable — exactly what the principle asks for.

♦The Bottom Line

You can absolutely program in Go. The code quality on a per-function, per-test, per-interface basis is in the top decile of open-source Go I've reviewed. The interface segregation, the cloning discipline, the property tests, the real Postgres in CI, the dependency budgets — these are not beginner moves. But you cannot stop, and that is the bug. Every release grows the public API. Every interesting thought becomes a module. Every proposal becomes 5 versions. Every CI gate is added with an escape hatch. Every architectural rule is documented and then broken. The library has not said "no" to itself in a long time, and that is the single most dangerous failure mode for a piece of software that ships a public API.

The 14-item plan above is small. None of it is "rewrite the world". The hardest item is 2 hours of work. The total time to clear the dashboard's red cards is probably a long weekend. Do it before the next release — because the release after that will add another module, another docs section, another 50 exports, and the gap between the library you have and the library you think you have will be wider still.
