01What Did I Forget?

Health score computed on filtered findings

main.go:275 passed activeFindings (post severity/confidence filtering) to ComputeHealthScoreWithCap. This meant --min-severity error --health-score would give a misleadingly high score because warnings/info were excluded from the computation. The health score should be a stable project-health metric independent of display filters.

Root cause: The health score was wired into the wrong stage of the pipeline — after display filtering instead of after suppression filtering.

InfoCapped display used hardcoded constant

output.go:139 displayed defaultInfoDeductionCap (the constant 20) instead of the actual configured cap. If a consumer set {"health": {"info-cap": 15}}, the display still said "capped at -20". The HealthScore struct didn't carry the cap it was computed with.

No integration test for suppression end-to-end

The suppression leak bug survived 2 releases because no test verified the full path: detect → suppress → filter → output. Unit tests tested the filter function in isolation, but no test verified that a suppressed finding was actually excluded from the final output and health score.

scanner.Err() was silenced, not handled

_ = scanner.Err() silenced the lint warning but didn't help users debug missing suppressions. A scanner error means suppression comments might be missed, and the user had no visibility into this.

02What Is Stupid?

Health score depending on display filters

This is architecturally wrong. Health = project quality metric. It should not change based on what you choose to display. The score should see ALL unsuppressed findings regardless of severity/confidence thresholds.

renderHealthScore reaching into a package constant

The display function referenced defaultInfoDeductionCap directly instead of receiving the data it needed. This is a violation of dependency injection — the function should be self-contained given its input struct.

filterSuppressed discarded suppressed findings

It returned (active, count) — the suppressed findings were thrown away. This meant there was no way to audit suppressions without re-scanning source files. The doctor command had a separate countSuppressions function that re-parsed ASTs, creating a potential split brain.

06Type Model Improvements

HealthScore now carries the cap it was computed with

Added InfoCapApplied int to the HealthScore struct. This makes the struct self-describing — the display function no longer needs to reach into a package constant. This is the "make impossible states unrepresentable" principle applied to display data: the struct carries everything needed to render it correctly.

filterSuppressed returns both active and suppressed slices

Changed from ([]Finding, int) to (active, suppressed []Finding). The suppressed findings are retained rather than discarded, enabling the --show-suppressed feature without a second pass. This eliminates the split brain between filterSuppressed and countSuppressions in doctor.go.

Extracted shouldExitWithError as a testable function

The exit-code decision was inline in run(), making it untestable without loading Go packages. Now it's a standalone function that both run() and tests can call. This follows the principle of separating decision logic from I/O logic.

07Did I Lie?

No, but the prior session's "all green" was hiding real issues

The prior session claimed all verification gates were green. They were — but the gates only test what's tested. The health score bug, the InfoCapped display bug, and the missing integration test were all invisible to the test suite. "All tests pass" is not the same as "the code is correct." The tests were green because they didn't test the invariants that were broken.

Lesson: A test suite that passes on broken code is not a green test suite — it's a blind one. The suppression bug survived 2 releases because the tests tested the filter function in isolation but never verified the end-to-end path. Integration tests are not optional for trust-critical features.
