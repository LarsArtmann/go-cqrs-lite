API Design

Improvements to the library's public interface that reduce friction for consumers.

CQ-1

Extend DecideFunc return to carry domain metadata

Breaking · v3

The current DecideFunc returns ([]Event, error) — no way for the decider to communicate domain semantics back to the caller. Consumers like go-localsync need to know what happened (created, updated, conflict, unchanged) to classify results. The current workaround is a countingDecide hack that reverse-engineers intent by counting events and checking state — fragile and couples to implementation details.

decider/decider.go :85 (DecideFunc type) decider/decider.go :98–155 (Execute method)
Current (v2)
type DecideFunc[State any] func(
  state State,
  currentVersion event.Version,
) ([]event.Event, error)
Proposed (v3)
type DecideResult struct {
  Events []event.Event
  Annotations map[string]any
}

type DecideFunc[State any] func(
  state State,
  currentVersion event.Version,
) (*DecideResult, error)
1

Introduce DecideResult struct alongside DecideFunc. The Annotations map lets consumers carry arbitrary domain metadata (e.g., "action": "created", "conflict_winner": "remote") without the library needing to understand domain semantics.

2

Expose Execute result. Change Repository.Execute to return (*DecideResult, error) instead of error. This is a breaking change — requires v3 bump. The benefit: consumers get their domain metadata back without hacks.

3

Backward-compatible shim for v2. In the short term, add an ExecuteWithResult method that returns (*DecideResult, error) while keeping Execute returning error. This lets consumers opt-in without a v3 bump.

Consumer impact: go-localsync's countingDecide hack (stack.go:189–212) and classifyAction (stack_adapters.go:12) become unnecessary. Domain semantics flow through the library's own return type instead of being reverse-engineered.

All decider consumers

CQ-2

Projection runner replay-to-live event gap

Event Loss Window

After replay() completes and before subscribeLive() takes effect, events published to the bus are silently missed. The runner does replay → live sequentially with no atomic handoff. Under load or with slow projections, this window is real and causes projection drift.

projection/runner.go :116–124 (replay → subscribeLive) projection/runner_live.go :subscribeLive
replay() → checkpoint saved
← gap: events published here are LOST →
subscribeLive() → processing events
1

Subscribe to bus before replay starts. Use a buffering subscriber that queues events without processing them. This ensures no events are missed during the replay phase.

2

After replay completes, drain the buffer and switch to live processing. Skip any buffered events whose ID ≤ last replayed event ID (idempotent deduplication). This is the "catch-up subscription" pattern used by EventStoreDB, Kafka, and PostgreSQL logical replication.

3

Add an integration test. A test that publishes events during the replay-to-live transition window and verifies the projection processes all of them. This is the key correctness proof.

Consumer impact: go-localsync's startProjectionRunner (runner.go:12) would benefit immediately — the projection runner is the backbone of read model consistency.
Impact
All projection users

4–6 hours

Medium (concurrency)
CQ-3

Middleware applied at Register time, not Dispatch time

Surprise Behavior

In the dispatcher package, middleware is baked into each handler at Register() time. Adding middleware after registration has no effect on already-registered handlers. This is documented but surprising — consumers expect middleware to apply globally regardless of registration order.

dispatcher/dispatcher.go :Register (middleware applied here) command/dispatcher.go :44 (Use method) query/dispatcher.go :44 (Use method)
1

Document the contract prominently. Add a package-level doc comment on dispatcher, command, and query that states: "Middleware must be added before calling Register. Middleware added after Register has no effect on existing handlers." Add a log warning in debug mode if Use is called after any Register.

2

Long-term: defer middleware application to dispatch time. Instead of wrapping the handler at registration, store the middleware chain separately and apply it at dispatch time. This is a larger refactor but removes the surprise entirely.

Impact
All dispatcher users
Effort
Doc: 30 min · Fix: 3 hr
Risk
Low (doc) · Medium (refactor)

CQ-4

listing/ has no SQL-backed AggregateReader

Production Blocker

The listing module only has InMemoryAggregateReader backed by an in-memory cache of the event journal. For production use (SQLite, PostgreSQL), consumers must implement their own AggregateReader. The docstring mentions SQLAggregateReader but it doesn't exist yet.

listing/in_memory.go :InMemoryAggregateReader listing/aggregate_reader.go :12 (AggregateReader interface)
1

Add SQLAggregateReader in listing/. Backed by a pre-computed aggregates table (populated by projection). Supports the same List/ListWithStatus interface with cursor-based pagination. Reuses the existing storage dialect abstraction for PG/SQLite compatibility.

2

Add a projection that maintains the aggregates table. Similar to how go-localsync maintains a sync items table. The StatusMiddleware already handles tombstone detection — the SQL reader just needs a table to read from.

Impact
listing module users
Effort
4–5 hours
Risk
Low (new code)
CQ-5

BatchProjection interface unused by Runner

Dead Interface

event.BatchProjection interface exists but the projection.Runner processes events one-by-one via Handle. The HandleBatch path is unimplemented. This means high-throughput projections can't benefit from batch processing (e.g., bulk SQL inserts).

event/projection.go :BatchProjection (interface) projection/runner.go :handleAndCheckpoint (single event)
1

Add batch processing in the runner. After replay or during live subscription, accumulate events up to a batch size or flush interval, then call HandleBatch if the projection implements BatchProjection. Fall back to single-event processing for regular Projection implementations.

2

Add WithBatchSize option to the runner. Default to 1 (backward-compatible). Consumers opt into batch processing explicitly.

Consumer impact: go-localsync's SQLite read model could use batch upserts instead of per-event inserts during replay — significant performance improvement for large datasets.

CQ-6

query/ imports event/ for error wrapping — unnecessary coupling

Layer Violation

The query dispatcher wraps errors using event.WrapInfrastructure from the event module. This creates an unnecessary dependency of the read-side (queries) on the write-side (events). The query module should use go-error-family directly, like it does in some places already — the usage is inconsistent.

query/dispatcher.go :import (event import) query/go.mod :event dependency
L1
event command query
query → event = unnecessary coupling on same layer
1

Replace event.WrapInfrastructure with direct errorfamily.NewInfrastructure calls in query's dispatcher. Remove the event import. If there are other event references, audit and remove them.

2

Update query/go.mod to remove the event dependency. Run nix run .#check-layers to verify the layer graph remains clean.

CQ-7

Dual pagination models with no bridge

Cohesion

Two pagination types exist with no shared abstraction: query.Pagination (offset-based, Page + PageSize) and listing.Page[T] (cursor-based, After cursor). Both live in the same library but serve different use cases with no documentation explaining when to use which, and no adapter to convert between them.

query/pagination.go :Pagination (offset) listing/types.go :30 (Page[T] cursor)
query.Pagination
type Pagination struct {
  Page     int
  PageSize int
}
// Offset-based → human UIs
// Supports jump-to-page
listing.Page[T]
type Page[T any] struct {
  Items   []T
  HasMore bool
}
// Cursor-based → append-only streams
// No total count (correct for logs)
1

Document the decision criteria. Add a package-level doc to both query and listing explaining when to use each: offset-based for user-facing paginated UIs, cursor-based for event streams and aggregate listings.

2

Consider a shared pagination sub-package. If both models are needed in the same application, a shared package with clear naming (OffsetPagination vs CursorPage[T]) reduces import confusion. Low priority — both models are correct for their use cases.

Developer experience
