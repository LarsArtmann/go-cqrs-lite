07Verification protocol

1

Read-only reviewers

Reviewers never build or test. Every finding carries file, line and quoted evidence and a confidence of verified, likely or speculative.

2

Source verification before any fix

Only findings re-verified at source by a second reader (or by the orchestrator) are fixed or reported as problems.

3

Fix receipts

Each fix gets a failing-then-passing test where feasible, plus the owning module's suite in workspace mode (GOWORK=off is blind until the release wave lands).

4

Gates

API golden regen on any surface move, package-surface, file size, scoped lint, doc-check, canonical facts, md-go, changelog symbols, docs-gates audit.

5

Report integrity

HTML parse, anchor cross-check, leftover-marker grep, every scorecard number recounted from the findings files.

08Risks

Release wave in flight

Pins on master point at untagged siblings. Nothing GOWORK=off can be tidied or proven until the owner cuts the wave; verification runs in workspace mode and says so.

Library surface

Removing or reshaping exported API is breaking for the fleet. Fixes stay additive or behavior-preserving on the v4 train; core/v5 is in its free window.

Loaded machine

Load average around 60 on 32 cores during research. Heavy gates run one at a time; reviewers only read.

Reviewer false positives

Hundreds of reviewer findings will include noise. The source-verification pass is mandatory before anything reaches the report or the tree.
