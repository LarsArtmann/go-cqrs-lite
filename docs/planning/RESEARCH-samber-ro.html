samber/ro — Reactive Streams
for go-cqrs-lite?

Can samber/ro replace our hand-rolled bus/ and dispatcher/? A detailed comparison of what it is, where it fits, and where it doesn't.

go-cqrs-lite 2026-05-29 status: research
01

What is samber/ro?

samber/ro is ReactiveX for Go — push-based, composable, type-safe streams. The core abstraction is Observable[T]: a lazy sequence of values that observers subscribe to. Values flow through operator chains (Map, Filter, Scan, Retry, etc.) instead of imperative callbacks.

Core types

Type What it does Our equivalent
Observable[T] A stream of values. Lazy — nothing happens until subscribed. None (closest: our Bus is eager)
Observer[T] Receives Next/Error/Complete notifications from an Observable. event.Handler
Subject[T] Both Observable and Observer. Multicasts to subscribers. MemoryBus (hand-rolled)
PublishSubject Emits only values after subscription. Our MemoryBus behavior
BehaviorSubject Replays last value to new subscribers. None (projection catch-up is manual)
ReplaySubject Replays last N values to new subscribers. None (journal replay is manual)
Subscription Lifecycle: Unsubscribe, cleanup teardowns. io.Closer on Bus

Key operators (the ones that matter for us)

Operator What it does Our current approach
Filter[T](fn) Only pass events matching predicate Subscribe(eventType, handler) — type-based only
Map[T,R](fn) Transform each event Middleware chain
Scan[T,R](fn, seed) Accumulate state across events (fold!) decider.Fold — but only on load, not live
Merge / Concat Combine multiple streams Manual goroutine wiring
Retry[T](n) Retry on error middleware.Retry — custom implementation
Timeout[T](d) Fail if no value within duration None (would need scheduler)
Catch[T](fn) Recover from errors with fallback stream middleware.Recovery
02

The three modules — what each actually is

dispatcher/ ours

A synchronous handler registry. map[string]H + middleware chain + closed flag. Register handlers by type name. Look up. Call. Return.

Pattern: Mediator / Command Dispatcher
Used by: command/, query/
Lines: 247

bus/ ours

In-process event pub/sub. Subscribe to event types. Publish events. All subscribers get notified. Essentially a hand-rolled PublishSubject[Event].

Pattern: Observer / Pub-Sub
Used by: event/, projection/, outbox/
Lines: 58 (interface) + 218 (MemoryBus impl)

samber/ro external

ReactiveX streams. Observable → operators → Observer. Lazy, composable, context-aware. Push-based with backpressure. 40+ plugin ecosystem.

Pattern: Reactive Streams (Rx)
Used by: Nothing yet
Size: Full framework

03

Fit analysis — where ro helps, where it doesn't

❌ dispatcher/ — NO FIT

Our dispatcher/ is a synchronous handler lookup: register by type name, dispatch, get result. samber/ro is async push-based streams. These are completely different patterns.

dispatcher/ does samber/ro does
Register("UserCreated", handler) ≠ No registry concept
Dispatch("UserCreated") → handler ≠ observable.Subscribe(observer)
Synchronous: call handler, return result ≠ Async: push values over time

Verdict: Keep dispatcher/ as-is. It's 247 lines of focused handler registry code. ro doesn't replace it.

✅ bus/ — STRONG FIT

Our bus/ is conceptually a Subject[Event]. MemoryBus is a hand-rolled PublishSubject. The mapping is direct:

Our bus/ interface samber/ro equivalent
Publisher.Publish(events) → subject.Next(event)
Subscriber.Subscribe(type, handler) → observable.Filter(byType).Subscribe(observer)
Subscriber.SubscribeAll(handler) → observable.Subscribe(observer)
Bus.Use(middleware) → ro.Pipe(observable, ro.Map(fn))
Bus.UsePublish(middleware) → ro.Pipe(source, ro.Map(fn), subject)

What we gain:
BehaviorSubject — new subscribers get the last event (projection catch-up for free)
ReplaySubject — new subscribers get last N events (replaces manual journal replay)
Operators — Filter, Map, Scan, Retry, Timeout replace hand-written middleware
Context propagation — built-in, not bolted on
Backpressure — natural flow control instead of unbounded channels
Composability — ro.Pipe(source, filter, retry, map, subscribe) instead of bus.Use(a); bus.Use(b); bus.Use(c)

⚠️ What we'd lose or need to rework

Concern Impact Mitigation
Type-based subscription ro has no built-in "subscribe by event type" — it's just Filter Wrap as a convenience: SubscribeType(observable, "UserCreated")
Ordered delivery ro's Merge is non-deterministic ordering Use Concat for ordered, or single-subject for per-aggregate ordering
Interface simplicity Our Bus is 4 methods. ro is a full framework. Define our own thin interfaces backed by ro internally
Existing middleware middleware/ has 8 event middlewares that wrap event.Handler Rewrite as ro operators (or keep our Bus interface, use ro as MemoryBus impl only)
External dependency ro is a large dependency for what might be a thin wrapper Accept it (we already depend on otel, watermill, etc.) or cherry-pick patterns
04

Three possible approaches

Option A: Full replacement — bus/ becomes ro

// event distribution becomes reactive streams
type EventBus = ro.Subject[Event]

// subscribe to a specific event type
userEvents := ro.Pipe(
  bus,
  ro.Filter(func(e Event) bool { return e.Type() == "UserCreated" }),
  ro.Retry(3),
)

sub := userEvents.Subscribe(ro.NewObserver(
  func(ctx context.Context, e Event) { // handle },
  func(err error) { // on error },
  func() { // on complete },
))

Pros: Maximum power. Operators replace middleware. ReplaySubject for projection catch-up.
Cons: Rewrites middleware/, outbox/, projection/, memory/. Large ro dependency in core.

Option B: Use ro as the MemoryBus implementation only

// keep our Bus interface, implement with ro internally
type MemoryBus struct {
  subject *ro.PublishSubject[Event]
}

func (b *MemoryBus) Subscribe(eventType Type, handler Handler) error {
  filtered := ro.Pipe(b.subject, ro.Filter(byType(eventType)))
  filtered.Subscribe(ro.OnNext(handler))
  return nil
}

Pros: Minimal blast radius. Bus interface unchanged. ro is an implementation detail in memory/ only.
Cons: Doesn't unlock operators for consumers. ro restricted to test code.

Option C: Cherry-pick patterns, don't import ro

// steal the Subject pattern, write our own 100-line version
type Subject[T any] struct {
  observers []Observer[T]
  mu        sync.RWMutex
  last      T        // BehaviorSubject: replay last
  hasLast   bool
}

func (s *Subject[T]) Next(value T) { /* multicast to all observers */ }
func (s *Subject[T]) Subscribe(ob Observer[T]) Subscription { /* register */ }

Pros: Zero dependencies. Exactly the API we need. Small surface.
Cons: Reinventing the wheel. Miss the operator ecosystem.

05

Impact on the core/ dissolution proposal

dispatcher/ — unchanged

Becomes a peer-level module. Not affected by ro. It's a sync handler registry, not a stream.

bus/ — depends on approach

Approach bus/ becomes dispatcher/ stays?
A. Full replacement Deleted — ro types replace it Yes — sync dispatch is separate
B. Impl only Kept as interface, ro in memory/ Yes
C. Cherry-pick Rewritten with Subject pattern internally Yes

middleware/ — significant rework under Option A

Current middleware Under Option A (ro)
EventLogging ro.Tap(func(e) { log(e) })
EventRetry ro.Retry(3)
EventRecovery ro.Catch(func(err) { ... })
EventTracing ro.Tap(func(e) { span.Record(e) })
EventMetrics ro.Tap(func(e) { meter.Record(e) })

Recommendation: Start with Option B (ro as MemoryBus impl). It validates the fit with zero blast radius. If it works well, promote to Option A in a separate proposal. The core/ dissolution shouldn't be blocked on this decision.

06

Open questions

# Question Context
1 Is ro's performance acceptable for high-throughput event streams? Observable has overhead (goroutines, channels). Benchmark against MemoryBus.
2 Does ro play well with Watermill? Both are stream abstractions. Could conflict or complement.
3 Should command dispatch also be stream-based? Could Dispatch return Observable[Result]? Async command handling?
4 How does Scan (fold over observable) interact with decider? Could a live Observable + Scan replace the load-fold-execute cycle?
5 Does ro's ReplaySubject make SeekableJournal redundant? ReplaySubject replays last N events from memory. But journal is persistent.
6 Is the ro dependency acceptable for a library that claims "minimal core deps"? ro depends only on stdlib. But it's a large API surface to expose.
