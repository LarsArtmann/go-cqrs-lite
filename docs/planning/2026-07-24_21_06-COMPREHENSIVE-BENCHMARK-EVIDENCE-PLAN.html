Comprehensive benchmark evidence plan

Measure the system we actually sell

Transform benchkit from a useful storage exercise into a trustworthy evidence system that separates raw primitives from the complete command-to-projection journey, proves CPU scaling, reports statistically defensible results, and prevents regressions without producing false alarms.

Evidence journeys

The current number is answering the wrong question

The reported events/sec times event generation, encoding, and EventSink.Save for one phase. The default dev suite uses one worker and only 500 events. It does not measure raw sink capacity, command dispatch, decider execution, publishing, live projection completion, or end-user query latency as one journey.

Target outcome

Every headline result will name its boundary, workload, concurrency, CPU limit, codec, payload distribution, durability mode, sample count, and uncertainty. A consumer can distinguish raw mechanism cost, storage cost, complete CQRS cost, saturation, recovery, and failure behavior.

01Current truth and scope

What works

  • Memory, SQLite, Pebble, optional Postgres factories
  • Write, stream-load, journal, KV read-model, projection, disk, CPU, heap, recovery phases
  • JSON/CBOR and mixed payload sizes
  • Named profiles, repeats, text/JSON/Markdown output
  • testing.B integration and module microbenchmarks

What is misleading

  • events/sec is write-phase throughput, not suite throughput
  • Event creation occurs outside the recorded Save latency but inside throughput time
  • Memory-32 describes GOMAXPROCS, not worker count
  • -benchtime=3x does not enlarge the benchkit workload
  • Uniform mixed payloads are not a realistic long-tail distribution

What is absent

  • Raw prebuilt-event sink benchmark
  • Complete command → decider → store → publisher path
  • Live publish → projection → query journey
  • Same-stream contention and failure/retry paths
  • CPU/concurrency saturation curves and statistical regression policy

Scope is deliberately benchmark evidence, harness correctness, reproducibility, reports, CI, and documentation. It does not redesign storage implementations unless benchmark evidence identifies a separate optimization task.

09Risks and safeguards

Benchmarking the harness

Event generation, collectors, clocks and channels can dominate memory results. Keep creation, raw sink and complete journey boundaries separate and profile the harness.

False CI regressions

Shared runners and tiny workloads are noisy. Gate only sustained stable metrics with repeated samples; publish tails and memory-backend variance as advisory until proven stable.

Backend unfairness

Durability, WAL, sync writes, pools and compaction settings must be explicit. Never compare in-memory SQLite, persistent SQLite and synced Pebble under one label.

Incorrect fast results

Every journey verifies counts, versions and state after timing. An error, dropped event or unfinished projection invalidates the sample instead of yielding an impressive zero.

API sprawl

Prefer composable phase interfaces and suite manifests. Do not add one Config boolean per new scenario; benchmark extensions need cohesive typed configuration.

Library-first value

Factories and capability contracts remain backend-neutral. Consumers can benchmark their own bundle without importing every backend driver.

10Definition of done

  • Headline metrics identify exact boundaries and never conflate generation, storage, full command processing or projection completion.
  • Raw memory sink capacity and one-worker/full-CPU scaling can be measured independently.
  • The complete command-to-read-model journey is benchmarked with correctness assertions.
  • CPU, workers, durability, codec, payload distribution, stream length, batch size and machine metadata are recorded.
  • Every repeated persistent run receives a fresh store and selects the true median sample.
  • Results have a stable versioned schema and reproducible suite manifest.
  • Core backends pass identical benchmark contracts; unsupported capabilities are explicit.
  • Regression checks use sustained samples and documented thresholds rather than single tiny runs.
  • CPU/heap/mutex/block/trace and soak modes can diagnose regressions after detection.
  • README, benchmark index, AI skill, changelog, API stability and release documentation agree.
  • nix run .#verify passes before any benchmark API is tagged stable.

Release decision

Do not tag benchkit/v0.1.0 merely because the current API works. Tag after M01–M18, schema compatibility, representative baselines, and verification are complete. M19–M23 may continue additively after that if their extension points are already stable.
